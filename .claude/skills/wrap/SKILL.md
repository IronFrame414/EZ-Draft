Run the wrap of `vault/PROCESS.md` (section 9, "Wrap unit") for phase $ARGUMENTS. You are the orchestrator. **Advisor (process v2.4):** you run on Sonnet 5.5 with an Opus 5.5 advisor. Consult it before marking a ticket `blocked` and when a decision is not covered by PROCESS.md or the spec; not otherwise (each call re-reads the whole transcript). Run it only after the phase PR is merged (`git fetch origin` and `git merge-base --is-ancestor <Develop at PR sha> origin/main` succeeds; the sha is in `vault/tickets/gates/phase-NN.md`).

1. `git fetch origin`; confirm the merge; set `Merged: yes` in `vault/tickets/gates/phase-NN.md`. Punch-list items Josh left unchecked, and wording or lessons he changed in the PR, become fix tickets in the phase (same procedure as gate-phase step 5) and are noted in the handoff; the launcher builds them before the next phase starts.
2. **Lessons** (PROCESS.md section 13): merge duplicates across `vault/lessons/*.md`, drop entries made obsolete, keep each role file under about 30 entries, update `vault/lessons/INDEX.md` (areas per file). Any ratified lesson with `seen` of 2 or more, or any ratified lesson a script could check, becomes a gate check, lint rule or hook: write the check proposal in the cost report's "Automate" list (you do not edit `scripts/` or `.claude/`; Josh applies it) and mark the entry `automated: <name>` once he has.
3. **Cost report** `vault/cost/phase-NN.md`, from `vault/cost/log.jsonl` and STATUS Notes: spend per ticket, per unit type, per model (Fable separately); tickets that needed escalation (tier changes) and why; places Opus or Fable ran on low-complexity work, or Haiku failed; defects the resumed step-8 reviewer missed that the auditor or Josh then caught (section 8 revisit flag); whether the phase cost more than a third of `weekly_ceiling_usd_est` (section 2a rule 9: recommend splitting the next phase if so); the median unit cost (for `per_unit_cap_usd_est`); recommended changes to the complexity table, ticket-size numbers and maxTurns, as a numbered list for Josh (PROCESS.md changes need his yes).
   Take the dollar figures from `node vault/tools/usage-by-agent.mjs --since <phase start ISO>` ($ by unit × role × model, $ per ticket, plan characters per role) and compare role shares and $ per ticket with `vault/cost/baseline-2026-10-19.md`.
   **v2.4 comparison** (Josh, 2026-10-22): write or update `vault/cost/v2.4-comparison.md`, one screen of tables. Per ticket: model and effort per dispatch and advisor calls per dispatch (`usage-by-agent.mjs` columns), whether it was batched, first-round PASS or FAIL and the number of rounds (STATUS Notes), tokens per ticket, and weekly-limit % used per ticket from the `meter_source` rows of `vault/cost/log.jsonl` (say where the meter was missing). Sections: (1) baseline: the same metrics for the tickets built before v2.4 (say so if fewer than 5); (2) v2.4 per-ticket averages per complexity tier; (3) share of usage by agent and by model, and the advisor share; (4) watch items, each marked "worse than baseline" when it is: first-round PASS rate on low (Haiku) tickets, share of tickets reaching round 3 or `blocked`, test defects found at the final review that a standalone test review would have caught, problems Josh found at the phase gate and traced to a ticket. A watch item worse than baseline over 10 or more tickets goes to `vault/tickets/needs-from-josh.md` with the numbers; never revert anything.
4. `node vault/tools/next_ticket.mjs --report`.
5. Handoff: next unit is the next phase's `spec-check` (needs Josh) or, if its spec is already signed off, `plan <first ticket>`. Commit `vault/` (`docs(vault): wrap phase $ARGUMENTS`); push `develop`; end the session. Report: cost total, Fable total, lessons kept, recommendations.
