description: Unit `plan <T>` - Stage 1 plan for one ticket, written by the planner from vault/plans/TEMPLATE.md. The launcher runs it as the planner agent; interactively the orchestrator dispatches the planner. Usage /plan-ticket EZD-xxx.
---

Plan ticket $ARGUMENTS (PROCESS.md section 6). No app code, no tests.

**If you are the planner agent** (launcher run with `--agent planner`): do the work below yourself. **If you are the orchestrator** (interactive): first check `node vault/tools/next_ticket.mjs --check` passes, the ticket is `todo`, and its phase has a row in `vault/spec/SIGNOFF.md`; then dispatch `planner` with the dispatch template in `.claude/skills/build-ticket/dispatch.md` (role planner; its Spec files, Decisions, Mockups and Architecture lines are the output of `node vault/tools/next_ticket.mjs --reads $ARGUMENTS planner`; lessons `--lessons planner <areas>`), and when it returns do the ledger step at the end.

Planner's work:
1. Read only: the ticket's `tickets.json` entry (`depends_on`, `acs`) and its row in `vault/tickets/phases/phase-NN.md` (`spec_phase` in tickets.json names NN); the spec files, decision files and mockups that `node vault/tools/next_ticket.mjs --reads $ARGUMENTS planner` prints, and the `docs/architecture.md` sections on its `Architecture:` line plus any other heading the ticket extends (`--headings`, then `--section`; never the whole file) (Q-0218; an `(anchor)` names the part of the file the ticket needs, and a decision row overrides the spec text and the ticket text), never a search of the spec or decisions folders (if the list misses something the ticket needs, raise it as a QP question); `vault/spec/non-goals.md`, `glossary.md`, `acceptance-criteria.md` (the ticket's ACs); the plans this ticket depends on, their interface contracts only (`node vault/tools/outline.mjs <plan> --section 3`; never another plan whole); the mockup for any screen touched; `vault/KNOWN-LIMITS.md` once; the lessons the dispatch carries.
2. Write `vault/plans/$ARGUMENTS.md` from `vault/plans/TEMPLATE.md`: header (ACs, Complexity, user-visible result) and the ten sections. Every statement cites a source; every test value cites its source; the interface contract matches the contracts of the plans it depends on; a visual checklist (one viewport) when a screen changes, and then EZD-016a is a dependency; Proposed wording for text not on a mockup; `security-review: yes|no`; complexity and model recommendation; open questions as QP-n (try Level 1 first: if a cited source answers it, write the answer and source in the plan instead). Section 2 ends with the `Architecture:` line (EZD-244). If a retriever you dispatched returned a `REPORT:` line, run `node vault/tools/research.mjs adopt` before you finish and cite the IDs it prints as `R-NNN` in section 2; a ticket no report covers says so in section 2.
3. **Size and readiness.** Run `node vault/tools/outline.mjs vault/plans/$ARGUMENTS.md --sizes`. Over 25,000 characters: tighten it first (section 1 as steps and the file table, no narrative, sources cited by ID instead of repeated, nothing said twice across sections), dropping no requirement, test row, source or question. Split only if it is still over 45,000 characters after tightening, or would touch more than about 20 files or need more than about 25 tests (Josh, 2026-10-22); then write a split proposal instead (lettered parts, each with scope, Done-when and ACs) under a heading `## Split proposal` at the top, and stop.
   **Readiness** (Josh, 2026-10-22: Opus thinks, Sonnet executes). Run `node vault/tools/plan_lint.mjs vault/plans/$ARGUMENTS.md --allow-questions` and fix until it prints `PLAN LINT OK`. Then dispatch `plan-checker` with only `Plan: vault/plans/$ARGUMENTS.md`. For each gap it lists, decide it in the plan from the sources (Build steps, Decided for the builder, sections 3 or 4) or add it as a QP question; if you changed section 1, 3 or 4, dispatch it once more. Two rounds at most; any gap still open becomes a QP question.
4. Return: the plan path, the complexity, the QP questions verbatim, one line on risks (20 lines max).

Ledger step (orchestrator, or the launcher for an agent-run unit): `node vault/tools/next_ticket.mjs --set-architecture $ARGUMENTS` (the launcher does it for an agent-run unit); STATUS row → `planned` (no QP questions) or `questions`; Complexity column from the plan header. If the plan is a split proposal: apply it (phase file, `tickets.json` with `acs` from `node vault/tools/gen_acs.mjs`, `STATUS.md`, one commit), then plan each part as its own unit. Give each QP question the next free Q-ID in `vault/questions/QUESTIONS.md` (`open`, asked by planner) and replace the QP number in the plan with the Q-ID (for a launcher run, `assignQuestionIds` in `vault/tools/next_ticket.mjs` does this; Q-0129). The next unit is then `questions <phase>`, which answers them before any build. `node vault/tools/next_ticket.mjs --check`; handoff; commit `vault/` (`docs(vault): plan $ARGUMENTS`); end the session.
