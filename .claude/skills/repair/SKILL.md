---
name: repair
description: Unit repair <check|waiting|ci|security|probe> - the overseer, the launcher's repair of a ledger failure, a wait, a failed phase PR CI gate, or the fix-mode probe (EZD-250, EZD-333).
---

Repair what holds the launcher, trigger $ARGUMENTS (`check`: the ledger check fails; `waiting`: a wait; `ci`: the phase PR's CI `gate` check failed; `security`: a production-sensitive file changed on the phase PR after the phase audit (EZD-337); `probe`: the fix-mode dry run). Only the launcher (`scripts/run.mjs`, vault/PROCESS.md section 10) starts this unit. You are the orchestrator and the overseer (decision 2026-11-05 "Overseer repair unit and unattended running", vault/spec/decisions/process.md): you resolve every block that is not a design or user-interface question, and you send Josh nothing else.

1. Read `vault/handoff/REPAIR.md` (trigger, fingerprint, the launcher's reason, the ledger check output). Run `node vault/tools/next_ticket.mjs --check`. Read the `vault/tickets/STATUS.md` notes of the tickets the reason names, and the files they point to (a patch, a log, a failed run).
2. Decide who settles it. A design or user-interface question that cannot be resolved internally is Josh's: report `JOSH: design: <question>` or `JOSH: ui: <question>`. Everything else is yours (CLAUDE.md rule 3 standing rule): product, scope, wording and money follow the spec, the decisions and the answers; if they do not settle it, record the answer as answered-agent with its source (`node scripts/ledger.mjs answer`). Account settings and anything only a third party can change: report `FAILED: <what and the evidence>`; the launcher logs it for Josh's daily check-in.
3. Ledger fixes: STATUS rows and notes and question rows through `node scripts/ledger.mjs status|answer` (never by editing the record files, which are views of the records database), research report fields, `vault/tickets/tickets.json`, phase file rows. Set a `blocked` ticket to `ready` or `in-progress` only when its note's cause is shown fixed on develop, and cite the commit in the note. Uncommitted vault files a check or CI run needs: commit them by path and push develop (`git push origin develop`).
4. A fix that needs a guarded path (`scripts/`, `.claude/`, `vault/tools/`, `vault/PROCESS.md`, `vault/PROCESS-EZDRAFT.md`), for example applying a patch from `vault/handoff/`:
   1. If `vault/handoff/LAUNCHER_FIX.md` already exists, an interactive fix is open: change no guarded path; report `FAILED: interactive fix mode is open`.
   2. Write `vault/handoff/LAUNCHER_FIX.md`: a line naming the fault, the line `Repair: <REPAIR.md's fingerprint>` exactly, then a `## Paths` heading with one `- <path>` bullet for each file you will change, nothing else. The path guard lets you write only those paths; the launcher closes a fix file only when it carries that `Repair:` line.
   3. Make the change with Edit or Write, or `git apply --include=<path>` per listed path. Never change, skip or narrow a test, the gate, CI or the read and shell guards: the launcher checks every file you changed after you end, undoes the whole repair if one is a hard-limit file (`repairForbidden` in `scripts/launcher-idle.mjs`), and logs it as REFUSED. If the fix needs one of them, report `FAILED: <why>` instead.
   4. Run the tests of what you changed: `node --test <the test files that import or name the changed files>` (find them with `grep -rl <file name> scripts vault/tools`). A failing test is fixed in the code, never in the test. You never change app code (`app/`, `packages/`, `worker/`, `supabase/`): an app fix becomes a fix ticket as in step 5.
   5. Dispatch code-reviewer in its finished-ticket mode, with REPAIR.md standing in for the plan, on the diff (`git diff -- <paths>`), and also security-reviewer when the change touches secrets, permissions, money, data isolation, `scripts/run.mjs`, `scripts/ledger.mjs` or anything under `.claude/`. Give each the diff, the test output and REPAIR.md. On FAIL, fix and re-review, at most two rounds; then undo your change (`git restore -- <paths>`) and report `FAILED: <the finding>`.
   6. Commit by path with a subject that starts `fix(repair):` (`git commit -m "fix(repair): <what>" -- <paths>`; the launcher reverts a hard-limit commit only when it carries that subject, and stops otherwise), push develop, then delete `vault/handoff/LAUNCHER_FIX.md`. The launcher deletes it too if you do not.
5. Kind `ci`: the run id is the `/actions/runs/<id>/` part of the link in the reason. Read `gh run view <id> --log-failed` (a cancelled run: `gh run view <id> --log`). Never re-run a failed job (vault/PROCESS.md rules 16 and 20: a flaky test is fixed, not re-run).
   - A cancelled or timed-out run (EZD-336), attempt 1 (`gh run view <id> --json attempt`), whose log shows an outside cause (runner, network, package mirror, GitHub outage): `gh run rerun <id>` once and report `REPAIRED: re-ran run <id> (<cause>)`. Attempt 2 or later, or a cause in our code or tests (a test that hangs): handle it as a failed run below.
   - Uncommitted or unpushed vault files: step 3.
   - A failure our code, tests or configuration causes: write one fix ticket by following `.claude/skills/gate-phase/SKILL.md` step 5: number per `vault/PROCESS-EZDRAFT.md` line 36, title `Fix: <failing step>: <first error>`, phase file row, `tickets.json`, ACs via `vault/tools/gen_acs.mjs`, its STATUS row with `node scripts/ledger.mjs ticket <T> <phase> <complexity> <depends-on> <title>` (status `todo`); then commit the phase file, `tickets.json` and `vault/spec/acceptance-criteria.md` by path (EZD-336: an uncommitted phase row broke every clean copy's ledger check). Report `REPAIRED: fix ticket <T> for <failing step>`.
   - A failure only GitHub or another third party can fix (runner outage, Actions quota, repository settings): report `FAILED: <what>, with the run link`.
5a. Kind `security` (EZD-337): the reason is `none: phase <N> PR merge held for a security pass of <base>..<head> (<url>)`. This kind never changes a guarded path (step 4 does not apply). Run `git diff --name-only --no-renames <base> <head>`. Dispatch `security-reviewer` once with `git diff <base> <head>`, that file list and the reason, asking for the "Production-sensitive changes: PASS / FAIL" verdict on that range (Q-0112).
   - PASS: append the line `Security pass at: <head>` to `vault/tickets/gates/phase-<NN>.md`, commit it by path (`git commit -m "docs(vault): phase <N> security pass of <base 7>..<head 7>" -- vault/tickets/gates/phase-<NN>.md`), push develop, report `REPAIRED: security pass of <base 7>..<head 7>`.
   - FAIL: write no pass line. File every finding as `.claude/skills/gate-phase/SKILL.md` step 5 says (a defect is a product fix ticket of phase <N>, written as in step 5 kind `ci`), commit the files you wrote by path, push develop, report `REPAIRED: fix ticket <T> from the security pass of <base 7>..<head 7>`; if no finding became a fix ticket, report `FAILED: security pass of <base 7>..<head 7>: <first finding>`.
6. Kind `probe`: if `vault/handoff/LAUNCHER_FIX.md` already exists, report `FAILED: interactive fix mode is open` and stop. Otherwise write it with the line `Repair: probe`, a `## Paths` heading and `- scripts/launcher/fix-mode-probe.txt`. Append one line `probe <UTC time>` to that file with the Edit tool. Do not commit it and change nothing else. Delete LAUNCHER_FIX.md, then step 7. Report `REPAIRED: probe edited scripts/launcher/fix-mode-probe.txt`, or `FAILED: <the refusal text, word for word>` if any step was refused.
7. End with `node vault/tools/next_ticket.mjs --check` passing and the handoff (`vault/handoff/TEMPLATE.md`). Line 1 of your report is exactly one of `REPAIRED: <what changed>`, `JOSH: design: <question>`, `JOSH: ui: <question>` or `FAILED: <why>`. Any other `JOSH:` line is logged as a failed repair and never sent.
