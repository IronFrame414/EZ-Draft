name: review-plans
description: Unit `review-plans <N>` - the code-reviewer reads all of a phase's plans together (missed requirements, conflicts, interface contracts that don't line up) and TRACE.md is regenerated. The launcher runs it as the code-reviewer agent. Usage /review-plans <phase number>.
---

Plan review for phase $ARGUMENTS (PROCESS.md section 6, "Plan review unit"). Read-only on app code; nothing is built.

**If you are the code-reviewer agent** (launcher run with `--agent code-reviewer`): do the review below and end with the report; the launcher writes it to `vault/plans/review-phase-NN.md` and the handoff. **If you are the orchestrator** (interactive): run `node vault/tools/next_ticket.mjs --report` first, dispatch `code-reviewer` in mode 1 with the list of the phase's plan paths and `vault/tickets/TRACE.md` (dispatch template in `.claude/skills/build-ticket/dispatch.md`), then write its report to `vault/plans/review-phase-NN.md` (two-digit phase) and do the ledger step.

Review (code-reviewer, mode 1):
1. Read every `vault/plans/EZD-<phase>xx.md` for the phase and `vault/tickets/TRACE.md` (phase section). Read spec files only to settle a specific doubt.
2. Report, numbered, with plan path and section: missed requirements (an AC of the phase with no plan row covering it; TRACE.md shows ACs per ticket); conflicts between tickets; wrong or missing dependencies; interface contracts that don't line up between a ticket and its dependents (a dependent imports a path, name, signature, route or `data-testid` the earlier plan doesn't provide, or provides differently); tests without a sourced expected value; a plan with a visual checklist that does not depend on EZD-016a; user-visible text not on a mockup that is not under Proposed wording; a plan missing `security-review: yes|no`, a complexity rating or ACs; a plan over the size limit (more than 20 files or more than 25 tests, PROCESS.md section 6 "Ticket size"; a plan with a `## Brief` gives its counts there, EZD-384) with no split proposal.
3. Run `node vault/tools/dep_check.mjs $ARGUMENTS` (EZD-384b): it checks each code-bound or legacy template v2 plan of the phase whose dependencies are all done against develop HEAD and against those dependencies' committed plans. Report each line it prints that starts with `- ` or `DEPENDENCY CHECK ERROR` as a finding (plan path, section 3); a `SKIP` line is not a finding. When it exits 1 or 2, the verdict is `VERDICT: FAIL`.
4. End with `VERDICT: PASS` (no findings that need a plan change) or `VERDICT: FAIL` and the list of plans to re-dispatch to the planner. 20 lines per finding at most; no code.

Ledger step (orchestrator; the launcher does it for an agent-run unit): save the report as `vault/plans/review-phase-NN.md`; for each plan that needs a change, the next `plan <T>` unit re-dispatches the planner with the findings (set that ticket back to `todo` with a note on why, `node scripts/ledger.mjs status <T> status=todo notes=<why>`, so `--next-unit` picks it up); an uncovered AC goes back to the planner of the ticket that owns it. Handoff with `node scripts/ledger.mjs handoff <a ticket of the phase>`; no commit: the launcher records this unit's results (REMEDIATION-PLAN 2.12; D2 (a)); end the session.
