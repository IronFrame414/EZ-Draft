name: build-ticket
description: Unit `build <T>` - Stage 3 for one ticket (re-validate, worktree, tests, test review, build, gate, reviews, merge to develop, push), then end the session. Usage /build-ticket EZD-xxx.
---

You are the orchestrator for one unit: build ticket $ARGUMENTS (PROCESS.md section 8; project additions in `vault/PROCESS-EZDRAFT.md`). You write no app code and no tests. Your checkout stays on `develop`. When the ticket is `done` or `blocked`, write the handoff and end the session; do not start another ticket.

**Load only:** of `vault/plans/$ARGUMENTS.md` its header and sections 5, 7, 8, 9, once (`node vault/tools/outline.mjs vault/plans/$ARGUMENTS.md --section header --section 5 --section 7 --section 8 --section 9`; the whole plan only if it has no numbered sections), the ticket's row in `vault/tickets/STATUS.md`, its `tickets.json` entry (`depends_on`, `acs`), and `.claude/skills/build-ticket/dispatch.md` (the dispatch template, once). Read spec or decision files only when a step below needs them; never search for them.

**Research reports.** After any dispatch that returned a `REPORT:` line, run `node scripts/ledger.mjs research $ARGUMENTS`; it moves each of this ticket's pending reports to `vault/research/R-NNN.md`, commits them and prints the IDs to cite (PROCESS.md section 13).

**Ledger writes (EZD-173).** Other units may run at the same time, so every ledger change goes through `node scripts/ledger.mjs`, which takes the ledger lock, writes and commits only the files it changed: `node scripts/ledger.mjs status $ARGUMENTS <key>=<value>...` (STATUS row: `status`, `complexity`, `commit`, `tests`, `notes`), `question $ARGUMENTS <asked-by> <text>` (prints the new Q-ID), `answer <Q-ID> <status> <answered-by> <answer> <sources>`, `append vault/DONE.md $ARGUMENTS` and `append vault/lessons/<role>.md $ARGUMENTS` (text on stdin: a DONE line or a planner's lesson line), `lesson $ARGUMENTS vault/lessons/<role>.md...` (a new entry on stdin headed `## L-next` with `status: candidate`; it takes the next L-number across all lesson files, writes the entry into each role file named and updates `vault/lessons/INDEX.md`), `seen $ARGUMENTS <L-nnn>` (raises an existing lesson's `seen` count in every file that holds it) and `handoff $ARGUMENTS` (text on stdin). Never edit STATUS.md, QUESTIONS.md, DONE.md, the lessons files or CURRENT.md with Edit or Write in a build unit.

**Plan sections per role** (optimize plan C3, Josh 2026-10-20; numbers from `vault/plans/TEMPLATE.md`). Every dispatch adds one line under `Plan:`, `Sections: <list>`, from this table; the agent prints them with `node vault/tools/outline.mjs <plan> --section <n>` (a plan without numbered sections prints whole).

**Reading map** (Q-0218). Fill each dispatch's `Spec files:`, `Decisions:` and `Architecture:` lines and its `Sections:` line by pasting the output of `node vault/tools/next_ticket.mjs --reads $ARGUMENTS <role>` (role as in the table below, for example `builder` or `code-reviewer mode 2`); it reads `tickets.json` (`spec_files`, `decisions`, `mockups`, with `(anchor)` naming the part of a file the ticket needs) and this table. Do not search the spec or the decisions folder. A reading list that looks wrong or incomplete is fixed in `tickets.json` by the orchestrator (fix mode), not worked around.

| Role | Sections |
| --- | --- |
| test-author | header, 3, 4 |
| builder | header, 1, 3, 4, 6 |
| code-reviewer mode 2 | header, 3, 4 |
| code-reviewer mode 3 | header, 1, 3, 4, 6 |
| security-reviewer | header, 1, 3, 7 |
| ui-verifier | header, 5 |
| calc-auditor | header, 4 |
| planner (re-validation) | header, 2, 3, 4, 9 |

0. **Pre-flight.** `node scripts/unit-steps.mjs preflight $ARGUMENTS`. Exit 3 → stop and report its line (it checks develop is clean, `next_ticket.mjs --check`, the ticket's status and dependencies, and the budget hold).
1. **Re-validate the plan** if any dependency's STATUS notes record a plan deviation: dispatch `planner` in re-validation mode (dispatch.md) with the deviating dependencies. After it returns, run `node scripts/ledger.mjs architecture $ARGUMENTS`. A changed test value or behavior comes back as a QP question: give it a Q-ID in `QUESTIONS.md`, run it up the chain (section 7); if it needs Josh, STATUS → `blocked` with the Q-ID, handoff, end. Skip when no dependency deviated.
2. **Worktree.** `node scripts/unit-steps.mjs worktree $ARGUMENTS`. It creates `.claude/worktrees/$ARGUMENTS` on `t/$ARGUMENTS` (STATUS → `in-progress`) or reports `RESUME tests=yes|no wip=N`: tests written → skip step 4; wip commits → the build started, continue at step 6. `RESUME merged=yes` means an interrupted unit already squashed the reviewed ticket onto develop: go straight to step 10 (`merge` resumes: develop gate, clean up, done); dispatch nothing.
3. **Pick models** (v2.4): before every dispatch run `node vault/tools/next_ticket.mjs --dispatch $ARGUMENTS <role> [--round N]` and pass its `model` and `effort` on the dispatch; when `orchestratorAdvice` is true (round 3), consult your advisor first with the open findings and pass its advice in Findings to address (dispatch.md); never give a subagent an advisor line, the tool does not reach them (Q-0333 (c)). Deviate only with a one-line reason. If `EZD_FABLE_ALLOWED` is `0`, or a Fable dispatch ends on a limit error, use Opus 5.5 where Fable is named and note the fallback. Record every model and effort with its source (`--dispatch` or the reason) in STATUS Notes.
   - **Advisor:** consult the advisor before a round 3 dispatch (`orchestratorAdvice`), before accepting a complexity rating you doubt, before marking a ticket `blocked`, and when a decision is not covered by PROCESS.md or the spec. Not otherwise.
   - **Batch:** when the ticket is `low` or `medium` and its Notes carry no `batch:` marker, run `node vault/tools/next_ticket.mjs --batch $ARGUMENTS`. One ID: build it alone. 2 or 3 IDs from a `low` ticket: a low batch (PROCESS.md section 4 Batches): one worktree, one test-author and one builder dispatch, one gate, the code-reviewer gives a verdict per ticket, each ticket merges with `unit-steps.mjs merge <T>`. 2 or 3 IDs from a `medium` ticket: a review batch (Review batch (medium), below); take it. Either way, before any worktree write `batch: <A>+<B>[+<C>]` (the `--batch` order) at the start of every member's Notes, and when a member ends (`done` or `blocked`) rewrite its marker to `batched with: <A>+<B>[+<C>]`.
   - **Never end your turn while a dispatched agent is still running.** Wait for its report; a unit whose session ends mid-dispatch loses that agent's work (EZD-018, 2026-10-22).

**Review batch (medium).**
   a. Run `unit-steps.mjs preflight <T>` for every member before any `worktree` call (preflight needs a clean develop); a member that prints `PREFLIGHT STOP` leaves the batch; one member left: build it alone.
   b. Then write the markers (the Batch bullet above).
   c. Members one at a time in `--batch` order: steps 1, 2, 4, 6, 7 each with its own worktree, `--dispatch <member> <role>` models and own round count. A member that becomes `blocked` leaves the batch; the others go on.
   d. Step 8 once for every member with a green gate (STATUS → `review` each): **one code-reviewer dispatch** (mode 3) with the Batch review dispatch of dispatch.md for all of them; **one security-reviewer dispatch** in the same form for all of them when any member's plan says `security-review: yes` or any member's gate printed `SECURITY FLAG:`; ui-verifier and calc-auditor stay one dispatch per member that needs them. Model and effort: run `--dispatch` for every member and use the highest model (Fable > Opus > Sonnet > Haiku) and effort (high > medium > low).
   e. Each member's verdict is its own `VERDICT <ticket>: PASS` or `VERDICT <ticket>: FAIL` line from each reviewer it got; no line for a member: review that member again alone (not a round).
   f. A member with PASS from every reviewer merges at once (step 10, `unit-steps.mjs merge <T>`), in member order, without waiting for the others. A FAIL goes to step 9 for **only that ticket**: its own ladder, its re-review by the single-ticket dispatch, only the reviewers with open findings. `MERGE RED` is that member's FAIL; `MERGE STOP: squash failed` is that member's FAIL with the finding "rebase t/<T> onto develop and resolve the conflict with <merged member>".
   g. When every member is `done` or `blocked`: one handoff for all, then `unit-steps.mjs finish <T> done|blocked` once per member in member order, then end.
   h. Resume: when the unit's ticket carries a `batch:` marker, run `unit-steps.mjs worktree <member>` for every member still carrying it and continue each from its RESUME state; a member in `review` without a recorded verdict is reviewed again.
4. **Tests.** Dispatch `test-author` (dispatch.md) with the worktree path. It writes failing tests to the plan's interface contract and commits `test($ARGUMENTS): …`. On harness tickets (EZD-006, EZD-008, EZD-016a, EZD-016b, EZD-019, EZD-021) it also builds the harness itself.
5. **Test review.** High tickets only (v2.4). Skip on `low` and `medium` tickets: the tests are reviewed with the code in step 8. On a high ticket dispatch `code-reviewer` in mode 2 with the plan path and worktree path. FAIL → record each finding (reviewer `code-reviewer`, round = the test-review round) with `node vault/tools/findings.mjs record <T> <round> <reviewer> <category> <text…>` (categories: `node vault/tools/findings.mjs categories`; first category in that order whose meaning fits; text = the finding line without its number and file:line, first 300 characters; a finding still open in the next round is recorded again in that round), then send the findings back to `test-author`, review again. Three failed test reviews → `blocked` with a one-line reason and a question; handoff; end.
6. **Build.** Dispatch `builder` at the round-1 tier. It commits `wip($ARGUMENTS): …` as it goes.
   - A **`PLAN-GAP`** from the builder or test-author: dispatch `planner` in plan-gap mode (dispatch.md; role `planner (re-validation)`, the gap under `Findings to address:`). It patches the plan or returns a QP question (→ Q-ID, up the chain as below). Then run `node scripts/ledger.mjs architecture $ARGUMENTS` and resume the same builder or test-author with `Plan updated: <sections>`. Record the planner's lesson line with `node scripts/ledger.mjs append vault/lessons/planner.md $ARGUMENTS` (text on stdin; section 13). A PLAN-GAP never moves the builder up a tier.
   - A **question** from the builder: Q-ID in `QUESTIONS.md`, up the chain; if it needs Josh → `blocked`, handoff, end.
   - A **change only Josh may approve** (a guard hook, `ci.yml`, `CLAUDE.md` or another agent-protected file): write the patch to `vault/handoff/$ARGUMENTS-<name>.patch`, STATUS → `blocked` with `needs Josh: apply vault/handoff/<file>.patch, then resume at step <n>`, handoff, end. Never end with the ticket `in-progress` while it waits on Josh: the launcher would re-run it, then table it (Josh 2026-10-27: the build keeps moving).
   - A **structural test mismatch**: send it to `test-author` for a structure-only repair (`test($ARGUMENTS): structural repair - …`), then `code-reviewer` confirms the diff changed no assertion, expected value, input or test count. FAIL → it becomes a question. PASS → back to the builder.
   - **`needs-josh-confirm` wording**: keep the list for STATUS Notes. It does not block.
7. **Gate.** Run `node scripts/gate.mjs .claude/worktrees/$ARGUMENTS` yourself, once. Keep the summary (touched paths, `SECURITY FLAG:` lines, failing tests). Red → back to step 6 as the next round, handing the builder the path of the worktree's `gate-failures.log`. Agents never get `gate.log`; if `gate-failures.log` is unclear, dispatch `log-summarizer` (model and effort from `--dispatch`) on `gate.log` and pass on its answer.
8. **Review.** STATUS → `review`. Dispatch in parallel, each with the plan path, worktree path, the gate summary and the path of `gate-failures.log` (reviewers do not run the gate and never read `gate.log`):
   - `code-reviewer` mode 3, always. On a high ticket resume the step-5 reviewer (same agent) instead of a fresh one; on a low or medium ticket it reviews the tests here too (mode 3 test check), at the effort `--dispatch` gives.
   - `ui-verifier` when the plan has a visual checklist (one viewport, the states on the checklist).
   - `security-reviewer` when the plan says `security-review: yes` **or** the gate printed any `SECURITY FLAG:` line.
   - `calc-auditor` when the plan's Reviewers line says so.
9. **FAIL** (any finding, *minor* included: PROCESS.md rule 20, Q-0268) → first record every finding of every reviewer, *minor* included, with `node vault/tools/findings.mjs record <T> <round> <reviewer> <category> <text…>` (categories: `node vault/tools/findings.mjs categories`; first category in that order whose meaning fits), round = the failed build round; text = the finding line without its number and file:line, first 300 characters; a finding still open in the next round is recorded again in that round. Then STATUS → `in-progress`. Next round from `--dispatch $ARGUMENTS builder --round N` (PROCESS.md section 4 ladder, v2.4): round 2 is the same model, resumed for *minor* findings (naming, style, one-file fix, no behavior or requirement) and fresh otherwise, with no advisor; round 3 is one tier up, with your advisor's advice in the dispatch (on a high ticket: your blocked review with the advisor, then `blocked`). A finding that a test is wrong goes to the test-author first, then the builder, as one round. Only the reviewers whose findings are open review again. After the 3rd failed round → consult the advisor, then `blocked` with a one-line reason and a question; leave the worktree; handoff; end. If the advisor is not working (vault/tickets/needs-from-josh.md), use the old ladder: one tier up per failed round.
10. **PASS** (zero findings from every reviewer; a flaky gate is a finding, never cleared by re-running: rule 20) → `node scripts/unit-steps.mjs merge $ARGUMENTS`. It squashes `t/$ARGUMENTS`, commits `feat($ARGUMENTS): <title>`, runs the develop gate for the phase, removes the worktree and branch, and sets STATUS `done` with hash and test count. When another unit's merge is running it prints `MERGE WAIT` and waits for it; let it run. `MERGE RED` (exit 1) → develop is restored; record it with `node vault/tools/findings.mjs record $ARGUMENTS <round> gate gate-red <text>` (round = the build round that failed; text = the last line `merge` prints after `MERGE RED`, or that line itself when none follows, first 300 characters), then treat it as a review FAIL (step 9) without recording it again. On `MERGE OK`: write STATUS Notes: models used, plan deviations (from the builder's and reviewers' reports), `needs-josh-confirm` wording. Notes never hold an unfixed issue (no "minor", "follow-up", "watch" or "known limit": rule 20); anything still wrong becomes a fix ticket in the phase. Append one line to `vault/DONE.md` (date · ticket · title · user-visible result · commit). Record any lesson with `lesson`, or `seen` when one already covers it (PROCESS.md section 13; search the role files first). Special cases: after EZD-000, copy `docs/architecture.md` to `vault/architecture.md` (`CLAUDE.md` never imports it, EZD-244); after a spike (EZD-027 to EZD-031), write `vault/spikes/$ARGUMENTS.md` from the template with its `Verdict:` line.
11. **Handoff and push.** Write the new handoff (template; 30 lines max) with `node scripts/ledger.mjs handoff $ARGUMENTS` (text on stdin), then `node scripts/unit-steps.mjs finish $ARGUMENTS done|blocked [<other vault paths this unit wrote>]` (ledger check, report, commits `vault/`, or only this unit's own paths while another unit is in flight, and pushes develop unless a merge is in progress). Before `finish` when the ticket is `done` or `blocked`: run `node vault/tools/findings.mjs repeats`; for each `REPEAT <category>` run `node vault/tools/findings.mjs list <category>`. If a planner lesson already states that rule, raise its `seen` with `node scripts/ledger.mjs seen $ARGUMENTS <L-n>`; otherwise write a new `candidate` planner lesson with `node scripts/ledger.mjs lesson $ARGUMENTS vault/lessons/planner.md` (entry on stdin headed `## L-next`, PROCESS.md section 13 format; it takes the next L-number across all lesson files; areas = the Areas lines of those tickets' plans, or for a plan without one the `vault/lessons/INDEX.md` areas its Sources cite; with a `Plan check:` line). Then run `node vault/tools/findings.mjs cover <category> <L-n>`. Ratification stays Josh's. End the session with a report of 20 lines or fewer: status first, then commit, models used, deviations, open questions.
