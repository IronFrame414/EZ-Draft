| EZD-1988 | What sent SIGTERM to builders on several lanes in the same second (2026-11-24 14:28:29Z, 2026-11-25 01:04:38Z, 08:22:09Z) | Not a loop code path. In each second another lane's builder ran `pkill -f "scripts/check.mjs"` from its Bash tool (EZD-1944 at 14:28:29.213Z, EZD-1903 at 01:04:38.644Z, EZD-1980 at 08:22:09.165Z, from their session transcripts). Every builder's command line held its prompt (`claude -p "<prompt>"`), which names `node scripts/check.mjs`, so the pattern matched every other lane's claude and check. macOS pkill spares only its own ancestors, so the sender's own claude lived. The loop (`node .../scripts/loop.mjs`) did not match, which is why it kept running. The same-second checks died with them: EZD-1959's loop check went red at "scripts tests" with no test named (REQUEUED 01:04:41Z), and EZD-1946's own check failed there too. The equal elapsed times (410/411 s, 1339/1339 s) are a shared start plus one kill moment, not a timer: 410, 906 and 1339 s share no period. The "killed" background tasks about 1 s before each exit are claude's own shutdown after the signal. Fix: claude now gets its prompt on stdin (scripts/loop/claude-exit.mjs startClaude), so its command line holds only flags, the run name and ids, and a pattern kill on prompt text cannot select it. The builder prompt also says never to stop processes by name or pattern. Builders' and the loop's checks still show `scripts/check.mjs` on their command lines, so a pattern kill can still stop a check; the builder rule is the guard there | AC-EZD-1988-1; loop.log 1931-1934, 2078-2081, 2193-2196 |
| EZD-1988 | Every place in the loop's code that kills, aborts or signals a claude, a process group or a lane, and whether it can reach a running builder | (1) loop.mjs claude timer, SIGTERM then SIGKILL to the claude's own pid at its time limit: only its own run, and it sets timedOut, so it never logs as CLAUDE DIED. (3) check.mjs step-group stop, SIGTERM to each step's own group (detached) when the check stops or exits early, and (4) its detached SIGKILL reaper 10 s later: only the groups of the check's own steps. A builder claude lives in the loop's group (spawned without detached), which is never a step group. (5) free-port.mjs, SIGTERM then SIGKILL to the group of whatever listens on the lane web port before e2e, plus the listener groups killed at check exit: it never signals its own group, and a builder claude does not listen on a lane web port. (6) docker-wait.mjs, SIGKILL to its own detached `docker info` group at its limit. (7) db/local.mjs LIMIT_RUNNER, kills the supabase CLI's descendants only. (8) self-restart.mjs dry run, SIGKILL to its own `--plan 1` child at 2 min; the restart itself exits 75 only after running tickets finish. (9) The watchdog's `launchctl kickstart -k com.ezdraft.build`, and launchd stopping the job, end the loop's whole process group, builders included (no AbandonProcessGroup): on purpose, and the loop would die with them. It did not die at any of the three times. (10) Usage-limit stop: ends only the run that hit the limit; it signals nothing. (11) oauth-usage and api-gate fetches use AbortSignal timeouts on their own requests only. No abort controller or idle timer is shared across lanes. None of (1)-(11) matches the evidence: a group kill would have taken the loop and every lane, and EZD-1944 and EZD-1980 lived through it | AC-EZD-1988-1 |
