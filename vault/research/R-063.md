Question: When Tracing.end is sent while a renderer main-thread task is running or just ended, how does that task's toplevel RunTask slice appear in JSON export; does flush wait for the task; can a Runtime.callFunctionOn response precede the slice close?

Findings:

1. Unfinished slice, JSON form. Not verified from primary source. The Perfetto data model is B/E pairs and X events as slices: https://perfetto.dev/docs/getting-started/other-formats . A secondary unofficial guide says Chrome emits a lone B for work still running when recording stopped, and that a lone B has no real duration: https://www.corewebvitals.io/chrome-trace/events . I did not find the Chromium or Perfetto JSON exporter code that decides between X without dur, B without E, or drop. Lighthouse issue on unmatched B/E: https://github.com/GoogleChrome/lighthouse/issues/10616 (search snippet only).

2. Flush. Consumer flush: the service asks each producer to Flush() its TraceWriters and reply; it answers once all ACK or the flush timeout expires. Source: https://perfetto.dev/docs/design-docs/life-of-a-tracing-session . Default flush_timeout_ms is 5 s: https://perfetto.dev/docs/reference/trace-config-proto . On flush the service forcefully reads shared-memory chunks not yet marked complete: https://perfetto.dev/docs/design-docs/trace-buffer . This scraping is used for data sources on threads without a task runner, where a flush task cannot be posted: same page, section "Out-of-order commits". So a thread with a task runner may be asked to flush by task, but the design allows scraping. Chromium's TracingHandler::End / StopTracing / PerfettoTracingSession::DisableTracing call tracing_session_->Stop(), then ReadTrace, with no flush timeout or explicit Flush() in that file: https://chromium.googlesource.com/chromium/src/+/main/content/browser/devtools/protocol/tracing_handler.cc . Data loss is reported as the data_loss argument of TracingComplete in the same file.

3. Lost end from scraping. When a scraped (incomplete) chunk is committed, TraceBuffer ignores its last fragment because it cannot tell whether the producer is still writing: https://perfetto.dev/docs/design-docs/trace-buffer . A slice end written in that fragment would be lost. Legacy base/trace_event design (pre-Perfetto) said: "If any thread hasn't finish its flush in time, finish the flush": https://chromium.googlesource.com/chromium/src/+/main/base/trace_event/trace_log.cc (historic comment, not current code).

4. CDP response ordering. Not established. Playwright's crBrowser stopTracing sends Tracing.end and awaits Tracing.tracingComplete with Promise.all; it makes no evaluate call in the tracing path, and it uses transferMode ReturnAsStream, not inline dataCollected JSON: https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/server/chromium/crBrowser.ts . The DevTools protocol Runtime and Tracing pages did not render text (redirect only): https://chromedevtools.github.io/devtools-protocol/tot/Runtime/ . I found no source stating when a Runtime response is sent relative to the RunTask end.

Gaps: Perfetto services/tracing flush code and Chromium TrackEvent flush code were not reachable (GitHub raw paths returned 404 on master). The JSON exporter path (ReadTraceAsJson) was named but not read.
