- Throttler: https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/platform/scheduler/common/thread_cpu_throttler.cc
  - `SetThrottlingRate`: `if (rate <= 1) {` stops the thread (`throttling_thread_.reset();`); otherwise creates or updates `ThrottlingThread`.
  - `ThrottlingThread::Throttle()`: `[[maybe_unused]] const int quant_time_us = 200;` then, on POSIX, `pthread_kill(throttled_thread_handle_.platform_handle(), SIGUSR2);` then `Sleep(base::Microseconds(quant_time_us));`.
  - `Sleep` on POSIX delegates to `base::PlatformThread::Sleep(duration);` (wall-clock sleep on the throttler thread).
  - Gate: `#if BUILDFLAG(IS_POSIX)` `#include <signal.h>` `#define USE_SIGNALS 1`; `#elif BUILDFLAG(IS_WIN)` is the Windows path. macOS is covered only through IS_POSIX (not checked further).
  - Install: `sa.sa_handler = &HandleSignal;` `sigaddset(&sa.sa_mask, SIGPROF);` `sa.sa_flags = SA_RESTART;` `sigaction(SIGUSR2, &sa, &old_signal_handler_)`.
  - `ThrottlingThread::HandleSignal(int)`: `static base::TimeTicks last_resume_time;` `base::TimeTicks now = base::TimeTicks::Now();` `base::TimeDelta run_duration = now - last_resume_time;` run capped: `std::min(run_duration.InMicroseconds(), static_cast<int64_t>(1000))`; `sleep_duration_us = run_duration_us * throttling_rate_percent / 100 - run_duration_us;` `wake_up_time = now + base::Microseconds(sleep_duration_us);` `do { now = base::TimeTicks::Now(); } while (now < wake_up_time);` `last_resume_time = now;`
- Windows path (for contrast only): `Sleep(run_duration); ::SuspendThread(...); Sleep(sleep_duration); ::ResumeThread(...);` in the same file.
- Public description: https://developer.chrome.com/blog/devtools-grounded-real-world says Chrome "launches a separate throttling thread that interrupts and suspends the tab's main thread for frequent short bursts", about 75% suspended at 4x. It gives no interval and no timing source.
- Third-party report (not Chromium source): https://github.com/daintreehq/daintree/issues/12456 describes busy-spin in cached views under the CDP throttle.

Answers:

1. Class and mechanism: `ThreadCPUThrottler` (singleton) owns a `ThrottlingThread` that sends SIGUSR2 to the renderer main thread with `pthread_kill`; the main thread's SIGUSR2 handler `HandleSignal` busy-waits (source above).
2. Cycle: the throttler thread signals, then wall-clock sleeps 200 µs (`quant_time_us`), so signals are about every 200 µs regardless of rate. In the handler, run = wall time since the previous handler exit (capped at 1000 µs), spin = run × (rate/100 − 1), so spin = run × (N−1). Rate 4 gives run:spin = 1:3, about 25% run. Timing is wall clock (`TimeTicks::Now`) in both places; no CPU-time clock is read. (Inference: the run window is not a fixed length; it is whatever time passes until the next delivered signal, and signals sent during a spin coalesce.)
3. Blocked waits: SIGUSR2 is not blocked, and `SA_RESTART` means the handler runs on the blocked thread and the interrupted call is restarted, not failed. So a sync XHR wait is also spun in the handler, which is consistent with the KNOWN probe. (Inference from handler and `SA_RESTART`; not tested here.)
4. Thread CPU: the spin runs on the main thread in signal context and is plain on-CPU busy-wait, so it is counted as main-thread CPU time. This is an inference from the code; I did not read the trace-event `tdur` code.
5. Preemption: nothing compensates. Timing is wall clock and the handler never reads CPU time. Off-CPU time is not counted as CPU, so CPU = wall − off-CPU. Preemption inside a run inflates `run_duration`, so the next spin is up to 3× that time (cap: run 1000 µs, spin up to 3000 µs). This amplifies rather than makes up lost time. Consistent with the KNOWN probe (200 ms wall loop gives cpu ≈ 200 − p) by identity. (Inference.)
