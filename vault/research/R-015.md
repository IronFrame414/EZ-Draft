# Findings

1. PG* variables (https://www.postgresql.org/docs/current/libpq-envars.html): PGHOST=host, PGHOSTADDR=hostaddr, PGPORT=port, PGDATABASE=dbname, PGUSER=user, PGPASSWORD=password, PGPASSFILE=passfile, PGOPTIONS=options, PGAPPNAME=application_name, PGSSLMODE=sslmode, PGSSLROOTCERT=sslrootcert, PGCONNECT_TIMEOUT=connect_timeout, PGTARGETSESSIONATTRS=target_session_attrs, PGSERVICE=service. Variables apply "if no value is directly specified by the calling code" (same page).

2. dbname as a connection string (https://www.postgresql.org/docs/current/libpq-connect.html): with expand_dbname, only the first dbname keyword is checked for "=" or a URI scheme and expanded; later dbname keywords are plain names. For psql, "The dbname can be a connection string. If so, connection string parameters will override any conflicting command line options." (https://www.postgresql.org/docs/16/app-psql.html). No SCOPE page says a PGDATABASE value is expanded as a connection string; the envars page only says PGDATABASE maps to dbname.

3. Percent-encoding (https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNSTRING): the URI "needs to be encoded with percent-encoding if it includes symbols with special meaning in any of its parts" (example uses %3D and %20). Per-field decoding rules for user, password, dbname and query values are not stated. "+" is not mentioned anywhere in the pages read. Not answered by SCOPE.

4. Schemes (https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNSTRING): "The URI scheme designator can be either postgresql:// or postgres://."

5. PGPASSWORD vs password file: the password file "can contain passwords to be used if the connection requires a password (and no password has been specified otherwise)" (https://www.postgresql.org/docs/current/libpq-pgpass.html). This implies an explicit password (including PGPASSWORD, which fills an unset password keyword per https://www.postgresql.org/docs/current/libpq-connect.html) wins over the file. The pages do not name PGPASSWORD in that sentence; treat as inference. PGPASSFILE is "the same as the passfile connection parameter" (envars page). Unix file must deny group and world access, else the file is ignored (libpq-pgpass page).

6. Visibility: "Use of this environment variable is not recommended for security reasons, as some operating systems allow non-root users to see process environment variables via ps; instead consider using a password file" (https://www.postgresql.org/docs/current/libpq-envars.html). The connection and psql pages make no statement on command-line visibility of a password in a URI or --dbname.

7. Linux /proc (https://man7.org/linux/man-pages/man5/proc.5.html): the fetched text covers hidepid. With hidepid=0 (default) all /proc/pid are readable by everyone; hidepid=1 hides other users' /proc/pid files "such as /proc/pid/cmdline and /proc/pid/status"; hidepid=2 also hides other users' directories. The fetched text did not state the permission rule for /proc/pid/environ or the ptrace access check, so who can read environ is not confirmed by SCOPE.

Gaps: items 3, 5 (exact precedence), 7 (environ rule) are not answered by the SCOPE pages read. Pages searched: libpq-envars, libpq-connect (incl. Connection Strings section), libpq-pgpass, app-psql (v16), man7 proc(5).
