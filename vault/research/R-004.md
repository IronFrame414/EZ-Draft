# Findings

## (1) GET /repos/{owner}/{repo}/environments/{environment_name}
- deployment_branch_policy: "object or null", with required booleans protected_branches and custom_branch_policies. The GET schema does not explain null. The PUT body says "To allow all branches to deploy, set to null." https://docs.github.com/en/rest/deployments/environments?apiVersion=2022-11-28
- can_admins_bypass: not on that page. Not confirmed (presence, default, behaviour unknown). Closest field: PUT body prevent_self_review (boolean, not marked required, no default stated): "Whether or not a user who created the job is prevented from approving their own job." Same URL.
- Read access: "Anyone with read access to the repository can use this endpoint." Same URL. Private repos with classic PAT or OAuth need repo scope.
- Permission category: the GitHub Apps permissions page lists GET /repos/{owner}/{repo}/environments and GET .../deployment-branch-policies under Actions, Read. https://docs.github.com/en/rest/overview/permissions-required-for-github-apps?apiVersion=2022-11-28
- GITHUB_TOKEN scope names include `actions` with access levels read, write, none. The page lists no `environments` scope. "If you specify the access for any of these permissions, all of those that are not specified are set to none." https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions
- Inference, not stated in a fetched page: `actions: read` in the job's permissions block is the GITHUB_TOKEN scope for these reads.

## (2) GET /repos/{owner}/{repo}/environments/{environment_name}/deployment-branch-policies
- Response: total_count (integer, required); branch_policies (array, required) of objects with id, node_id, name, type. type is `branch` or `tag`. https://docs.github.com/en/rest/deployments/branch-policies?apiVersion=2022-11-28
- Pagination: per_page (max 100, default 30) and page (default 1). Same URL.
- Permission: "Anyone with read access to the repository can use this endpoint." Actions, Read per the Apps permissions page (URL in 1).
- custom_branch_policies must be true for the environment to have these policies. Same URL.

## (3) GET /repos/{owner}/{repo}/commits/{commit_sha}/pulls
- Described as "Lists the merged pull request that introduced the commit to the repository." If the commit is not on the default branch it also returns open and merged PRs associated with it. https://docs.github.com/en/rest/commits/commits?apiVersion=2022-11-28
- Item fields in the schema: merged_at (string or null, required), base.ref (required), number (required), title (required).
- merge_commit_sha: NOT in the response schema as fetched. The page does not say the match is by merge commit sha.
- Permission: the Apps permissions page lists this endpoint under Pull requests, Read, "no additional permissions", i.e. `pull-requests: read`. https://docs.github.com/en/rest/overview/permissions-required-for-github-apps?apiVersion=2022-11-28

## (4) Annotated tag
- POST /repos/{owner}/{repo}/git/tags: body tag, message, object (sha), type (commit, tree or blob; "Normally this is a commit"), all required. 201 response has sha, tag, object{sha,type,url}. https://docs.github.com/en/rest/git/tags?apiVersion=2022-11-28
- "Note that creating a tag object does not create the reference that makes a tag in Git." Same URL.
- POST /repos/{owner}/{repo}/git/refs: body ref (required; "If it doesn't start with 'refs' and have at least two slashes, it will be rejected") and sha (required). https://docs.github.com/en/rest/git/refs?apiVersion=2022-11-28
- Permission: the Apps permissions page lists POST git/refs and POST git/tags under Contents, Write. For git/refs it has an "additional permissions" checkmark with no explanation in the fetched text; git/tags has none. Whether `contents: write` alone is enough for each is not stated in the fetched text.

## (5) Required headers
- Exact curl example: `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, `Authorization: Bearer YOUR-TOKEN`. https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api?apiVersion=2022-11-28

## (6) CLAUDECODE
- Yes. Variables table: "CLAUDECODE: Set to `1` in subprocesses Claude Code spawns (Bash and PowerShell tools, tmux sessions, hook commands, status line commands, stdio MCP server subprocesses)." https://code.claude.com/docs/en/env-vars
- The same table says CLAUDE_CODE_CHILD_SESSION is set to 1 in Bash, PowerShell and Monitor subprocesses and is not set for stdio MCP servers. Same URL.
- Origin: GitHub issue #531 (closed); a collaborator wrote "v0.2.47 is out with this feature" on 2025-03-18. https://github.com/anthropics/claude-code/issues/531
- Not checked in a live shell.

## Gaps
- can_admins_bypass: absent from the docs.github.com environments page as fetched.
- merge_commit_sha: absent from the commits/pulls response schema as fetched.
- Exact GITHUB_TOKEN scope needed for each endpoint: the docs give categories (Actions, Contents, Pull requests), not a per-endpoint GITHUB_TOKEN table.
