# Findings

## 1. Content-MD5 or x-amz-checksum on PutObject to an Object Lock bucket

- AWS: "The Content-MD5 or x-amz-sdk-checksum-algorithm header is required for any request to upload an object with a retention period configured using Object Lock." If you use the PutObject API you must specify Content-MD5, x-amz-sdk-checksum-algorithm, or both. https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html
- Backblaze: "From a functionality standpoint, Object Lock with Backblaze B2 works the same way as it does with AWS." https://www.backblaze.com/docs/cloud-storage-object-lock
- Backblaze S3 PutObject page lists no Content-MD5 or x-amz-checksum header (required or optional). https://www.backblaze.com/apidocs/s3-put-object
- Not found: a B2 statement that a checksum is required, or that B2 rejects a default-retention upload without one.
- Not settled by the AWS page: whether the rule covers bucket default retention or only per-request retention headers ("a retention period configured using Object Lock"). Test against a real bucket.

## 2. SDK v3 "checksum only when required"

- Client options: `requestChecksumCalculation` and `responseChecksumValidation`. Values: `WHEN_SUPPORTED` (default) and `WHEN_REQUIRED`. https://github.com/aws/aws-sdk-js-v3/issues/6810 and https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html
- Environment: `AWS_REQUEST_CHECKSUM_CALCULATION`, `AWS_RESPONSE_CHECKSUM_VALIDATION`. Shared config: `request_checksum_calculation`, `response_checksum_validation`. https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html
- Default changed in v3.729.0: clients add an extra checksum on all Put calls and validate Get responses. https://github.com/aws/aws-sdk-js-v3/issues/6810
- JS default algorithm is CRC32 (AWS support table). https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html
- WHEN_REQUIRED is defined as checksum "performed only when required by the API operation." The AWS page does not say whether PutObject counts as required, or whether the SDK then sends Content-MD5. Not found.
- Issue #6819 (reporter, not maintainers): with WHEN_REQUIRED, deleteObjects still sent `x-amz-sdk-checksum-algorithm: CRC32`; versions up to 3.729.0 sent Content-MD5. Closed "not planned": "AWS SDK for JavaScript is designed to be used with AWS services." https://github.com/aws/aws-sdk-js-v3/issues/6819
- Whether B2 rejects CRC32 default headers: not found. Backblaze's PutObject page documents no checksum headers at all.
- Backblaze's JS v3 guide sets only endpoint and region; no checksum or forcePathStyle setting. https://www.backblaze.com/docs/cloud-storage-use-the-aws-sdk-for-javascript-v3-with-backblaze-b2

## 3. writeFiles-only key

- Put Object maps to `writeFiles`. https://www.backblaze.com/docs/cloud-storage-s3-compatible-app-keys
- "If an app key is restricted to a bucket, the `listAllBucketNames` permission is required" for "compatibility with SDKs and integrations." Same page.
- The B2 name is `listAllBucketNames`, not `listBuckets`. `listBuckets` maps to List Buckets and Head Bucket; `listAllBucketNames` maps to List Buckets. Same page.
- Not found: a statement that PutObject itself needs listBuckets, listAllBucketNames or readFiles, or which SDK call fails without them. Test it.
- Prefix: the page states prefix limits for readFiles and listFiles ("only the files that have a name that begins with that prefix can be downloaded"). Not found for writeFiles with a prefix. Same page.
- Per-file retention: the Object Lock page names only `readBucketRetentions` and `writeBucketRetentions`. No per-file retention capability is named. https://www.backblaze.com/docs/cloud-storage-object-lock

## 4. Region and path style

- Endpoint form: `s3.<region>.backblazeb2.com`, "<region> is similar to us-west-004." https://www.backblaze.com/docs/cloud-storage-call-the-s3-compatible-api
- Backblaze's JS v3 guide uses endpoint `https://s3.us-west-004.backblazeb2.com` and region `us-west-004`. It says to copy the endpoint from bucket details and set the region to match. https://www.backblaze.com/docs/cloud-storage-use-the-aws-sdk-for-javascript-v3-with-backblaze-b2
- Path style: the endpoint accepts the bucket name in the hostname or the path. "The AWS SDKs and most integrations require only an endpoint URL ... (without the bucket name included)." forcePathStyle is not mentioned in any Backblaze page read. https://www.backblaze.com/docs/cloud-storage-call-the-s3-compatible-api
