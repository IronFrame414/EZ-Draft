# Findings

## 1. IANA media type strings
- DXF: `image/vnd.dxf` (registered, reference "[Jodi_Moline]"). https://www.iana.org/assignments/media-types/image.csv
- GLB (binary glTF): `model/gltf-binary` (reference "[Khronos]; [Saurabh_Bhatia]"). https://www.iana.org/assignments/media-types/model.csv
- PDF: `application/pdf` (RFC 8118). https://www.iana.org/assignments/media-types/media-types.xhtml
- HEIC: `image/heic`; HEIF: `image/heif` (both ISO/IEC JTC 1 refs). https://www.iana.org/assignments/media-types/image.csv
- PNG: `image/png`. https://www.iana.org/assignments/media-types/image.csv
- JPEG: `image/jpeg` (RFC 2045, RFC 2046). https://www.iana.org/assignments/media-types/image.csv
- Not checked: whether a non-image `application/dxf` is registered (the application section fetch was truncated).

## 2. Bucket allowed_mime_types matching (storage-api)
- Shared validator `validateMimeType(mimeType, allowedMimeTypes)` in `src/storage/validators/mime-type.ts`. https://raw.githubusercontent.com/supabase/storage/master/src/storage/validators/mime-type.ts
- Requested type is parsed; wildcard is built from its top-level type (e.g. `image/*`). An allowed entry matches if it equals the requested type or that wildcard. Entry `*/*` never matches.
- Raw string compare first (case-sensitive), then parsed compare (lowercased, so case-insensitive).
- Parameters after `;` (e.g. `;charset=`) are ignored for matching (parser validates them, returns `type/subtype`).
- Allowed entries that fail to parse are skipped, not thrown.
- Standard upload: `mimeType = formData.fields.contentType?.value || formData.mimetype`; binary upload: `content-type` header, default `application/octet-stream`. Source: `src/storage/uploader.ts`. https://raw.githubusercontent.com/supabase/storage/master/src/storage/uploader.ts
- TUS: contentType comes from the `contentType` key in the `Upload-Metadata` header on POST (`parsedMetadata?.contentType`); HEAD/PATCH read it from the stored upload metadata. Source: `src/http/routes/tus/lifecycle.ts`. https://raw.githubusercontent.com/supabase/storage/master/src/http/routes/tus/lifecycle.ts
- TUS MIME check runs in `onCreate` only: bucket fetched with `file_size_limit, allowed_mime_types`; if contentType present and list non-empty, `validateMimeType` runs. `onUploadFinish` does not re-check MIME (as far as the fetched files show).

## 3. File size limits
- Global limit: Free plan cannot exceed 50 MB; Pro and up can set up to 500 GB; Team table 500 GB; Enterprise "Custom"; beyond 500 GB contact Supabase. https://supabase.com/docs/guides/storage/uploads/file-limits
- Bucket limit cannot be higher than the global limit (docs). Code caps it: `uploader.ts` takes min of bucket limit, tenant limit and config (`getStandardMaxFileSizeLimit`); TUS `maxSize` returns `bucket.file_size_limit || globalFileLimit`, then caps at global. https://raw.githubusercontent.com/supabase/storage/master/src/http/routes/tus/index.ts
- So a bucket limit above the global limit is not honored; the global value wins.
- Docs do not state the enforcement error for size.

## 4. Errors and order
- `InvalidMimeType`: message "mime type ${mimeType} is not supported", HTTP 415. https://raw.githubusercontent.com/supabase/storage/master/src/internal/errors/codes.ts
- `EntityTooLarge`: message "The ${entity} exceeded ${limit}", HTTP 413. Same file.
- `InvalidFileSizeLimit`: HTTP 400 (config format error, not an upload error). Same file.
- Order (standard upload, inferred from `uploader.ts`): MIME and pre-stream size checks in `fileUploadFromRequest`, then `prepareUpload` (`canUpload` permission), then streaming with truncation check (`EntityTooLarge`), then `completeUpload` which writes the object row via `upsertObject`. So MIME and size checks run before the storage.objects write. The RLS insert policy check is therefore after these checks, but the exact RLS ordering inside `upsertObject` was not read.
- TUS: MIME check on create (`onCreate`) happens before the upload URL is issued; size enforced by tus `maxSize` on requests. Relation to the DB insert on finish not confirmed.
- Docs do not describe the RLS error text.
