## Findings

1. Dashboard action: no Postgres-only restart is documented in SCOPE. The documented actions are a full project restart, which restarts all databases including read replicas (https://supabase.com/docs/guides/platform/troubleshooting), and a per-Read-Replica restart from the Infrastructure Settings page (same URL). No restart duration is stated (same URL; https://supabase.com/docs/guides/platform/migrating-to-supabase/postgres has none either). No source says whether Realtime WebSocket clients stay connected through a restart. The Realtime architecture and concepts pages do not cover it (https://supabase.com/docs/guides/realtime/architecture, https://supabase.com/docs/guides/realtime/concepts).
2. Realtime database role on hosted projects: the Realtime server defaults its DB user to `supabase_admin` via `db_user = System.get_env("DB_USER", "supabase_admin")`, reused for the primary repo, libcluster and replica repos (https://github.com/supabase/realtime/blob/main/config/runtime.exs). No separate replication or extension user appears in that file (same URL). This is the code default, not a hosted-project statement.
3. `supabase_admin` is described as "An internal role Supabase uses for administrative tasks, such as running upgrades and automations" (https://supabase.com/docs/guides/database/postgres/roles). The roles page does not mention Realtime.
4. The roles page says `supabase_etl_admin` "has replication privileges for change data capture, bypasses Row Level Security" and is used by Supabase Pipelines (https://supabase.com/docs/guides/database/postgres/roles). It does not say Realtime uses it.
5. `postgres` role: "The default Postgres role. This has admin privileges." (https://supabase.com/docs/guides/database/postgres/roles). The page does not say whether `postgres` is a superuser on hosted projects.
6. Slots: Realtime uses at most two replication slots, one for Broadcast from database and one for Postgres Changes (https://supabase.com/docs/guides/realtime/concepts). The Broadcast slot is "always started" as one connection (same URL). The slot name pattern `supabase_realtime_messages_replication_slot*` is not in any fetched page.
7. Terminating backends: `select pg_terminate_backend(pid);` ends the session's connection (https://supabase.com/docs/guides/database/connection-management). Both `pg_terminate_backend` and `pg_signal_backend` require "either be a superuser, hold the `pg_signal_backend` role" (same URL). "even `pg_signal_backend` can't be used to stop a session belonging to an actual superuser role" (same URL). Not stated: whether `postgres` may terminate `supabase_admin` sessions, which depends on whether `supabase_admin` counts as a superuser role. Unverified.
8. Reading `pg_replication_slots`: not covered by any SCOPE page I fetched. Not answered.
9. Open bug, search snippet only, not fetched: supabase/realtime issue #2246 reports that slot teardown drops nothing when more than one realtime replication slot exists (https://github.com/supabase/realtime/issues/2246).

## Gaps (answer from SCOPE is not available)

- No Postgres-only restart action found in the docs. Check the live dashboard (Project Settings / Infrastructure) and Supabase support for its name, duration and Realtime effect.
- No hosted statement on the Realtime database role or on `postgres` privileges over `supabase_admin` or replication backends.
- No hosted source on whether `pg_terminate_backend` against the Realtime replication backend is safe.
