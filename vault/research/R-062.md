## 2. Timing and inclusivity
- In `sendMagicLink` the frequency check runs first, before token generation and before the send. Same order in `sendConfirmation`. Source: mail.go (funcs sendMagicLink, sendConfirmation).
- `sendMagicLink` records `time.Now()` after the check and before `sendEmail`. After a successful send it assigns that time to `RecoverySentAt` and persists `recovery_token` and `recovery_sent_at` (UpdateOnly). So the stored value is the pre-send time, written after the send. Source: mail.go (func sendMagicLink).
- Check (func validateSentWithinFrequencyLimit): refuses iff `sentAt.Add(frequency).After(time.Now())`. Strict `After`, so at exactly max_frequency elapsed the request is allowed (inclusive). Source: mail.go (func validateSentWithinFrequencyLimit).

## 3. GOTRUE_RATE_LIMIT_EMAIL_SENT enforcement
- Field: `RateLimitEmailSent Rate` with default "30". Source: https://raw.githubusercontent.com/supabase/auth/v2.197.0/internal/conf/configuration.go (GlobalConfiguration).
- Parsing (internal/conf/rate.go, func Decode): a plain number such as "30" gives an interval-type rate with Events = that number and OverTime defaulting to one hour. A two-part "events/duration" form such as "10/5s" gives a burst-type rate. Source: https://raw.githubusercontent.com/supabase/auth/v2.197.0/internal/conf/rate.go
- Local stack value "1000/hour": by this paraphrase it splits into two parts, so it is burst-type, and "hour" is not a valid Go duration. This suggests a parse error. NOT verified; check the parser at the tag before relying on it.
- Algorithm: an interval type uses `NewIntervalLimiter` (internal/ratelimit/interval.go). This is a FIXED WINDOW. Count resets when whole intervals elapse, with `last` advanced in whole intervals. Source: https://raw.githubusercontent.com/supabase/auth/v2.197.0/internal/ratelimit/interval.go. Burst type is a token bucket (internal/ratelimit/burst.go).
- Scope: state is in process memory guarded by a mutex, so each server process counts separately. Source: internal/ratelimit/interval.go (and ratelimit.go).
- Enforcement point: `sendEmail` (mail.go). If `Events == 0` it refuses. If autoconfirm is off it calls `a.limiterOpts.Email.Allow()` and refuses when false. Both refusals return `EmailRateLimitExceeded`. Source: mail.go (func sendEmail).
- Host: no SMTP-host check was found in the `sendEmail` or `SMTPConfiguration.Validate` paths. So the limiter applies regardless of the SMTP host, including a local mail catcher. Source: mail.go (func sendEmail); internal/conf/configuration.go (SMTPConfiguration.Validate). This is inferred from the absence of a check, not from a positive statement.
- Wiring: `New()` in internal/api/apilimiter sets `o.Email = ratelimit.New(gc.RateLimitEmailSent)`. Source: https://raw.githubusercontent.com/supabase/auth/v2.197.0/internal/api/apilimiter/apilimiter.go

## 4. Refusal error for max_frequency
- `sendMagicLink` and `sendConfirmation` wrap the refusal as `apierrors.NewTooManyRequestsError(apierrors.ErrorCodeOverEmailSendRateLimit, ...)`. Source: mail.go (funcs sendConfirmation, sendMagicLink, validateSentWithinFrequencyLimit).
- `ErrorCodeOverEmailSendRateLimit` = "over_email_send_rate_limit"; `ErrorCodeOverRequestRateLimit` = "over_request_rate_limit". Source: https://raw.githubusercontent.com/supabase/auth/v2.197.0/internal/api/apierrors/errorcode.go
- `NewTooManyRequestsError` sets HTTP 429. Source: https://raw.githubusercontent.com/supabase/auth/v2.197.0/internal/api/apierrors/apierrors.go
- So a max_frequency refusal is HTTP 429 with code over_email_send_rate_limit. The rate-limit refusal from `sendEmail` (EmailRateLimitExceeded) is wrapped the same way in sendConfirmation and sendMagicLink.
