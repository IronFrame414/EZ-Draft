## 2. Ticket IDs and statuses

- Format `EZD-<number>` with an optional lowercase letter for split parts (`EZD-016a`). `next_ticket.mjs` parses only this format: no other suffixes.
- Phase N owns numbers N×100 to N×100+99 (Phase 0: 000–099). Fix tickets from a phase gate take the next free number in their phase, title starting `Fix:`.
- A dependency on a split ticket's base number means all of its lettered parts (R26 R33). `tickets.json` `depends_on` is already expanded.
- 36 tickets depend on a later-numbered ticket in the same phase; `next_ticket.mjs` picks by dependencies, never by number alone.
- A new or split ticket is added to the phase file, `tickets.json` (with `acs` from `gen_acs.mjs`) and `STATUS.md` in one commit by the orchestrator; `next_ticket.mjs --check` must pass.
- Statuses are the PROCESS.md section 13 set. Phase 0's 37 tickets are `ready` (planned and questioned under process v1; retroactive sign-off in `SIGNOFF.md`).

## 3. Agents beyond the roster

**calc-auditor** (the domain specialist PROCESS.md section 4 allows): `claude-opus-5-5`, effort high, maxTurns 30, writes nothing. Checks the NEC Art. 220 load calc, voltage drop, wire sizing, dimensions, scaling, area, takeoff quantities and the code-check rules against known values. Level-3 answerer for NEC, Florida Building Code and calculation questions. Reviews, in Stage 3 step 8, any ticket whose plan touches a calculation, dimensions, scaling, takeoff formulas or code-rule checks (the plan's Reviewers line says so).

**security-reviewer's domain here:** tenant isolation and row-level security, the `can()` helper, money permissions (See company costs, See sell prices; Owner and Designer have both, Foreman and Crew company costs only, R26 R2), auth and sessions, the client link, webhooks and the inbound API, migrations, and the production-sensitive paths in section 7.

**ui-verifier:** one viewport per ticket, named by the plan's visual checklist: desktop 1600 × 1000 by default; iPad landscape 1180 × 820 for device-layout tickets; phone size for field-pack and client-link tickets. Screenshots go in `vault/plans/shots/`, downscaled before the agent reads them.

**phase-auditor** runs on `claude-fable-5-1`; Opus 5.5 is the fallback (Q-0004 and PROCESS.md section 4).

Write limits beyond the roster table: the orchestrator may also write `CLAUDE.md` (Q-0005: EZD-000 does not overwrite it) and `docs/architecture.md`; in `vault/spec/` it may write only `decisions/`, `glossary.md`, `non-goals.md`, `acceptance-criteria.md`, `READINESS.md` and a section file that does not exist yet (a Stage 0 gap filled from Josh's answer). test-author may also write `test-utils/` and `test-harness/`. The builder may add new workflow files under `.github/workflows/` but never `ci.yml`. `SIGNOFF.md`, `budget.json` and `BUDGET_HOLD.md` are written only by Josh and `scripts/budget.mjs`.

## 4. Gate scope and test runs (Q-0006, Q-0019, Q-0114)

- In a ticket worktree, `scripts/gate.mjs` runs the phase's tests plus the `@smoke` set; at the repo root or with `--full` it runs the full suite (the phase gate and CI). After each squash merge the orchestrator runs `node scripts/gate.mjs . --phase <N>` on `develop`. This is Josh's refinement of PROCESS.md section 8 step 7 for this project (Q-0006, Josh, Oct 11).
- Only one gate runs at a time on the machine (the gate script holds a lock).
- Playwright workers = 4 on the Mac mini (Q-0114, Josh, Oct 17; replaces the Windows answer of 2 in Q-0019). Plans that cite Q-0019 for the worker count read it as 4.
- The gate writes `gate.log` in the worktree and prints the summary; reviewers read the summary.

## 7. CI, hosting and releases

- CI runs on the PR to `main` and by hand (Q-0021; PROCESS.md section 12). Two push-triggered workflows are allowed by Josh's decisions and are the only exceptions: `release.yml` on push to `main` (Q-0106: merging the phase PR backs up production, applies migrations and makes the build live, or stops with the live site unchanged) and the dev-migration workflow on a push to `develop` that changes `supabase/migrations/**` (Q-0107). EZD-002's test T2 pins both to their branch.
- The phase PR is opened from the agents' GitHub account `ironframe414-agent` (Write role; Q-0108). Only Josh approves and merges.
- **Production-sensitive paths** (Q-0112): `.github/workflows/**`, `scripts/release/**`, `scripts/backup/**`, `scripts/hosting/**`, `supabase/migrations/**`, `supabase/bootstrap/**`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `.npmrc`. The gate flags them as security paths on every ticket; at the phase gate security-reviewer writes a "Production-sensitive changes: PASS / FAIL" section for the PR. A FAIL blocks the PR.
- Vercel: production builds from `main` only. Whether the Ignored Build Step is set (PROCESS.md section 12, which the phase gate's empty `chore: preview` commit relies on) or `develop` previews stay on (EZD-003's plan, Q-0007) is Q-0116, waiting on Josh. Until he answers, EZD-003 is not built.
- Phase gate additions: the full gate on `develop` also runs the phase's Build gate test from its phase file; the PR carries the phase's Field check (Josh's own test on real jobs and devices, which does not block the next phase; what it finds becomes tickets).
