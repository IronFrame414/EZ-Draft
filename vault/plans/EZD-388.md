## 1. What to build
The diagnosis is in section 2 ("Diagnosis"): the load sensitivity is in the D-Split rule, not in the count and not in the fixture's margin. The fix moves the iPad long-task pan row to a new unthrottled profile `ipad-cpu` and counts the trace's own main-thread tasks by CPU time × 4 there. **These code-bound blocks are written for Q-0737 option (a), the planner's recommendation; Q-0737 is still open.** If it is answered (b) or (c), this plan goes back to step code-bound before any build (section 9). Desktop and `ipad-1x` keep `splitTasks` unchanged.

- **Diagnosis** (design step, from R-061, the merged code and Q-0623's own figures):
  1. *How the throttle works (R-061).* A throttler thread signals the page's main thread every 200 µs; the signal handler busy-waits on the wall clock for (rate − 1) × the wall time since the thread last resumed (run capped at 1,000 µs), so at rate 4 the thread spends 3/4 of its time spinning. The handler also runs on a thread blocked in a wait (`SA_RESTART`), the spin is main-thread CPU, and nothing makes up time the OS takes away. This matches the Q-0623 probe (a pure 100 ms wait shows cpu 76-78) and lesson EZD-359 (the POSIX throttle spins and does not suspend).
  2. *What D-Split then computes.* For a task with own work `o` ms that the OS takes off the CPU for a share `f` of its wall time, spin and run both lose that share, so `ms = 4o / (1 − f)` and `cpu = 4o`. D-Split's score `cpu × 4 − ms × 3` is then `4o × (1 − 4f) / (1 − f)`: it reaches 0 at `f = 0.25` for every task, however much work it does. For P2's wall-bounded 200 ms loop the score is `200 − 4p` with `p = 200f` ms preempted, under the line from `p = 38` (Q-0623 cost line), that is `f = 0.19`.
  3. *The count is not load sensitive.* The long-task observer still delivers the 8 wheel tasks: the desktop row (rate 1, `cpu > 50`, needs `p > 150` to miss) holds 8 on the same fixture run while the iPad row counts 4 to 6, on CI (`vault/plans/EZD-374.md` section 1 item 2, A1 row 2) and on the Mac (EZD-372 STATUS note, gate 4).
  4. *The fixture's margin cannot fix it.* A longer loop only moves P2's line from `f = 0.19` (200 ms) toward `f = 0.25`, and a loop that counts only its own running time scores the same `4o × (1 − 4f) / (1 − f)`. No fixture holds 8 once the Mac takes a quarter of the main thread.
  5. *The same flaw hides real app work.* Under that load an iPad pan task of any size becomes a wait and passes (fail open). Rule 18 asks to close the class, so the fix is in the rule, on the row the benchmark pan gates, not only in the fixture. That overrides Q-0623 (a): Q-0737.
- **Why option (a) is never weaker at idle** (code-bound step): on an idle Mac a throttled task with own work `o` has `ms = cpu = 4o`, so today's score is `4o` and it counts when `o > 12.5` ms; `countByCpu` at rate 1 counts when `tdur × 4 > 50`, that is `o > 12.5` ms. The line is the same; only the load sensitivity goes. With no trace, the row errors instead of counting less (D-NoTrace).
