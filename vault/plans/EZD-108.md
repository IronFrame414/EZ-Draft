## 1. What to build

Data: no new table or column. `app_user.language` (`en`/`es`) and `app_user.ipad_input_mode` (`pencil`/`finger`/null) exist (`supabase/migrations/20261019165202_create_app_user.sql`; 03c user). `app_user` stays select-only for `authenticated`; two new owner-rights functions:
- `public.update_my_profile(p_language text, p_ipad_input_mode text) returns table (saved_language text, saved_ipad_input_mode text, language_changed boolean)`, plpgsql, volatile, security definer, `search_path = ''`. Body, in order: `perform private.require_api_gate()`; `v_user := private.app_user_id()`, null → `42501 permission_denied`; a null or out-of-list value → `22023 invalid_input`; read the old language `for update`; update only the caller's row and only when a value differs (so `updated_at` stays); return the row with `language_changed = old is distinct from p_language`.
- `public.current_user_has_password() returns boolean`, plpgsql, stable, security definer, `search_path = ''`: `perform private.require_api_gate()`, then `coalesce((select coalesce(u.encrypted_password,'') <> '' from auth.users u where u.id = auth.uid()), false)`.
- Each: `revoke all on function … from public, anon, service_role;` then `grant execute … to authenticated;` (L-016; pattern `20261027001745_guard_gated_rpcs.sql`). Both bodies ran on the pinned stack (PostgreSQL in `supabase_db_ezdraft`, rolled back, 2026-10-29). No money fields.

Pinned Auth facts this design rests on (probed on local Auth v2.197.0, 2026-10-29; R-044): `secure_password_change = true` maps to `GOTRUE_SECURITY_UPDATE_PASSWORD_REQUIRE_REAUTHENTICATION=true`; `updateUser({ password })` on a session created more than 24 h ago returns 400 `reauthentication_needed` (a `current_password` does not lift it); on a fresh session it succeeds and Auth deletes every other session of the user; re-using the current password returns 422 `same_password`; a code-only user has an empty `encrypted_password` before and after sign-in.

- Risks: the session move after a password change (step 6) relies on `@supabase/ssr` writing the new session's cookies over the old ones; T15 proves it in a browser. `current_user_has_password` reads `auth.users`, a Supabase-managed table whose column may change on an Auth upgrade (T4 catches it). A password-change test that leaves the throttle counting can clash with EZD-033's tests only through the same email, and every test uses a random email.

## 10. Open questions
- Q-0447 (was QP-1): Supabase asks for an emailed 6-digit code before a password can be set from a session older than 24 hours (most users stay signed in for months, Q-0048), but Q-0412 lists only New password and Confirm for Set password; options: (a) when Supabase asks, email the existing confirmation code (Q-0102 wording) and show a Code box under the two fields, as this plan does (recommended); (b) ask the person to sign out and sign in again before setting a password; (c) set it with the server's admin key with no extra check, which lets anyone holding a stolen session add a password.
