  - It compares those counts with what the parser returned: not read = raw count − parsed count, per type.

In DXF entity types (*planner's mapping*, technical) that is:

| 08 term | DXF entity types required |
| --- | --- |
| linework | LINE, ARC, CIRCLE, LWPOLYLINE, POLYLINE, ELLIPSE, SPLINE |

| text | TEXT, MTEXT |
| dims | DIMENSION |

| layers | the LAYER table, and group 8 on every entity |

  - Every other type (LEADER, MULTILEADER, WIPEOUT, IMAGE, ATTRIB, SOLID, POINT, proxies, 3D types and so on) may be unread. It is then counted and listed (R16), not a no-go.

### Step 2: Raw scanner `src/raw-scan.mjs` (builder; pure: Node built-ins only, no parser)
`rawScan(text)` returns `{ binary, header, entities, blocks }`.

**Input handling**
- Binary DXF:
  - A file whose first bytes are `AutoCAD Binary DXF` gives `binary: true` and nothing else.
  - The report then marks the file unreadable (S11 States: "Unreadable file").
  - Its parse is skipped.
- Text DXF is read as group-code / value line pairs:
  - each code is trimmed and parsed as an integer;
  - a trailing `\r` is removed from each value, so CRLF and LF files give the same result.

**Header**
- From the HEADER section: `$ACADVER` (group 1), `$INSUNITS` (group 70) and `$DWGCODEPAGE` (group 3), each `null` when absent.

**ENTITIES section**
- Each `0 <TYPE>` starts a record.
- `VERTEX`, `ATTRIB` and `SEQEND` are sub-records of the POLYLINE or INSERT before them. They are counted in `subRecords`, not as entities.
- Per record:
  - the layer is its group 8 value (default `0`);
  - it is paper space when group 67 = 1.
- Output: `{ total, byType, byLayer, paperSpace, subRecords }`.

**BLOCKS section**
- `BLOCK` (name from group 2) through `ENDBLK` is one definition.
- The records inside are counted with the same sub-record rule.
- Output: `{ count, entities, byBlock: { <name>: n }, byType }`.

**Decoding (planner's choice)**
- The file is first read as `latin1`, which is safe for ASCII, to find `$ACADVER`.
- `AC1021` (R2007) and later are then decoded as UTF-8. Earlier versions stay `latin1`, the usual `ANSI_1252` code page.
- The decoding used is reported.
- Real handling of other code pages is EZD-901a's job.

### Step 3: Report `src/report.mjs` (builder)
`buildReport({ label, fileName, bytes, sha256, text, parser })` runs `rawScan`, then the parser (`parseSync` or the pinned API), then compares the two.

**Parsed counts (`parsed`)**
- The parser's entities are grouped by type, layer and paper-space flag.
- Its blocks are counted by name and by number of entities.
- `handles` is true when parsed entities carry their group 5 handle.

**Not read (`notRead`)**
- `notRead[type] = raw − parsed` for every type where raw is greater.
- It is computed for ENTITIES and BLOCKS separately and then combined, as `notReadBySection { entities, blocks }` and `notRead`.
- A type where the parser returns more than the file holds goes into `extra`.

**Results JSON (`schema: 1`)**

| Group | Fields |
| --- | --- |
| Identity | `ticket` `"EZD-029"`, `label` |
| File | `file { name, bytes, sha256 }` (base name only) |
| Runtime | `runtime { node, platform, parser { name, version }, decoding, limits { seconds, memoryMb } }` |
| Contents | `header`, `binary`, `raw`, `parsed`, `notRead`, `notReadBySection`, `extra` |
| Timing | `timing { readMs, parseMs, reportMs, ms }` |
| Memory | `memory { maxRssMb, heapUsedAfterMb }` |
| Job fit | `fitsOneSlice` |
| Outcome | `pass` |

- `fitsOneSlice` is `ms ≤ (seconds − 30) × 1000`, the EZD-009 run budget. It is recorded only, because a synchronous parse cannot be split across job slices (EZD-009 Step 4).

**Printed lines** (developer text, not user wording)
- `EZD-029 report: <label>`
- `entities in file: <raw.total + raw.blocks.entities>; read: <parsed total>`
- one line per not-read type, sorted by count descending: `<n> entities of type <TYPE> not read`. The shape follows R26 R16's "N entities of type X not drawn".
- `time: <ms> ms; peak memory: <maxRssMb> MB; limits: <seconds> s, <memoryMb> MB`
- The report holds counts, type names, layer names, sizes and times only. It never holds text values.

### Step 4: Limits and the child process (builder; the EZD-028 Step 5 pattern, copied)
- `src/limits.mjs`:
  - `SECONDS` = **300** and `MEMORY_MB` = **2048** (Q-0027 (a): Vercel Pro defaults, 300 s and 2 GB). They are named constants with a comment citing Q-0027 (a).
  - `SLICE_MARGIN_SECONDS = 30` (EZD-009 Step 4).
  - `judge({ exitCode, timedOut, maxRssMb }, limits)` returns `{ pass, reason }`. The reason is `timeout`, `crashed`, `memory` (when `maxRssMb ≥ memoryMb`) or `null`.
- `src/child.mjs <file> <label>`:
  - reads the file;
  - builds the report and times each phase with `process.hrtime.bigint`;
  - sets `memory.maxRssMb = process.resourceUsage().maxRSS / 1024`;
  - prints the report JSON as the last stdout line.
- `src/run-in-limits.mjs`:
  - Arguments: `--file <path>` (repeatable), `--label <label>`, `--standin <units>`, `--out <dir>`.
  - With `--standin`, it first writes the stand-in to `<out>/standin/standin-<units>.dxf` (Step 5) and records the generation time apart from the parse.
  - It spawns `process.execPath --max-old-space-size=<MEMORY_MB> src/child.mjs …` and kills the child after `SECONDS`.
  - It applies `judge` and sets `pass`.
  - It prints the human lines and the JSON.
  - It merges the result under `runs[<label>]` in `<out>/results.json`.
  - It exits non-zero when the child timed out, crashed or reached the memory cap.

### Step 5: Stand-in generator `src/standin.mjs` (builder; Node built-ins only, never the writer under test)
It is independent of the packages under test, for the same reason as EZD-016b Step 1 reason 1.

**API and file**
- `generateStandIn({ units }) → string` writes an ASCII DXF R2000 file (`AC1015`, LF line endings).
- HEADER: `$ACADVER AC1015`, `$INSUNITS 1`, `$DWGCODEPAGE ANSI_1252`, `$HANDSEED`.
- TABLES:
  - LTYPE `CONTINUOUS`;
  - LAYER `0` and `EZD-L0` … `EZD-L9` (11 layers);
  - STYLE `Standard`;
  - BLOCK_RECORD for every block.
- BLOCKS, ENTITIES, and a minimal OBJECTS section.
- Every entity and block entity has a unique group 5 handle, assigned in sequence from `100` (hex).
- Built from the DXF Reference group codes. It is checked only by the raw scanner and the parser, not against AutoCAD (Risks).

**Spike inputs**
None of the values below is a product value (KNOWN-LIMITS 5; same standing as the inputs of EZD-027, EZD-028 and EZD-030). All lengths are decimal inches (03 rule 5).

**Units and layers**
- The file is `units` repetitions of one 100-entity unit (u = 0 … units − 1).
- Every entity of unit u is on layer `EZD-L<u mod 10>`, so 1,500 units give 10 layers × 15,000 entities each (the same per-layer size as EZD-027's scene).

**Per unit**
- Model space, 98 entities: LINE 53, ARC 10, CIRCLE 5, LWPOLYLINE 10, ELLIPSE 2, SPLINE 2, TEXT 4, MTEXT 3, INSERT 5, HATCH 2, DIMENSION 2.
- Paper space (group 67 = 1), 2 entities: LINE 1, TEXT 1.
- Unit total: LINE 54, ARC 10, CIRCLE 5, LWPOLYLINE 10, ELLIPSE 2, SPLINE 2, TEXT 5, MTEXT 3, INSERT 5, HATCH 2, DIMENSION 2 = **100**.

**Geometry of the model-space entities**
The k-th model-space entity of a type in unit u is that type's base entity below, moved by (1.5·k, 0.25·u). All z values are 0.

| Type | Base entity (u = 0, k = 0) |
| --- | --- |
| LINE | (0,0) → (96,0) |
| ARC | centre (120,120), radius 24, start 0°, end 90° |
| CIRCLE | centre (200,120), radius 12 |
| LWPOLYLINE | closed (70 = 1), 4 vertices (300,0), (348,0), (348,36), (300,36) |
| ELLIPSE | centre (400,120), major-axis endpoint relative (30,0), ratio 0.5, parameters 0 to 6.283185307179586 |
| SPLINE | degree 3, flag 8, 8 knots 0,0,0,0,1,1,1,1, 4 control points (500,0), (520,40), (560,40), (580,0) |
| TEXT | insertion (600,0), height 6, value `EZD-029 T<u>-<k>` |
| MTEXT | insertion (600,60), height 6, attachment 1, value `EZD-029 M<u>-<k>` |
| INSERT | block `EZD_B<(u + k) mod 10>`, insertion (700,0), scale 1, rotation 0 |
| HATCH | pattern `SOLID`, solid flag 1, 1 polyline loop, closed, 4 vertices (800,0), (848,0), (848,48), (800,48) |
| DIMENSION | linear (70 = 0, rotation 0); extension points (0,0) and (96,0); dimension-line point (96,−24); text midpoint (48,−21); measurement 96; block `*D1` |

**Paper-space entities of unit u**
- LINE (0, 0.25·(u mod 96)) → (36, 0.25·(u mod 96)).
- TEXT at (1, 1 + 0.25·(u mod 96)), height 0.125, value `EZD-029 P<u>`.
- So everything stays on a 36 × 24 sheet.

**BLOCKS**
13 definitions, 43 entities:
- `*Model_Space` and `*Paper_Space`, both empty;
- `EZD_B0` … `EZD_B9`, each holding 4 LINE forming a 12-inch square: (0,0)–(12,0), (12,0)–(12,12), (12,12)–(0,12), (0,12)–(0,0);
- `*D1`, holding 3 LINE: (0,−24)–(96,−24), (0,−2)–(0,−26) and (96,−2)–(96,−26).

Every DIMENSION points at `*D1`. This is a stand-in shortcut: real files have one block per dimension.

**Totals for 1,500 units (150,000 entities)**
- LINE 81,000 (79,500 model + 1,500 paper), ARC 15,000, CIRCLE 7,500, LWPOLYLINE 15,000, ELLIPSE 3,000, SPLINE 3,000, TEXT 7,500 (6,000 + 1,500), MTEXT 4,500, INSERT 7,500, HATCH 3,000, DIMENSION 3,000.

## Risks
- **The verdict rests on a generated stand-in.**
  - The stand-in is hand-built to the DXF Reference and checked only by the raw scanner and the parser.
  - Real architect files carry what it does not: proxy entities, MULTILEADER, WIPEOUT, IMAGE / xrefs, one block per dimension, many layouts, other code pages, possibly binary DXF.
  - The real-file run (Step 7) is where those show up. Until then the note says so.
  - If the parser reads a stand-in type badly because the generator is wrong, the builder checks the generator against the DXF Reference before blaming the parser, and the README says what was found.
- **HATCH and other required types in dxf-parser.** Not verified by the planner. If a required type is unread:
  - the order is own handler first, then replacement (Step 9);
  - a replacement touches EZD-000 T4, EZD-016b T2 / T8, the root devDependency and EZD-020's lint list;
  - that may not fit one session. If it does not, the orchestrator splits off **EZD-029b "switch to the replacement parser"** (scope: the Step 8 replace-path files; Done when: G1 plus EZD-000 T4 and EZD-016b T2 / T8 passing with the new parser). EZD-029 then closes with the evaluation and a "replace" Decision.
- **A parse is one synchronous unit.**
  - EZD-009 splits jobs between units, and a single parse cannot be split.
  - A file whose parse does not fit one slice (`fitsOneSlice` false) needs a streaming parse or a size limit. Those are EZD-901a's and EZD-1702's to settle.
- **Emulation is not the platform.**
  - The build PC runs Node v24, while Vercel and CI run 22 (EZD-000 Risks).
  - Windows peak working set is not Vercel's memory accounting.
  - The Storage download that a real job starts with is not measured.
  - The results record the Node version. EZD-901a proves the real run (as EZD-028 Risks).
