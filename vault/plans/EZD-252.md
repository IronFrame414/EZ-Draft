# EZD-252 · Fix: a test file that writes error_alert rows must hold the error-alert lock

- **ACs:** AC-EZD-252-1, AC-EZD-252-2 (`vault/spec/acceptance-criteria.md` lines 439-440)
- **Complexity:** high (section 8)
- **User-visible result:** none in the app. A test file that makes the app write an error alert without the shared lock now fails the gate, and the write is refused, so the alert-count tests stay reliable.
- Phase: 1 · Planned by: planner · Date: 2026-10-28 · Status: planned

## 1. What to build
Design (Q-0385 (a): detect the write itself; CLAUDE.md rule 18: a design that cannot drift):
- **D1 Detection at the write.** A row trigger `ezd_test_alert_write_guard` on `public.error_alert` (AFTER INSERT OR UPDATE OR DELETE, FOR EACH ROW), installed in the local test database by the Vitest global setup. Every write path is covered, including SQL functions added later. A fixed list of RPC names (`record_error_alert`, `release_error_alert_email`; `report.ts` line 69, `alert-email.ts` line 91) would miss a write function added later, so no list is used. Cost: section 9.
- **D2 Attribution per file.** Each Vitest file gets a random token. The setup file's fetch wrapper sends it as header `x-ezd-test-file` on every request to the local Supabase origin. PostgREST exposes it as `request.headers`, the same way the API gate reads `x-ezd-api-gate` (migration `20261027001405_create_require_api_gate.sql` line 42). `holdErrorAlertLock()` opens its lock connection with `application_name` = `ezd-alert-lock <token>`. The trigger refuses a tagged write unless a backend whose `application_name` is `ezd-alert-lock <same token>` holds advisory lock 9024 (`alert-lock.ts` line 9).
- **D3 Refuse, then fail the file.** A refused write raises SQLSTATE `EZ252`, so the row is never written. The fetch wrapper sees `code: 'EZ252'` in the failed response and records a violation. The setup file's `afterEach` and final `afterAll` throw, the same way as `net-guard/vitest.setup.ts`. Refusing also stops a write that lands after the file's last check.
- **Roles:** every file of the check is under `test-harness/` or is a test config, so the test-author writes them all (`.claude/hooks/guard-paths.mjs` lines 15-17, 80-84). The builder writes only `docs/architecture.md`, then runs the gate.

Data: no migration and no production schema change. Test-only objects in the local database: schema `ezd_test`, function `ezd_test.alert_write_guard()`, trigger `ezd_test_alert_write_guard` on `public.error_alert`.
