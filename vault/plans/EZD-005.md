## Approach

Technical choices that no source makes are marked *planner's choice (CLAUDE.md rule 4)*. The code-reviewer and security-reviewer confirm them at plan review.

### Step 1: Naming and shape decisions (planner's choices)
1. **The `user` entity is the table `public.app_user`.** `user` is a reserved word in PostgreSQL, so every SQL reference would need quotes, including in EZD-006's policies and token hook. Every other entity keeps its Data model name (`tenant`, `membership`, `membership_project`, `project`). Recorded in `docs/architecture.md` (Step 6) so later plans write `app_user`.
2. **Keys are `uuid` with `gen_random_uuid()` defaults.** Storage paths start with `<tenant_id>/` (EZD-000 Storage) and the auth ids are uuid. "Tenant 1" (02 Scope row; ticket Done when) is a **fixed seed id**: tenant `00000000-0000-4000-8000-000000000001`. Josh's `app_user` id is `00000000-0000-4000-8000-000000001001`. Both are RFC 4122 version-4 shaped, so strict uuid validators (Zod) accept them.
3. **`tenant` and `app_user` have no `tenant_id` column.**
   - `tenant` is the tenant; its key is `id`.
   - `app_user` is one person across tenants. Data model puts the tenant link on `membership (user_id, tenant_id)`. A per-tenant user row would duplicate membership and break one-email-one-person sign-in (magic link by email, R26 R15). S15 Validation "Invite email … not already a member of the tenant" implies one email may already be a user elsewhere.
   - So these two are the tenant-less tables. EZD-006's "every table has tenant\_id and an index" CI test needs an explicit list of tenant-less tables with a reason each. The Data model itself lists other tables with no tenant (code\_rule, benchmark\_run), so that list is needed anyway. Recorded in `docs/architecture.md` (Step 6).
   - The security-reviewer confirms this at plan review.
4. **Link to Supabase Auth:** `app_user.auth_user_id uuid null unique references auth.users(id) on delete set null`, instead of making `app_user.id` equal to the auth id.
   - Invited users exist before they ever sign in ("Invite pending" rows, S15; EZD-105 "an app invite token valid for 7 days").
   - A local seed then never writes Supabase's internal `auth.users` / `auth.identities` rows.
   - Filling `auth_user_id` at first sign-in is EZD-007's job; this ticket only provides the column.
5. **Cross-tenant links are blocked by composite foreign keys.**
   - `membership` and `project` each get `unique (id, tenant_id)`.
   - `membership_project` references `(membership_id, tenant_id)` and `(project_id, tenant_id)`, so a listed project can never belong to another tenant than the membership.
   - Tenant isolation, 11 Security and audit.
6. **Enumerated values are `text` with a `check` constraint**, not Postgres enums. Stored codes are lower snake case. Adding a value later is a constraint change, which keeps "add before remove" simple (11 Operations).
7. **Timestamps:** every table gets `created_at timestamptz not null default now()`. The four tables that are edited also get `updated_at timestamptz not null default now()`, kept current by a shared trigger function `public.set_updated_at()` (`security invoker`, `set search_path = ''`). `membership_project` rows are only inserted and deleted, so it has no `updated_at`.
8. **RLS is enabled on all five tables with no policy.**
   - With no policy, the publishable (anon) key and signed-in users read and write nothing. The secret (service-role) key, used here only by the seed and tests (EZD-000 service-key rule), bypasses RLS.

## Risks
- **EZD-006 must know the shape.** `tenant` (key `id`) and `app_user` (global) carry no `tenant_id`. EZD-006's "every table has a policy and tenant index" test needs an explicit tenant-less list, and its `app_user` policy must find visible users through `membership` with the tenant taken from the claim (11 rule 10: claim read once per query, not a membership join to find the tenant). Its token hook maps `auth.uid()` → `app_user.auth_user_id` → `membership`. If the security-reviewer rejects Step 1.3 at plan review, `app_user` gains a `tenant_id` and T2's app\_user column list and T7 change.
- **Table name `app_user`.** Later plans and the EZD-006 harness must use `app_user`, not `user`. Recorded in docs (Step 6). The code-reviewer may prefer quoting `"user"`; changing it after merge is a rename that EZD-023a's add-before-remove check would refuse, so decide at plan review.
- **Who fills `auth_user_id`.** EZD-007 (first sign-in) and EZD-105 (invite accept) must link only a verified email to its `app_user`. A wrong link would give one person another person's memberships. Security-reviewer item for those plans.
- **`last_active_at` writes.** If a later ticket updates it on every request, that is one write per request. Its planner should throttle it (for example once per few minutes).
- **`phase_default` has no defined meaning.** 03 lists it on `project` with no values, and no ticket row reads it. It is created as nullable `text` with no check, so nothing is decided; the first ticket that uses it must define it (likely candidates: the status bar's Existing / Proposed default, 04 Status bar, or a field phase, 10 Field; this is not decided here).
- **No `customer_id` on `project`.** 03 has `client_name`. EZD-113 (customer table) and EZD-118 ("client from customer list") will need a customer link; their planners add it.
- **Missing foreign keys.** `property_record_id` and `submittal_profile_id` have no FK until EZD-711 / EZD-712 create those tables. Those planners must add them.
- **Check constraints and later values.** A new project type or status means dropping and re-adding a check constraint. EZD-023a's destructive-migration check should treat a widened check constraint as non-destructive.
- **Seed overlap with EZD-016a.** EZD-016a's "seed script (tenant 1 with Josh as owner, …)" must reuse these rows and `app/test-utils/seed-ids.ts`, not create a second tenant 1.
- **Cloud tenant 1.** `seed.sql` runs only on the local stack. The dev database stays empty until Josh runs Step 7's file there (Q-0033 (a)), so until then he cannot sign in on previews. Prod gets tenant 1 from the first real release before launch (Q-0106; Q-0113; EZD-023b Step 9), which refuses to start (`owner_email_missing`, nothing changed) if `TENANT1_OWNER_EMAIL` is not set while tenant 1 is missing. After that release Josh deletes the secret; the release reminds him with `owner_email_secret_unused` until he does (Q-0112 finding 16).
- **The file is now also a contract with EZD-023b.** EZD-023b's release replaces `PASTE-YOUR-EMAIL-HERE` (exactly once) and reads `ezd_bootstrap_done` / `ezd_bootstrap_already_done`. Changing the placeholder, the codes or the all-or-nothing block breaks the release; T17 and T18 here and EZD-023b T7, T9 catch it.
- **Seed and bootstrap drift.** The two files hold the same rows by hand. A later ticket that changes tenant 1's or Josh's seeded values must change both; T18 checks the ids and names only.
- **`scripts/db/sql.mjs` needs `docker` on PATH.** On the build machine it is at `/usr/local/bin/docker` (vault/plans/EZD-004.md finding F1); on CI (`ubuntu-latest`) it is on PATH. The builder may write `scripts/db/` (`.claude/hooks/guard-paths.mjs` lines 81–82; Q-0148).
- **One active company per person (Q-0043 (a))** is not a constraint here: `unique (tenant_id, user_id)` still allows memberships in two tenants (T7 (d)), because invited and deactivated rows elsewhere are allowed. EZD-105 refuses a second active membership and EZD-006's hook sets no tenant claim if two exist (vault/plans/EZD-006.md Step 2).
- **No reply address until S15a is filled.** `contact` is `{}` in the seed and the bootstrap, so company emails carry no Reply-To until Josh enters the company email in S15a (EZD-112; vault/plans/EZD-008.md Risks).
- **Docker** must be running for every test here (docs/architecture.md `### Local database`; EZD-004a T12 message).
- **Performance:** no effect on the budgets. The indexes follow 11 rule 10, and `open_items_count` is the stored counter rule 9 asks for.
