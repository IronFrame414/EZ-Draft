## What already exists (checked in the repo, Oct 11)
- **The workflow already runs the gate.** `.github/workflows/ci.yml` on `develop` is workflow `CI` with job `gate` on `ubuntu-latest`, timeout 30 minutes. Its steps are:
  - checkout with `actions/checkout@v4`;
  - Node 22 with `actions/setup-node@v4`;
  - `npm install -g pnpm`;
  - a Playwright browser install, only when `playwright.config.*` exists;
  - `node vault/tools/next_ticket.mjs --check`;
  - `node scripts/gate.mjs .`.
- **Triggers:** `pull_request` to `main`, and `workflow_dispatch`. There is **no `push` trigger**. Josh removed `push: develop` and `pull_request: develop` in aad5540 "to save Actions minutes and Vercel builds" (the ci.yml header comment; PROCESS.md: "GitHub Actions runs the gate and ledger check once per phase, on the phase PR (`develop` → `main`), plus by hand from the Actions tab… Per-ticket checks are local").
- **What the gate runs:** `scripts/gate.mjs` runs `typecheck`, `lint`, `test` and `build` (required), plus `test:e2e` and `perf` once they exist. It exits 1 if any of them fails or is missing. That covers "lint, type check and tests". EZD-000 and EZD-001 supply those scripts.
- **`main` is behind `develop`.** `main` still holds the kit-commit ci.yml (aee21dc: `push` to `develop`, `pull_request` to `main` and `develop`, no `workflow_dispatch`). A pull request runs the workflow file from the PR's own merge commit, so the phase PR uses `develop`'s file. The manual "Run workflow" button needs the workflow on the default branch, so it may not work until the Phase 0 PR merges. The orchestrator checks this with `gh workflow view CI` before relying on it.
- **Line endings are already settled.** `.gitattributes` already sets `* text=auto eol=lf`, so a checkout on Windows and one on the Linux CI machine hold the same file contents. No change is needed.

So the CI pipeline itself is already in place and Josh owns it. The ticket's remaining work is:
1. Prove, with tests, that a failing test, lint error or type error makes the gate fail, and therefore CI.
2. Prove that CI runs the same tool versions as the local gate.
3. Document CI in the conventions file so later tickets add their CI checks the same way.

## Risks
- **CI drift from the local gate.** CI runs the gate only at the phase PR, so a difference between this Windows PC and the Linux runner shows up once per phase, late. Examples: file-name case (Windows ignores case, Linux does not), Node 22 vs 24, or the latest pnpm vs the pin. T5 covers pnpm. Node and file-name case are not covered (EZD-000 risk; TypeScript's default `forceConsistentCasingInFileNames` covers TS imports only).
- **The manual run may not exist until Phase 0 merges.** `main`'s ci.yml has no `workflow_dispatch`, so the Actions-tab run may be unavailable before the Phase 0 PR merges. The phase-gate skill relies only on the PR run, so nothing breaks.
- **Later tickets that need services in CI.** EZD-004 ("migrations run in CI" against a local Supabase), EZD-016a/b and EZD-025 need Docker services that ci.yml does not start. Each needs a new workflow file or a Josh edit to ci.yml. EZD-004 also does not list EZD-002 in its Depends on (tickets.json), although its Done when says "in CI". The orchestrator may want to add that dependency.
- **Fork PRs on a public repo.** The repo is public, so fork PRs to `main` can trigger the workflow. `pull_request` runs without secrets, and GitHub asks for approval on first-time contributors. ci.yml sets no `permissions:` block (Josh's file). T2 bans `pull_request_target` and `workflow_run` in every workflow, the two triggers that would run fork code with secrets.
- **Push-triggered deploys (Q-0106, Q-0107).** A push to `main` (Josh's merge) releases production and a push to `develop` that changes migrations migrates the cloud dev database. T2 pins both to their one branch, so a later ticket cannot quietly widen them.
- **Pinning Josh's file.** T1 and T2 pin the content of Josh's ci.yml. If Josh edits it, these tests may need the test-author to update them. That is intended: a CI change is then visible in a failing test.
