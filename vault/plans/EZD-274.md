# EZD-274 · Fix: a passing API rate-limit error is an ordinary failed unit, not a usage-limit hold

- **ACs:** AC-EZD-274-1, AC-EZD-274-2

- **Areas:** tooling, scripts, testing
- **User-visible result:** a short API "rate limit" or "too many requests" error no longer stops the launcher with a hold and a notice; the unit is retried on the next model, and a real usage limit is still handled as before.

## 10. Open questions
- Q-0444 (was QP-1): Q-0438 (b) says "rate limit" or "too many requests" without "usage limit" is an ordinary failure, but Q-0437 (a) says a message naming "5-hour", "five-hour", "session limit" or "week" is a limit, and the two disagree on a text that has both (EZD-193 T3, T6 and T9 already feed `5-hour limit reached` plus a `rate limit` line); options: (a) Q-0438 as written, so such a text is retried on the ladder (U3 and U4 then expect `null`, and T3, T6, T9 need new stderr fixtures as earlier-test edits); (b, recommended, planned) the rate-limit words count only when the text also names no five-hour or weekly form, so a real limit message is never retried as a failure.
- Q-0445 (was QP-2): a transient rate-limit error goes straight to the next rung with no pause, so a burst that lasts longer than three tries tables the ticket or leaves the launcher waiting for a change; options: (a) no pause, as Q-0438 (b) says (planned); (b) wait a fixed time before the next rung after a rate-limit failure (Josh gives the minutes), which adds a wait to EZD-268's ladder and one more test.
