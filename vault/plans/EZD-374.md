# EZD-374 · Fix: the pan and load perf checks fail on CI (plan_not_ready, EZD-207c P2 pan counts)

- **ACs:** AC-EZD-374-1
- **Complexity:** medium (section 8)
- **Areas:** ci, testing, scripts, tooling, docs
- **User-visible result:** the CI check on develop measures the plan's pan and load speed again instead of reporting "plan not ready", and the perf tool's own pan test stops failing on the CI machine.
- Phase: 4 · Planned by: planner · Date: 2026-11-10 · Status: planned

## 1. What to build

**Cause (found at plan time; sources in section 2).**
1. *plan_not_ready is the EZD-373 cause.* `runPan` waits up to 30 s (`PLAN_READY_MS`) for `[data-testid="plan-canvas"][data-plan-state="ready"]` and `window.__ezdraftPlan.stats().glyphs > 0`, else returns `plan_not_ready` (`scripts/perf/pan-script.mjs:19-21, 125-139`; EZD-207c D-Wait). The pan page `/dev/benchmark-plan` takes that branch (`page.tsx:18` `data-perf-wait-plan`) and builds its text with the same `createGlyphAtlas` (`BenchmarkPlan.tsx:17`). On CI that call rejects and glyphs stay 0 (P373 Cause 2), so every pan and load row is `plan_not_ready` (A1-tickets.md phase 4 row 1). EZD-373's fix makes glyphs > 0 on any machine. No perf-tool code changes for this; B1 (section 4) proves it on the Mac.
2. *The P2 count depends on the machine's CPU load.* The iPad long-task rows use `ipad-1x` at rate 4 (`registry.mjs:26-33`, `perf.config.mjs:25-32`). A task counts when `cpu × 4 − ms × 3 > 50` (`trace-tasks.mjs:93-100`; Q-0623 (a)). The throttle's spin counts as CPU, so a 200 ms busy wheel task (`pan.test.mjs:15-18`) scores `200 − 4p`, where p is the time the OS takes the thread off the CPU. It turns into a "wait" at p ≥ 38 ms: Q-0623's own cost line, "P2 goes red when one iPad task is preempted >= 38 ms". The root `test` script runs 4 files at once (`package.json` `--test-concurrency=4`; Q-0114) on CI's 4-vCPU public-repo runner (`ci.yml:20` `ubuntu-latest`; ARCH line 1430 "public repo"). Several perf test files beside it launch Chromium. CI counts 4 or 5 on the iPad row while desktop holds 8 (A1 row 2), and that fits preemption: the desktop row needs p > 150 ms. This is inferred, not measured. The CI logs show only `4 !== 8`, and P2 prints no task detail, so P2 gains diagnostics (step 2).
3. *Why the fix is isolation.* With a share f of off-CPU time, the iPad score of any busy task is about `W(1 − 4f)`. No fixture length keeps it over 50 once f nears 25%. The rule (Q-0623) and the budgets are fixed by the ticket row. So the only robust fix is that nothing else runs beside the pan fixture test. It runs alone after the other repo tests (CLAUDE.md rule 18: close the class).
