### Causes (planner, from the code; AC-EZD-251-2)
Paths below are under `app/`. RTR = `src/app/api/health/route-timeout-report.test.ts`.
- **C1, a second row from another file.** `src/server/auth/password-sign-in.test.ts` "EZD-033 T18" makes Auth answer 503, so `signInWithPassword` calls `reportSignIn('auth_password_unavailable')` (`src/server/auth/actions.ts` lines 66-68, 141) with the real store, which commits an `error_alert` row (fingerprint for location `auth.sign_in`). That file does not hold `holdErrorAlertLock` and never deletes the row, against the rule in `test-harness/errors/alert-lock.ts` lines 1-6 (EZD-024 V7). Vitest runs 4 files at once (Q-0114), so when T18 overlaps RTR T3, T3's whole-table count (RTR lines 210-217) sees 2 rows. This is the failure Q-0356 records (`error_alert` held 2 rows instead of 1). RTR T1 (`expectOneAlertRow`) and T2 (line 195) count the whole table too, so they have the same exposure.
- **C2, a stray report from T2 that lands in T3.** T2 starts the report unawaited (RTR line 190). The report reaches `fetch` only after `await errorFingerprint` (`crypto.subtle.digest`, `src/server/errors/fingerprint.ts` line 50, which runs on the libuv thread pool) and supabase-js `await getAccessToken()`. supabase-js looks up the global `fetch` when each request is made, not when the client is created (`node_modules/@supabase/supabase-js/dist/index.mjs` lines 260-263, v2.118.0). T2 calls `vi.unstubAllGlobals()` (line 194) only `await Sentry.flush(2000)` later. When load delays the digest past that point, T2's store call goes to the real `fetch` and commits a row with the same fingerprint as T3's. If that row commits after T3's `beforeEach` delete, T3's report updates it instead of inserting (`on conflict (fingerprint)`, `supabase/migrations/20261027001745_guard_gated_rpcs.sql` line 209). Then `occurrences` is 2 and `ref` holds T2's event id, and `expectOneAlertRow` fails.
- **C3, a fixed polling window.** T3 polls for the row for at most 5000 ms (RTR line 216). No source sets that limit: EZD-181 section 3 says only that the answer never waits for the report. Under load, the report chain can take longer than the window.
- Excluded: the two gates do not share a database, because each lane has its own stack (EZD-172 section 3, `values` row). No other Vitest file writes `error_alert` without the lock. The planner checked every caller of `reportError`, `noteBrowserEvent`, `reportJobFailure` and `reportWebhookFailure` in `src/`, and every test that reaches one: each holds the lock or mocks the report. Two other routes also report: `api/permissions` has no unit test, and `jobs/sweep` has no test. The Playwright step runs after `test`, in the same `spawnSync` sequence (`scripts/gate.mjs` line 90).
