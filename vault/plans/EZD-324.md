# EZD-324 · Fix: the device layout test B5 does not fail at random in CI

- **ACs:** AC-EZD-324-1, AC-EZD-324-2 (`vault/spec/acceptance-criteria.md` lines 615–616)
- **Complexity:** low
- **Areas:** testing, ui, ci
- **User-visible result:** none in the app; the iPad layout-switch browser test stops failing at random in CI, so merges are not held up by it.
- Phase: 2 · Planned by: planner · Date: 2026-11-04 · Status: planned

## 1. What to build
Cause, found and measured in this planning session (section 2, E1–E6): **a wrong wait in the test, not a late switch in the app.** WebKit reports a media-query change only in its next rendering update (the HTML "update the rendering" steps: media-query changes are reported before animation-frame callbacks run). On a CPU-starved headless Linux WebKit, that update came 4 to 23 s after `setViewportSize` returned. B5 starts its 5 s expect window at `setViewportSize`, so it timed out before the browser had told the app anything. Once the change event fires, the app switches within 1.3 s (E5). The ticket row's rule therefore applies: the fix goes in the test. No assertion is removed or weakened. The fix adds a wait for the browser's next animation frame after each resize.

No data, no migration, no app code.
