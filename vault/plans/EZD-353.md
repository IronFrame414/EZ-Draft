# EZD-353 · Fix: captureTraffic does not block the page's loopback Realtime websocket

- **ACs:** AC-EZD-353-1, AC-EZD-353-2
- **Complexity:** low (section 8)
- **Areas:** testing, realtime
- **User-visible result:** none in the app; the browser tests that record a page's traffic now see the Realtime connection and the bell's requests exactly as a normal page makes them, so debt D-085 closes.
- Phase: 4 · Planned by: planner · Date: 2026-11-06 · Status: planned

## 1. What to build

Cause (probe P1, section 2): `captureTraffic` fulfills every loopback request from Node (`route.fulfill`), the page's document included. A fulfilled document has no IP address, so Chromium 156 puts it in the public address space, and its Local Network Access check refuses the page's websocket to `127.0.0.1` (`net::ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS`). Websockets are not routed by `context.route`, so the check runs. hub.ts then reconnects and fetches `/api/realtime/token` again (D-085). An unrouted `127.0.0.1` page is in the loopback space and is not checked. Fix: on Chromium, `captureTraffic` grants `local-network-access` to the context before it routes; P1 shows the socket then opens, both for a new page and for a page that existed before the grant.
