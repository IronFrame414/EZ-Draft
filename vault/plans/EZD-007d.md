### Findings against the parent text (planner, 2026-10-20)
- **D1 Local Auth rate limits (EZD-007a Risk 3: "a later part may hit them (that part's plan decides)").** The merged `supabase/config.toml` lines 208–210 allow `sign_in_sign_ups = 30` and `token_verifications = 30` per 5 minutes per IP. Every Vitest file calls Auth from 127.0.0.1: EZD-006's tests already call `signIn` (one `verifyOtp` each) 19 times (`grep -rn "signIn(" app/src --include='*.test.ts'`), EZD-007a–c add about 17 more Auth calls, and this part adds about 20 code requests and 12 verifications (T4–T8, T13, T19, T26 part d). One phase gate would pass 30 and fail for the wrong reason. So this part raises both keys to `1000` for the local stack only, the same *planner's choice* the parent made for `email_sent` (P-Step 1: "raised for the local stack only, so tests can send many emails"; EZD-007a Step 1). `config.toml` reaches no cloud project (parent V7); cloud limits stay Supabase's (EZD-007a runbook). Auth reads `config.toml` only at `supabase start`, so the orchestrator runs `pnpm db:stop` once before this ticket's first gate (parent V3 (3)).
- **D2 Per-email resend interval.** `[auth.email] max_frequency = "1s"` (`config.toml` line 231) refuses a second email to the same address within 1 second (HTTP 429). Tests that request twice for one address (T5, T8 (c), (g), (h), T26 part d, whose sign-up already sent one) wait at least 1,100 ms between the two sends and read the second email with `after`.
- **D3 Contract details the parent left open, decided here** (*planner's choice*, CLAUDE.md rule 3; the security-reviewer confirms):
  - `actions.ts` carries `'use server'`, so it exports only the five async functions (Next.js refuses other exports in a Server Actions file). Cookie names are string literals in the contract, not exported constants.
  - The actions take `(formData: FormData)` as P-Step 3 says. EZD-007f's form may wrap one in a client closure for `useActionState`; the signature does not change.
  - `ezd_sign_in_email` gets the same flags as the session cookies (`httpOnly`, `sameSite: 'lax'`, `path: '/'`, `secure` on https) with `maxAge` `900` (P-Step 3, Q-0049). "https" is read the way EZD-007c's default jar reads it: the first comma-separated value of the `x-forwarded-proto` request header equals `https` (EZD-007c finding C2).
  - The same answer for every address (AC-1): `requestSignIn` returns `{ step: 'code' }` and sets `ezd_sign_in_email` whether Auth accepted the address or refused it (the hook's 403 `sign_in_not_allowed`, EZD-007a section 3). Only a malformed email (`invalid_email`, no Auth call, no cookie) and an Auth rate-limit answer (HTTP status 429 → `too_many_requests`, no cookie) differ (P-Step 3). `createSessionClient()` throwing (missing env or secret) is not hidden: the action rejects (docs/architecture.md Errors and logging, 500 unexpected); it does not depend on the address, so it reveals nothing about accounts.
  - `verifySignInCode` takes the email from the form field `email` when it is non-empty, otherwise from the `ezd_sign_in_email` cookie (P-Step 3 "from the cookie or the form"). No valid email, or a code not matching `^\d{6}$` after trimming → `{ error: 'code_invalid' }` with no Auth call. A Supabase rate-limit answer from `verifyOtp` (HTTP status 429) → `{ error: 'too_many_requests' }`, and the cookie stays (Q-0169 (a)); every other `verifyOtp` error → `code_invalid` (P-Step 3). Only `'ok'` clears `ezd_sign_in_email`.
  - `confirmSignInLink` returns `link_invalid` with no Auth call when `token_hash` is empty or `type` is not `email`; a `verifyOtp` error → `link_invalid`, except HTTP status 429 → `too_many_requests` (Q-0169 (a)); `'ok'` clears `ezd_sign_in_email` too and redirects to `/`.
  - `completeSignIn` fails closed on errors: an `rpc('link_app_user')` error → `auth.signOut({ scope: 'local' })`, then throws `Error('link_app_user_failed')`; a `refreshSession()` error → `auth.signOut({ scope: 'local' })`, then throws `Error('session_refresh_failed')` (a session without the tenant claim would show an empty company for up to `jwt_expiry` = 3600 s, Q-0052 (c)). Both are unexpected errors (docs/architecture.md Errors and logging: 500); no user wording is added. An `emit` error is caught and does not fail the sign-in (P-Step 3: "the acceptance is already committed").
  - The request gate copies every cookie the session client wrote onto the redirect response, so a refresh that cleared the cookies reaches the browser even when the answer is `307`.
- **D4 Done-when cases the parent left ambiguous.** P-T8 (b) reads "no email … or, if an auth user already existed, `no_access`". The fresh-member case has no auth user, so the `no_access` path of `verifySignInCode` was untested. T8 (h) adds it: a member who signed in once and was then deactivated gets the email (the hook runs only when an auth user is created) and `{ error: 'no_access' }` with no session left. P-T8 (a)–(g) values are unchanged.
- **D5 `completeSignIn` refuse rules (L-012).** The parent's emit-error rule and D3's error rules have no failing input in a database test. T36 tests `completeSignIn` alone with a stub client: no row, no access, RPC error, refresh error, emit error, plain active member.
- **D6 Not in this part.** `createTestMember` and `cleanupTestMembers` already exist in `app/test-harness/auth-users.ts` (EZD-007a section 3; finding A2); this part adds only `addMembership`. The sign-in pages, `signInWithCode` and Playwright are EZD-007f; message keys are EZD-007e (actions return codes, not text; parent Split Part 007d "Proposed wording: None").
