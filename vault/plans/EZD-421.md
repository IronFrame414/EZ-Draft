# EZD-421 · Fix: route bodies that call an RPC after the session read can answer 500 and alert for an ended session (split proposal)

- **ACs:** AC-EZD-421-1, AC-EZD-421-2 (`vault/spec/acceptance-criteria.md:1056-1057`, generated from Done-when). Each part below carries both, for its own routes; the orchestrator generates each part's ACs from its Done-when with `node vault/tools/gen_acs.mjs`.
- **Areas:** auth, security, api
- **User-visible result:** When a signed-in person's session has ended (signed out elsewhere, deactivated, or a token refresh that failed) and a request is already past the sign-in check, the app answers "not signed in" and sends them to sign-in, instead of a "something went wrong" error, and Josh gets no false error alert email for it.

## Split proposal

**Why.** Planned whole, the ticket touches about 51 files (37 route files, 4 server modules that report on their own, the shared rule, the route-failure walker test, 3 new route test files, docs) and needs about 55 tests (one ended-session case per route, live-session controls, the shared rule's unit tests, the walker). That is over the size rule (PROCESS.md section 6 "Ticket size": over 20 files or over 25 tests; Josh 2026-10-22). Counted on develop 2026-11-12:
- `reportRouteFailure` (`app/src/server/errors/route-failure.ts:7`) is called by 35 route files and by `app/src/server/profile/password.ts:138,152,214,227`; `GET /api/permissions` (`app/src/app/api/permissions/route.ts:27`) and `app/src/app/api/dev/permissions/projects/[id]/route.ts:62` call `reportError` directly (architecture "Error reporting (EZD-024)", Route 500s bullet). `/api/health` reports without a session and is out of the class.
- Every one of those routes reaches the database after `getSession()` succeeded: through `requireApiPermission` (`app/src/server/permissions/can.ts:56-57`, the `current_permissions` read) and through the route's own reads and writes on `createSessionClient()`. In the window EZD-395 confirms (supabase-js 2.118.0 falls back to the publishable key when the refresh fails; plan EZD-395 section 3 Data flow hop 4), each such call goes out as anon, fails `42501`, lands in the route's catch and answers 500 with `reportRouteFailure` (the example in Q-0753 and the ticket row, `vault/tickets/phases/phase-02.md:81`).
- An "ended session" here is both cases Q-0052 (c) names: the token's own expiry with a failed refresh, and a session ended in the database while the token is still valid (deactivation or a scope change ends sessions, 11 Operations; `current_app_user_id()` returns null for it, architecture "Auth and session (EZD-007)" Current user). Q-0052 (c) makes both "fail closed at 401", so both get the shared rule.

**Why cut here.**
- **Part a** builds the shared rule once and proves it on the projects routes, the largest group and the one Josh's editor uses most. Parts b and c reuse it unchanged.
- **Part b** is the settings and profile routes and the server modules that report failures themselves (`server/profile/password.ts`, `server/profile/profile.ts:93`, `server/users/users.ts:94`, `server/assistant/user-key.ts:70,254`), so each self-reporting module is audited with the route that calls it.
- **Part c** is the remaining routes and then closes the class so it cannot drift (CLAUDE.md rule 18; D3 (a)): the existing walker `app/src/app/api/route-failure.test.ts` (T7) is extended to fail any session route file whose 500 path does not go through the shared rule. It runs last because it can pass only when a and b are merged.

Built a → b → c. Each part is planned as its own unit on template v2 from its section here. Each part plan applies the planner lessons for auth, security and api, notably:
- every failing call has a stated outcome on a throw, and the shared rule fails closed toward the existing 500 and alert, never toward a silent 401 (L-059): a check of "has the session ended" that itself errors keeps the 500 and the alert;
- the shared rule names the class, not the 42501 example (L-029, L-047): which error forms it treats as "the session may have ended", how it then confirms the session ended, and that a live session with the same error keeps its 500 (AC-EZD-421-2);
- every helper a step uses is named by its exporting file, found by grep at plan time (L-065 notes): `accessTokenEnded` and `getSession` from `app/src/server/auth/session.ts` as merged by EZD-395, never from its plan;
- the routes' existing EZD-169 and route tests keep their expected values; any `toEqual` on a changed result is listed as a test-author edit (L-067 note);
- write-route tests send `appOriginHeaders()` (`app/test-harness/e2e/same-origin.ts`) if a part writes a Playwright spec (L-067).

### Part EZD-421a · The shared ended-session rule, on the projects routes
- **Scope:**
  - One shared rule, exported from one server module (part a decides the file and name), that a route catch calls in place of `await reportRouteFailure(e, ROUTE); return fail(500, 'db_unavailable')`: when the session has ended it answers 401 `{ "error": { "code": "not_signed_in", "message_key": "error.not_signed_in" } }` with `Cache-Control: no-store` (the `requireApiSession` body, `app/src/server/auth/session.ts:36-48`; EZD-349) and reports nothing; otherwise it calls `reportRouteFailure` and answers the route's existing 500 body (architecture "Errors and logging"; EZD-169).
  - How it confirms the session ended, decided at part a's design step from the merged EZD-395 code: a fresh read that does not use `getSession()`'s per-request `cache()` (`session.ts:12`), with EZD-395's `accessTokenEnded(exp, nowMs)` for the token case and a null `current_app_user_id()` for the database-ended case (Q-0052 (c)). It sends no new anon read and widens no grant (ticket row: "Do not widen what an anon call may read").
  - The 11 projects route files: `app/src/app/api/projects/route.ts`, `projects/counts/route.ts`, `projects/[id]/assistant/route.ts`, `[id]/checkpoints/route.ts`, `[id]/model/route.ts`, `[id]/objects/route.ts`, `[id]/plan-scale/route.ts`, `[id]/sync-conflicts/route.ts`, `[id]/thumbnail/route.ts`, `[id]/versions/[versionId]/thumbnail/route.ts`, `[id]/versions/[versionId]/thumbnail/complete/route.ts`; plus `app/src/server/assistant/assistant.ts:224` (its own `reportError`, reached from the assistant route) audited and routed through the rule where it is on the ended-session path.
  - `docs/architecture.md` "Errors and logging" (Route 500s bullet) and "Auth and session (EZD-007)" (Session helpers bullet): one sentence each naming the shared rule.
- **Done when:** Every listed projects route call answers 401 with Cache-Control: no-store and writes no error alert for an ended session; a live session's 500 and alert are unchanged.
- **Depends on:** EZD-395 (ticket row; `accessTokenEnded` and the `getSession` 42501 branch). EZD-169 (`reportRouteFailure`, done) and EZD-349 (the 401 body with no-store, done) are used directly and are missing from the row.
- **Files (about 17):** the shared-rule module (new or `route-failure.ts`), `session.ts` only if the rule needs a new export, the 11 route files, `server/assistant/assistant.ts`, `docs/architecture.md`; test-author: the shared rule's unit test file and one projects ended-session route test file.
- **Tests (about 20):** the shared rule: ended token case → 401, no-store, zero reports; database-ended case → 401, zero reports; live session with a 42501 → 500 and one report; a non-42501 failure → 500 and one report; the ended-session check itself throwing → 500 and one report (fails closed toward the alert, L-059); plus one ended-session case per projects route (11) and live-session 500 controls for three of them. Expected bodies, header and the count of zero or one report come from the `requireApiSession` body (`session.ts:39-48`), EZD-169's report shape (`route-failure.ts:7-16`) and AC-EZD-421-1/-2.
- **Part complexity:** high: auth behaviour on every projects write and read path, a security property (no widening, fail closed), and a shared rule two later parts build on. test-author and builder Fable 5.1.
- **security-review: yes** (auth, API; gate SECURITY_PATHS `api/`).
- **Proposed wording:** none: the 401 reuses `error.not_signed_in`, already in the catalogs (EZD-349).
