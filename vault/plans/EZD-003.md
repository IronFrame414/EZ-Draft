## Approach

Two kinds of steps:
- **Repo steps.** The test-author and builder do these in the worktree, and the gate checks them offline.
- **Account steps.** Only Josh does these: Vercel and the DNS host. No agent logs in to Vercel or Spaceship, installs or runs the `vercel` CLI, or changes a DNS record (CLAUDE.md rule 4; `.claude/settings.json` deny rules; guard-bash.mjs).

Agents check the result only with read-only requests: a public HTTPS fetch, a public DNS answer, and `gh api` GETs.

Technical choices no source makes are marked *planner's choice (CLAUDE.md rule 4)*; the code-reviewer confirms them at plan review.

### Step 1: Vercel config in the repo (builder)
- **Root Directory is `app`** (*planner's choice*). Vercel builds the Next.js app from `app/`, the package EZD-001 creates, and installs the pnpm workspace from the repo root. This is Vercel's monorepo setup. The setting itself lives in the Vercel project (Josh, Step 5). The repo holds only what Vercel reads from that folder.
- **`app/vercel.json` (new):**
  ```json
  {
    "$schema": "https://openapi.vercel.sh/vercel.json",
    "framework": "nextjs",
    "regions": ["iad1"]
  }
  ```
  - `regions: ["iad1"]` (Washington, D.C., US East). ### Step 2: Live check script (builder)
`scripts/hosting/check-live.mjs` uses Node 22 built-ins only (global `fetch`). It is **never run by the gate**, because the gate runs offline (EZD-002 plan Step 5). The orchestrator runs it by hand (T8).

- **Exports:**
  - `HOST` = `'ezdraft.ezcontractorbinder.com'`.
  - `evaluate(obs)`: a pure function. It takes the observations below and returns `{ ok: boolean, results: [{ id, pass, detail }] }`, one entry per check id in the fixed order `dns, tls, status, host, vercel, title, hsts, redirect`. When `dns` or `tls` fails, the later checks are reported as failed with detail `skipped`.
  - `observe(host)`: does the network requests and builds `obs`.
- **Observations (`obs`):**
  - `https`: either `{ error: { code } }` or `{ status, finalUrl, headers, body }`. It comes from `fetch('https://' + host + '/', { redirect: 'follow' })`. Same-host redirects, for example to a sign-in page from EZD-007, are followed. `code` is the `cause.code` that Node's fetch reports on failure.
  - `http`: `{ status, location }`, from `fetch('http://' + host + '/', { redirect: 'manual' })`.
- **Checks, all required:**

  | id | Pass when | Source |
  | --- | --- | --- |
  | `dns` | `https.error.code` is not `ENOTFOUND` / `EAI_AGAIN`. The fail detail names the needs-from-josh DNS item | R24 #1 ("a subdomain added in DNS") |
  | `tls` | No TLS error. Any `https.error.code` other than the DNS codes counts as a TLS or connection failure, for example `CERT_HAS_EXPIRED`, `ERR_TLS_CERT_ALTNAME_INVALID`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE` | Done when "over HTTPS" |
  | `status` | `https.status === 200` | Done when "loads" |
  | `host` | `new URL(finalUrl).protocol === 'https:'` and its `hostname === HOST` | R24 #1 address |
  | `vercel` | `headers['server']`, compared case-insensitively, equals `vercel` | Ticket Scope "pointing to Vercel" |
  | `title` | `body` has a `<title>` element whose text contains `EZ Draft` | EZD-001 Step 2 (`metadata.title` = `EZ Draft`); 02 product name |
  | `hsts` | A `strict-transport-security` header with `max-age=N` where N > 0 | Done when "over HTTPS" (browsers stay on HTTPS). Vercel sends it by default: the apex shows `max-age=63072000`, Oct 11 |
  | `redirect` | `http.status === 308` and `http.location` starts with `https://ezdraft.ezcontractorbinder.com` | Done when "over HTTPS" (plain HTTP must not serve the app). 308 is what Vercel returns on the same account (apex, Oct 11) |
- **CLI:** `node scripts/hosting/check-live.mjs` runs `observe(HOST)`, then `evaluate`. It prints one line per check as `<id> PASS|FAIL <detail>` and exits 0 if all pass, otherwise 1. It reads no env values and sends no credentials.

### Step 3: Preview deploy check (orchestrator, read-only; EZD-002 hand-over)
Previews come from Vercel's Git integration whenever `develop` is pushed. The phase PR (develop → main) shows the preview of the `develop` head (Q-0007; SETUP.md Notes; phase-gate skill step 4). There is no workflow and no `vercel` CLI.

After the next `git push origin develop` (build-phase skill step 10, or phase-gate step 4), the orchestrator runs read-only checks. For the `develop` head SHA, `gh api repos/IronFrame414/EZ-Draft/commits/<sha>/statuses` or `gh api "repos/IronFrame414/EZ-Draft/deployments?sha=<sha>"` (and that deployment's `statuses`) must show a Vercel entry with state `success` and a non-empty target URL (T7).

The preview URL itself is not fetched: Vercel's default Deployment Protection asks for a Vercel login on previews (Step 5.4), so a script would get 401. Josh, who is logged in, clicks it at the phase gate (PROCESS.md Phase gate step 5).

**Do not set SETUP.md's optional Ignored Build Step.** That command builds only `main` and pull requests, which turns off `develop` previews, and Q-0007 keeps them. It would also leave the phase PR with no preview, for this reason:
- The phase-gate skill pushes `develop` **before** it opens the PR (step 4).
- So that build has no pull-request id. Vercel's `VERCEL_GIT_PULL_REQUEST_ID` is empty when the push comes before the PR exists.
- The command would therefore skip the one build the PR shows.

Level 1 answer (Q-0007; phase-00 Build gate "the app deploys to a preview URL"). For the orchestrator: SETUP.md is Josh's file, so it tells Josh rather than editing it.
