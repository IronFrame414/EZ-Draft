# EZD-034 · Captcha on sign-in

- **ACs:** AC-EZD-034-1, AC-EZD-034-2
- **Complexity:** high (per part below)
- **User-visible result:** the sign-in page shows a short security check before it sends the sign-in email, so a script cannot use the sign-in service to find out which emails have accounts.
- Phase: 0 · Planned by: planner · Date: 2026-10-20 · Status: questions

## Split proposal

The whole ticket would touch about 14 files (config, action, widget component, sign-in page and form, two catalogs, Playwright config, harness helper, `.env.example`, `docs/architecture.md`, `docs/runbook.md`, and the existing Auth tests of EZD-007a and EZD-007d) and need more than 10 tests, over the PROCESS.md section 6 split limit. Ordering matters: once Auth's captcha is on, every code request without a token is refused (R-013), so the page must send a token **before** the local stack turns captcha on, or every sign-in test in phase 0 goes red. Hence the order a → b.

### EZD-034a · Captcha widget on the sign-in page

- **Scope:** a widget component in `app/src/components/auth/` that loads the provider's script on the sign-in page only (explicit render; R-013 (6)), in the page's language (`getSignInLanguage()`, EZD-007d; Q-0047 (a)), with the site key read per request on the server and passed as a prop (docs/architecture.md Environment variables: values read per call, `next build` needs none). `SignInForm` step 1 (EZD-007f) renders it and posts its token as form field `captcha_token`; the send button stays disabled until a token exists; the widget is reset after every request, since tokens are single-use (R-013 (6)). `requestSignIn` (EZD-007d) passes the field as `options.captchaToken` to `signInWithOtp` (R-013 (4)) and maps Auth's captcha refusal (HTTP 400, captcha error code; R-013 (2), code string confirmed on the pinned CLI 2.121.0 by the test-author, lesson L-009) to `{ error: 'captcha_failed' }` with no cookie. New keys `error.captcha_failed`, `error.captcha_unavailable` in `en` and `es` (docs/architecture.md Messages: `sign_in` namespaces `common`, `error`; Spanish by the builder, Q-0030 (a)). Playwright web-server env gets the provider's published always-pass test site key (R-013 (5)); `signInWithCode` (EZD-007f helper) waits for the token before it submits. Auth's captcha stays **off** in this part, so Auth ignores the token (R-013 (1): the check returns early when captcha is disabled).
- **Files (8):** `app/src/components/auth/Captcha.tsx` (new), `app/src/app/sign-in/SignInForm.tsx`, `app/src/app/sign-in/page.tsx`, `app/src/server/auth/actions.ts`, `app/src/server/messages/catalogs/en.ts`, `.../es.ts`, `app/playwright.config.ts`, `app/test-harness/sign-in.ts`; tests in `app/e2e/sign-in.spec.ts` and `app/src/server/auth/sign-in.test.ts`.
- **Done when:** the sign-in page shows the security check in the page's language and sends its token with the code request; the send button stays off until the check gives a token; a refused check shows `error.captcha_failed` and a fresh check; a script that fails to load shows `error.captcha_unavailable`; the browser tests sign in with the provider's test site key.
- **ACs:** AC-EZD-034-2.
- **Depends on:** EZD-007d, EZD-007f; **EZD-016a** (missing from the ticket row: the part has a visual checklist, so the browser harness is a dependency, planner rule). Q-0241 (provider) must be answered first: script URL, render call, test keys and token lifetime all differ by provider (R-013 (5), (6)).
- **Visual checklist (desktop 1600 × 1000):** sign-in card, step 1: widget loading (send off) · widget ready (send on) · captcha refused (error + fresh widget) · script failed (unavailable message). No board exists for the sign-in page (vault/mockups/INDEX.md; ticket `mockups: []`), so the layout follows EZD-007f's card (vault/tickets/README.md rule 6).

### Risks

- With captcha on, every test that requests a code reaches the provider's verify server through local Auth, because Auth has no setting for another verify address (R-013 (3)); a provider outage or no internet turns the gate red (QP-2).
- hCaptcha refuses `localhost` and `127.0.0.1` (R-013 (5)) and the browser tests run on `http://127.0.0.1:3000` (EZD-007f F7); if Q-0241 is (b) hCaptcha, the harness needs a host name instead. This is an input to Q-0241.
- EZD-033 (ready, unbuilt) calls `signInWithPassword`, which Auth checks (R-013 (1)); its plan has no captcha token.
- Supabase's captcha also covers password recovery and `resend` (R-013 (1)); the app never calls recovery (EZD-033 section 3), so nothing else changes.

## Open questions

- Q-0242 (was QP-1): Auth checks the captcha only on the code request (and sign-up, password sign-in, recovery, resend), not on the code check or the emailed link (R-013 (1)), but the ticket row asks for it on "the code and link checks" too. Options: (a) captcha only where Auth checks it, nothing on the code step or `/auth/confirm` (recommended: Q-0175's leak is the code request, and a wrong code gives the same answer for every email); (b) also show the check on the code step and the link page and have the app server verify the token with the provider before checking the code (a second secret in Vercel and one more provider call per sign-in).
- Q-0243 (was QP-2): With captcha on in the local stack, every test code request makes local Auth call the provider's verify server with the published test secret (no other verify address can be set, R-013 (3)), and the browser tests load the widget script from the provider. Do tests count these as live-service calls under CLAUDE.md rule 6? Options: (a) allow both calls with the provider's test keys, so the gate and CI need internet (recommended: the ticket row asks for test keys, and rule 6's list names AI, email, render and EZ Binder, not captcha); (b) allow Auth's verify call but serve a stub widget script in browser tests through a Playwright route that returns the provider's dummy token (the real widget is never tested); (c) keep captcha off on the local stack and check AC-EZD-034-1 by hand on the dev project (no automated test of it).
