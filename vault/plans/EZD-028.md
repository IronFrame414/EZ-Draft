## Approach

The spike is one throwaway workspace package, `spikes/EZD-028-pdf/` (`@ezdraft/spike-ezd-028-pdf`), following EZD-000's folder layout. Nothing in `app/`, `packages/` or `worker/` imports it (C4). It is written in plain ESM JavaScript (`.mjs`) with JSDoc types (*planner's choice, CLAUDE.md rule 4*). The reason: Step 5 runs the writer in a separate Node process, and CI and Vercel use Node 22 (EZD-000 Runtime), which cannot run TypeScript without extra flags or a new dependency. The drawing-list shape here is provisional; EZD-238 defines the real one in TypeScript and may change it.

Values marked *spike input* are test data chosen for this spike. They are not product decisions, and the note says so (KNOWN-LIMITS item 5 applies in spirit).

### Step 1: The hard-coded room (spike input)
Model units are decimal inches, y up (03 rule 5 stores coordinates in decimal inches). The room is the 12' × 10' room that EZD-016b's synthetic fixtures use (phase-00 row EZD-016b), so later tickets can compare against it:
- Room interior: rectangle (0,0) to (144,120).
- Door: a 36" leaf hinged at (12,0), drawn open at 90°: leaf line (12,0)→(12,36); swing arc with centre (12,0), radius 36, from (48,0) to (12,36). The wall outline has a gap from x = 12 to x = 48 on y = 0.
- Floor hatch: lines at 45° (direction (1,1)), perpendicular spacing 6", anchored so that one line passes through (0,0), clipped to the room rectangle.
- Check dimension: dimension line (0,−24)→(144,−24); extension lines (0,−2)→(0,−26) and (144,−2)→(144,−26); a 45° tick at each end; label `12'-0"` centred above the dimension line.
- Room label `EZD-028 ROOM` at the room centre. Scale label `1/4" = 1'-0"` centred under the dimension.
- Placeholder stroke widths (not tested, not a decision; 09 gives only the order "cut heavy … dims and leaders thinnest"): walls 1.5 pt, door 0.5 pt, hatch 0.25 pt, dimension 0.25 pt. Colour black.

### Step 2: The drawing list (`src/drawing-list.mjs`)
`buildRoomList()` returns `{ view, items }` with no DOM and no PDFKit import (EZD-238 "no DOM"; 02 Geometry core):
- `view`: `{ scale: 1/48, paperSize: [2592, 1728], paperOrigin: [1188, 774] }`. The scale is 1/4" = 1'-0", the plan scale in 09 Sheet set rules. The page is 36 × 24 in at 72 pt per inch (Step 4). The origin centres the room on the page: the room is 216 × 180 pt on paper, and the page centre is (1296, 864).
- `items`: each has `kind` (`line` | `polyline` | `arc` | `hatch` | `text`), `role` (`wall`, `door`, `hatch`, `check-dimension`, `room-label`, `scale-label`), `layer` and `weight` (EZD-238 lists both). Geometry is in model inches.
- **Geometry fields per kind** (*planner's choice*, PLAN-GAP 2026-10-23). A point is a 2-element array `[x, y]` in model inches, y up. Angles are degrees, counter-clockwise from +x, y up.
  - `line`: `from`, `to` (points).
  - `polyline`: `points` (array of ≥ 2 points), `closed` (boolean).
  - `arc`: `center` (point), `radius` (inches), `startAngle`, `endAngle` (degrees; the arc runs counter-clockwise from `startAngle` to `endAngle`). Its end points are `center + radius·(cos θ, sin θ)` for θ = `startAngle` and `endAngle`.
  - `hatch`: `boundary` (array of points, closed implicitly), `segments` (array of `{ from, to }`, the pre-clipped lines).
  - `text`: `text`, `font`, `size`, `width` (below), `anchor` (point, model inches: the baseline point the alignment refers to), `align` (`left` | `center` | `right`: where `anchor` sits on the baseline).
  - `layer` equals `role`; `weight` is the Step 1 stroke width in pt; `text` items have `weight` 0 (spike inputs).
- **The 12 items, in this order** (Step 1 geometry; spike inputs where not in Step 1):
  1. `polyline` `wall`: points (48,0), (144,0), (144,120), (0,120), (0,0), (12,0); `closed` false (the door gap).
  2. `line` `door`: (12,0) → (12,36).
  3. `arc` `door`: `center` (12,0), `radius` 36, `startAngle` 0, `endAngle` 90.
  4. `hatch` `hatch`: `boundary` (0,0), (144,0), (144,120), (0,120); 31 `segments` (T6).
  5–9. `line` `check-dimension`: dimension line (0,−24) → (144,−24); extension lines (0,−2) → (0,−26) and (144,−2) → (144,−26); ticks (−2,−26) → (2,−22) and (142,−26) → (146,−22).
  10. `text` `check-dimension`: `12'-0"`, `mono`, `anchor` (72,−22), `align` `center`.
  11. `text` `room-label`: `EZD-028 ROOM`, `sans`, `anchor` (72,60), `align` `center`.
  12. `text` `scale-label`: `1/4" = 1'-0"`, `mono`, `anchor` (72,−32), `align` `center`.
- **Model to paper:** paper point (PDF user space, y up, origin bottom-left) = `paperOrigin + model × scale × 72`, so 1 model inch = 1.5 pt. The writer then flips to PDFKit's top-left: `y_pdfkit = 1728 − y_paper`.
- **Text box** (T9): in paper pt, x from `anchor − width` (`right`), `anchor − width/2` (`center`) or `anchor` (`left`) over `width`; y from `anchor − size` to `anchor + size`.
- `hatch` items carry the boundary and the **pre-clipped segments** (*planner's choice*). Explicit segments draw the same way in WebGL, SVG and PDF, which no tiling-pattern approach does (02 "screen and print cannot drift"). The spike clips against a rectangle only; general polygons are Clipper's job in EZD-238.
- `text` items carry `text`, `font` (`sans` = Instrument Sans 400, `mono` = DM Mono 400; 04 Type: DM Mono for every measurement and number), `size` in paper points (09: text prints at a fixed paper size), anchor and alignment, and `width` in paper points. The width comes from `src/metrics.mjs`, which loads the font file with `fontkit` and sums the advances of `font.layout(text)` × size / unitsPerEm. That is the "metrics from bundled font files" of 02 PDF out. All text is 6.75 pt (3/32", the 09 minimum on 24×36).
- Font files are read by path from EZD-010's `app/src/styles/fonts/instrument-sans-latin-400-normal.woff2` and `dm-mono-latin-400-normal.woff2`. Reading a file does not import the app, so C4 holds. If PDFKit or fontkit cannot embed the woff2 files correctly (T2 or T8 fails), the builder tries the same families' `.woff` files, then TTF, kept in `spikes/EZD-028-pdf/fonts/` with their licence files, and records what worked. That outcome is a finding for the note, not a failure of the spike.

### Step 3: The PDF writer (`src/write-pdf.mjs`)
`writePdf(list) → Promise<Uint8Array>` uses PDFKit only (02 Named tools):
- `new PDFDocument({ size: [2592, 1728], margin: 0, info: { Title: 'EZD-028 room' } })`, one page. The default Helvetica must not end up in the file; the builder uses the pinned PDFKit's option to disable or replace the default font. If that cannot be done, it is recorded and T2 shows it.
- Registers the two font files and uses only them for text.
- Maps model to paper with `view` and flips y to PDFKit's top-left coordinates.
- Arcs become Bézier curves. Hatch segments are drawn as plain stroked lines.
- Wraps each item's drawing in a marked-content sequence `/EZ_<role> BMC … EMC`, written with `doc.addContent`, with `-` in the role replaced by `_` (e.g. `EZ_check_dimension`) (*planner's choice*). This is how tests find the check dimension, the hatch and the door without relying on draw order. EZD-715 can reuse it for its identical Done when.
- `doc.outline.add(null, 'EZD-028 room')`: one bookmark to page 1 (ticket; 02 "one bookmark per sheet").
- No encryption and no permissions dictionary (08 Permit set "not password-locked; markup allowed").

### Step 4: Units (why 2592 × 1728)
The PDF default user-space unit is 1/72 inch (ISO 32000-1 §8.3.2.3). 24×36 ARCH D (08 Permit set; Round 24 #48) in landscape is 36 × 72 = 2592 pt wide and 24 × 72 = 1728 pt high, which matches the ticket's Done when. The check dimension's labeled length is 12'-0" = 144 in, and at 1/4" = 1'-0" (scale 1/48; 09) that is 3 in on paper = **216 pt**.

### Step 5: Inside a function with the production limits (`src/child.mjs`, `src/run-in-limits.mjs`)
02 Background jobs and P4 put PDF writing in Vercel Functions, and the PDF job is EZD-715. Neither EZD-003 (hosting) nor EZD-009 (job queue) is needed to answer whether PDFKit fits the limits. A local emulation is enough for a spike, and the real platform run comes with EZD-715 (*planner's choice*; the code-reviewer confirms):
- `run-in-limits.mjs [--out <dir>] [--stress]` spawns `process.execPath --max-old-space-size=<memoryMb> src/child.mjs --out <dir> [--stress]`, using the same Node binary, and kills the child after `<seconds>`. `<dir>` is resolved against the current directory and created if missing; without `--out` it is the spike's `out/` folder.
- The child builds the list, writes the PDF to `<dir>/EZD-028-room.pdf` (`<dir>/EZD-028-stress.pdf` with `--stress`), and prints one JSON line on stdout: `ms` (wall clock from start of build to file written, by `process.hrtime.bigint`), `maxRssMb` (`process.resourceUsage().maxRSS` / 1024), `bytes`, `execArgv` (the child's own `process.execArgv`, so it shows `--max-old-space-size=2048`), `node` (`process.version`), `pdfkit` (the version in pdfkit's `package.json`) and `pdf` (the file name written).
- The parent writes `<dir>/results.json` as `{ limits: { seconds, memoryMb }, room, stress }`: it reads the file if present, sets `limits` and its own key (`room`, or `stress` with `--stress`) to the child's JSON, and keeps the other key. It exits 1 if the child timed out, crashed, or reported `maxRssMb ≥ memoryMb`, else 0.
- `<seconds>` and `<memoryMb>` are constants at the top of `run-in-limits.mjs`: **300** and **2048** (Q-0027 (a): Vercel Pro defaults, 300 s and 2 GB). The builder confirms the figures on Vercel's limits page on the build date; a difference is a question, not an edit (CLAUDE.md rule 6).
- `--stress` (recorded only, not a pass condition): the same writer on a list of 150,000 straight segments on one 24×36 page. That is the size of the benchmark reference DXF in 11 Budgets and R26 R9. It records `ms`, `maxRssMb` and `bytes`, so the note can say how a dense sheet compares with the limits and with PBC's 10 MB per file (08).
- `bytes` and `ms` of the room run are recorded, not tested.

## Risks
- **Default font.** PDFKit registers Helvetica by default, and an unused but written Helvetica dictionary fails T2. The pinned version's way to turn that off must be found by the builder. If none exists, that is a finding for the note and for EZD-715.
- **woff2 in PDFKit.** fontkit reads WOFF2, but subsetting and embedding from WOFF2 is less used than TTF. The fallback order is in Step 2. If only TTF works, EZD-238, EZD-702b and EZD-715 need TTF copies next to EZD-010's woff2 files. The note records it.
- **Local emulation is not the platform.** The build PC's CPU is faster than a 1 vCPU function, and RSS on Windows (peak working set) is not the same as Vercel's memory accounting. The room is tiny, so the margin is large, but the stress numbers are only indicative. EZD-715 proves the real run. Node on this PC is v24 and the platform is 22 (EZD-000 Risks); the results record the version.
- **pdfjs-dist API details.** The operator-list format (`constructPath` arguments) and marked-content items differ between pdfjs versions. The test-author writes T3, T6 and T7 against the pinned version.
- **Install weight.** `spikes/*` is a workspace member, so the gate's `pnpm install` also installs the spike's packages. pdfjs-dist and pdf-lib are already common, but install time grows a little.
- **Not decided here, so later planners must not read the spike as deciding it:** the typeface printed on permit sheets, line weights, the size step "one size up from notes" (09), and the form of the production check dimension and scale bar (S13 Validation). The spike uses Instrument Sans and DM Mono only because they are the bundled files. These are EZD-238, EZD-702b and EZD-715 questions.
- **Committed generated PDF.** It changes every run (creation date). That is acceptable for a throwaway folder; refresh it only in Step 6.3.
