### Step 1: Private schema and grants (migration `<ts>_create_private_schema.sql`)
- `create schema private;` It is **not** added to `[api] schemas` in `config.toml` (stays `public, graphql_public`, EZD-004 Step 1), so nothing in it is callable through the REST API. *Planner's choice*, following Supabase's advice to keep `security definer` functions out of exposed schemas.
- `revoke all on schema private from public; grant usage on schema private to anon, authenticated, service_role, supabase_auth_admin;` `anon` and `service_role` need usage only because PostgREST calls the Step 1b gate function as the request's role (Q-0087 (ii)); `anon` can execute exactly one function in `private`, `api_request_gate` (T10).

### Step 1b: PostgREST request gate (migration `<ts>_create_api_request_gate.sql`; Q-0087 (ii))
Source: Q-0087 (security-reviewer, Stage 2): "Server requests carry a server-only secret header; `private.api_request_gate()` (registered as `pgrst.db_pre_request`) refuses every anon/authenticated PostgREST request without a matching header (allow-list: anon `rpc/health`); fails closed. RLS stays the independent backstop. EZD-006 owns it in phase 0." Supabase and PostgREST names below are marked *(confirm on pinned version)*; the builder reads them from the pinned CLI, not from memory.
- **Secret and hash.** The secret is 32 bytes from a CSPRNG, written base64url (43 characters; the same strength the security-reviewer set for EZ Binder secrets in Q-0079). Only its SHA-256 hex digest is stored in the database, in **Supabase Vault** under the name `ezd_api_gate_sha256` (*planner's choice*; fallback if the pinned Vault is unusable: a custom setting on role `authenticator`, recorded in docs, see Risks). Never in a table (the audit's `table_in_private_schema` code forbids tables in `private`, Step 6) and never in the repo (CLAUDE.md rule 12).
- `private.set_api_gate_hash(p_hash text) returns void` (`security definer`, `set search_path = ''`, owner `postgres`; no execute grant to any API role): raises `22023` unless `p_hash` matches `^[0-9a-f]{64}$`; creates or updates the Vault secret `ezd_api_gate_sha256` *(confirm Vault function names on pinned version)*. Josh runs it in each cloud project's SQL editor (runbook, Step 8); the local script and the test global setup run it as `postgres`.
- `private.api_request_gate() returns void`, `language plpgsql`, `security definer`, `set search_path = ''`, owner `postgres`; execute granted to `anon`, `authenticated`, `service_role` (PostgREST calls it as the request's role), revoked from `public`. Body:
  1. The request role is read from `current_setting('role', true)` (PostgREST sets it per request *(confirm on pinned version)*), **not** `current_user`, which inside a `security definer` function is the owner.
  2. `service_role` → return (server jobs and seeds with the secret key pass).
  3. `anon` and `current_setting('request.path', true)` = `/rpc/health` → return (EZD-004 Step 2: health stays public) *(confirm the path format on pinned version)*.
  4. Read the stored hash from Vault. Null or empty → `raise exception 'api_gate_not_configured' using errcode = '42501'` (fails closed).
  5. `h := current_setting('request.headers', true)::json ->> 'x-ezd-api-gate'` (header name *planner's choice*). If `h` is null or `encode(sha256(convert_to(h, 'UTF8')), 'hex')` ≠ the stored hash → `raise exception 'api_gate' using errcode = '42501'`. `sha256()` is built into PostgreSQL 11 and later, so no extension is needed.
  6. Any other role → refuse the same way.
  - SQLSTATE `42501` is chosen so EZD-005 T10 and this plan's T14 (which accept `42501` for refused anon reads) stay green.
- Registration, in the same migration: `alter role authenticator set pgrst.db_pre_request = 'private.api_request_gate';` then `notify pgrst, 'reload config';` *(confirm on pinned version)*. Every PostgREST request runs it: tables, RPC and GraphQL (`/graphql/v1` is served through PostgREST's `rpc/graphql`) *(confirm on pinned version)*. Auth, Storage and Realtime do not go through PostgREST and are not gated (Risks).
- Not done here (*planner's choice*): removing `graphql_public` from `[api] schemas`. The gate already refuses GraphQL without the header, and keeping the list unchanged keeps EZD-004's config and T22 (d)'s expected value single. Noted for the security-reviewer.
- **Local secret.** `scripts/db/api-gate.mjs` (builder; Node 22 built-ins only) exports `newGateSecret()` and `gateHash(secret)` and has a CLI: `generate` prints a new secret and the line `select private.set_api_gate_hash('<hash>');` (for Josh's runbook step). `scripts/db/local.mjs up` (EZD-004's file, extended) gains a last step: generate a fresh secret, store its hash in the local database (through `runLocalSql` from `scripts/db/sql.mjs`, which EZD-005 adds for its Q-0033 (a) bootstrap test, vault/plans/EZD-005.md Step 7), and write the secret to the gitignored file `supabase/.temp/ezd-api-gate-secret` (*confirm `supabase/.gitignore` from `supabase init` ignores `.temp`; otherwise the builder adds the line*). EZD-007 makes `local.mjs env` print it as `SUPABASE_API_GATE_SECRET`. Nothing is committed.
- **Test secret.** The Vitest global setup generates its own random secret each run and stores its hash (Step 7).

### Step 2: Claims and the token hook (migration `<ts>_create_custom_access_token_hook.sql`)
`private.custom_access_token_hook(event jsonb) returns jsonb`, `language plpgsql stable security definer set search_path = ''`, owner `postgres`. Execute granted to `supabase_auth_admin` only; revoked from `public`, `anon`, `authenticated`.

It runs on every token Supabase Auth issues (sign-in and each refresh). It does one indexed query: `app_user` by `auth_user_id = (event->>'user_id')::uuid` (unique index), left-joined to `membership` with `status = 'active'` on `user_id` (`membership_user_id_idx`). It adds these top-level claims to `event->'claims'` and returns `jsonb_build_object('claims', …)`. Required Supabase claims are left as they are. Claim names are *planner's choice*:

| Claim | Value | Set when |
| --- | --- | --- |
| `app_user_id` | `app_user.id` | an `app_user` row is linked to this auth user |
| `tenant_id` | the active membership's `tenant_id` | exactly one `active` membership exists (two or more: not set, Q-0043 (a)) |
| `membership_id` | that membership's `id` | same as `tenant_id` |
| `project_scope` | `'all'` or `'listed'` (`membership.scope`) | same as `tenant_id` |

- **Two or more `active` memberships** (Q-0043 (a), Josh 2026-10-12: one active company per person in v1): the hook sets `app_user_id` only and no `tenant_id`, `membership_id` or `project_scope` claim, so the person reads no tenant rows. It does not pick one. This state should never arise, because the write paths refuse it (below); the hook fails closed if it does (T9).
- **For EZD-105 (and every path that makes a membership `active`):** inviting a person who already has an `active` membership in another tenant is refused (Q-0043 (a)). The same holds where an invite turns `active`: EZD-007's sign-in-accepts-a-pending-invite path (Q-0050 (a)) and EZD-105's invite accept must not activate a second membership. Those planners add the check and its test; this ticket adds no constraint for it (a database constraint would also make T9's defensive case impossible to set up). The orchestrator copies this note to the EZD-105 and EZD-007 plans (Level 2).
- An `invited` or `deactivated` membership never produces a tenant claim (ticket Scope "deactivating a user … ends their sessions"; a deactivated person who signs in again gets a token with no tenant and reads no tenant rows).
- No row found: the claims are returned unchanged (no app keys). The hook never fails sign-in. What the app shows a signed-in person with no tenant is for EZD-007 / EZD-102.
- `supabase/config.toml` (builder) gets:
  ```toml
  [auth.hook.custom_access_token]
  enabled = true
  uri = "pg-functions://postgres/private/custom_access_token_hook"
  ```
  If the pinned CLI refuses a hook outside `public`, the builder moves only the hook to `public` (execute still revoked from `anon`/`authenticated`) and records why in `docs/architecture.md`; T19 then reads the recorded schema.

### Step 3: Policy helpers (migration `<ts>_create_rls_helpers.sql`)
All `stable`, `security definer`, `set search_path = ''`, owner `postgres`. Execute granted to `authenticated` only (revoked from `public` and `anon`). They read the request's JWT claims with `auth.jwt()`.

| Function | Returns | Body (what it does) |
| --- | --- | --- |
| `private.session_is_live()` | boolean | `exists (select 1 from auth.sessions where id = (auth.jwt()->>'session_id')::uuid)`; false when the claim is missing |
| `private.tenant_id()` | uuid | If `session_is_live()` is false: `raise exception 'session_ended' using errcode = '42501'`. Otherwise the `tenant_id` claim, or null |
| `private.app_user_id()` | uuid | Same session check; the `app_user_id` claim, or null |
| `private.all_projects()` | boolean | `coalesce(auth.jwt()->>'project_scope' = 'all', false)` |
| `private.listed_project_ids()` | uuid[] | `coalesce(array_agg(project_id), '{}')` from `public.membership_project` where `membership_id` = the `membership_id` claim and `tenant_id` = the `tenant_id` claim (primary key `(membership_id, project_id)` serves it) |
| `private.tenant_user_ids()` | uuid[] | `array_agg(user_id)` from `public.membership` where `tenant_id` = the `tenant_id` claim (index `unique (tenant_id, user_id)`) |
| `private.can_see_project(p uuid)` | boolean | `p` is a project of the claim tenant and (`all_projects()` or `p = any(listed_project_ids())`). For one-off checks such as EZD-018's channel join; table policies use the array form below |

Why this shape:
- **Once per query, no membership join per row** (11 rule 10; ticket Scope). Policies always call helpers wrapped in a scalar subquery, `(select private.tenant_id())`, which PostgreSQL runs once per statement as an InitPlan. The tenant comes from the claim, not from `membership`. Listed projects are read once per statement into an array (one primary-key range scan), not joined per row. T17 and the audit's `helper_not_wrapped` / `policy_joins_membership` codes check this.
- **"A deactivated user's next request is refused"** (Done when). A JWT stays valid until it expires, so ending the session alone does not stop the next request. Every tenant policy calls `private.tenant_id()`, which checks that the token's session still exists in `auth.sessions` (one primary-key lookup per statement) and raises SQLSTATE `42501` if it does not. PostgREST returns HTTP 403 for that code to a signed-in caller. Supabase Auth also refuses the refresh token (its rows go with the session) and, in the pinned version, `getUser` for that token (T3). *Planner's choice*; security-reviewer confirms.
- Listed projects are read live, so a narrowed list applies on the next query even before the session ends. The `project_scope` claim is what forces the session end on a scope change (Step 4).

### Step 4: Ending sessions (migration `<ts>_create_end_sessions_triggers.sql`)
- `private.end_user_sessions(p_app_user_id uuid) returns void` (`security definer`, `set search_path = ''`, `volatile`; no execute grant to any API role): `delete from auth.sessions where user_id = (select auth_user_id from public.app_user where id = p_app_user_id)`. A null `auth_user_id` deletes nothing.
- Trigger `membership_end_sessions` (`after update or delete on public.membership for each row`, function `private.membership_end_sessions()`): calls `end_user_sessions(old.user_id)` when `new.status is distinct from old.status`, when `new.scope is distinct from old.scope`, or on delete. Status and scope: ticket Scope; 11 Operations. Delete (Remove user, S15 Row menu; EZD-106) is *planner's choice*: removal is stronger than deactivation.
- Trigger `membership_project_end_sessions` (`after update or delete on public.membership_project for each row`): calls `end_user_sessions` for the user of `old.membership_id` on delete, and on an update when `new.membership_id is distinct from old.membership_id` or `new.project_id is distinct from old.project_id` (such an update removes the old listed project from the old membership, so it is a narrowing). A removed listed project narrows the user's scope (ticket Scope "changing their project scope"). An **inserted** listed project does not end sessions: Q-0044 (b) (security-reviewer, Stage 2): "only narrowing changes end sessions …; adding a listed project does not, because listed projects are read live on every statement". No ticket plans to update these rows (EZD-129 writes inserts and deletes); the update case is a guard.
- Sessions of the person end in every tenant, because sessions are not per tenant. They sign in again and the hook issues fresh claims.
- **For EZD-129 (phase 1):** it writes `membership.scope` and `membership_project` and relies on these triggers to end sessions on a narrowing (Q-0044 (b); 11 Operations). It must not bypass them (no `session_replication_role` tricks, no trigger disabling).
- **For EZD-018 (Q-0052 (c)):** EZD-018 redefines `private.end_user_sessions` in a new migration (`create or replace`, same signature and grants) to also push `session.ended` on the user's Realtime channel. This ticket's migration is not edited (EZD-000 Migrations).

### Step 5: Policies and grants (migrations `<ts>_create_tenancy_policies.sql` and `<ts>_restrict_api_table_grants.sql`)
All policies are `to authenticated`. `anon` gets no policy. Policy names `<table>_<command>`.

| Table | select (USING) | insert / update / delete |
| --- | --- | --- |
| `tenant` | `id = (select private.tenant_id())` | none: writes refused (grants revoked, below) |
| `app_user` | `id = (select private.app_user_id()) or id = any ((select private.tenant_user_ids()))` | none |
| `membership` | `tenant_id = (select private.tenant_id())` | none |
| `membership_project` | `tenant_id = (select private.tenant_id()) and ((select private.all_projects()) or project_id = any ((select private.listed_project_ids())))` | none |
| `project` | `tenant_id = (select private.tenant_id()) and ((select private.all_projects()) or id = any ((select private.listed_project_ids())))` | insert WITH CHECK `tenant_id = (select private.tenant_id())`; update USING = the select expression, WITH CHECK `tenant_id = (select private.tenant_id())`; delete USING = the select expression |

- **Template for later tables** (recorded in docs, Step 7): for a table with `tenant_id` and `project_id`, every policy's USING and WITH CHECK is `tenant_id = (select private.tenant_id()) and ((select private.all_projects()) or project_id = any ((select private.listed_project_ids())))`, optionally `and` more conditions; a table with `tenant_id` only uses the first clause. RLS checks tenant and project scope only, never permission rows (EZD-102 row).
- **Grants** (`<ts>_restrict_api_table_grants.sql`), *planner's choice*, security-reviewer confirms. Every privilege the API roles hold on a table is granted **explicitly, by name, in a migration**. Nothing relies on Supabase's default privileges or on the cloud-only project setting "Automatically expose new tables", which Josh left on (orchestrator's brief 2026-10-12); the app behaves the same with it on or off. In this order:
  1. **Schema:** `grant usage on schema public to anon, authenticated, service_role;` (`anon` needs it only to execute `public.health()`, EZD-004 Step 2; `service_role` for server jobs and seeds that use the secret key, Step 1b).
  2. **Defaults grant nothing:** `alter default privileges for role postgres in schema public revoke all on tables from anon, authenticated, service_role;`. A table a later migration creates then has no API privileges until that migration grants them, locally and in the cloud, whatever the cloud setting says *(builder confirms on the pinned CLI that the setting works through `postgres`'s default privileges in `public`, so this revoke overrides it in both states; if it works another way, the builder stops and raises a question)*.
  3. **Start the five existing tables from nothing:** `revoke all on public.tenant, public.app_user, public.membership, public.membership_project, public.project from anon, authenticated, service_role;`. `anon` never needs a table: the client link uses server routes (03 rule 11). `public.health()` keeps its explicit `anon` execute grant (EZD-004 Step 2). TRUNCATE, REFERENCES and TRIGGER are never granted to an API role (TRUNCATE is not subject to RLS).
  4. **Explicit grants, one statement per role and set:**
     - `grant select, insert, update, delete on public.project to authenticated;`
     - `grant select on public.tenant, public.app_user, public.membership, public.membership_project to authenticated;` These four tables decide who sees what, so `authenticated` gets no insert, update or delete (the revokes this plan already had). A signed-in member must not be able to change their own scope, status or memberships by calling the REST API directly with their own token. The tickets that write them (EZD-105, 106, 112, 129) add a reviewed write path (Risks).
     - `grant select, insert, update, delete on public.tenant, public.app_user, public.membership, public.membership_project, public.project to service_role;` (server jobs, seeds; `service_role` bypasses RLS but still needs table privileges).
  - No sequence grants: EZD-005's tables use `uuid` keys and have no identity or serial column (vault/plans/EZD-005.md table definitions).
- **Table grants convention** (for every later migration that creates a table or view in `public`; recorded in docs, Step 8; checked by the audit, Step 6): the same migration ends with explicit statements that name the table: `grant select, insert, update, delete on public.<t> to authenticated;` (or the narrower set the table's entry in `TABLE_GRANTS` records, with its reason), `grant select, insert, update, delete on public.<t> to service_role;`, nothing for `anon`, and `grant usage on sequence …` for any sequence the table owns. `grant … on all tables in schema public …` does not count, because it hides which table was meant. Functions in `public` already follow the same rule (`revoke all … from public`, then `grant execute` by name; EZD-004 Step 2; `GATED_RPC_CALLS`, Step 7).
- These policies and grants stay in force behind the Step 1b gate: "RLS stays the independent backstop" (Q-0087). T1–T14 therefore send the gate header, so they test this layer on its own (Tests).

`app/test-harness/rls/table-grants.ts` exports:
- `TABLE_GRANTS = { tenant: { privileges: ['SELECT'], reason: '…' }, app_user: …, membership: …, membership_project: … }` (each `['SELECT']`; Step 5). A table not listed expects `['SELECT', 'INSERT', 'UPDATE', 'DELETE']` for `authenticated`. - `explicitGrantRoles(migrationTexts: string[], table: string): Set<string>` (pure). It strips `--` and `/* */` comments, splits statements on `;`, and returns the roles named after `to` in every `grant <privileges> on [table] <name list> to <role list>` statement whose name list contains the table (`x`, `public.x` or `"public"."x"`, case-insensitive for unquoted names). `grant … on all tables in schema …`, `grant usage on schema …` and `revoke …` name no table and add nothing (*planner's choice*, so a migration must say which table it means).

## Risks
- **Direct REST calls and `can()`: closed by the gate (Q-0087 (ii)).** RLS checks tenant and scope only (EZD-102 row), so a member's token used against PostgREST directly could otherwise write rows `can()` would refuse. The Step 1b gate refuses every anon or authenticated PostgREST request (tables, RPC, GraphQL) that lacks the server-only header, so only server routes, which call `can()`, reach PostgREST; RLS and the Step 5 grants stay the backstop. What remains: (1) the token still reaches Auth, Storage and Realtime, which are not behind PostgREST, so EZD-132 must keep Storage policies tight (Q-0087) and EZD-018 relies on Realtime's own policies; (2) the secret must never reach a browser (EZD-007 tests it) and must be stored in each cloud project and Vercel before cloud use (runbook; until then the cloud refuses every signed-in request); (3) EZD-133 adds a direct-PostgREST money-column refusal test (Q-0087). EZD-105, 106, 112 and 129 still need a reviewed write path for `membership`, `membership_project`, `tenant` and `app_user`, because server routes run as `authenticated` and the Step 5 revokes apply to them too.
- **Gate details depend on the pinned PostgREST and Supabase versions:** `pgrst.db_pre_request` on `authenticator`, `notify pgrst, 'reload config'`, `request.path` / `request.headers` / `role` settings, the GraphQL route through PostgREST, and Vault's function names. T22 proves them locally. If Vault cannot be used, the fallback is a custom setting on role `authenticator`; pooled PostgREST connections read role settings only when they connect, so after storing a new hash the API must reconnect (restart the local stack; on the cloud, a project restart, added to the runbook). Per-request cost: one Vault lookup and decrypt per PostgREST request, no per-row work (11 rule 10 is unaffected).
- **Deleting `auth.sessions` rows on the cloud.** Supabase restricts changes to the `auth` schema on hosted projects. Data changes by a `postgres`-owned function are expected to work, but this is not verified on a cloud project. The local stack proves the tests. If the cloud refuses it, session ending needs another path (for example an Auth admin call from a server route), and Steps 3 and 4 change. Check at the first cloud migration (Q-0023 path).
- **Auth version specifics.** The `session_id` claim, the hook event shape, `getUser` refusing a deleted session, and `generateLink` / `verifyOtp` parameter names depend on the pinned CLI and supabase-js. The test-author and builder read them from the pinned versions, not from memory.
- **Raising inside policies.** `private.tenant_id()` raises for a dead session. That is the "refused" signal for REST, Storage and Realtime authorization. EZD-018's planner must check how a raise behaves inside Realtime's authorization and Postgres Changes, and prefer Broadcast with `private.can_see_project`.
- **EZD-007 must link and re-issue.** The hook finds a person only through `app_user.auth_user_id`. At first sign-in that link is empty, so the first token has no app claims. EZD-007 links the verified email (EZD-005 Risks) and then refreshes the session so the hook runs again. EZD-016a's seeded users must be created the harness way (auth user plus link), or they will sign in to empty screens.
- **Cloud hook is a manual switch.** `config.toml` covers the local stack only. Until Josh enables the hook in each cloud project (runbook step), every cloud user reads zero rows, including Josh at the Phase 0 field check. The orchestrator adds the step to `needs-from-josh.md`.
- **Per-query cost.** Each statement does up to two `auth.sessions` primary-key lookups (from `tenant_id()` and `app_user_id()`), plus, for listed users, one `membership_project` range scan. There is no per-row work, so 11 rule 10 holds. EZD-017 measures rows written per save, not this.
- **Session ends sign people out.** Every status or scope change, removal, and removed listed project signs the person out on every device; an added listed project does not (Q-0044 (b)). Unsynced outbox changes stay on the device (03 rule 9 "never evicted"), but crew must sign in again on site.
- **One active company per person is enforced by the write paths, not here (Q-0043 (a)).** If EZD-105, EZD-007's invite acceptance (Q-0050 (a)) or EZ Binder user sync (S15a "Sync users") ever lets a second membership turn `active`, that person reads nothing until one is deactivated (T9 behaviour). Those planners must test the refusal.
- **EZD-133 overlap.** EZD-133's "CI test that fails when a table has no row-level security policy" should reuse `auditRls` (its `no_policy` code), not build a second check. Note for EZD-133's planner.
- **Default privileges** apply to tables created by `postgres` through migrations; after Step 5 they grant the API roles nothing. A table created another way (for example by hand in Studio, or by another role) could keep other default grants. The audit's `anon_has_privileges` and `authenticated_grants_mismatch` codes catch it locally; nothing checks the cloud catalog (no agent holds cloud credentials, CLAUDE.md rule 12).
- **Cloud project settings (orchestrator's brief, 2026-10-12).** "Automatically expose new tables" was left **on** by Josh, matching the local CLI default. The app does not depend on it either way: Step 5 revokes the default privileges it works through and every table grants explicitly, enforced by the `@smoke` audit (T23). *(builder confirms the mechanism on the pinned CLI, Step 5.2.)* Turning the setting on or off later in the dashboard might change grants on tables that already exist *(not verified)*; behind the Step 1b gate and RLS that still exposes no rows, but the runbook asks Josh to leave both settings as they are. "Enable automatic RLS" was left **off**, so local and cloud match; every migration enables RLS on its own tables (EZD-005 Step 1.8), and the audit's `rls_disabled` code fails any table that does not.
- **Later table-creating tickets must grant explicitly (for the orchestrator, Level 2).** Phase 0 plans that create tables after this ticket: EZD-009 (`job`), EZD-024 (`error_alert`), EZD-025 (`backup_run`), EZD-033 (`sign_in_throttle`). Each migration must end with the Step 5 grants (and a `TABLE_GRANTS` entry with a reason where `authenticated` gets less than all four, for example `job`, whose direct writes are revoked, or a server-only table that gets an empty set). Otherwise their gate fails on the `@smoke` audit (`grants_not_explicit`, `authenticated_grants_mismatch`). Their plans do not say so yet.
- **Test runtime.** Each sign-in costs a few local HTTP calls. About 25 sign-ins across the files fit in EZD-004's 15,000 ms `testTimeout` per test with `maxWorkers: 2` (Q-0019).
- **Ticket size.** Seven small migrations, one small script, the harness and six test files. This still fits one session; if the test-author's harness alone overruns, the orchestrator can split it as EZD-006a (harness, audit, policies, gate) and EZD-006b (hook claims and session ending). This plan does not propose that split.
