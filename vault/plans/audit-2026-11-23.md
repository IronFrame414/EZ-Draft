## One change this audit made outside its own worktree (read this first)

When the desktop app created this audit's worktree at 21:31 ET (02:31Z), it switched on `extensions.worktreeConfig = true`
in the shared git settings, `/Users/josh/Projects/ezdraft/.git/config` (file time 21:31). It also wrote
`.git/worktrees/audit-2026-11-23-dca1a9/config.worktree`, which only sets `core.untrackedCache = true`. The repo's git
safety guard refuses to run while that setting is on (`vault/tools/trusted-git.mjs:88-92`). So lane 2's gate for
**EZD-1001b** failed at its first database step (`.claude/worktrees/EZD-1001b/check.log`:
`TrustedGitError: worktree config is on: unset extensions.worktreeConfig`).

It also hit **EZD-604** (lane 1). Its e2e failed with the same TrustedGitError, 24 lines in `.claude/worktrees/EZD-604/check-failures.log` (21:36 ET). The loop logged `[2026-11-23T02:36:09Z] EZD-604 check red (round 1); builder fixing`, so **this incident used up one of EZD-604's two fix rounds**. EZD-728 (lane 3) shows no such error. EZD-1001b's builder has since rerun its gate past `db:up`; at 21:58 ET its `check.log` was in e2e.

About 10 minutes later this session ran `git config --unset extensions.worktreeConfig`, which put the setting back the
way it was. A copy of the old config is in this session's scratchpad. Any lane that went red between 02:31Z and about
02:41Z should get a recheck; don't count it as a real failure. **Any future worktree the desktop app creates on this repo
will do the same thing.** Make worktrees by hand with `git worktree add` instead. Hand-over note:
`side-session-notes/.../audit-worktreeConfig-incident.md`.

## Area 2. Flaky tests

**Correction to the brief:** the lanes do **not** share one database. `docker ps` shows four separate Supabase stacks:
`supabase_*_ezdraft` (54321) and `ezdraft-lane1/2/3` (54421, 54521, 54621). `scripts/check.mjs:21` points each lane at
`.lanes/laneN`. So "two lanes reset each other's database" can't be the cause. The lanes do share CPU, memory, Docker,
the heavy-stage lock and `/tmp`.

Inside one lane, each `db:up` runs `supabase db reset --local` and stores a **new gate secret**
(`scripts/db/local.mjs:70-72`, `storeLocalGateSecret` at 89-99). The gate runs `db:up` twice ("database", then
"database again" before e2e). Anything that touches a lane's stack between those two steps would break that lane's
tests. No such event was seen (**lead, unverified**).

Playwright runs **4 workers with 0 retries** (`app/playwright.config.ts:105-107`), and `heavy_slots` is 2 since
2026-11-20, so two lanes can run e2e at once (8 browsers, two `next start` servers). The machine has 12 cores and 32 GB.

**Load check (fair comparison).** The busiest load reading within ±10 min of each flaky failure was 19.8–28.1. Over the
same span, the busiest reading around passing merges had a median of 19.1, and 45% were ≥19.8 (53 merges since
heartbeats began, `vault/build/heartbeat.jsonl`). So the machine is busy all the time, and load does **not** separate
failures from passes. CPU strain is a contributing factor at most. The likely causes are specific to each test:
