# EZD-107 · Custom roles (split proposal)

- **ACs:** AC-EZD-107-1 … AC-EZD-107-4 (`vault/spec/acceptance-criteria.md:1114-1117`, stage-0), shared out to the parts below. AC-1, -2 and -3 are split by clause (AC map).
- **Complexity:** high (part a), medium (part b); reasons per part
- **Areas:** security, migrations, data-model, api, ui, testing
- **User-visible result:** On Settings → Users + permissions, Josh sees the Roles row under the users table: the four preset cards, his own custom roles and a New role card. He makes a role from scratch or from a preset, or saves a modified person's switches as a new role, then gives that role to someone else. A preset opens read-only; a custom role can be renamed, re-ticked and, when nobody holds it, deleted. Every role change is logged.
- Phase: 7 · Planned by: planner · Date: 2026-11-11 · Status: split proposal

## Split proposal

**Why.** Planned whole, the ticket would touch about 29 files and need about 26 tests. That is over the size rule (PROCESS.md section 6 "Ticket size": about 20 files or 25 tests; Josh 2026-10-22). The count:
- **Database:**
  - the name rules on `public.role`: unique per company ignoring case (AC-2; S15 Validation "Custom role names are unique within the tenant"), and a length bound (L-061). The table has only `length(btrim(name)) > 0` today (`supabase/migrations/20261024100002_create_role.sql:6`);
  - the write path: create, edit and delete as security-definer functions. Each checks `settings_users` inside (Q-0695, `decisions/10-permissions-and-settings.md` row 59) and writes its event_log row in the same transaction (Q-0695, `decisions/03-data-model.md` row 33: "Permission, role, membership, scope and invite changes write their row in the same transaction"). Today any signed-in member may insert, update and delete custom roles straight through the table (`20261024100002_create_role.sql:57-73`; architecture "Permissions and roles (EZD-101)"), a path that writes no event_log row;
  - the roles read with each role's holder count (AC-3: Delete only when no member holds it);
  - the harness lists: `GATED_RPC_CALLS` (`app/test-harness/rls/gate.ts:141`), `TABLE_GRANTS` (`app/test-harness/rls/table-grants.ts:46`) with the exact list in `app/src/server/db/rls.audit.test.ts:205`, `CAP_LOCK_READ_ONLY` (`app/test-harness/rls/cap-locks.ts:36`), `MONEY_ROUTE_CASES` (`app/test-harness/money/route-cases.ts:289`).
- **Routes:** `GET`, `POST /api/settings/roles` and `PATCH`, `DELETE /api/settings/roles/[id]`, each behind `requireApiPermission('settings_users')` (`app/src/server/permissions/can.ts`; Q-0695 row 59).
- **Events:** `role.created`, `role.updated` and `role.deleted` as `log_only` in `app/src/lib/events/registry.ts:64` (Q-0695 03-data-model row 33; S15 Events emitted).
- **Screen:** the Roles row cards (board S15 "Role presets" row), the role dialog for viewing a preset, editing a custom role and making a new one, Save as new role in the user inspector, en and es keys, the architecture section, and the browser test for Josh's slice 7 script step 4 (`vault/tickets/PHASES.md` slice 7).
- **Tests:** about 10 database, 4 route, 1 unit, 6 component and 2 browser tests, plus edits to 2 existing test files (`app/src/server/db/permissions.test.ts` T4 and T8; `rls.audit.test.ts` T18 list).

**Why cut here.**
- **Part a** is the whole server side of the `role` table: rules, reads, writes, guard and events. It is tested at the database and route level with no screen. It carries the security risk (definer writes, a grant change on an EZD-101 table, a delete that must not race an assignment) and gets its own security review. It needs no screen board, so the escalated Q-0696 (no board for the custom-role editor) does not hold it.
- **Part b** is the screen over part a's finished routes. It decides nothing on the server. Q-0696 holds it until Josh answers (`vault/questions/QUESTIONS.md:15`: "Holds EZD-105 and EZD-107 under (a)").

Built a → b. Each part is planned as its own unit from its section here, on template v2. Each part plan applies the planner lessons for its areas, notably:
- `revoke all … from public` on every new function, and test callers that match the grants (L-016, L-023);
- SQL contract text run on the pinned stack (L-009);
- every harness list the part joins named with the test that lists it exactly as a test-author edit row (L-049);
- migration timestamps after develop's newest at merge time (L-060);
- empty, maximum and malformed cases for every input, with a bound for each (L-052, L-061);
- the delete-against-assignment race written as a held transaction with exact outcomes (L-062);
- every new control in the touch-target list with a test (L-060), and every checklist row with the board's measured values (L-054).

### Part EZD-107a · Role rules, reads and writes
- **Scope:**
  - **Migration 1 (name rules):**
    - a unique index on `public.role (tenant_id, lower(btrim(name)))`. It counts the preset rows, so a custom role named "owner" is refused (AC-2 "a name already used in the company (ignoring case)"; the presets are rows of the company's `role` table, `20261024100003_seed_preset_roles.sql:9-12`);
    - a check `length(name) <= 1000`. 1000 is the bound the app already uses for project, customer and company names (`app/src/lib/projects/new-project.ts:10` `PROJECT_NAME_MAX = 1000`; `app/src/server/customers/customers.ts:25`; `app/src/server/company/company.ts:175`).
  - **Migration 2 (write path):**
    - `revoke insert, update, delete on public.role from authenticated` and drop the policies `role_insert`, `role_update` and `role_delete` (`20261024100002_create_role.sql:57-70`). The definer functions become the only member write path, so no role change can skip its same-transaction event_log row (Q-0695 03-data-model row 33; CLAUDE.md rule 18, close the whole class; the `user_permission` precedent, `table-grants.ts:46`). `TABLE_GRANTS` gains `role: ['SELECT']`. `release safety` does not scan `revoke` or `drop policy` (architecture "Release safety (EZD-023a)", "Not checked");
    - `public.list_roles()` (stable): every role of the caller's company with its holder count. Holders are memberships of any status whose `role_id` is the role; the foreign key that blocks a held delete counts every status (`20261024100004_add_membership_role_id.sql:4-6`). Order: Owner, Designer, Foreman, Crew (S15 Role select order), then custom roles by `lower(name)`, then id;
    - `public.create_role`, `public.update_role` and `public.delete_role`. Each runs `private.require_api_gate()` first and checks an active membership holding `settings_users` from the token's `membership_id` claim (the `public.create_project` pattern, `20261105105039_create_create_project.sql:14-23`; Q-0695 row 59). Each writes its event_log row in the same transaction through the event_log write function of the ticket Q-0720 names;
    - create and update take the name, trimmed, and the switch set. The set is checked against `private.permission_keys()` and stored once per key, in catalog order. Empty is allowed: a role "from scratch" ticks nothing (S15 Controls "New role ... from scratch");
    - update changes `role.default_permissions` and the name only. Holders keep their own `user_permission` rows (Q-0695 03-data-model row 35; AC-3);
    - a preset is refused on update and delete (S15 Decision 6; the `role_preset_guard` backstop, `20261024100002_create_role.sql:24-50`);
    - delete locks the role row, then refuses while any membership holds it (Q-0695 row 35; AC-3), with the foreign key as the backstop;
    - grants to `authenticated` only (L-016), and `GATED_RPC_CALLS` entries for all four.
  - **Server:** `app/src/lib/roles/roles.ts`: the `RoleSummary` type and the name check shared with part b. `app/src/server/roles/roles.ts`: the body parser and the mapping from database error to route status, with the body shape of architecture "Errors and logging".
  - **Routes:** `GET` and `POST /api/settings/roles`; `PATCH` and `DELETE /api/settings/roles/[id]` (the customers routes' shape, `app/src/app/api/settings/customers/route.ts`, `[id]/route.ts`; `DELETE` answers `200 { removed: true }` as `app/src/app/api/sync-conflicts/[conflictId]/route.ts:41` does). A name taken is `400 role_name_taken`, as `customer_email_taken` is (`customers/route.ts:74`). Nothing changed on `PATCH` is 200 with no write and no event (the customers `[id]` precedent).
  - **Events:** the three `log_only` entries with their payloads, emitted after the commit; a failed emit does not fail the save (`customers/route.ts:78-92`).
  - **Inventories:** `GATED_RPC_CALLS`, `TABLE_GRANTS` and its list in `rls.audit.test.ts:205`, `CAP_LOCK_READ_ONLY` (`list_roles` counts), `MONEY_ROUTE_CASES` (four cases), `database.types.ts`, the `error.*` keys in `en.ts` and `es.ts` (architecture "Messages and language", "Route error keys"), `docs/architecture.md` (a section "Custom roles (EZD-107a)", and the "Permissions and roles (EZD-101)" bullet at line 1093 that says members may write custom roles directly).
- **Contract other tickets rely on (Q-0730):** `GET /api/settings/roles` answers `200 { roles: RoleSummary[] }` in the order above, `401 not_signed_in`, `403 permission_denied` (`error.not_authorized`) and `500 db_unavailable`, with `Cache-Control: no-store`. `RoleSummary` is `{ id: string; name: string; preset: RolePreset | null; defaultPermissions: PermissionKey[]; holders: number }`, exported from `app/src/lib/roles/roles.ts` (`RolePreset` and `PermissionKey` from `app/src/lib/permissions/catalog.ts`).
- **Tests (about 15) and files (about 20):**
  - database tests:
    - create: the stored row (trimmed name, keys once in catalog order, `preset` null, holders 0) and its event_log row with actor and IP;
    - the name rules: blank refused, a used name in any letter case refused (custom and preset names), 1001 characters refused and 1000 kept, the same name in another company kept;
    - the switch set: an unknown key such as `approve_translations` (removed by Q-0234) refused, a null element refused, a repeated key stored once, empty and all 37 kept;
    - no `settings_users`: 42501 from all four functions, and nothing written;
    - update: holders' `user_permission` rows unchanged after re-ticking the role; nothing changed writes no row and no event;
    - preset, another company's role and an unknown id refused;
    - delete: refused while an invited member holds the role, done when nobody does;
    - the race: one session holds an uncommitted assignment of the role while a second calls delete, and after the commit the delete is refused;
    - `list_roles`: order, holder counts across statuses, no other company's role;
    - direct table insert, update and delete by a member with `settings_users` refused 42501;
  - route tests: 401, 403, 400 (each malformed body, a list of 38 keys, a name of 1001 characters), 404 (bad and unknown id), each refusal mapped, the success bodies, the emit after commit and a failed emit;
  - test-author edits: `permissions.test.ts` T4 (the member client now gets 42501, the service role still `preset_role_change_refused`) and T8 (custom roles made by the service role; a member's direct insert refused); `rls.audit.test.ts` T18 list gains `role`.
  - Files: 2 migrations, `database.types.ts`, `lib/roles/roles.ts`, `server/roles/roles.ts`, 2 route files, `registry.ts`, `en.ts`, `es.ts`, `docs/architecture.md`, 4 harness lists, 2 edited test files, 3 new test files.
- **Done when:**
  - a custom role can be created, renamed, re-ticked and deleted only through the four checked functions, each needing `settings_users`;
  - a blank name, a name already used in the company in any letter case, an unknown switch and a held or preset role are refused with their codes;
  - editing a custom role changes its defaults only, never its holders' switches;
  - every create, edit and delete writes its event_log row in the same transaction;
  - the roles read lists each role with its holder count in the S15 order.
- **ACs:** AC-2 (the server refusals); AC-3 (defaults only, preset and held refusals); AC-4 (all). AC-1's server half (a role made with a given set).
- **Depends on:**
  - Done, missing from the row: EZD-101 (`role`, `catalog.ts`, `role_preset_guard`), EZD-102 (`requireApiPermission`), EZD-022 (event registry), EZD-190 (`require_api_gate` in every public definer function), EZD-133 (`MONEY_ROUTE_CASES`), EZD-346 (same-origin walk of every write route).
  - Missing from the row, per the Q-0720 answer: the ticket that creates `event_log` and its write function (EZD-105a under (a); EZD-109 under (c)). Under (b) the same-transaction event clause of AC-4 needs EZD-109 first.
  - Not needed: EZD-106. The row's EZD-106 dependency is the screen's (Save as new role sits in the inspector), so it moves to part b (Q-0730).
- **The part plan settles:**
  - the exact signatures, return shapes and SQL error codes, run once on the pinned stack (L-009);
  - the event_log `details` for each action, within Q-0695's columns;
  - how the client address reaches the function, as the event_log owner's plan defines it (Q-0695 03-data-model row 33: the first `x-forwarded-for` value, full address, never `throttle.ts`'s /64 key at `app/src/server/auth/throttle.ts:133`).
- **Complexity:** high: security-definer writes with permission and tenant checks, a grant change on an existing table with its test edits, event rows in the same transaction and a delete race (PROCESS.md section 4). Test-author Opus 5.5, builder Opus 5.5.
- **security-review: yes** (permissions, data access, API, migrations). **Reviewers:** code-reviewer · calc-auditor no · ui-verifier no · security-reviewer yes.
