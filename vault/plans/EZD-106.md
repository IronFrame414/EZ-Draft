# EZD-106 · User inspector (split proposal)

- **ACs:** AC-EZD-106-1 … AC-EZD-106-9 (`vault/spec/acceptance-criteria.md:1101-1109`, stage-0), shared out to the parts below. AC-2, -4 and -6 are split by clause (AC map).
- **Areas:** security, migrations, data-model, auth, api, ui, testing
- **User-visible result:** On Settings → Users + permissions, Josh clicks a person and the right-hand panel shows their role, language and all 37 switches in groups with counts. Changing the role re-ticks the switches and shows "(modified)" when they differ. Reset puts them back, and Save (or Ctrl/Cmd+S) applies them on the person's next request. The More (…) menu deactivates, reactivates or removes a person. The last person who can open the Users page can never lose that switch, be deactivated or be removed.

## Split proposal

**Why.** Planned whole, the ticket would touch about 30 files and need about 45 tests. That is over the size rule (PROCESS.md section 6 "Ticket size": about 20 files or 25 tests; Josh 2026-10-22). The count:
- **Database (Q-0695, `decisions/10-permissions-and-settings.md` rows 59, 60, 62; `decisions/03-data-model.md` rows 33, 35):**
  - the last `settings_users` holder guard: a trigger on `user_permission` and on `membership` status, user, tenant and delete. It takes a per-company transaction lock, then recounts, lets a company-delete cascade pass (the `private.role_preset_guard` precedent, `supabase/migrations/20261024100002_create_role.sql:24`), and refuses with `last_settings_users_holder` (09n "Last settings_users holder" rows 1-5);
  - the session-ending trigger fix: `private.membership_end_sessions` (`20261026112732_membership_end_sessions_user_tenant_change.sql`) and `private.membership_project_end_sessions` (`20261019170005_create_end_sessions_triggers.sql:47-70`) end sessions only when the old status was active (Q-0695 row 62; AC-7). Q-0721 (a) builds both in EZD-105a, so this ticket only tests them (Part EZD-106a);
  - security-definer functions: save a member's switches, role and language; deactivate; reactivate (refused when the person is active in another company, Q-0043); remove (deletes the membership, so `user_permission`, `membership_project` and `invite` cascade, and deletes the person's `user_ai_key` row for this company, which points at `app_user` and does not cascade: `20261110120001_create_user_ai_key.sql:9`, Q-0637). Each checks `settings_users` inside (Q-0695 row 59);
  - `list_users` (EZD-104) redefined so deactivated members are listed but not counted (EZD-104 plan, Decided "Rows listed"; 09n "Status bar" row 1);
  - grants and the harness lists (`app/test-harness/rls/gate.ts:7` `GATED_RPC_CALLS`, `private-execute.ts:20` `PRIVATE_EXECUTE`, `cap-locks.ts:22` `CAP_LOCK_READ_ONLY` for any function that counts).
- **Routes:** save (PATCH), remove (DELETE), deactivate and reactivate (POST) under `/api/settings/users/[id]`, each `requireApiPermission('settings_users')` (`app/src/server/permissions/can.ts:52`). Each joins `MONEY_ROUTE_CASES` (`app/test-harness/money/route-cases.ts:74`) and the same-origin walk.
- **Events:** user_permission.updated, user.deactivated, user.reactivated and user.removed as `log_only` in `app/src/lib/events/registry.ts` (Q-0706, 03-data-model row 50). Each has its event_log row in the same transaction (AC-4; Q-0695 row 33; Q-0720).
- **Screen (S15 Controls, States; board S15):**
  - the inspector body: role select with "(modified)", the language toggle and its helper text, and 37 switches in the six `catalog.ts` groups with "n of m" group counts and the "n of 37" counter;
  - the footer: unsaved indicator, Reset to preset or role, and Save with Ctrl/Cmd+S;
  - the unsaved prompt on leaving or changing the selection (EZD-103b);
  - the error state with Retry, the offline note, and the last-holder refusal shown in the inspector;
  - the selected pending invite: invite details, Resend, Cancel invite, and Copy link (Q-0706);
  - the More (…) menu items Edit, Deactivate, Reactivate and Remove;
  - deactivated rows in the table;
  - en catalog keys, touch targets, and the browser tests for Josh's slice 7 script steps 3 and 5 (`vault/tickets/PHASES.md` slice 7).

**Why cut here.**
- **Part a** is every write and every guard, testable at the database and route level with no screen. It carries the security risk: definer writes, a concurrency-safe guard, session ending, the AI-key delete. It gets its own security review. The answered Q-0720 (c) and Q-0721 (a) shape only part a.
- **Part b** is the screen over part a's finished routes. It decides nothing on the server: what a person may do, and who sees Copy link, is answered by part a and `list_users` (Q-0706). The answered Q-0722 (a), Q-0724 (a) and Q-0725 (a) shape only part b.

Built a → b. Each part is planned as its own unit from its section here, on template v2. Each part plan applies the planner lessons for its areas, notably:
- `revoke all … from public` on every new function, with its `PRIVATE_EXECUTE` entry and test callers that match the grants (L-016, L-023);
- SQL contract text run on the pinned stack (L-009);
- every harness list the part joins named as a test-author edit row (L-049);
- a migration timestamp after develop's newest at merge time (L-060);
- empty, maximum and malformed cases for every input, with a bound for each (L-052, L-061);
- every caller of a redefined function checked, including null from a cascade (L-021 rule on redefinitions): the membership_project trigger runs inside the membership delete's cascade;
- the async and ordered cases named with the held await (L-062): the two-holders-at-once case of 09n row 4.
