# EZD-255 · Fix: a hold or limit message names the repair unit when a repair hits it

- **ACs:** AC-EZD-255-1, AC-EZD-255-2
- **Complexity:** low (two small pure helpers and four call-site edits in the launcher, tested through EZD-250's existing launcher harness; section 8)
- **User-visible result:** when a repair unit is stopped by a budget hold, a plan limit, the five-hour limit, the per-unit cap or the turn limit, Josh's notification, the hold file and the launcher log say "repair <kind> for "<the wait it was fixing>"" instead of naming the wait as if it were the stopped unit.
- Phase: 1 · Planned by: planner · Date: 2026-10-28 · Status: planned

## 1. What to build
Code base: EZD-250 as merged (this plan was written against its branch `t/EZD-250` at `46a3b15a`; line numbers below are from that commit, so find each edit by its quoted text). In `scripts/run.mjs` the launcher's main loop holds `next` (the `--next-unit` text) and, when EZD-250 D12 chooses a repair, `repair = { action, fp, kind, next }` with `unitName = 'repair'` and `arg = kind`. Four hold and limit texts still name `next`, which for a repair is the wait text (`none: …`), not the unit that ran (Q-0404):
- (a) budget hold before the unit: `applyGates({ … nextUnit: next … })` → `BUDGET_HOLD.md` line `- Next unit when released: <next>` (`scripts/budget.mjs` `writeHold`);
- (b) plan limit (weekly) during the unit: `writeHold({ … nextUnit: next })` and `notify(\`plan limit reached during ${next}. …\`)`;
- (c) five-hour limit during the unit: `log(\`five-hour limit; waiting until … then resuming ${next}\`)`;
- (d) per-unit cap during a repair: the repair branch makes the line `r.outcome` (raw `error:error_max_budget_usd`), which says neither which repair stopped nor why.
