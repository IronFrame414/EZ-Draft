## Approach

### Design in one paragraph
Two scheduled GitHub Actions workflows run on `main` only. Each uses secrets held in the GitHub environment `release` that only `main` may use and administrators cannot bypass, the same environment as EZD-023b's release workflow, and checks that rule before it reads any secret (Q-0106; Q-0112; Step 3). Until launch the environment holds no secrets and both runs end `not_configured` (Q-0113).
- **Nightly:** `pnpm backup:files` copies every Storage object whose `storage.objects.updated_at` is newer than the last successful run, minus an overlap, into `files/<bucket>/<name>` in the off-site bucket. It skips copies that are already equal. It never deletes a stored version: an object deleted at the source gets a delete marker off-site, and the provider's lifecycle rule removes replaced or deleted versions 90 days later (Q-0075).
- **Weekly:** `pnpm backup:db` runs `supabase db dump` three times and uploads the files plus a `manifest.json` to `db/<UTC timestamp>/`.

Before writing anything, each run refuses unless the off-site bucket has versioning **Enabled**. Each run is recorded in a new tenant-less table, `backup_run`, which EZD-135 reads.

`pnpm backup:restore` takes the newest complete dump and builds a scratch local Supabase (a second CLI stack on its own ports) from the repo's migrations up to the dump's migration version. It loads `data.sql`, uploads the copied files, and checks that the named projects, their files and the migration version are back.

A trigger on `storage.objects` makes sent-package files impossible to delete, move or overwrite. A "delete" of one is therefore a soft delete on its owning row.

### Step 2: Sent-package files are soft deletes (migration `<ts>_sent_files_soft_delete.sql`; builder)
- **Path rule.** This extends EZD-000's layout; *planner's choice of the segment name*. Sent-package files live in bucket `exports` at `<tenant_id>/<project_id>/sent/<sent_package_id>/<file>`.
  - EZD-000 already puts "sent-package files soft-deleted" in `exports`.
  - Sent versions are permanent (11 Data retention; R24 #4a).
- **Trigger.** `private.refuse_sent_file_change()` (`language plpgsql`, `set search_path = ''`, no execute grant to any API role). It is attached as trigger `sent_files_soft_delete`, `before delete or update on storage.objects for each row`. It raises `sent_file_change_refused` (SQLSTATE `P0001`) when the **old** row has `bucket_id = 'exports'` and `name ~ '^[^/]+/[^/]+/sent/'`, and either:
  - the operation is DELETE; or
  - the operation is UPDATE and `bucket_id`, `name` or the object's version column changes (a move or an overwrite removes the sent bytes). The version column is whichever the pinned Storage schema uses for the stored object version, else `metadata->>'eTag'` *(builder confirms)*.
  
  Other updates pass. Inserts are never refused.
- **Soft-delete contract** (recorded in docs; *planner's choice*): the ticket that creates `sent_package` (03 Tables) puts the "delete" on the owning row (for example `deleted_at`, `deleted_by`) and hides it from lists. The Storage object stays, and so does its off-site copy.
- **Applies to everyone**, including the secret key, because Storage API calls end in SQL on `storage.objects`. EZD-124's Delete is offered only before any send, so normal use never hits the trigger.
- *(builder confirms)*: a migration run by the pinned CLI may create a trigger on `storage.objects`. If the local stack refuses it, the builder stops and raises a question. There is no silent fallback (Risks).

- **`config.mjs`**: `loadBackupConfig(env)` reads these names (*planner's choice of names*):

  - `loadBackupConfig(env, { kind })` requires the names of that workflow's exact list (Step 3): 8 for `files`, 6 for `db` (no `BACKUP_SOURCE_SUPABASE_URL` / `BACKUP_SOURCE_SECRET_KEY`); the restore needs the `files` set. Result: `not_configured` / `env_missing` (Step 3).

- **`environment.mjs`**: `checkBackupEnvironment(processEnv, github)`: in GitHub Actions, `environment_unprotected` unless `evaluateEnvironmentRule(await github.environmentBranchRule('release'))` passes (Step 3); `github` is EZD-023b's `createGitHubApi` with `GITHUB_TOKEN`, injected so tests use a fake.
- **`s3-store.mjs`**: `createS3Store(cfg)` over `@aws-sdk/client-s3`.
  - Methods: `versioningStatus()`, `objectLockStatus()` (`GetObjectLockConfiguration` → `{ enabled, mode, days }`), `head(key)`, `putFile(key, path, { contentType, meta })`, `getToFile(key, path, { versionId? })`, `list(prefix)`, `listVersions(prefix)` (versions and delete markers, paged), and `hide(key)`.
  - `hide(key)` sends `DeleteObject` **without** a `VersionId`. On a versioned bucket that adds a delete marker (Backblaze calls it hiding the file) and removes no bytes (Q-0075: "replaced or deleted file versions kept 90 days"). It is the only `DeleteObjectCommand` in `scripts/backup/`.
  - There is **no method that deletes a version**: no `DeleteObject` with a `VersionId`, no `DeleteObjects`. Only the provider's lifecycle rules (Step 7) remove versions. A static test enforces this (T4).
  - Client settings: `forcePathStyle: true`, and checksum calculation "when required" for S3-compatible providers *(builder confirms the option name for the pinned SDK)*.
  - The provider is **Backblaze B2** through its S3-compatible API (Q-0074 (a)): `BACKUP_S3_ENDPOINT` = the bucket's S3 endpoint (`https://s3.<region>.backblazeb2.com`) and `BACKUP_S3_REGION` = that region *(builder confirms the endpoint form, B2's answer to `GetBucketVersioning`, and that a key without `deleteFiles` may add a delete marker; if adding a marker needs `deleteFiles`, the builder raises a question instead of widening the key)*.
- **`source.mjs`**: a `postgres` (postgres.js) client to the source database (`max: 2`), plus supabase-js Storage with the secret key.
  - `listChangedObjects({ since, buckets, pageSize: 500 })` pages through `storage.objects` (`bucket_id`, `name`, `updated_at`, `metadata->>'size'`, `metadata->>'eTag'`, `metadata->>'mimetype'`). The order is `updated_at, id`, using a keyset, never OFFSET.
  - `listAllObjectKeys({ buckets, pageSize: 500 })`: every current `bucket_id`, `name` pair in scope, keyset by `(bucket_id, name)`, for the delete-marker pass.
  - `download(bucket, name, toPath)`.
  - `newestMigration()` = `select max(version) from supabase_migrations.schema_migrations`.
  - `startRun(kind, scope)` / `finishRun(id, fields)` on `backup_run`.
  - `lastSucceeded(kind, scope)`.
- **`files.mjs`**: `runFileBackup({ full?, onlyBuckets?, overlapSeconds = 3600, concurrency = 4 }, deps)`. Steps:
  1. `store.versioningStatus()` must be `Enabled`. Otherwise record a failed run, `versioning_off` (ticket "object versioning on"), and stop before any PUT. Then `store.objectLockStatus()` must be enabled with default retention mode `GOVERNANCE` and at least **91** days (Q-0111); otherwise record a failed run, **`object_lock_off`**, and stop before any PUT (*planner's choice* to check it at run time, so a bucket set up without the lock is noticed; *builder confirms* B2 answers `GetObjectLockConfiguration` through the S3 API for a key with `readBucketRetentions`; if it does not, the builder raises a question).
  2. `startRun('files', scope)`.
  3. `since` = null when `full` or there is no earlier success. Otherwise it is the last succeeded `files_cursor` minus `overlapSeconds` (*planner's choice*: an upload committed late with an older `updated_at` is still seen).
  4. For each changed object (`updated_at > since`, limited to `onlyBuckets` if given):
     - **Skip** when `head('files/<bucket>/<name>')` has metadata `source-etag` equal to the eTag **and** `ContentLength` equal to the size.
     - **Otherwise copy:** download to a temporary file, SHA-256 it, then `putFile` with `contentType` = mimetype and meta `{ 'source-etag', 'source-updated-at', sha256 }`.
     - A copy that changes bytes creates a new version off-site (versioning).
  5. **Delete-marker pass** (Q-0075; *planner's choice* of how deletes reach the off-site copy): after every copy in step 4 succeeded, list the source keys in scope (`listAllObjectKeys`) and the off-site current keys under `files/<bucket>/` for the same buckets (`list`). Each off-site key with no source object gets `hide(key)`.
     - **Guard:** when the source lists 0 objects in scope while off-site has at least 1 current key there, nothing is hidden and the run fails with `source_empty` (a wrong or empty source must never mark a whole backup deleted).
     - A hidden copy keeps its bytes as a noncurrent version for 90 days (Step 7 lifecycle rule), so a restore within that time still finds it (Step 5 `pickRestoreVersions`).
     - Objects in a source bucket that was removed entirely are hidden too (no source keys for that bucket), unless the whole scope is empty (guard).
  6. Finish `succeeded`, with `files_cursor` = the largest `updated_at` seen (or the previous cursor if nothing was seen), plus the counts, `objects_hidden` and bytes.
  7. Any error finishes `failed` with a code (`source_unavailable`, `download_failed`, `upload_failed`, `versioning_off`, `source_empty`, `hide_failed`) and the counts so far. The next run re-checks from the last success; equal copies are skipped.
  8. The temporary files are removed in `finally`.
  9. The CLI prints one JSON line `{ ok, kind: 'files', code?, copied, skipped, hidden, bytes }` and exits 0 only if `ok` (or `not_configured`).
- **`dump.mjs`**: `dumpDatabase({ dbUrl | local, outDir })` makes three `supabase db dump` runs: `roles.sql` (`--role-only`), `schema.sql`, `data.sql` (`--data-only --use-copy`). These are the same files and flags as EZD-023b Step 6 step 13 *(builder confirms flags)*. EZD-023b's merged `scripts/release/dump.mjs` exports `dumpDatabase` with this signature, so the builder imports it instead of writing a second one (no behaviour change). The weekly dumps therefore also leave out the data of `auth.sessions`, `auth.refresh_tokens`, `auth.one_time_tokens` and `auth.flow_state`, and fail with `dump_failed` if `roles.sql` holds a password (Q-0112 finding 11; vault/plans/EZD-023b.md Step 6 step 13). A restore signs everyone out, which is expected.
- **`db.mjs`**: `runDbDump({ now }, deps)`. Steps:
  1. Versioning and Object Lock preflight, as files.
  2. `startRun('db_dump', 'all')`.
  3. Dump into a temporary folder. Any run that fails or file that is 0 bytes → `dump_failed`.
  4. `newestMigration()`.
  5. prefix = `db/<now as yyyyMMdd'T'HHmmss'Z'>/`.
  6. Upload `roles.sql`, `schema.sql`, `data.sql`, then **last** `manifest.json` = `{ format: 1, created_at, source_ref, newest_migration, files: [{ name, size, sha256 }] }`. `source_ref` comes from `supabaseRefFromDbUrl` (EZD-023b), or `local`.
  7. Finish `succeeded`, with `location` = prefix and `bytes_copied` = the sum of the three sizes.
  8. The temporary folder is removed in `finally`.
  9. The CLI prints `{ ok, kind: 'db_dump', code?, location?, bytes }`.
- **Off-site key layout** (*planner's choice*): `files/<bucket_id>/<object name>` and `db/<ts>/{roles.sql, schema.sql, data.sql, manifest.json}`. A dump folder without `manifest.json` is incomplete and is never restored. The two prefixes carry different lifecycle rules (Q-0075; Step 7): `files/` keeps replaced or deleted versions 90 days; `db/` keeps each dump 13 weeks.
- **Root `package.json`** (extend): scripts `backup:files` (`node scripts/backup/files.mjs`), `backup:db` (`node scripts/backup/db.mjs`), `backup:restore` (`node scripts/backup/restore.mjs`). None of `typecheck`, `lint`, `test` or `build` runs them.
- **Dependencies** (CLAUDE.md rule 11; EZD-000 C1):
  - `@aws-sdk/client-s3`: the row already exists, added by EZD-023b for its release dumps (vault/plans/EZD-023b.md Step 11), `root`, same version. No new row; the builder only confirms the `Why` cell names the backups too.
  - Add `root` to the `Used in` of `postgres` (EZD-006) and `@supabase/supabase-js` (EZD-004), at the same versions.

### Step 5: Scratch stack (`scripts/backup/scratch.mjs` + `scripts/backup/scratch/supabase/config.toml`; builder)
- **`config.toml`** (*planner's choice*):
  - `project_id = "ezdraft-restore"`;
  - ports: API `55321`, DB `55322`, shadow `55320`, pooler `55329`, so it does not clash with EZD-004's 54321–54329;
  - `[db.seed] enabled = false`;
  - disabled: `[studio]`, `[inbucket]` (or the mail catcher key of the pinned CLI), `[realtime]`, `[analytics]`, `[edge_runtime]`;
  - `[db] major_version` the same as `supabase/config.toml`.
  
  The stack needs Postgres, Auth, Storage and the API gateway only (Q-0019: memory).
- **`prepareWorkdir({ newestMigration })`**: a temporary folder with a copy of `config.toml` and of every `supabase/migrations/*.sql` whose 14-digit prefix is ≤ the dump's `newest_migration`. If that version is missing from the repo, or the repo's newest migration is older, it refuses with `repo_older_than_dump`. Released migrations are never edited (EZD-023a), so the copied files equal what the source ran.
- **`startScratch(workdir)`**:
  1. `supabase stop --workdir <w> --no-backup` (ignore failure), so a leftover volume is never reused.
  2. `supabase start --workdir <w>`, excluding the services above *(builder confirms flag and service names)*. A fresh start applies the copied migrations, so the schema, policies and triggers (Step 2's included) and `supabase_migrations` come from the repo, not from the dump.
  3. Returns `{ apiUrl, dbUrl, secretKey, dbContainer }` from `supabase status --workdir <w> -o json`.
- **`loadData(scratch, dataSqlPath)`**: runs `docker exec -i <dbContainer> psql -v ON_ERROR_STOP=1 --single-transaction -U <superuser> -d postgres`. stdin is:
  1. `SET session_replication_role = replica;`
  2. `TRUNCATE <every table named by a COPY/INSERT line in data.sql> CASCADE;`
  3. `data.sql`.
  
  psql handles pg_dump's meta-commands. The user is the local superuser of the pinned stack *(builder confirms)*. Rows that migrations inserted are replaced by the dump's rows. With the replica role, triggers do not fire during the load.
- **`uploadFiles(scratch, store, tmp)`**:
  1. `alter table storage.objects disable trigger sent_files_soft_delete` (in the scratch database only).
  2. Pick one version per key under `files/` with `pickRestoreVersions(listVersions('files/'))` (pure; *planner's choice*): the current version when the newest entry is a version; when the newest entry is a delete marker (the file was deleted at the source, Step 4), the newest version before it, which the 90-day rule still keeps (Q-0075); keys with no version left are skipped. For each pick: create its bucket if missing (private), download that version, then upload it through scratch Storage with `upsert: true` and the stored content type. So a project deleted in the app, and hidden off-site by a later nightly run, still comes back within 90 days.
  3. Re-enable the trigger in `finally`.
  
  The overwrite is needed: the restored `storage.objects` rows point at file versions that only the upload creates *(builder confirms Storage's upsert behaviour)*.
- **`stopScratch(workdir)`**: `supabase stop --workdir <w> --no-backup`.

### Step 6: Restore script (`scripts/backup/restore.mjs`; builder)
- CLI: `pnpm backup:restore [--project <uuid>]… [--dump <prefix> | --from-dir <dir>] [--keep] [--record] [--local] [--env-file <absolute path outside the repo>]`.
- **Guards** (`scripts/backup/local-guards.mjs`, built here; the same three guards the earlier EZD-023b plan had, which it no longer builds under Q-0106), in this order:
  1. `agent_refused` when `CLAUDECODE` is set *(builder confirms Claude Code sets it for agent commands)*;
  2. `ci_refused` when `CI` or `GITHUB_ACTIONS` is set (`scripts/gate.mjs` sets `CI=1`);
  3. `tty_required` when stdin or stdout is not a terminal.
  
  4. `env_file_not_absolute` when the `--env-file` value is not an absolute path;
  5. `env_file_in_repo` when that path (resolved, with symbolic links followed where the file exists) is inside the repository root (Q-0112: "restore key file outside the repo").

  They run **only when `--env-file` is given**, before the file is read. That is how Josh's real keys come in, from a file **outside the repo**, for example `C:\Users\JSBis\ezdraft-secrets\restore.env`, which holds the **restore** key (list and read only) and the source values (*planner's choice of example path*; Josh may pick another folder outside the repo). Outside the repo, no agent tool that works in the repo reads it by accident, and no `git add` can commit it. Josh also adds a Read deny for that folder in his own Claude user settings (Step 7 runbook). `scripts/backup/local-env.mjs` parses it with Node's `util.parseEnv` *(builder confirms on Node 22)* and passes values only to the run, never into `process.env`; output goes through `redactUrl` and `safeLines` (EZD-023b). Without `--env-file`, every value comes from the process env, which in tests points to the stub bucket and the local stack.
- **`runRestore(opts, deps)` order:**
  1. `usage`: a `--project` value that is not a UUID.
  2. Find the dump:
     - `--from-dir`: read the folder. With `manifest.json`, use it. With EZD-023b's `release.json` and no manifest, `newest_migration` = the largest 14-digit prefix in `git ls-tree -r --name-only <release.tag> supabase/migrations`.
     - `--dump <prefix>`: that folder, under `db/` (weekly dumps) or `releases/` (EZD-023b's pre-release dumps, which carry the same `manifest.json`).
     - Otherwise `pickLatestDump(keys)`: the greatest `db/<ts>/` that has `manifest.json`.
     - None → `no_dump`.
  3. Download the dump files to a temporary folder. The SHA-256 of each must equal the manifest (`dump_corrupt`; `release.json`'s `sha256` entries when restoring a release folder that has no manifest).
  4. `prepareWorkdir` (`repo_older_than_dump`).
  5. `startScratch`, `loadData`, `uploadFiles` (skipped for `--from-dir`, which has no files).
  6. **Checks**, each a problem code in the summary:
     - `migrations_mismatch`: scratch `max(version)` ≠ `newest_migration`.
     - `trigger_disabled`: `sent_files_soft_delete` is not enabled.
     - For each `--project P`:
       - `project_missing`: no `public.project` row with id P;
       - `file_missing`: a scratch `storage.objects` row whose name starts `<tenant_id>/<P>/` cannot be downloaded;
       - `file_mismatch`: its SHA-256 differs from the off-site copy's `sha256` metadata.
     - Also counted, not failing: `files_restored`, and `orphan_rows`, which is rows with no off-site copy. A file uploaded after the last nightly copy can be one of these.
  7. Print one JSON line: `{ ok, code?, dump, newest_migration, projects_found, files_restored, files_checked, orphan_rows, problems: [{ code, ref }] }`. With `--keep`, it also prints `scratch: { apiUrl, dbUrl, workdir }`. It never prints keys or passwords.
  8. `--record`: insert one `backup_run` row (`kind 'restore_drill'`, `status` succeeded or failed, `location` = the dump prefix, `error` = the first problem code) in the **source** database (`BACKUP_SOURCE_DB_URL`, or the local stack with `--local`).
  9. `finally`: `stopScratch` unless `--keep`, and remove the temporary folders.
- Exit 0 only when `ok` (no problems).

  Any surprise stops the builder with a question, not a looser test.
- **Auth and Storage versions.** `data.sql` from the cloud is loaded into the pinned local stack. If the cloud's Auth or Storage tables have columns the pinned stack lacks, the load fails. The drill exists to find that; the fix is a CLI bump (EZD-004 row).
- **Gate time and memory.** T1 starts a second Supabase stack beside the gate's own (Q-0019: 16 GB). It runs in Phase 0 ticket checks, phase gates and CI only (Step 8 guard). CI's job limit is 30 minutes for the whole gate (ci.yml, Josh's file). If T1 pushes it over, only Josh can raise it.
- **Ticket size.** Two migrations, eight script modules, two workflows, a stub server and 18 tests (Q-0075 added the delete-marker pass, T4's new cases and T18). This is comparable to EZD-009 and EZD-023b, so it is planned as one session. If it overruns, the natural split is EZD-025a (`backup_run`, the soft-delete trigger, the backup scripts and workflows: T2–T5, T9–T12, T16) and EZD-025b (scratch stack, restore, runbook: T1, T6–T8, T13–T15, T18). This plan does not propose that split.
- **Scheduled workflows can stop silently.**
  - GitHub disables them after 60 days without repository activity, and runs can be delayed at busy times.
  - The System status page (EZD-135) showing the last backup is the spec's place to notice this (11 Operations).
  - EZD-135's planner may want an age warning.
- **First runs before setup (Q-0113).** Workflows exist only on `main` after the Phase 0 merge, and the source exists only once Josh creates `ezdraft-prod` from the Before-launch checklist. Until then runs end `not_configured` (green), every night, possibly for many phases. A partly configured setup fails loudly: because the `release` environment is shared (Step 3), the release's secrets may be set before the backup-only ones; the backup runs then end `env_missing` (red) until Josh adds the rest, which is the intended loud failure.
- **Object Lock cannot be undone early.** With Governance mode and no `bypassGovernance` key, nobody (Josh included) can delete a backup copy before its 91 days end; a client's deletion request reaches the backups only when the lock and the lifecycle rule expire (Q-0111, accepted by Josh). The restore drill's own test data also stays 91 days.
- **The backup key can write anywhere in the bucket, including `releases/`.** B2 keys take one name prefix, and the backup key needs both `files/` and `db/`. It cannot delete versions, and Object Lock keeps every release dump version 91 days, so the worst it can do is add a newer version or a delete marker; the original versions stay readable by version id for at least 91 days. The restore reads the newest versions, so a consistent rewrite of a release folder would not be detected; this is accepted as low risk because the key lives only in the main-only `release` environment.
- **Restore file path rules on Windows.** `env_file_in_repo` compares resolved paths; the builder handles drive-letter case and `\` vs `/` *(builder confirms with Node's `path.win32`)*.
- **Point in time.** Files are copied nightly and the database weekly, so a restore can bring back files newer than the dump (`orphan_rows` counts the reverse case). Supabase Pro's daily backups (7 days) remain the first line for database loss (11 Data retention).
- **Off-site copies outlive app deletes, for a bounded time.** That is the point of the drill. Under Q-0075 a deleted project's files stay off-site for 90 days after the next nightly run marks them deleted, and its rows stay in each weekly dump for 13 weeks. A restore older than that cannot bring them back.
- **Backblaze specifics** *(builder confirms against B2's docs before Josh's first run)*: B2's answer to `GetBucketVersioning` (a B2 bucket keeps all versions by default; if B2 does not answer `Enabled`, the preflight accepts B2's equivalent and the builder raises a question with the exact answer); whether a key without `deleteFiles` may add a delete marker through the S3 API; the lifecycle field names; the S3 endpoint form.
- **Drill timing and markers.** The drill (runbook step 3) deletes the project and restores right away, before any nightly run hides the files, so it tests current versions. T4 and T18 cover the hidden-file path with the stub.
