| Plain words | The perf step of develop's CI gate failed on `long-tasks-during-pan:ipad fail 1 0` (one counted long task, budget 0) in runs 43188731323 (develop 22c51838) and 43205322837 (develop 812218ce), with EZD-372's fix (d186042f) and EZD-388's `ipad-cpu` profile (64734653) merged (ticket row, `vault/tickets/phases/phase-02.md:78`). The two runs' `perf-results/latest.json` (fetched for Q-0752 (a) into `test-results/d398/<run>/latest.json`) settle the cause: in both, the one counted task has `cpu` null, and its `misses` evidence shows the task's own top-level trace slice starting 0.1 ms and 0.5 ms before it, 48.7 ms and 50.0 ms long, with only 2.2 ms and 2.1 ms of CPU time (section 2, E-1, E-2). So it is cause (2) of the design step: a perf tool defect in matching, not app work and not a missing `tdur`. `countByCpu` (`scripts/perf/trace-tasks.mjs:109-140`, EZD-388) matches an observed task only to a slice of over 50,000 µs (`trace-tasks.mjs:123`). That is the filter from before EZD-372. EZD-372's D-Match rule (a slice that starts within 3 ms and lasts over 50 ms or at least `ms` − 3 ms) went only into `attributeTasks` (`trace-tasks.mjs:68`). EZD-388's plan was written against the old code (`vault/plans/EZD-388.md` D-Count step 6). `docs/architecture.md` (Performance check (EZD-017), Long tasks (G5)) already states the D-Match rule for every pan row. The fix puts that one rule inside the shared `matchTop`, so both counters use it and cannot drift again. Each CI task then becomes a wait (2.2 × 4 = 8.8 ms of CPU, under the 50 ms line), which is what Q-0737 (a) says it is. Budget 0, the 50 ms line, the rate 4, the 3 ms window and the row stay; no retry (ticket Scope; Q-0073 (a); CLAUDE.md rule 16). Proof: 5 new unit tests (R1-R5, R5 on the two CI tasks' own numbers, red on develop), 5 counting lane gates in a row with another lane busy, then the row passing in the develop CI gate job (AC-EZD-398-1; Q-0748 (b)). One fix does not cover EZD-393: EZD-393's failure is a wait that is listed, against `pan.test.mjs` T1's `details.waits` deep-equal `[]` (`vault/plans/EZD-393.md` Brief); this row fails because a task is counted. |
