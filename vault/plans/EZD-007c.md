### Findings against the parent text (planner, 2026-10-19)
- **C1 Sync signature and a cookie jar.** Dependents call `createSessionClient()` synchronously (`vault/plans/EZD-026b.md` line 67 `createSessionClient().from('app_user')…`; `EZD-009.md` line 148 `enqueueJob(createSessionClient(), …)`; `EZD-018.md` line 96). Next.js 16's `cookies()` and `headers()` are async, so the client stays synchronous and reads them inside the `@supabase/ssr` cookie callbacks, which may be async *(confirm on `@supabase/ssr` 0.12.7: `getAll` and `setAll` may return a Promise)*. EZD-007d's request gate (`proxy.ts`, P-Step 4) builds its client "on the request and response cookies"; for AC-1 ("only through `createSessionClient()`") it passes its own jar to the same function instead of building a second client. So `createSessionClient(jar?)` takes an optional `SessionCookieJar` (section 3); without one it uses `next/headers` (*planner's choice*, CLAUDE.md rule 3). Tests use the same jar to sign in without a browser.
- **C2 Cookie options.** P-Step 3 fixes `httpOnly: true`, `sameSite: 'lax'`, `path: '/'`, `maxAge` `34560000` (Q-0048 (a), 400 days) and `secure` on `https`. The options are applied per cookie in the jar's `set`, keeping the `maxAge` `@supabase/ssr` passes (it sends `maxAge: 0` to delete a cookie at sign-out *(confirm on pinned version)*), so a removal is never turned into a 400-day cookie. "The request is `https`" is read from the first value of the request's `x-forwarded-proto` header (Vercel sets it; *confirm `next start` sets it on the pinned Next.js*). P-T13 (part d) checks the headers in a real sign-in; T35 here checks the jar.
- **C3 Writing cookies from a Server Component.** Next.js refuses `cookies().set` outside a Server Action or Route Handler. The default jar's `set` catches that error and drops the write: the token refresh is written by EZD-007d's request gate before the page renders (P-Step 4), and a Server Action or Route Handler writes normally (the `@supabase/ssr` Next.js pattern; *planner's choice*). The security-reviewer confirms.
- **C4 Error code for a missing secret.** `serverGateSecret()` throws `Error('api_gate_secret_not_set')`, a stable code in the style of `email_transport_not_set` (docs/architecture.md Environment variables, `EMAIL_TRANSPORT` row), and never the Zod error, so the value can never appear in a message or a log (CLAUDE.md rule 8). *Planner's choice.*
- **C5 `local.mjs env` with no secret file.** The file is written by `local.mjs up` (EZD-006; `scripts/db/local.mjs` lines 53–62). If it is missing or blank, `env` exits 1 with a stderr line naming `pnpm db:up` and prints no JSON, so a web server never starts with a missing secret and silently signs everyone out. Refuse rule, so it gets a test (L-012): T33. *Planner's choice.*
- **C6 Vitest global setup unchanged.** `app/test-harness/supabase-env.global-setup.ts` copies only the three names in its `NAMES` from `local.mjs env` and then sets its own per-run `SUPABASE_API_GATE_SECRET` (lines 11–15, 51), so the fourth key `env` now prints does not replace the per-run secret. No edit (parent V10).
- **C7 What counts as "reaching Supabase".** Today two non-test files under `app/src/` import `@supabase/*`: `app/src/server/db/client.ts` (`createPublicDbClient()`, anon, used only by `health.ts` for `rpc/health`, the one anon call the gate allows, docs/architecture.md API request gate). After this ticket the allowed set is exactly those two files plus `app/src/server/auth/supabase-server.ts`; T34 checks it. A later ticket that needs another Supabase client (for example EZD-009's job handlers with the secret key) edits T34's list in its own commit with a reason, and the security-reviewer approves it (the `TENANTLESS_TABLES` pattern, docs/architecture.md Row-level security).
