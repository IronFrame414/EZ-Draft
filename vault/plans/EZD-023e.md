- **G. Tag, then go live** (archived step 16).
  1. **Notice `previous_deployment_unknown`** (non-blocking): when `previousTag` (part b's `previousReleaseTag(tags, tag)`, Step 4 step 8) is not null and part c's `previousDeploymentId` is null, add the notice and its summary line (section 6).   2. Unless part b's `resume` is true: `await github.createTag(tag, sha, 'Release ' + tag + ' (#' + prNumber + ')')` (archived step 16; vault/plans/EZD-023b.md Step 3 `createTag`). - **H. Verify** (archived step 17; Q-0032 (a): EZD-003's subdomain check runs inside every release).
  1. `expected` = the largest 14-digit prefix among the names that `git(['ls-tree', '--name-only', sha, 'supabase/migrations/'])` lists and that match `^\d{14}_[a-z0-9_]+\.sql$` (check C5's pattern), or `null` when there is none. Read from the commit, so it works on `alreadyLive` runs too, where part d made no worktree (*planner's choice*).
  2. **Health loop.** `start = now()`; loop: `res = await fetch(HEALTH_URL, { method: 'GET', signal: AbortSignal.timeout(HEALTH_REQUEST_TIMEOUT_MS) })`; it passes when `res.status === 200` and `(await res.json()).schema_version === expected` (the route's 200 body is `{ status, schema_version }`, `route.ts` line 10). A rejected `fetch` or `json()` counts as not passing. Not passing: if `now() − start >= VERIFY_LIMIT_MS`, health has failed; else `await sleep(VERIFY_INTERVAL_MS)` and loop. With a fake clock the polls happen at 0, 5, …, 120 s: 25 polls (same loop shape as part c's build wait, vault/plans/EZD-023c.md Step 4 step 9.3). Log `health ok` or `health not ok after <n> tries`.
  3. Only when health passed: `live = await checkLive()`; it passes when `live.ok === true`. A throw counts as failed. On failure log `live check failed: <ids of the results with pass false, joined by ', '>` (ids only; `evaluate` returns `{ ok, results: [{ id, pass, detail }] }` with the 8 ids `dns`, `tls`, `status`, `host`, `vercel`, `title`, `hsts`, `redirect`, finding V7).
  4. Either failing gives **`verify_failed`**. Then **automatic rollback** (11 Operations: "Rollback is Vercel's previous deployment"; Q-0106):

If it resolves, `rolledBack = true`, then poll health for status `200` alone (any `schema_version`: the old build reads the newer database, archived Step 7 step 4) with the same interval and limit, and log `rollback health ok` or `rollback health not ok`. If the promote throws, `rolledBack = false` and the summary uses the "rollback failed" line (section 6).
     - otherwise (first release, or an `alreadyLive` run): nothing is promoted, `rolledBack = false` (archived step 17: "With no `previous` … nothing is rolled back").
     - The database is never rolled back (archived Step 7 step 3; R26 R12).

> How production changes. Merging a pull request into `main` starts Actions → **Release** (`.github/workflows/release.yml`). It saves a copy of the production database to Backblaze under `releases/`, applies the migrations, sets up Worth Properties and your owner account on the first release, tags the commit (`phase-N` or `phase-N.k`), makes that commit's own build live and checks the site. If anything fails before the build goes live, the live site does not change. If the checks after going live fail, it puts the previous build back. Agents never see the production secrets; they live only in the GitHub environment `release`.
>
> ### Until launch
> - Merging into `main` releases nothing. Actions → **Release** ends green with the summary `production not configured — nothing released`, because `release` holds no secrets yet.
> - Phase field checks use the Vercel preview of the phase pull request.
>

> **Auto-assign Custom Production Domains** has been off since the Vercel setup (Vercel and the subdomain, step 2: Settings, Environments, Production, Branch Tracking). Never turn it back on. > ### Rollback
> 1. **Automatic.** When the checks after going live fail, the release puts the previous build back. The run is red, and the summary says `verify_failed` and that the previous build was put back.
> 2. **By hand** (a problem found later). In Vercel → **Deployments**, open the previous production deployment (its commit carries the previous `phase-…` tag) and use **Instant Rollback**.
> 3. **Leave the database alone.** Never revert, edit or delete a migration. The previous build works with the current database, because migrations add before they remove.
> 4. **Check.** Run `node scripts/hosting/check-live.mjs`. `/api/health` still shows the newer `schema_version`; that is expected.
> 5. **Fix forward.** Fix on `develop`, open a pull request to `main` and merge it; the release names it `phase-N.k`.
> 6. **If data was damaged, stop.** Never load a dump into production by hand. The run summary names the dump taken before the release (`releases/<tag>-<time>/`); the restore steps are in the backups section (EZD-025).
>
> ### Dumps
> In B2 under `releases/`, one folder per release run. They hold client data. Object Lock keeps them at least 91 days, and the lifecycle rule deletes them after 13 weeks (set with the backups, EZD-025).
