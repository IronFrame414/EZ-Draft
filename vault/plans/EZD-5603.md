# EZD-5603 · Assistant panel, states and photo (split proposal)

- **ACs:** AC-EZD-5603-1 … AC-EZD-5603-14 (`vault/spec/acceptance-criteria.md:1839-1852`, stage-0). Each AC goes to one part below. AC-10, AC-12, AC-13 and AC-14 are split by clause (see the AC map). AC-10's Accept, Adjust and Reject clause is mapped to EZD-5604, whose plan adds the three buttons to its `expectTouchTargets` test (Q-0651 (a); note for TRACE and the AC map).
- **Complexity:** high (both parts); reasons per part
- **Areas:** ui, testing, security, api, dependencies
- **User-visible result:** An Assistant button on the plan's rail opens a panel where the inspector sits. Josh types a prompt, picks Sonnet or Opus, and reads a plain-text reply with what it cost and the session total. With no key, a bad key or no credit, the panel says so plainly and links to My profile. The prompt is never lost. A photo (JPG, PNG, HEIC or WebP, up to 20 MB) can go with one prompt. It is shrunk in the browser and stripped of location data on the server before Anthropic sees it.
- Phase: 56 · Planned by: planner · Date: 2026-11-09 · Status: split proposal

## Split proposal

**Why.** Planned whole, the ticket would touch about 28 files and need about 36 tests. That is over the size rule (PROCESS.md section 6 "Ticket size": about 20 files or 25 tests; Josh 2026-10-22). Where the count comes from:
- **14 stage-0 ACs, five of them compound.** AC-12 has five clauses and AC-14 has four.
- **A new screen region.** The panel goes in the inspector's place (Q-0474; board S03c aside 336 px, `S03cAIAssistant.dc.html:150`). It has:
  - a header, the conversation, the prompt box, the model picker and the cost line;
  - three key states: No key, key refused and out of credit (boards S03cAIAssistantNoKey and S03cAIAssistantKeyError; Q-0638 gaps 13 and 6);
  - the waiting state, the network and provider failure lines (Q-0637 wording row; 3a);
  - My profile mounted over the editor (Q-0638 gap 12);
  - the outbox drain before each prompt (Q-0638 gap 9; Q-0640 row 56-7; Q-0641 row 56-7);
  - the selection sent with a prompt (Q-0640 row 56-2);
  - history caps (Q-0638 gaps 7 and 9).
- **A rail change.** `RailTool.shortcut` is required today (`app/src/components/shell/rail-types.ts:10`), but the Assistant's tooltip on the board has no key (`S03cAIAssistant.png`). `ToolRail` also has a single `activeId` (`ToolRail.tsx:7-19`), but the Assistant is pressed while a drawing tool stays active.
- **A photo pipeline across browser and server.** In the browser:
  - the type and size checks (A4, A5);
  - a shrink to JPEG (long edge at most 1,568 px, at most 3,500,000 bytes);
  - HEIC conversion, which needs a decoder that the boundary rules make a lazy module (ARCH Entry points and lazy modules: `HEAVY_PACKAGES`, `app/src/lazy/<name>/`).

  On the server:
  - the JPEG magic-byte check;
  - a `sharp` re-encode with `limitInputPixels` that strips EXIF GPS and XMP;
  - an image block in the provider call for that one prompt only (Q-0637 photo row; Q-0638 gap 7).

  Two new direct dependencies need lines in docs/architecture.md (CLAUDE.md rule 7). Q-0637 asks for two checks first: whether `sharp` runs on the host, and how iOS handles HEIC.

**Why cut here.**
- The photo is the only part that crosses into server code and new dependencies. It changes EZD-5602's body reader at one marked branch: P5602 D-Body, "a `photo` entry → `photo_not_supported` (EZD-5603 replaces this branch with its strip)". It also changes the provider request content (P5602 D-Request). Part a uses EZD-5602's route as planned and changes no server code. This keeps part a's security surface to the browser only.
- Part b needs part a's prompt box, send path and error mapping, so the order is a → b. EZD-5604 depends on the base number, so it waits for both parts (`vault/tickets/README.md`, "How tickets are written").
- Same pattern as EZD-213 and EZD-212: the screen first, then the piece with its own dependencies and checks.

Each part is planned as its own unit from its section here. Each part plan applies the planner lessons for ui, testing, security, api and dependencies, notably:
- L-021: grep the tests that pin the icon list (`app/src/components/shell/HeaderButton.icon.test.tsx`), the rail entries (`ToolRail.test.tsx`, `tool-defs.test.ts`) and the inspector region (`EmptyEditor.test.tsx`), and name each edit;
- L-052: the empty, over-limit and malformed cases for the prompt and the photo;
- L-054: checklist rows measured from the board HTML;
- L-060: every new button in `expectTouchTargets` (`app/test-harness/touch-targets.ts:8`);
- L-064: each fixture file named with its source, and each browser row with its Playwright project and command;
- L-061: the photo's byte bound, with boundary values.

  - **key state.** Read from `GET /api/profile` `aiKey: { last4 } | null` (P5601 section 3) when the panel opens, and again when My profile closes (Q-0638 gap 12). The part plan proposes the loading and read-failure lines under 3a.
  - **No key state.** Board S03cAIAssistantNoKey: the heading line, the body line, and "Open My profile" with `arrow_forward`. The prompt box and send are disabled (Q-0638 gap 13). Drawing by hand is unchanged (S03c States).

    - An empty conversation shows only the prompt box (Q-0638 gap 13).
    - The user's prompt shows as a bubble.
    - A reply renders as plain text, with no links, images or markup (Q-0637; AC-9).
    - A text-only reply has no buttons (Q-0638 gap 13).

    - The session total covers this editor page load and is held in memory only (Q-0638 gap 13; 00f glossary "Session (Assistant)": this plan names its code name).

  - **model picker.** "Model · pick per prompt"; "Claude Sonnet 5.5 · about 2¢ a prompt" first, then "Claude Opus 5.5 · about 4¢ a prompt". The button shows "Sonnet 5.5" or "Opus 5.5", and its accessible name is "Model" (S03c wording; Q-0474; Q-0638 gap 13). The values are `'sonnet'` and `'opus'` (`ASSISTANT_MODELS`, P5602 step 5). After a send the picker keeps the last pick for the rest of this editor page load; each page load starts on Sonnet 5.5 (Q-0653 (a); Q-0474).
  - **send.** The request is `POST /api/projects/[id]/assistant`, multipart with one field `request` holding a JSON `AssistantInput` (`{ prompt, history, model, floorId, selectedIds }`, P5602 section 3 and step 11). The steps:
    1. Drain the outbox (`OutboxSync.flush()`, `app/src/lib/outbox/outbox-sync.ts:51`) before every prompt.
    2. If the drain fails, make no request. The prompt stays, and the normal save message shows (Q-0638 gap 9; Q-0640 row 56-7; Q-0641 row 56-7).
    3. Read the selected ids from EZD-208's selection (Q-0640 rows 56-2 and 56-8).
    4. While waiting, send is disabled and a waiting line shows (Q-0638 gap 13; wording under 3a).
    5. When the tab closes or the panel unmounts, abort the request (Q-0637 call path).

    The send control is named "Send" (Q-0638 gap 13). The prompt is capped at 8,000 characters (P5602 D-Body).
  - **history.**
    - It holds only completed user and reply pairs, because the server needs alternating turns of even length (P5602 D-Body).
    - Each turn is cut to 2,000 characters.
    - Past 20 turns, the oldest pair is dropped (Q-0638 gaps 7 and 9).
    - History is text only.
  - **errors.** Each `error.code` from the route maps to a line (P5602 D-Map and section 6 keys):

    - `assistant_no_key` shows the No key state.

  - **touch.** Send, the model picker and its options, × and Open My profile each have a tap target of at least 44 px with no keyboard (Q-0630 standing rule; S03d E; L-060).

### Part EZD-5603b · Assistant photo: control, browser shrink, server strip
- **Scope:**
  - **control.**
    - "Photo" with the board's `add_photo_alternate` icon. Its screen-reader name is "Attach a photo" (A1; AC-11).
    - It accepts JPG, PNG, HEIC and WebP up to 20 MB, one photo per prompt (S03dSelectedObjects-wording.md approved rules). 20 MB is 20,000,000 bytes (decimal): 20,000,000 is accepted and 20,000,001 shows A5 (Q-0652 (b); Q-0512, Q-0637, S03dSelectedObjects-wording.md:32).
    - A wrong type shows A4 and a larger file shows A5, in the board's error box (board S03cAIAssistantPhoto states).
    - The attached photo shows as a thumbnail with its file name and size. Its × is labelled "Remove photo" (A2), with a 44 px hit area around the 22 px circle (`S03cAIAssistantPhoto.dc.html:194`; L-060).
    - A3 shows under the prompt (AC-6). The sent prompt's bubble shows the photo above it, from memory only (board, line 180).
  - **browser shrink.** Decode the photo, with HEIC through a decoder in a new lazy module. Draw it to a canvas with a long edge of at most 1,568 px. Encode it as JPEG, lowering quality until it is at most 3,500,000 bytes. A photo that cannot be decoded is refused with nothing sent (Q-0637 photo row; AC-7). Q-0637 asks for iOS Safari's HEIC behaviour to be checked first.
  - **request.** Add a binary `photo` part to the multipart body. The whole body must be at most 4,000,000 bytes, and a test runs at that maximum (Q-0638 gap 7; AC-13). The photo goes only with its prompt. Later prompts' history is text only (AC-8).
  - **server strip.** This replaces P5602 D-Body's `photo_not_supported` branch.
    - Take at most 4,000,000 bytes, JPEG only by its magic bytes.
    - Re-encode with `sharp` and `limitInputPixels`, with no metadata carried over.
    - On any failure, refuse with a code and a line under 3a and make no provider call (Q-0637 photo row).
    - The base64 image block appears only in the provider request (Q-0638 gap 7; P5602 D-Request content).
    - The bytes stay in function memory. They are never written to storage, a job, a log, Sentry or the console (Q-0637; AC-8).
  - **dependencies.** `sharp` becomes a direct dependency of `app`; it is in the lockfile today only through Next (`pnpm-lock.yaml:4038`, 0.35.5). Add the HEIC decoder. Each gets a docs/architecture.md line (Adding a dependency; CLAUDE.md rule 7). The decoder goes in `HEAVY_PACKAGES` with its lazy folder (ARCH Entry points and lazy modules). Q-0637 asks for `sharp` on the host to be checked first.
  - **the photo stays.** It stays in the box after a 429, 5xx or timeout, and after a failed drain (Q-0638 gap 13; Q-0640 row 56-7).
  - **touch.** Photo and Remove photo pass the 44 px check (AC-10).
- **Tests (about 14) and files (about 12):**
  - Unit tests of the browser checks:
    - each accepted type;
    - `.gif`, `.pdf`, `.svg` and an empty file;
    - 20,000,000 bytes accepted and 20,000,001 bytes showing A5 (Q-0652 (b)).
  - Shrink tests: a 4032 × 3024 JPEG comes out with a long edge of 1,568 and at most 3,500,000 bytes; a HEIC fixture is converted.
  - Server-strip tests:
    - a JPEG fixture carrying EXIF GPS and XMP reaches the stub with neither, read back with `sharp(...).metadata()`;
    - a PNG sent as `photo`, 4,000,001 bytes and corrupt JPEG data are each refused with no provider call.
  - Body tests: exactly 4,000,000 bytes with the largest photo succeeds; the second prompt's stub request has no image block; no storage upload, job row, Sentry event or console output carries the photo bytes or a canary in them.
  - Component tests: A1 to A5, and the photo stays after a 429.
  - Touch targets.
  - Files: the photo control and the prepare module in `app/src/editor/assistant/`, the lazy HEIC folder, `server/assistant/photo.ts`, P5602's `assistant.ts` body branch and request content, `AI/providers/anthropic.ts` content type, `eslint-rules/boundaries.mjs`, `app/package.json`, `docs/architecture.md`, catalogs, fixtures (a GPS and XMP JPEG built in the test with `sharp().withExif()` and `withXmp()`, and a committed HEIC sample with its source), and the tests.
- **Done when:**
  - The Photo control is named "Attach a photo". It takes JPG, PNG, HEIC and WebP up to 20 MB, one per prompt. A wrong type shows A4, a larger file shows A5, × reads "Remove photo", and A3 shows under the prompt.
  - The browser sends a JPEG with a long edge of at most 1,568 px and at most 3,500,000 bytes, and HEIC is converted.
  - A photo with EXIF GPS and XMP reaches the stub with neither. A failed strip refuses with no provider call.
  - A 4,000,000-byte body with the largest photo succeeds.
  - The photo is not in the next prompt's request, and it is never stored or logged.
  - The photo stays after a 429, 5xx, timeout or failed drain.
  - Photo and Remove photo pass the 44 px check.
- **ACs:** AC-EZD-5603-6, -7, -8, -11; AC-10 (Photo, Remove photo); AC-12 (photo stays after 429, 5xx, timeout); AC-13 (4,000,000-byte multipart body); AC-14 (photo stays when the drain fails).
- **Depends on:** EZD-5603a. EZD-5602 is missing from the derived row as a direct dependency: this part edits P5602's body branch and provider request content (P5602 steps 6-8 and 11). EZD-016a is done.
- **The part plan settles:** the HEIC decoder package, its licence and whether it runs in a Web Worker; how iOS Safari handles HEIC; and whether `sharp` runs on the host. These are the "checked first" items in Q-0637, looked up through `retriever-web` with a REPORT at that plan. It also settles the server refusal code and its 3a line.
- **Complexity:** high. It adds image decoding in two runtimes, two new dependencies, a security-sensitive strip and a body-size limit (PROCESS.md section 4). Test-author Opus 5.5 (binary fixtures and byte-exact bounds); builder Opus 5.5.
- **security-review: yes.** It touches the API (multipart body and the route's photo branch), data access (photo metadata off the device; nothing stored) and dependencies (`sharp`, the HEIC decoder). **Reviewers:** code-reviewer · calc-auditor no · ui-verifier yes · security-reviewer yes.
