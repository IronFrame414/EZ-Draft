# EZD-395 · Fix: an ended session can get a 500 and an alert instead of 401 when its token refresh fails

- **ACs:** AC-EZD-395-1, AC-EZD-395-2 (`vault/spec/acceptance-criteria.md:1051-1052`, done-when)
- **Complexity:** high (section 8)
- **Areas:** auth, security, api, testing
- **User-visible result:** When someone's sign-in runs out at the wrong moment while Auth cannot refresh it, the app answers "not signed in" (and pages go to the sign-in screen) instead of a server error, and Josh gets no false error-alert email.

- **Library confirmation (design step, 2026-11-12, installed files under `node_modules/.pnpm/`; versions `app/package.json:29-31`, auth-js `package.json` 2.118.0).** The finding holds:
  1. `@supabase/supabase-js` 2.118.0 `dist/index.mjs:290-303`: `fetchWithAuth` calls `getAccessToken()` on every REST request and sends `Bearer <supabaseKey>` when it returns no token; `:829-840`: `_getSessionToken` reads `auth.getSession()` and `_getAccessToken` falls back to `supabaseKey` (the publishable key, `supabase-server.ts:48-50`).
  2. `@supabase/ssr` 0.12.7 `dist/main/createServerClient.js:38`: the server client runs with `autoRefreshToken: false`, so no refresh happens at client start; refreshes happen only inside `getSession`.
  3. `@supabase/auth-js` 2.118.0 `dist/main/GoTrueClient.js:2540-2547`: inside 90 s of expiry (`EXPIRY_MARGIN_MS` = 3 × 30,000 ms, `dist/main/lib/constants.js:6,9,13`) `__loadSession` refreshes; `:2548-2573`: on a failed refresh it returns the stored session only while `stored.expires_at * 1000 > Date.now()`, else `session: null`. `:4211-4216`, `:4296-4331`: a failure is cached for 60 s (`REFRESH_FAILURE_COOLDOWN_MS`, `constants.js:21`) and a non-retryable failure keeps the stored session while the token is still valid. `:4021-4046`: a retryable failure (Auth outage) is retried, then returns the same error, so the storage check above decides in both cases.
  4. `getClaims` (`GoTrueClient.js:5515-5532`) reads the session through `getSession` and rejects an expired token (`helpers.js:454-461`).
  So when the refresh fails and the real expiry passes between `getClaims`' session read (`session.ts:19`) and the RPC's session read (`session.ts:22`), the RPC goes out with the publishable key; `current_app_user_id` is executable by `authenticated` only, so it fails 42501 and `session.ts:23` throws.
- **Design result (how the ended-session 42501 is told apart, Brief).** The RPC goes out without the user's token only when auth-js finds the stored session past `expires_at` (point 3). `expires_at` is the token's `exp`: GoTrue sends `expires_at` with every session, and auth-js computes it only when the field is missing (`dist/main/lib/fetch.js:145-152`). So "42501 and `claims.exp * 1000 <= Date.now()`" is the same test auth-js applies, read from the token `getClaims` verified, and it needs no extra request. A 42501 for a live token (a broken grant) still throws, 500 and alerts (rule 18, D3 (a)). Rejected options: (a) map every 42501 to `null`, as `loadPermissionContext` does (`app/src/server/permissions/context.ts:26-28`): a broken grant would then answer 401 to everyone and never alert; (b) send the RPC with the verified token in an explicit `Authorization` header (`postgrest-js` 2.118.0 `setHeader`): the anon fallback goes away, but the expired-JWT answer becomes a PostgREST code not pinned in any source, and a test could not make the local PostgREST see an expired token without waiting 3600 s (Q-0052 (c), `jwt_expiry`); (c) a second `auth.getSession()` after the 42501: one more Auth call, and a refresh that succeeds in between would turn an ended-session call into a 500 and an alert.
- Test method (for the code-bound step): a new Vitest file under `app/src/server/auth/` against the local stack, as `app/src/server/auth/session.test.ts:1-127` does (next/headers mock, sign-in by `generateLink` + `verifyOtp`).
