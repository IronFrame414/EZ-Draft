Diagnosis (design step):
- D1. The failing side is the throttled one, and page B's 5th `evaluate` is the last task before `stopTrace` (`profiles.test.mjs:182-186`). The plain side, asserted first at `:195`, passed in the same run (phase-4-release.md:61: the message names `throttled`). So the null mark is most likely the throttled side's last run, the task still running or just closing when `Tracing.end` flushes. On a loaded 4-vCPU runner whose main thread is throttled at rate 4, that flush can scrape the chunk and drop the slice end (R-063). The slice then has no `X` with a `dur` holding the mark, and `markTaskCpu` gives `null` by its contract (EZD-392 section 3). This is the ticket's second cause: the trace lacks the task's CPU time, not a `markTaskCpu` miss.
- D2. The fix for D1: wait for the marked tasks to close before the trace stops. One unmarked `evaluate` per page after the loop is enough. A page's main thread runs tasks one at a time, so the fence's task starts only after the last marked task's slice has ended, and the fence's own events follow that slice end, so it is not the last fragment of the chunk (R-063). Page A is fenced too: its last marked task is followed only by page B's last run, on another process. The fence is unmarked, so neither `markTaskCpu` call reads it, and it is untimed, so it changes no measured value (D5).
- D3. Reproduce-first: no unit can run N5 outside the gate, because Chromium cannot start in the unit sandbox (KNOWN-LIMITS, unit sandbox hole (1)). A failure under local load has never been seen: the 13 worktree `gate.log` files show `ok 5 - EZD-207c N5 throttle slows the page` and none holds `a marked task has no CPU time` (grep, 2026-11-12), and EZD-392 met its AC with 10 counting lane gates in a row under load. The CI artifact would not settle the cause either: `gate.log` keeps N5's assert message, not the trace (Q-0749 (b): a unit cannot fetch it anyway). So instead of a pre-fix reproduction run that would almost surely pass and tell nothing, N5's failure message carries the evidence (D4). Any later failure on a lane or on CI then names its cause. This corrects the Brief's "reproduce first" for this ticket; Q-0750 set that step for EZD-420, whose failure could be run locally.
- D4. The evidence comes from a new pure helper in `scripts/perf/trace-tasks.mjs`, beside `markTaskCpu`, and copies `describeMisses` (EZD-372 D-Miss, `trace-tasks.mjs:148`). For each mark of the name whose `markTaskCpu` value is `null` it gives `{ run, open, held }`: the mark's place in `ts` order; whether the mark's thread has a top-level slice that starts at or before the mark and never closes; and whether a top-level `X` with a numeric `tdur` on that thread holds the mark. The export is `describeMarkMisses(events, name)` and the message format is D-Msg (section 1, Decided for the builder; section 3).
