# EZD-256 · Fix: only one gate at a time takes over a dead lock

- **ACs:** AC-EZD-256-1, AC-EZD-256-2
- **Complexity:** high (section 8)
- **User-visible result:** when a gate or a lane sweep left a lock behind and two gates start at the same moment, only one of them runs (or sweeps); the other refuses as it does today when a gate is running.
- Phase: 1 · Planned by: planner · Date: 2026-10-28 · Status: planned

## 1. What to build

Data: none (no tables, no migrations). Tooling ticket (EZD-253 mark): no file under `app/`, `packages/`, `worker/` or `supabase/`.

The fault: ticket Scope below (Q-0408 QP-1; EZD-172 section 10 QP-1), in `takeLock` and `takeSweepLock`. The fix: the only unlink of a lock a gate does not own happens while that gate holds the lock's take-over folder, after it reads the lock again and still finds the same dead text. The take-over folder is put in place by `renameSync` of a filled folder onto `<lock>.takeover`; the kernel lets that rename through only while the target is missing or empty (POSIX rename(2); probed by the planner on this Mac, Node 22.23.3: onto an empty folder succeeds, onto a non-empty one `ENOTEMPTY`, onto a file or a symlink (also one to an empty folder) `ENOTDIR`; `rmSync(<symlink>, { recursive: true, force: true })` removes the link and leaves its target). The holder file inside has a unique name (`<pid>-<uuid>`), so a dead holder's file is removed by its exact name and that never removes a live holder's file.

Starts after EZD-172 (with round 8, Q-0408 (a)) is on develop; edit by function name (line numbers are from `t/EZD-172` 4f88fc59).
