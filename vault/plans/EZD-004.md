### Step 2: First migration: the health row
`supabase/migrations/<YYYYMMDDHHMMSS>_create_health_function.sql`, created with `pnpm supabase migration new create_health_function` (EZD-000 Migrations; C5).

The ticket says "the app reads a health row" but names no table. A new table would have to carry `tenant_id` and pass EZD-006's "table has no policy / lacks tenant index" CI test (03 intro "Every table carries tenant_id"; 11 Operations), which a health table cannot sensibly do. So *planner's choice*: **no new table**. The row comes from a function that reads the migration history the CLI already keeps:

```sql
create function public.health()
returns table (status text, schema_version text)
language sql stable security definer set search_path = ''
as $$
  select 'ok'::text, max(version)::text from supabase_migrations.schema_migrations
$$;
revoke all on function public.health() from public;
grant execute on function public.health() to anon, authenticated;
```

- `schema_version` is the 14-digit timestamp of the newest applied migration, so the row proves both "the app reaches the database" and "the migrations applied".
- `security definer` with an empty `search_path` lets the function read `supabase_migrations.schema_migrations` without granting that table to `anon`. Returned data is the literal `ok` and a migration timestamp; no tenant data.
- `supabase_migrations` exists before the first migration runs on both `supabase db reset` (local) and `supabase db push` (cloud), so the SQL body validates at creation.

### Step 3: Local database for the gate and CI
`scripts/db/local.mjs` (builder; Node 22 built-ins only, no new dependency). Subcommands:
- `up`:
  1. `supabase status`; if the stack is not running, `supabase start`.
  2. `supabase db reset --local`, which drops the local database and applies every migration, then `seed.sql`. Every gate run therefore proves the migrations apply from scratch (ticket Done when).
  3. If the CLI fails and its output mentions Docker, print `Local Supabase needs Docker running (start Docker Desktop).` to stderr; exit 1 on any failure.
- `env`: reads `supabase status -o json` and prints one JSON object with exactly the three app variable names of Step 5 mapped to the local values (URL = the API URL; publishable key = the CLI's publishable key, or its anon key if the pinned CLI prints no publishable key; secret key = its secret key, or service-role key). These are the CLI's published local defaults, not secrets (CLAUDE.md rule 12 concerns real keys).

Root `package.json` (extended, not replaced; EZD-000 Step 1):
- New scripts: `db:up` (`node scripts/db/local.mjs up`), `db:env` (`node scripts/db/local.mjs env`), `db:reset` (`supabase db reset --local`), `db:stop` (`supabase stop`), `db:types` (`node scripts/db/gen-types.mjs`).
- `test` becomes `pnpm run db:up && ` followed by the existing `test` command unchanged: EZD-000's `node --test "scripts/**/*.test.mjs"` (with EZD-001's `--test-concurrency=2` between `--test` and the glob, vault/plans/EZD-001.md Step 3), then the fan-out.

This is how "migrations run in CI" is met without touching Josh's files:
- `scripts/gate.mjs` runs `test` (gate.mjs `required`), and `.github/workflows/ci.yml` runs the gate on `ubuntu-latest`, whose runners have Docker running. So the phase PR's CI run starts the local Supabase, applies every migration and runs the health tests, with no ci.yml edit and no new workflow.
- Locally, the same gate run does the same against Docker Desktop.
- Worktrees: every checkout uses `project_id = "ezdraft"`, so a worktree reuses the containers already running and `db reset` applies that worktree's migrations. This is safe because one ticket runs at a time (PROCESS.md Limits; Q-0019).
- The local database is for agents and tests (11 Operations "local (agents and tests)"); each gate run wipes it. Documented in Step 7.

### Step 6: The app reads the health row
- `app/package.json`: add `@supabase/supabase-js` and `zod` at the EZD-000 Dependencies versions. If EZD-000's builder recorded a different `@supabase/*` package and no `@supabase/supabase-js` row, add the row (`Added by` = `EZD-004`).
- `app/src/server/db/client.ts`: `createPublicDbClient()` returns a supabase-js client typed with `Database` from `database.types.ts`, built from `env.ts` values, with `auth: { persistSession: false, autoRefreshToken: false }`. Server-only by location (`src/server/`, EZD-000 Folder layout); EZD-133 adds the lint rule that keeps it out of browser code.
- `app/src/server/db/health.ts`: `readHealth(): Promise<{ status: 'ok'; schema_version: string | null }>` calls `rpc('health')` and returns its single row; throws on any error or on a row whose status is not `ok`.
- `app/src/app/api/health/route.ts`: `GET` with `export const dynamic = 'force-dynamic'`.
  - Success: `200` with body `{ "status": "ok", "schema_version": "<14 digits>" }`.
  - Any failure (missing env, network error, missing function): `500` with body `{ "error": { "code": "db_unavailable", "message_key": "error.db_unavailable" } }` (shape and status from EZD-000 Errors and logging; code and key are planner's choice).
  - Both responses carry `Cache-Control: no-store`, so Vercel never serves a cached health result.
  - The route is public and has no `can()` check: it reads no tenant data and uses only the publishable key, never the secret key (EZD-000 Server-only data access). Security-reviewer confirms. It writes no log line, because `logger.ts` does not exist yet and C8 forbids `console.` (EZD-000 C8).

### Step 7: Cloud dev workflow and runbook (cloud part waits for Josh)
- `.github/workflows/supabase-dev.yml` (new; the builder may add workflows, guard-paths.mjs).     on:
      push:
        branches: [develop]
        paths: ['supabase/migrations/**']

## Risks
- **Docker is not running yet.** Docker Desktop is installed but its daemon was off at plan time, and `docker` is not on the agent shell's PATH. From this ticket on, every gate run (and so every later ticket) fails at `db:up` until Docker Desktop runs; SETUP.md asks Josh to turn on "Start Docker Desktop when you sign in". The CLI talks to the daemon directly, so the PATH alone should not matter; the builder confirms.
- **Gate time and memory.** The first `supabase start` pulls several images, and every gate run adds a `db reset` (tens of seconds). Analytics and the edge runtime are off to save memory on the 16 GB PC (Q-0019). CI pulls the images on each phase PR, inside the 30-minute job limit.
- **pnpm build-script approval.** If the `supabase` postinstall is not allowed, the CLI binary is missing and T10 fails both locally and in CI. The exact setting depends on the pinned pnpm major.
- **Migration history is part of the health row.** A database restored from a dump without the `supabase_migrations` schema (EZD-025's restore drill) would return `schema_version: null`. EZD-025's planner should know that.
- **CLI-version specifics.** The status JSON key names (publishable vs anon key; Inbucket vs Mailpit), `-o json` output and the default Postgres major depend on the pinned CLI. The test-author and builder read them from the pinned CLI, not from memory.
- **Bundle size.** `@supabase/supabase-js` is imported only under `app/src/server/` here. EZD-018 brings it into the browser for Realtime, which counts against the 200 KB budgets (11 Budgets); EZD-017 measures it.
- **Shared Supabase organization (Q-0003; Q-0024 (a)).** EZ Draft's projects sit in the same organization as EZ Binder's. Anyone with access to that organization can reach both, which is why the workflow uses a dev-only connection string and not an account access token (Step 5); the security-reviewer checks this. The cloud steps wait only on Josh doing them; the local part of the ticket (everything the gate checks) does not wait.

- **An agent's push now changes the cloud dev database (Q-0107, accepted by Josh).** The orchestrator's `develop` push applies any new migration to `ezdraft-dev` without a separate click. A migration that passes the local gate but fails on the cloud project turns the workflow red; previews then run against the older dev schema until a fix is pushed. A migration edited after it reached the dev database (EZD-023a freezes only released migrations, M2) is not re-applied by `db push`, so dev can drift from the files; the fix is a new migration, not an edit.

- **The `dev` environment must exist before the secret works.** If Josh puts `SUPABASE_DEV_DB_URL` into `dev` but the workflow runs before `dev` limits branches to `develop`, any branch could use it; the runbook orders "lock first, then the secret" (Step 7 item 4). If the secret is missing, the workflow keeps its green "not set" notice.
