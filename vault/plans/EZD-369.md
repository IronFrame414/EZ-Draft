# EZD-369 · Fix: three strikes, then a full assessment before a unit runs again

- **ACs:** AC-EZD-369-1 (T1-T5), AC-EZD-369-2 (T6-T9), AC-EZD-369-3 (T10)
- **Complexity:** medium
- **Areas:** tooling, testing, security
- **User-visible result:** no unit runs a fourth time after three failed attempts until an assessment has found and fixed every cause; gate-phase 4 ran 19 times before this.
- Phase: 1 · Planned by: orchestrator (session 13) · Date: 2026-11-10 · Status: ready

## 1. What to build
Josh 2026-11-10 chat: "After something fails 3 times, it should be stripped down and fully assessed to be sure it will pass on the 4th attempt ... find and implement a permanent solution."

Today the launcher's no-progress guard counts runs in a row (`scripts/run.mjs:1036`, `guardAfterUnit` in the lane path) and sets a unit aside after two. Any edit of `.git/set-aside.json`, or setting a ticket back to `ready`, starts the count over. A build that ends `blocked` counts as progress. So gate-phase 4 ran 19 times, and EZD-212a, 366 and 367 bounced between `ready` and `blocked`. A strike ledger that never resets on a release, plus a hold that only a committed assessment lifts, ends that whole class.

| Choice | Decision | Source |
| --- | --- | --- |
| D-Key | Key = the unit text the launcher ran (`<unit> <arg>`: `gate-phase 4`, `build EZD-212a`, `questions 5`); counted per key, never across keys | Q-0129 loop (questions 5/56 alternated) |
| D-Strike | `strikeVerdict` returns `'strike'` when `outcome !== 'ok'`, or `progress` is false, or `unit === 'build'` and `statusAfter === 'blocked'` | the 2026-11-10 bounces |
| D-Reset | `'reset'` when `outcome === 'ok'`, `progress` is true, and either (a) `unit === 'build'` and `statusAfter === 'done'`, (b) `unit === 'gate-phase'` and `gateRecord` is true (the phase's `vault/tickets/gates/phase-NN.md` exists), or (c) `unit` is any other kind (`plan`, `questions`, `review-plans`, `wrap`, `repair`). Otherwise `'none'` (for example a build that made progress and is still in flight) | D-Strike |
| D-Exempt | `export function strikeExempt({ outcome, note })` is true for the outcomes `limit-five-hour`, `limit-weekly`, `interrupted` (the launcher's own restart or stop) and `dry-run`, and for any outcome whose note matches `/hit your (weekly|five-hour|5-hour) limit/i` (the 2026-11-09 weekly-limit runs ended `error:success` with that note). The launcher calls `recordStrike` only when it is false: those stops are not the unit's fault | the 2026-11-09 weekly-limit loop; run.mjs outcomes |
| D-File | `.git/unit-strikes.json` in the main checkout (beside set-aside.json): `{ "<key>": { "count": n, "history": [{ "at": ISO, "outcome": s, "note": first 200 chars }] } }`, written atomically; `'reset'` deletes the key; a missing or unreadable file means no strikes | `setAsideUnits` |
| D-Hold | `strikeHolds()` = keys with `count >= STRIKE_LIMIT` whose assessment `vault/handoff/assessments/<slug>.md` (slug = key with spaces → `-`, lower-case) is missing, or lacks a line `Verdict: ready`, or whose line `Covers strikes: <m>` has `m < count`. A ready assessment that covers the count lifts the hold; the next strike (count + 1 > m) holds it again | Josh: "fully assessed ... on the 4th attempt" |
| D-Assess | The assessment (overwatch or an interactive session): every attempt in the key's history and its report; each distinct cause; the fix of each with its commit; evidence per cause from a cheap targeted check (the failing test files with `node --test`, the failing e2e specs alone, the ledger check on a vault copy with untracked files, `record-develop` clean, the lane ports free, `LAUNCHER_FIX.md` absent, the phase's tickets `done`/`blocked` for a gate); then `Covers strikes: <count>` and `Verdict: ready` (or `Verdict: not ready` with what is left). Committed by path before the hold lifts (an untracked vault file fails the ledger check) | Josh 2026-11-10 |
| D-Pre | gate-phase step 0, each a short command: ledger check on a vault copy with untracked files; `node scripts/unit-steps.mjs record-develop` shows nothing unrecorded; `vault/handoff/LAUNCHER_FIX.md` absent; every product ticket of the phase `done` or `blocked`; no ticket of the phase `in-progress`/`review`; when `vault/handoff/assessments/gate-phase-N.md` exists, every cause it lists is fixed. Any red → fix it or stop with the handoff naming it; never start the 30-minute gate on a known red. A red full gate files every defect as step 5 says (one fix ticket per failing test), never only a handoff line (the 18:14 gate-phase 4 run, 2026-11-10, wrote only a handoff) | the 2026-11-09/10 gate-phase 4 attempts; code review re-check |
