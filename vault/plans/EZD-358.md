# EZD-358 · Fix: the EZD-207c E3 no-database test waits for the first draw before reading draw calls

- **ACs:** AC-EZD-358-1 (`vault/spec/acceptance-criteria.md` line 822)
- **Complexity:** low
- **Areas:** testing
- **User-visible result:** none in the app; the benchmark-page browser test stops failing at random at the merge gate, so merges are not held up by it.
- Phase: 4 · Planned by: planner · Date: 2026-11-06 · Status: planned

## 1. What to build
Cause (read from code on develop, section 2 C1–C4): **a wrong wait in the test, not an app fault.** `attachCanvas` sets `ready`, then `redraw()` only schedules a frame (`root.invalidate()`, frameloop `demand`). `PlanCanvas` sets `data-plan-state="ready"` when `attachCanvas` resolves, so Playwright can see "ready" before that frame has rendered. Until it renders, `stats().drawCalls` is three.js `gl.info.render.calls` = 0. E3 read the stats once right after "ready" and so lost the race once (ticket row). Fix: E3 waits until the stats report a draw, and that wait's result is what E3 asserts. No assertion is removed or weakened. A new negative test proves the wait fails when the plan never reports a draw.

No data, no migration, no app code.
