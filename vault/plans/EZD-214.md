# EZD-214 · Status and phase switch (split proposal)

- **ACs:** AC-EZD-214-1 … AC-EZD-214-9 (`vault/spec/acceptance-criteria.md:993-1001`, stage-0), shared out to the parts below (AC-1 split by clause; AC map)
- **Complexity:** high (both parts); reasons per part
- **Areas:** ui, data-model, migrations, testing, security, api
- **User-visible result:** The status bar's View control switches the plan between Existing and Proposed: the Existing view hides New work, the Proposed view hides Demo, and the project remembers the choice. A wall drawn in Proposed is New. A wall, door or window's Status can be set to Existing, Demo or New in the inspector, for one object or many at once.
- Phase: 6 · Planned by: planner · Date: 2026-11-09 · Status: split proposal

## Split proposal

**Why.** Planned whole, the ticket touches about 32 files and needs about 40 tests. That is over the size rule (PROCESS.md section 6 "Ticket size": about 20 files or 25 tests; Josh 2026-10-22). Where the count comes from:
- Data and API. `project.phase_default` exists as a plain nullable text column (`supabase/migrations/20261019165203_create_project.sql:18`). EZD-214 adds the check (existing or proposed), the default Existing and not null (03 Q-0664 row "View default"; AC-1). The column then has to be loaded with the model (`app/src/server/model/model.ts:329-332` selects only id, name, tenant_id, customer; `ModelLoad.project` in `app/src/lib/outbox/model-api.ts:14`). It also needs a write route checked on Edit model. No project update route exists (`app/src/app/api/projects/` has GET/POST list, model, objects, checkpoints, sync-conflicts). The RLS policy `project_update` lets any member who can see the project update the row (`supabase/migrations/20261019170006_create_tenancy_policies.sql:45-50`), so the route is where Edit model is checked: security review.
- Display. The phase view and the three Phase eyes live in a device-session store (03 Q-0664: "eye toggles … belong to the device session … reset on reload"; Q-0667: a View switch resets the eyes). The canvas then leaves hidden statuses out of the drawing list (`app/src/editor/plan/batches.ts:74` `planDrawingList`), the wall hover index (`app/src/editor/plan/hover.ts:135`) and the pick index (`app/src/editor/selection/pick-index.ts:64`). The hover and pick indexes resync by changed ids, so a visibility change needs a full resync, the way a floor change already does (`hover.ts:147-158`). Then comes the status-bar View control (board S03Plan footer) and its browser tests.
- Status on objects. Every creation path hard-codes `status: 'existing'`: `createWallData` (`packages/geometry/src/walls/wall.ts:58`), `createOpeningData` (`packages/geometry/src/openings/opening.ts:38`) and new rooms in `reconcileRooms` (`packages/geometry/src/rooms/sync.ts:92`). Their editor callers are `wall-chain.ts:58`, `room-rect.ts:54`, `model-changes.ts:135` and the opening tool (EZD-211a/b). Each must take the view's status (S03 Status bar "View" row; 03 Q-0630 row 6 "Existing until EZD-214"; AC-1, AC-5).
- The inspector Status select for walls, doors and windows, with bulk Mixed and one undo step, built on P213a/P213b (05 Q-0664 row "Status on objects").
- The assistant's change format gains `set_status` (05 Q-0664 row "AI commands"; P5604a D-Schema, D-Prompt).

**Why cut here.**
- Part a is the view: data, route, store, canvas filter and the status-bar control. It needs no inspector and no tool change. Its browser tests seed New and Demo objects through the existing test hook `__ezdraftEditor.edit` (`app/src/editor/ProjectEditor.tsx:165-177`).
- Part b is the status on objects: creation paths, inspector, assistant. It reads part a's store through one function, so neither part guesses the other's names.
- Each part is under the size rule: part a about 17 files and 23 tests, part b about 16 files and 18 tests.
- Built a → b. Each part is planned as its own unit from its section here. Each part plan applies the planner lessons for its areas. For part a: L-009 (run the check-constraint SQL on the pinned stack), L-016 and L-023 (only if a function is added), L-049 (the edit to `app/src/server/db/tenancy.test.ts:196`, which writes `phase_default: 'x'` and is refused by the new check), L-052 (empty, malformed and over-limit bodies on the route; every caller of `ModelLoad`), L-060 (migration timestamp after the newest on develop at merge time; touch targets for the two View buttons), L-061, L-054 and L-064. For part b: L-021 (catalog lists pinned by tests), L-050, L-052 (every caller of the changed creation signatures, including `app/src/server/projects/template-objects.ts:40`, `packages/geometry/src/benchmark/benchmark.ts:91` and the three `test-utils/fixtures.ts`) and L-064.

### Part EZD-214a · Phase view and display
- **Scope:**
  - **Migration.** `project.phase_default`: existing nulls become `existing`; default `existing`; not null; check `phase_default in ('existing','proposed')`. `database.types.ts` is regenerated (03 Q-0664 "View default"; AC-1 "new projects start Existing"; 09m row 7). No object row is rewritten. Every stored object is already Existing (09-calc Q-0558; 03 Q-0630 row 6; the three creation paths above), so both views show it (AC-6; 09m row 1).
  - **Load.** The model route returns the project's `phaseDefault` with the model (`ModelLoad.project`). Every `ModelLoad` fixture and caller gets the new field.
  - **Write.** A route sets `phase_default` for one project. It runs only with Edit model on that project (03 Q-0664: "the toggle writes it (Edit model)"; `requirePermission` pattern in `app/src/app/api/projects/[id]/model/route.ts:28-30`). A body other than `existing` or `proposed` is refused. Another company's project reads as not found. The edit lock is not built yet: the editor gates edits on `viewer.canEdit` only (`ProjectEditor.tsx:280`). The part plan states that the lock ticket adds the lock check to this route. Behaviour when the write cannot reach the server: QP-3.
  - **Phase store** (device session, in `app/src/editor/`):
    - `view` (`existing` | `proposed`), starting from the loaded `phaseDefault`.
    - `eyes` (`existing`, `demo`, `new`, each on or off).
    - `setView(view)` resets the eyes to that view's defaults: Existing view → Existing and Demo on, New off; Proposed view → Existing and New on, Demo off (Q-0667; AC-9). For an editor it then writes `phase_default`. For a view-only user it writes nothing (AC-7; 05 Q-0664 "Views and permissions").
    - `setEye(status, on)` overrides the display until the next View switch or reload (AC-3; Q-0667).
    - `shown(status)` is the one test the canvas uses.
    - `newObjectStatus()` gives `existing` in the Existing view and `new` in the Proposed view. Part b reads it (S03 Status bar "View" row; AC-1).
    - Pure rules first, so 09m rows 1 to 7 are one table test.
  - **Canvas.** An object whose status is not shown is left out of the drawing list, wall hover and the pick index, for every object type through its `data.status`. Rooms carry status (Q-0570), and dimensions and text will (03 Q-0667), so a later type needs no change here (CLAUDE.md rule 18). A View or eye change rebuilds the drawing list once and resyncs both indexes in full. Pan and zoom stay as they are (11 rules 2 and 4). Whether a hidden opening still cuts its wall: QP-1. What else a hidden object is left out of (snapping, box select, Select all, a current selection): QP-4.
  - **Status bar.** The View control from board S03Plan: label `View`, a group with accessible name `Phase view` and two buttons `Existing` and `Proposed`. The active button is white with ink text. It goes in `StatusBar`'s `start` slot (`app/src/components/shell/StatusBar.tsx:9`). The slot is shared with EZD-219's Scale, Snap, Cursor and Zoom, which are not built here. The control shows for view-only users too and works as display only (05 Q-0664 "Views and permissions").
  - **Test hook.** The phase store is exposed on the dev test hook, so EZD-218's eyes and these browser tests drive `setEye`.
- **Tests (about 23) and files (about 17):**
  - migration and db tests: check, default, backfill, the `tenancy.test.ts` edit;
  - route tests: 401, 403 without Edit model, 404 for another company, 400 for a bad body, 200 writes;
  - the load returns `phaseDefault`;
  - phase-store table tests: 09m rows 1 to 7, AC-9 reset, override held until switch;
  - canvas filter tests: the drawing list without hidden statuses; one rebuild per View switch; hover and pick skip hidden objects;
  - control component tests: the active button, and view-only;
  - browser specs for Josh's Slice 6 step 1, display half, with a seeded New wall: Existing hides it and Proposed shows it; the choice survives a reload; a view-only user's switch writes nothing.
- **Done when:**
  - With a New wall and a Demo wall in the model, the Existing view hides the New wall and shows the Demo wall, and the Proposed view does the reverse (09m rows 2, 4).
  - Turning an eye on or off overrides the view until the next switch, and a switch resets the eyes (09m rows 5, 6; Q-0667).
  - An editor's View choice is saved on `project.phase_default` and survives a reload; a new project opens in Existing.
  - A view-only user's switch changes the display and saves nothing.
  - Objects stored before this phase show in both views.
- **ACs:** AC-EZD-214-1 (control, saved choice, new projects Existing), -2, -3, -6, -7, -9.
- **Depends on:** EZD-213a, EZD-213b, EZD-213c (ticket row; same phase order). **Missing from the row:**
  - EZD-208b: it wires the selection controller into `ProjectEditor.tsx`, which this part also changes, and owns box select and Select all (QP-4).
  - EZD-016a: browser harness, visual checklist.
  - Done already: EZD-005a (project table), EZD-120b, EZD-120c (load and store), EZD-012b (`StatusBar`), EZD-207a, EZD-207b (canvas, hover), EZD-208a (pick index), EZD-210b (drawing tools).
- **The part plan settles:** the route path and body; the store's file and exported names; the visual checklist from board S03Plan (`.ssg`, `.ssi`, `.ssion` in `vault/mockups/html/project/S03Plan.dc.html:42-44,164`); the answers to QP-1, QP-3 and QP-4.
- **Complexity:** high: a migration, a permission-checked write route, a store and a filter across three canvas indexes (PROCESS.md section 4). Test-author Sonnet 5.5, builder Opus 5.5.

### Part EZD-214b · Status on objects
- **Scope:**
  - **New objects take the view's status.** `createWallData` and `createOpeningData` take a status. New rooms made by `reconcileRooms` take a status, and `wallEditChanges` passes it on (`app/src/editor/tools/model-changes.ts:105-143`). Every editor creation path passes part a's `newObjectStatus()`: wall chain, room rectangle (four walls and the room), door and window tools, rooms made by an edit, and assistant adds. Sources: S03 Decisions "Existing/Proposed sets the default status for new objects"; 03 Q-0630 row 6; AC-1, AC-5. Paste and Duplicate keep the copied status (05 Q-0630 row 19). Template walls at Create stay Existing (new projects start Existing; `app/src/server/projects/template-objects.ts:40`). The part plan decides whether the status argument is required, so no caller can leave it out (CLAUDE.md rule 18).
  - **Inspector Status select.** The wall panel's read-only Status row (P213b `inspector-status`, "Status, read only") becomes a select: Existing, Demo, New, each with its board dot. Grey `#7a828e`, red `oklch(0.6 0.19 28)` and cobalt `oklch(0.55 0.17 262)` are the S03Plan Phase rows (`S03Plan.dc.html:82-84`). Door and window panels get the same row after Impact rating / Sill height. There is no header pill (05 Q-0664 "Status on objects"; Q-0633 G7).
  - **Status edits.** P213a's `InspectorEdit` gains a status field. Bulk edit shows Status as Mixed when the selected objects differ. One change over the selection is one `applyEdit`, so it is one undo step (AC-4; `app/src/editor/model/model-store.ts:73-78`). Each object's status is set on its own and there is no cascade to hosted openings (S03 Decisions "Demo is set per object"). A bearing wall may be set to Demo until EZD-215 adds the engineer block (EZD-215 row; 05 Q-0630 row 15 precedent). View-only users read Status as plain text (05 Q-0630 row 9).
  - **Saved.** The change goes through the existing save path and survives a reload (AC-5; 03a).
  - **Assistant.** P5604a's `assistantChangeSchema` gains `{ op: 'set_status', ref, status }` (05 Q-0664 "AI commands"; AC-8). `applyAssistantReply` lists it under `updated`, so P5604b previews it as an update. The `D-Prompt` sentence "Never write status, …" is rewritten to name `set_status`. `remove` stays the Delete key. P5604a test C2's "`status` on an update is refused" stays true.
- **Tests (about 18) and files (about 16):**
  - geometry tests for the status argument of each creation function;
  - tool tests: a wall chain and a room rectangle drawn in Proposed are New, room included; a door placed in Proposed is New;
  - inspector edit and view tests: single, bulk, Mixed, one undo step;
  - panel tests: wall, door and window rows, and view-only;
  - assistant schema and apply tests;
  - browser specs for Josh's Slice 6 step 1: draw a wall in Proposed, switch to Existing, the wall is New and hidden; a status set in the inspector survives a reload.
- **Done when:**
  - A wall drawn in Proposed is New and the Existing view hides it; one drawn in Existing is Existing.
  - A room made in Proposed is New.
  - Setting Status in the inspector on several selected objects changes them all in one undo step and survives a reload; differing statuses read Mixed.
  - An assistant `set_status` change previews as an update.

## 10. Open questions
- Q-0668 (was QP-1) (design): In the Existing view a New door in an Existing wall is hidden (09m row 2), and in the Proposed view a Demo door is hidden (09m row 4 by the same rule); undecided is whether the wall is then drawn whole where the hidden opening sits (a; the wall as it stands in that phase), or keeps an empty gap (b); recommended (a).
- Q-0669 (was QP-2) (design, scope): Room outlines come from every wall on the floor whatever its status (`packages/geometry/src/rooms/sync.ts`), and a room keeps the status it was made with, so in the Proposed view a Demo wall still divides two rooms and their labels; options: (a) one set of rooms for both views in v1, each room shown by its own status; (b) each view gets its own rooms (Existing from Existing and Demo walls, Proposed from Existing and New walls) as a new ticket that changes reconcile, room numbering and room areas; recommended (a) for EZD-214, with (b) put to Josh as scope.
- Q-0670 (was QP-3): When an editor switches the View offline, or the `phase_default` write fails, the display switches at once, but whether the choice is (a) kept on the device and sent when the app is back online, latest choice winning (S03 States "Offline: edits continue and save on the device"), (b) shown as failed with the existing "Changes not saved" banner and Retry, or (c) dropped, so the next open uses the stored value, is undecided; recommended (a).
- Q-0671 (was QP-4): Undecided is what a hidden object is still part of besides drawing, hover and click-picking (left out under S03 Hover "highlights the object that a click would select"): options (a) nothing: it is not box-selected, not taken by Select all ("visible, selectable layers", S03 Ctrl+A row), not snapped to while drawing or moving, and leaves the current selection when it becomes hidden; (b) as (a) but snapping still uses every wall on the floor; recommended (a).
