# EZD-363 · Fix: the disabled tool button rule in ToolRail.module.css keeps its hover inside the hover media query

- **ACs:** AC-EZD-363-1 (generated from the Done-when, `acs_source: done-when` in `vault/tickets/tickets.json`; not yet a row in `vault/spec/acceptance-criteria.md`): "The EZD-014b touch and hover CSS test passes and a disabled tool shows the same look on touch and mouse."
- **Complexity:** low
- **Areas:** ui, testing
- **User-visible result:** a greyed-out drawing tool (while the plan loads) looks the same on the iPad and with a mouse, and the phase 4 gate is green again.
- Phase: 4 · Planned by: planner · Date: 2026-11-09 · Status: planned

## 1. What to build
No data, no migration, no app logic. One selector in one CSS file changes; one earlier-ticket test string follows it (E1); two new tests (U1 unit, B1/B2 browser).

Root cause (verified in this session): `app/src/components/shell/ToolRail.module.css` lines 55–61 hold the rule `.tool:disabled, .tool:disabled:hover { background: transparent; color: var(--ez-slate-300); cursor: default; }` outside any `@media` block (added by EZD-210b, a34868ee). EZD-014b's `touch-css.test.ts` (f) requires every selector containing `:hover` to sit in `@media (hover: hover)` (except the pressed rule) and the rail's hover-media rules to be exactly `.slot:hover .tip` and `.tool:hover`. So the `:hover` half can neither stay outside nor move inside; it is removed. EZD-014b is phase 0, so the phase-4 ticket gate never ran that test; only the full gate did (lesson EZD-136 plan-gap).

### Decided for the builder
| Choice | Decision | Source |
| --- | --- | --- |
| Move `:disabled:hover` into `@media (hover: hover)` or remove it | Remove it. Moving it adds a third rule to the rail's hover-media list, which EZD-014b (f) pins to exactly `['.slot:hover .tip', '.tool:hover']` | `touch-css.test.ts` lines 147–162; ticket row ("keeping the hover rule list the test expects; do not edit or weaken the test") |
| What replaces it | `.tool[aria-pressed='true']:disabled` in the same rule. Specificity: `.tool:disabled` 0,2,0 equals `.tool:hover` 0,2,0 and comes later, so it wins over the hover background; `.tool[aria-pressed='true']:disabled` 0,3,0 equals `.tool[aria-pressed='true']:hover` 0,3,0 and comes later, so a disabled tool that is also the active tool keeps the disabled look when hovered, as the removed `.tool:disabled:hover` (0,3,0) made it. `@media` adds no specificity. Result: the disabled look is the same with and without hover for every state, so touch and mouse match | Done-when; W3C Selectors Level 4 §17 (specificity); CLAUDE.md rule 18 (close the class); EZD-210b contract "ToolRail `disabled?: boolean`: `true` → every button `disabled`" with any `activeId` (`vault/plans/EZD-210b.md` section 3) |
