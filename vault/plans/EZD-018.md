## Approach

Choices that no source makes are marked *planner's choice (CLAUDE.md rule 4)*. The code-reviewer and security-reviewer confirm them at plan review. Supabase details that depend on the pinned CLI and SDK versions (the `realtime.messages` column names, `realtime.topic()`, `realtime.send()`, the join-refusal status, how an expired token is reported) are read by the test-author and builder from the pinned versions, not from memory (same rule as EZD-006 and EZD-007 Risks).

### Design in one paragraph
Every channel is a Supabase Realtime **private** channel, so joining it runs row-level security on `realtime.messages`. Topics are `project:<project_id>` and `user:<app_user_id>` (*planner's choice*). A project topic may be received and tracked (presence) only when `private.can_see_project(<id>)` is true (ticket Scope; EZD-006 Step 3). A user topic may be received only by that user (`private.app_user_id()`). **No client may broadcast**: browsers only receive broadcasts and track presence. Every broadcast comes from the database through two `private` functions that later tickets call from triggers (job progress, lock changes, review count, notifications), so an event is pushed only after the change that caused it commits (*planner's choice*; reason: a member's browser cannot fake a "lock released" or "job done" event for others). The browser connects with `@supabase/realtime-js` directly, using an access token from a server route. One per-tab hub shares one channel per topic, reconnects on events (never on a timer), and calls each subscriber's refetch exactly once after every re-subscription. When the database ends a user's sessions (deactivation, removal, a narrowed scope; EZD-006 Step 4), it also pushes `session.ended` on that user's channel, and the hub drops every channel and sends the person to sign-in (Q-0052 (c)).

### Step 1: Topic helpers (migration `<ts>_create_realtime_topic_helpers.sql`; builder)
All in schema `private`, `language plpgsql` or `sql`, `stable`, `security definer`, `set search_path = ''`, owner `postgres`; `revoke all … from public`; execute granted to `authenticated` only (Realtime evaluates the policies as `authenticated` with the user's JWT claims).

| Function | Returns | Body |
| --- | --- | --- |
| `private.realtime_topic_id(topic text, kind text)` | uuid | If `topic` matches `^<kind>:[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$` (lower-case canonical UUID), the UUID; else null. Never raises on bad input |
| `private.realtime_can_receive(topic text)` | boolean | `project:` topic → `coalesce(private.can_see_project(<id>), false)`; `user:` topic → `<id> = private.app_user_id()`; any other topic → false |
| `private.realtime_can_track(topic text)` | boolean | `project:` topic → `coalesce(private.can_see_project(<id>), false)`; any other topic → false (no presence on user channels) |

- `can_see_project` checks the claim tenant and the listed projects live (EZD-006 Step 3), so a project added to a scoped user's list can be joined on the next join, without a sign-out (Q-0044 (b)).
- **Ended sessions.** `private.app_user_id()` and the tenant check inside `can_see_project` raise `42501` when the token's session no longer exists (EZD-006 Step 3). Inside Realtime's join check a raise means the join fails, which is the wanted result (EZD-006 Risks asked this planner to check it). T3 proves it on the local stack. If the pinned Realtime turns a raise into something other than a refused join, the builder catches the exception inside `realtime_can_receive` / `realtime_can_track` and returns false, and T3 stays unchanged.
- Postgres Changes are **not** used (EZD-006 Risks: "prefer Broadcast with `private.can_see_project`"). Broadcast and Presence only.

### Step 2: Realtime policies (migration `<ts>_create_realtime_message_policies.sql`; builder)
On `realtime.messages` (RLS is on in the Supabase-managed table; the builder confirms):
```sql
create policy realtime_messages_select on realtime.messages
  for select to authenticated
  using ( realtime.messages.extension in ('broadcast', 'presence')
          and (select private.realtime_can_receive((select realtime.topic()))) );

create policy realtime_messages_insert on realtime.messages
  for insert to authenticated
  with check ( realtime.messages.extension = 'presence'
               and (select private.realtime_can_track((select realtime.topic()))) );
```
- Select = may join and receive broadcast and presence. Insert = may track presence. No insert policy for `broadcast`, so a client's own broadcast is refused (Design paragraph).
- No policy for `anon`: a browser without a signed-in token cannot join any private channel.
- Helpers are wrapped in scalar subqueries, as EZD-006 Step 3 requires for table policies (run once per check).
- EZD-006's `auditRls` reads schemas `public` and `private` only, so it does not see these policies. T8 checks them instead.

### Step 3: Broadcast from the database (migration `<ts>_create_realtime_broadcast_functions.sql`; builder)
- `private.broadcast_project(p_project_id uuid, p_event text, p_payload jsonb) returns void` and `private.broadcast_user(p_app_user_id uuid, p_event text, p_payload jsonb) returns void`.
  - `volatile`, `security definer`, `set search_path = ''`, owner `postgres`.
  - Raise `22023` when `p_event` does not match `^[a-z][a-z_]*\.[a-z][a-z_]*$` (the same name format as EZD-022 Step 1, *planner's choice*) or an argument is null.
  - Body: `perform realtime.send(p_payload, p_event, 'project:' || p_project_id::text, true)` (user: `'user:' || p_app_user_id::text`). The last argument marks the message private. If the pinned Realtime has no `realtime.send`, the builder inserts the equivalent row into `realtime.messages` and records it in docs; T1, T4 and T9 do not change.
  - `revoke all … from public`; **no grant** to `anon`, `authenticated` or `service_role`. `private` is not exposed through the API (EZD-006 Step 1), so nothing outside SQL can call them. Triggers owned by `postgres` (later tickets) and the tests' admin connection can.
- **How later tickets push** (recorded in docs, Step 8): a trigger on the changed table calls one of these functions. EZD-009: `job.progress` / `status` changes → `broadcast_project(job.project_id, 'job.progress', …)`. EZD-125: `edit_lock` changes → `broadcast_project(…, 'lock.changed', …)`. EZD-127: `project.open_items_count` changes → `broadcast_project(…, 'review.count', …)`. EZD-110: `notification` insert → `broadcast_user(…, 'notification.created', …)`. Each ticket adds its event name to the typed map (Step 5) in the same commit; the names here are examples for those planners, not decided.
- **`session.ended`** is the one event this ticket wires to a real trigger (Step 3b; Q-0052 (c)).
- **Payload rule** (from 03 rule 2 and 11 Security; recorded in docs): every member who can see the project receives every project-channel message, and RLS checks project scope only, never permissions (EZD-102 row). So a payload carries only ids, statuses, counters and timestamps. It never carries money fields, model data, names or emails. A subscriber that needs more refetches through a server route, where `can()` applies.

### Step 4: Token route `app/src/app/api/realtime/token/route.ts` (builder)
EZD-007 keeps auth cookies `httpOnly`, so browser code cannot read the access token (EZD-007 Step 3 and Risks).
- `GET` only. `const s = await requireApiSession()`; a `Response` (401, EZD-007 T12 shape) is returned as is.
- Reads the current session from `createSessionClient().auth.getSession()` (already verified by `requireApiSession` and refreshed by the middleware, EZD-007 Step 4).
- Returns `200` JSON `{ url, apiKey, accessToken, expiresAt, appUserId }`:
  - `url`, `apiKey`: the Supabase URL and the **publishable** key from EZD-004's `env.ts`, read per request. Returned here so the browser bundle needs no build-time Supabase values (EZD-004 Step 5: "`next build` needs no Supabase values").
  - `accessToken`, `expiresAt`: the session's access token and its `expires_at` (seconds).
  - `appUserId`: `s.appUserId` (EZD-007 `Session`).
- Headers `Cache-Control: no-store`. Never logs anything (EZD-000 Errors and logging; C8). Never the secret key (EZD-000 service-key rule), never the API gate secret (Q-0087; `createSessionClient()` sends it to Supabase, the route never returns it).
- After deactivation or any other session end, `requireApiSession()` returns 401, because EZD-007's `current_app_user_id()` returns null for an ended session (EZD-007 Step 2.3; Q-0052 (c)), so a tab cannot fetch a new token (T17 (c)).
- *Planner's choice*, security-reviewer confirms: the access token reaches browser memory (not storage) for the Realtime socket only. The refresh token stays in the `httpOnly` cookie.

### Step 5: The browser helper `app/src/lib/realtime/` (builder)
Files: `topics.ts`, `events.ts`, `hub.ts`, `adapter.ts`, `index.ts`, `react.ts`.

- **`topics.ts`**: `projectTopic(id)`, `userTopic(id)` (lower-cased UUID), `parseTopic(topic)`.
- **`events.ts`**: typed event maps, extended by later tickets in the same commit as their trigger:
  ```ts
  export interface ProjectChannelEvents { 'dev.ping': { n: number } }
  export interface UserChannelEvents { 'dev.ping': { n: number }; 'session.ended': Record<string, never> }
  ```
  `dev.ping` is the test event of the Done when. It has no trigger; only tests send it. `session.ended` is sent by Step 3b (Q-0052 (c)); T19 checks that the literal in the migration is a key of `UserChannelEvents`.
- **`adapter.ts`**: the only file that imports `@supabase/realtime-js`. It wraps `RealtimeClient` behind a small interface `RealtimeAdapter` (connect, disconnect, setAuth, channel(topic, { private: true, presenceKey }), removeChannel, socket open/close listeners). Channels are created with `config: { private: true }`.
- **`hub.ts`**: `createRealtimeHub({ fetchToken, adapter, env, onSessionEnded })`, pure logic over the adapter, so it is unit-tested with a fake adapter (T10–T16, T24). `index.ts` exports `getRealtimeHub()`, a per-tab singleton bound to the real adapter, to `fetch('/api/realtime/token')` and to `onSessionEnded = () => window.location.assign('/sign-in')` (Q-0052 (c): "the app drops all channels and goes to sign-in"), created lazily on first use in the browser and never during server rendering.
- **Hub API:**
  ```ts
  hub.project(projectId): ChannelHandle<ProjectChannelEvents> & { presence(): PresenceMember[]; onPresence(cb): () => void }
  hub.user(): ChannelHandle<UserChannelEvents>
  ChannelHandle<E> = {
    status: 'connecting' | 'subscribed' | 'reconnecting' | 'refused' | 'closed'
    ready: Promise<'subscribed' | 'refused'>
    on<K extends keyof E>(event: K, cb: (payload: E[K]) => void): () => void
    onResync(cb: () => void | Promise<void>): () => void
    onStatus(cb): () => void
    release(): void
  }
  PresenceMember = { appUserId: string }
  ```
- **Behaviour** (each item is tested):
  1. **One channel per topic per tab.** `hub.project(P)` called twice returns handles on one channel. The channel is removed when the last handle is released (T10). While any handle is open, the hub also keeps its own subscription to `user:<appUserId>` (shared with `hub.user()` handles), so `session.ended` arrives even in a tab that opened only a project channel (*planner's choice*, needed for Q-0052 (c)); it is removed with the last handle.
  2. **Presence.** On a project channel the hub tracks `{ appUserId }` with presence key = `appUserId` (from the token route), so one person with two tabs is one member. `presence()` returns unique members sorted by `appUserId`. The payload carries no name: EZD-126 resolves names through a server route (Step 3 payload rule) (T16).
  3. **Network requests happen only on events, never on a timer.** The hub fetches a token (a) at first connect, (b) once after the server refuses or closes a channel (for example an expired token), and (c) once per socket reopen after a drop. The hub itself starts no interval and no repeating timeout (T12). `@supabase/realtime-js`'s own heartbeat frames and socket reconnect backoff travel on the WebSocket, not as HTTP requests, and run only to keep or restore the socket (*planner's reading* of "no timer-driven request"; recorded in docs).
  4. **Refused join, bounded.** A first join error triggers one token fetch and one retry. A second error sets `refused`, resolves `ready` with `'refused'`, removes the channel (stopping the library's own rejoin attempts) and never retries that handle (T13).
  5. **Reconnect, resubscribe, refetch once** (ticket Scope). When a subscribed channel drops (channel error, timeout, close not caused by `release()`, or socket close), status becomes `reconnecting`. On the next socket open, or at once on the window `online` event, the hub fetches a token once, calls `setAuth`, and rejoins. On `SUBSCRIBED` it calls every `onResync` callback **exactly once**. The first subscription calls none. A rejoin that is refused goes to `refused` as in 4 (an access change while offline) (T11, T14, T15).
  6. **Events are typed** by the maps in `events.ts`; an unknown event name is a type error.
  7. **No React work per message by default.** The hub is plain TypeScript. `react.ts` adds `useProjectChannel(projectId)` (acquire on mount, release on unmount) and `usePresence(projectId)` (`useSyncExternalStore`, so only components that read presence re-render). Consumers that need event data choose their own store (11 rule 4 spirit: no React render per message unless the view shows it).
  8. **Session ended** (Q-0052 (c)). On `session.ended` on the user channel the hub: calls `removeChannel` for every topic it holds (project and user); drops the access token from memory; sets every handle's status to `closed` and resolves any pending `ready` with `'refused'`; makes no further `fetchToken` call and no further join, including on later socket, `online` or `visibilitychange` events and on later `hub.project()` / `hub.user()` calls (they return `closed` handles); then calls `onSessionEnded()` once (T23, T24).
- **No `@supabase/supabase-js` in browser code** (*planner's choice*): the browser gets only the Realtime client, which has no table-query API (03 rule 1) and is smaller than the full client (11 Budgets). The hub is imported only by client components that need it; EZD-020's lazy-module rules can later move it into its own chunk.

## Risks
- **Open subscriptions after access is removed (Q-0052 (c)).** Realtime checks the policies when a channel is joined, not for each message. When EZD-006 ends the person's sessions, the database now pushes `session.ended` and an unmodified app drops every channel at once and goes to sign-in (Step 3b, Step 5 item 8; T23, T24); rejoins and new tokens are refused (T3 (c), T17 (c)). Remaining window: **≤ `jwt_expiry` (3600 s; EZD-007 Step 1), tampered browsers only**, which ignore the push and keep already-joined channels until the token expires. Messages carry ids and counters only (Step 3 payload rule). If T23 shows the pinned Realtime does not deliver to an already-joined channel after the user's sessions are deleted, the builder stops and raises a question.
- **Presence identity.** Realtime cannot check the presence payload against the token, so a member who edits their own browser code could show up under another member's `appUserId` on a project they can already see. Only members of that project can track presence there (Step 2). *Planner's choice*: accept, and keep names out of the payload (EZD-126 resolves names on the server). Security-reviewer confirms.
- **Access token in browser memory.** A script injected into the page could read the token from memory for its lifetime (≤ 3600 s). It is **refused by PostgREST without the gate header** (EZD-006 Step 1b; Q-0087 (ii); EZD-006 T22), so it cannot read or write tables or call RPCs; it **reaches Realtime (intended**, limited by Step 2's policies), **Auth** (for example reading the own user; EZD-007 turns on secure password change) **and Storage** (EZD-132 must keep Storage policies tight, Q-0087). RLS stays the backstop. This is the cost of browser Realtime that 03 rule 1 accepts; the refresh token stays `httpOnly`.
- **Supabase version specifics.** `realtime.messages.extension`, `realtime.topic()`, `realtime.send()`, whether public and private channels with the same topic are kept apart (T5 (c) proves it locally), the refusal status, and how a raise inside a policy is reported during a join all depend on the pinned CLI and SDK. The test-author and builder read them from the pinned versions. If public channels are not kept apart, the builder stops and raises a question (a cloud "private channels only" setting would then be a runbook step for Josh).
- **`realtime.send()` inside later triggers.** If it ever raises, the change that called it rolls back. Later planners (EZD-009, EZD-110, EZD-125, EZD-127) should decide whether their trigger catches send errors. Messages are delivered after commit, so a rolled-back change sends nothing.
- **Bundle size.** `@supabase/realtime-js` adds to every entry point that imports the hub (the editor, and the Projects page once EZD-110's bell uses the user channel). Budgets: Projects 200 KB, editor 500 KB (11 Budgets). EZD-017 measures it; EZD-020 may move the hub into a lazy chunk.
- **Node WebSocket in Vitest.** The local-stack tests run `@supabase/realtime-js` in Node 22. EZD-004 T5(c) already does this through supabase-js, so it is expected to work; if the pinned version needs a WebSocket package in Node, the test-author adds it as a devDependency with a docs row (C1).
- **Lint override.** A later flat-config block that sets `no-restricted-globals` or `no-restricted-properties` for `app/src` replaces this ticket's options unless it repeats them (Step 7 docs note). T18 (g) runs on the whole repo, so the gate catches a removed rule only if T18's cases still apply to the real config; the code-reviewer checks.
- **Test time.** T1 signs in two users and waits for Realtime; T2–T6 open about 20 local Realtime connections. With `maxWorkers: 2` (Q-0019) and EZD-004's 15,000 ms `testTimeout`, each test fits; T1 needs a Playwright timeout of at least 60,000 ms (sign-ins plus three 10,000 ms waits).
- **Ticket size.** Four small migrations, one route, the hub with a fake adapter, a dev page, one lint block and the tests. This fits one session; if the hub tests overrun, the orchestrator can split the hub (T10–T16) from the database side (T2–T9). This plan does not propose that split.
