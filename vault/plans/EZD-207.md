# EZD-207 · Plan canvas (split proposal)

- **ACs:** AC-EZD-207-1 … AC-EZD-207-10 (`vault/spec/acceptance-criteria.md:714-723`, stage-0), shared out to the parts below
- **Complexity:** high (parts a and b), medium (part c); reasons per part

The performance check pans and zooms the 3,000-object benchmark plan at desktop and iPad size and fails on any React commit (c).

## Split proposal

**Why.** Planned whole, the ticket touches about 45 files and needs about 50 tests. That is over the size rule (PROCESS.md section 6 "Ticket size": about 20 files, about 25 tests; Josh 2026-10-22). Sources of the count (all read 2026-11-05):
- the ticket row (`vault/tickets/phases/phase-02.md:13`) and AC-EZD-207-1 to -10;
- **dependencies to install.** No `three` or `@react-three/fiber` is in `app/package.json` yet. Their rows are already pinned in ARCH Dependencies: `three` 0.186.1, `@react-three/fiber` 9.8.2, and `@types/three` 0.186.0 (Used in: spikes only, so the row changes). `eslint-rules/boundaries.mjs:42-43` already allows `three` and `@react-three/` in `app/src/editor/`;
- **rendering.** The drawing list (P238 `buildDrawingList(document, view, dimensions)`, `DrawingItem` kinds line, arc, fill, hatch and text) becomes merged geometry: one line buffer per layer and one glyph atlas for all text. This is 11 rule 4 and the EZD-027 carry-over (`vault/spikes/EZD-027.md:40`: 0 buffers rebuilt on pan, 0 idle renders, about 21 draw calls). Text has two fonts once EZD-205a lands: DM Mono 400 (P238) and Instrument Sans 600 for the room label (P205 part a);
- **input.** Zoom toward the cursor (wheel, trackpad pinch, touch pinch) and pan (space-drag, right-drag, two-finger drag) (S03 Canvas interactions). All of it runs with no React render per pointer event (11 rule 4; ARCH Editor shell).
- **zoom stack.** It needs two icons not yet in `app/src/components/icon/icons.json` (`remove`, `fit_screen`; `add` is there). That means the icon pipeline files plus `HeaderButton.icon.test.tsx`, which pins the icon list (lesson L-021);
- **hover.** Hover uses EZD-206's `WallSnapIndex` (P206 seam "EZD-207 hover"; Q-0563). The `showObject` seam for the conflict-row Show button belongs here too (Q-0511 (b), Q-0568);
- **performance check.** It needs a benchmark page that runs with no database. The perf check starts `next start` with no Supabase env (ARCH Performance check), and P236 "dependents" says "207: `generateBenchmarkModel()` in memory". The check also needs:
  - a 3-second pan **and zoom** (`scripts/perf/pan-script.mjs` today does two drag sweeps of about 2.9 s, with no zoom);
  - an iPad-size profile with CPU throttling (`scripts/perf/perf.config.mjs` `PROFILES` has `desktop` only; P017 G12: "the iPad-throttled and Surface profiles are EZD-207's");
  - the `frame.ipad` trend row (`scripts/perf/budgets.mjs`, present but unused);
  - edits to the EZD-017 tests that pin profiles and config.

The work splits into three lettered parts, built a → b → c. A dependency on EZD-207 (EZD-208, 209, 216, 223, 224, 231, 235, 237) means all three parts (`vault/tickets/README.md`, split rule). Each part is planned as its own unit from its section here.

### Part EZD-207a · Plan canvas: renderer, drawing, grid, pan and zoom
- **Scope (renderer):**
  - One persistent React Three Fiber canvas and WebGL renderer for the whole editor, drawn on demand (`frameloop` demand). The Plan scene is drawn into it; later tabs add their scenes to the same canvas and never create or destroy a context (11 rule 4; 02 Stack 2D + 3D; ticket Scope). It is mounted once in the frame's canvas region by EZD-120c's `ProjectEditor` (`app/src/editor/ProjectEditor.tsx`, P120c step 6) when the session is `ready`.
  - Code lives in `app/src/editor/plan/` (reserved for the canvas by `boundaries.mjs:11`).
  - The device pixel ratio cap is decided in part a's plan. EZD-027 measured at 1x (`EZD-027.md:40`); part c measures a high-density screen.
- **Scope (drawing):**
  - The scene draws from `buildDrawingList` (P238) for the open floor: lines, arcs, fills and hatches. Geometry is merged per drawing layer, item kind and line-weight role, with no object per wall (11 rule 4). Text items are part b's.
  - Status colours per drawing layer come from board S03's Phase rows (`html/project/S03Plan.dc.html:82-84`): `existing` `--ez-slate-400`, `demo` `--ez-red`, `new` `--ez-cobalt`. Every phase 4 wall is Existing (Q-0558).
  - WebGL needs numbers, so the token values in `app/src/styles/tokens.ts` (`TOKENS`) are converted to sRGB by a pure function, hex and `oklch()` both. `--ez-cobalt` and `--ez-red` are `oklch()`.
  - Buffers are rebuilt only when the model or floor changes, never on pan or zoom (11 rules 2 and 4).
- **Scope (grid):**
  - The grid is drawn in model units on the canvas and moves with pan and zoom. Part a's plan decides its meaning (Q-0568 "plans decide grid meaning"). Board S03 has 32 px squares of `--ez-canvas-grid` on `--ez-canvas` (`S03Plan.dc.html:47`), and at the board's 100% zoom a square is about 1 ft.
  - Part a's plan also decides how the WebGL grid meets the frame root's CSS grid. ARCH Editor shell: "The grid is CSS on the frame root until EZD-207 decides how its WebGL grid meets it".
- **Scope (camera and input):**
  - The orthographic camera zooms toward the cursor on wheel and trackpad pinch (wheel with ctrl), and on a two-pointer touch pinch. It pans on space-drag, right-drag and two-finger drag (S03 Canvas interactions).
  - Input listeners on the canvas element change the camera and call the R3F invalidate. They set no React state. Readouts that change per pointer move use refs (ARCH Editor shell; 11 rule 4).
  - Part a's plan decides zoom limits, the zoom factor per wheel step, what 100% means, the first view on open (Fit), and Fit on an empty model (Q-0568 "plans decide … zoom limits, Fit on an empty model"). Fit itself (the model's bounds plus a margin) is camera math in part a; the Fit button is part b's.
- **Scope (seams for dependents):** part a's section 3 gives these as one canvas handle that `ProjectEditor` passes on, each read or called synchronously inside a pointer handler with no React state (11 rule 4; ARCH Editor shell). Part a's plan names the handle and its members.
  - `getCursor(): { x: number; y: number } | null`, read from the input controller's ref: CSS px from the canvas region's top-left, `null` before the first pointer event (P209 C17 props; P209 section 9 note "`getCursor` from the canvas input controller's ref"). EZD-210b passes it to `TypedEntryLayer`.
  - `pixelsPerInch`, the camera's current screen px per model inch, a finite number above 0 (P206 seam "EZD-210 Wall tool": `pixelsPerInch` from the camera; P206 `SnapRequest.pixelsPerInch`).
  - Model-to-screen and screen-to-model transforms for a point (model inches, +x east, +y north, P203 Decided Axes; screen CSS px as `getCursor`) (P210 Ledger notes; P210 part b Scope (pointer and overlay)).
  - A camera-change callback that runs outside React on every pan or zoom, with an unsubscribe (P210 Ledger notes), so EZD-210b's overlay and P209's box follow the view.
  - A pointer hand-off: the active tool registers one receiver and gets left click, double-click, drag and move in model inches; space-drag, right-drag and two-finger drag stay with the canvas and never reach it (P210 Ledger notes; S03 Canvas interactions). With no receiver registered, left input does nothing in part a.
- **Scope (shell, states, permissions):**
  - Header `views={['plan']}`, so the Plan tab shows (Q-0568; `EditorHeader` `views` prop, `components/shell/editor-views.ts`).
  - No left panel or inspector, and the status bar shows the disclaimer only (Q-0568; P120c Frame row).
  - Loading keeps P120c's skeleton (Q-0214; Q-0506).
  - A canvas that cannot start (no WebGL, context creation throws) shows an inline message with Retry in the canvas region (Q-0214; Q-0568; `components/states` `InlineError`, EZD-015).
  - A user without Edit model gets the same canvas, pan and zoom (S03 Permissions; Q-0568).
  - No rail and no typed bar exist yet. The Wall and Room rectangle rail entries come with EZD-210, the bar with EZD-209 (Q-0500: a control appears when its ticket ships). Part a tests that a loading or view-only editor shows neither (rail region absent).
  - The S03 "Empty" hint is not built here. Q-0500 applies it once the grid and the tools ship, so EZD-221 (templates, the last of them) adds it.
- **Done when:**
  - AC-EZD-207-1 and AC-EZD-207-9, verbatim.
  - AC-EZD-207-4 for lines, arcs, fills and hatches.
  - AC-EZD-207-6 except "tools are disabled": while the model loads the canvas shows a skeleton; if the canvas cannot start it shows an inline message with Retry.

The orchestrator records them against EZD-210b in TRACE.md.

  - Then: a scroll at a point keeps the model point under the cursor where it was. A pan or zoom rebuilds no geometry buffer and makes no React commit (EZD-027 carry-over; 11 rule 4). With nothing changing, no frame is drawn (ticket Scope).

- **Depends on:**

  - missing from the row: EZD-120c (the editor route and `ProjectEditor` this mounts into; reached only through EZD-236 → EZD-120), EZD-015 (`InlineError`, done), EZD-016a (browser harness, for the visual checklist; done), EZD-027 (spike carry-overs; done).

- **Scope (hover):**

  - The lookup goes through EZD-206's `WallSnapIndex.spatial.query(rect)` and `getWall(id)`, kept current with `upsertWall` / `removeWall` per changed wall (P206 seam; Q-0563; 11 rule 4).

  - Seams for EZD-210b (P210 Ledger notes; P210 part b Scope (pointer and overlay)), added to part a's canvas handle and listed in part b's section 3 with signatures: the hover-mode setter (`wall` | `off`), and the hovered wall id (`string | null`, `null` over empty space or with mode `off`), read synchronously inside a pointer handler so pick mode picks the highlighted wall (AC-EZD-207-3 "the wall a click would pick").
- **Scope (text):**

- **Scope (Show seam):**
