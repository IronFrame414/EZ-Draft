# EZD-125 · Edit lock service (split proposal)

- **ACs:** AC-EZD-125-1 … AC-EZD-125-10 (`vault/spec/acceptance-criteria.md:1145-1154`, stage-0), shared out to the parts below (each AC in exactly one part)
- **Complexity:** high (part a), medium (part b); reasons per part
- **Areas:** data-model, migrations, security, realtime, api, testing
- **User-visible result:** nothing new on screen until EZD-126 draws the banner, toast, prompt and Stop editing button (phase-01.md row EZD-126). After this ticket two people opening the same project cannot both change it: the first with Edit model holds the lock, everyone else's editor saves nothing, a Request edit that goes unanswered releases the lock after the Defaults minutes with the holder's saved work checkpointed, and a save from a former holder is refused (phase-01.md row EZD-125; S06 Edit lock; R24 #16, #17).
- Phase: 8 · Planned by: planner · Date: 2026-11-11 · Status: split proposal

## Split proposal

**Why.** Planned whole, the ticket touches about 27 files and needs about 40 tests, over the size rule (PROCESS.md section 6 "Ticket size": about 20 files, about 25 tests; Josh 2026-10-22). Sources of the count:
- 10 stage-0 ACs (`acceptance-criteria.md:1145-1154`), several with three or four refusal cases each (AC-5: the holder's own request, a second pending request, no Edit model, a free lock, Cancel; AC-6: holder-only Release, Keep and Stop editing, a late Keep, ask again after Keep; AC-7: deadline at request time, a later Defaults change, sweep, lock read and save each applying it);
- the database side: `edit_lock` gains `holder_app_user_id`, `since`, `device_id`, `offline`, and a new table `edit_request` (Q-0697 03 "Edit lock data"; 03c:20-21), each lock change one conditional write under `select … for update` on the `edit_lock` row (Q-0697 03; 03b rule 6), a redefinition of `public.save_objects` (latest body `supabase/migrations/20261109100000_number_model_objects.sql:128`) so a save applies an expired deadline (Q-0697 03 "Auto release"), a sweep function, broadcast triggers (ARCH Realtime "Clients never broadcast"), event_log rows in the same transaction (Q-0697 10) and an `edit_request` notification to the holder (04 Notifications "edit request"; ARCH Notifications `private.create_notification`);
- the server side: a lock module, four route files (state and acquire, release, request and cancel, respond), one more pass in the once-a-minute sweep route (`app/src/app/api/jobs/sweep/route.ts`, EZD-5601 precedent at lines 33-41), the model load's lock read (`app/src/server/model/model.ts:355`), the Realtime event map (`app/src/lib/realtime/events.ts`), the event registry (`app/src/lib/events/registry.ts:21-26, 90-95` already lists six `lock.*` names; `lock.request_cancelled` is missing, Q-0697 10), the generated database types, error message keys, the harness lists (`app/test-harness/rls/gate.ts`, `table-grants.ts`, `private-execute.ts`, `app/test-harness/money/route-cases.ts`) and `docs/architecture.md`;
- the browser side: a typed client for the lock routes, a lock controller over the project channel, the open flow in `openEditorSession` (`app/src/editor/editor-session.ts:60-74` today builds a sync for every `canEdit` viewer with the load's `lockEpoch`), Stop editing through EZD-224's `makeCheckpoint` (Q-0681 (a)) and the tab-close release (Q-0697 04).

**Why cut here.**
- The database and routes stand alone and are tested at the API level, which is what the ticket's Done-when names ("API test", phase-01.md row EZD-125). Every AC about who gets the lock, the epoch, requests, the deadline, broadcasts and cascades is decided on the server (03b rule 6; Q-0697 03 and 10).
- The browser half needs EZD-224's `makeCheckpoint` (`vault/plans/EZD-224.md` Build step 9; Q-0681 (a); Q-0697 03 "Phase 8 dependencies"), and EZD-224 is `blocked`, held for re-planning (`vault/tickets/STATUS.md` row EZD-224, Josh 2026-11-11). Cut here, part a can be built while EZD-224 is held; only part b waits.
- Part a's security review covers one set of definer functions and routes; part b adds no server surface.

Built a → b. Each part is planned as its own unit from its section here.

### Part EZD-125a · Edit lock: tables, functions, routes and sweep
- **Scope:**
  - Migration 1 (timestamp after develop's newest migration at merge time, L-060): `edit_lock` adds `holder_app_user_id uuid null` (null when free), `since timestamptz null`, `device_id text null`, `offline boolean not null default false` (Q-0697 03 "Edit lock data"; 03c:20; glossary 00i "Lock holder"); new table `public.edit_request` (`id`, `project_id`, `tenant_id`, `requester_app_user_id`, `requested_at`, `deadline_at`, `response` in `release`, `keep`, `auto`, `cancelled` or null, `responded_at`), foreign key pair to `project (id, tenant_id)` with `on delete cascade` (Q-0697 03 "Rows cascade with the project"; 03c:21), at most one row with `response is null` per (project, requester) by a partial unique index (Q-0697 03 "One pending request per user"; S06:75), the EZD-006 select policy, `<table>_api_gate`, `authenticated` select only and `service_role` all four (ARCH Model working copy "Tables" pattern; `TABLE_GRANTS` edit, L-049).
  - Migration 2, every function `security definer`, `set search_path = ''`, `revoke all … from public` then grants by name (L-016), each public one calling `private.require_api_gate()` first and added to `GATED_RPC_CALLS` (ARCH Model working copy "Functions"; L-049): acquire (free lock → caller, `since`, `device_id`, epoch + 1; caller already holder → `device_id` updated, epoch unchanged; held by another → answers the holder; needs a granted `edit_model` row and project scope, as `save_objects` steps 2-4, `20261109100000_number_model_objects.sql`), release by the holder only with reason `stop_editing`, `closed` or `request_accepted` (S06 Events "lock.released (reason: …)"; epoch + 1, holder null), request (refused for the holder, without Edit model, or with a pending request; on a free lock answers `lock_free`; `deadline_at = requested_at + p_minutes`, minutes whole 1 to 1,440; Q-0697 03 "Auto release"; 09o Auto-release deadline rows 1-5), cancel (the requester's own pending row → `cancelled`), respond (`release` or `keep`, holder only, `where response is null`, so a Keep after the deadline loses; Q-0697 03; 09o row 4), a lock read that returns holder id, `since`, epoch and the caller's pending request, and a `service_role`-only sweep. Every one of them, and the redefined `save_objects`, first applies any pending request whose `deadline_at <= now()` on the database clock: server checkpoint through `private.make_checkpoint` (`20261105200004_create_model_save_functions.sql`), every pending request of the lock set to `auto`, holder null, epoch + 1, then the call goes on (Q-0697 03 "The sweep cron, every lock read and every save apply it"). `save_objects` keeps its signature, language plpgsql and return shape; a save that finds an expired request does the auto release and then returns `{ status: 'stale_lock_epoch' }` without raising, so the auto release commits (Q-0697 03). Its callers stay as they are: `saveObjects` (`app/src/server/model/model.ts:223, 228`) and `public.save_objects_resolving` (`20261107180001_create_sync_conflict_functions.sql:289`). A release by `closed` or `request_accepted` makes a server checkpoint first in the same transaction; `stop_editing` does not, because the browser made one with its thumbnail just before (Q-0681 (a); Q-0664 "server checkpoint at lock release or timeout leaves preview_path null").
  - Broadcasts on `project:<id>` through `private.broadcast_project` from triggers on `edit_lock` and `edit_request` (ARCH Realtime "Clients never broadcast", "Payload rule"), ids and timestamps only (Q-0697 03), with each event name added to `ProjectChannelEvents` in `app/src/lib/realtime/events.ts` in the same commit (ARCH Realtime; `scripts/db/__tests__/realtime-sql.test.mjs` T19); `realtime.send` adds `id` to the payload and `toEventPayload` drops it (ARCH Realtime; L-021 rule on `realtime.send`).
  - event_log: `lock.acquired`, `lock.requested`, `lock.request_cancelled`, `lock.request_declined`, `lock.released` (with reason), `lock.auto_released` in the same transaction as the lock change, actor and IP from the route; an auto release has actor system and IP null (Q-0697 10; 11:80; Q-0695 event_log columns and IP rule). `lock.request_cancelled` joins `EVENTS` (`app/src/lib/events/registry.ts`).
  - A request creates one `edit_request` notification for the holder through `private.create_notification` (`20261102210539_create_notification_functions.sql:10`), payload `{ name }` = the requester's name (ARCH Notifications: `edit_request` needs a string `name`; `app/src/lib/notifications/kinds.ts:14`).

### Part EZD-125b · Edit lock in the editor: open, Stop editing, tab close
- **Scope:**
  - A typed browser client for part a's routes in `app/src/lib/lock/` (browser and server code folder, ARCH Folder layout `src/lib/`), each answer a result type with every failure code (L-058).
  - A lock controller in `app/src/editor/lock/`: the lock state for one open project, refetched through part a's lock read on every lock event and every resync of the project channel (`getRealtimeHub().project(id)`, `onResync`; ARCH Realtime "Resync", "Requests only on events"; 11 rule 11, no polling), with the actions EZD-126 binds to its controls: Start editing, Request edit, Cancel request, Release, Keep editing, Stop editing (S06 Controls; Q-0697 05).
  - Open: `openEditorSession` asks part a's acquire for a viewer with Edit model; the holder gets the autosave sync with the acquired `lock_epoch`; a user without Edit model, or anyone while another person holds the lock, opens view only with no sync and saves nothing (04:90; S03:16-17; AC-EZD-125-4). Start editing later builds the sync with the new epoch.
  - Stop editing and leaving the editor: drain the outbox, `makeCheckpoint` (EZD-224 step 9; Q-0681 (a)), then release with reason `stop_editing`, and wait for it; a failed checkpoint keeps the lock and returns the error, shown with Retry (Q-0697 04; S06 Decision 12; 03b rule 7). Release from the holder prompt drains first, then answers `release` (S06 "Release: saves holder's work").
  - Tab close: a best-effort `keepalive` release with reason `closed` carrying `lock_epoch`, not sent while this device's outbox still has entries, so the queued edits drain at the next open (Q-0697 04; 03b rules 7, 9).
  - The holder's own refused save after their other device released gets its own wording, not "Someone else is editing" (Q-0697 05; 09o lock_epoch row 5); the key comes from part a.
- **Tests (about 16) and files (about 9):** client result-type tests with stub fetch; controller tests over every lock event and resync (refetch once per event, no timer); session tests: free lock gives a sync with the acquired epoch, a held lock or no Edit model gives none; Stop editing call order (drain, checkpoint, release) and a failed checkpoint keeping the lock; tab close sends nothing while the outbox has entries and one keepalive release when it is empty.
- **Done when:** opening a project whose lock is free gives it to a user with Edit model and the editor saves with the acquired epoch, while a user without Edit model, or anyone while the lock is held, opens view only and saves nothing; Stop editing drains the outbox, makes a checkpoint and then releases, and a failed checkpoint keeps the lock and returns the error; a tab-close release is not sent while that device's outbox has entries.
- **ACs:** AC-EZD-125-4, -8.
- **Depends on:** EZD-125a, EZD-224 (`makeCheckpoint`; Q-0697 03 "Phase 8 dependencies"), EZD-120b, EZD-120c, EZD-120d (outbox, session, app-wide drain), EZD-018 (hub). EZD-224 is `blocked` today (`vault/tickets/STATUS.md`), so this part waits for its re-plan and build.
