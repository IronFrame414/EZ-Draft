## Approach

### What the registry holds (Level-1 decisions, with sources)
- **Which names.** The ticket Scope says "every event name in Hooks, events and integrations". Section 07 names 48 distinct events. They fall into three kinds:
  - `webhook` (12). These are the 9 rows of "Outbound webhooks to EZ Binder" plus the 3 "Added in Round 24" names under Delivery rules. The Round 24 names are webhooks because EZD-1302 lists them among the outbound event payloads (phase-13.md).
  - `internal` (34). These are every name in "Internal app events", including `import.ready` (named "(new)" inside the `import.completed` row) and `render.client_ready` (named in the `render.approved` row and again in the last row; listed once).
  - `log_only` (2). These are `catalog_item.created` and `detail.placed`. 07 Canonical names says such screen events "write the event log only and are not webhooks".
- **Not in this ticket.** The other screen-section event names (e.g. `project.created` in S01, `render.requested` in S07/S08, `user.invited` in S15) are not named in section 07, so they are outside this Scope. Each ticket that emits one adds it to the registry as `log_only` in the same commit. The scan test forces that, and EZD-1314 audits it (phase-13.md).
- **Spelling.** Names are copied from 07 without markdown escapes (`lock.request_declined`, not `lock.request\_declined`).
- **Payloads.** Payload fields are not defined here:
  - Outbound payloads are EZD-1302's job (its row: "with the payloads in the table").
  - Internal event payloads are not specified by 07, so each emitting ticket narrows its own entry.
- **Delivery.** The event log write is EZD-109's and webhook delivery is EZD-1301's (ticket Scope). Realtime or notification fan-out is not in the Scope. emit() therefore only validates the name and hands the event to a list of sinks. That list is empty in this ticket, and later tickets add sinks without changing any caller.

### Step 1: Registry `app/src/lib/events/registry.ts` (shared browser/server; EZD-000 Folder layout `src/lib/`)
- `export type EventKind = 'webhook' | 'internal' | 'log_only'`.
- `export const EVENTS = { '<name>': { kind: '<kind>' }, … } as const satisfies Record<string, { kind: EventKind }>`. In this ticket it holds the 48 entries in the Tests section and nothing else, grouped by kind, and each group has a comment citing its 07 sub-heading. Later tickets add `log_only` entries for screen events outside 07 ("Not in this ticket" above), so the tests check that the 48 are present with their kinds and that every other entry is `log_only` (T1, T3), not a fixed total.
- `export type EventName = keyof typeof EVENTS`.
- `export function isRegisteredEvent(name: string): name is EventName`. Uses `Object.hasOwn(EVENTS, name)` so inherited keys such as `toString` are not events.
- `export interface EventPayloads { … }`. Has one key per `EventName`, each typed `Record<string, unknown>` in this ticket. It is an interface, not a mapped type, so later tickets narrow a single entry in place. A type-level assertion in the test (T6) keeps its keys equal to `EventName`.
- No imports from `src/server/` (so a browser module may read names). No dependencies.
- *Planner's choice (CLAUDE.md rule 4)*: name format `^[a-z][a-z_]*\.[a-z][a-z_]*$`. All 48 names in 07 fit it, so a malformed entry such as `lock.*` or an escaped underscore is caught by T2.

### Step 2: emit() `app/src/server/events/emit.ts` (server-only; EZD-000 Folder layout `src/server/`)
- Types:
  - `EmitContext = { tenantId: string; projectId?: string | null; actorId?: string | null }`. tenantId is required because every row is tenant-scoped (03 opening paragraph).
  - `EmittedEvent<N> = { id: string; name: N; at: string; tenantId: string; projectId: string | null; actorId: string | null; payload: EventPayloads[N] }`.
  - `EventSink = (event: EmittedEvent<EventName>) => void | Promise<void>`.
- `createEmitter({ sinks, now = () => new Date(), newId = () => crypto.randomUUID() })` returns `{ emit }`, where `emit<N extends EventName>(name: N, payload: EventPayloads[N], ctx: EmitContext): Promise<EmittedEvent<N>>`:
  1. If `!isRegisteredEvent(name)`, it rejects with `UnknownEventError` (exported class, `name = 'UnknownEventError'`, message contains the offending name) **before** any sink runs. This holds in production too. A dynamic unknown name is a bug, and "nothing fails silently" (EZD-000 Errors and logging).
  2. It builds the envelope:
     - `id`: a new UUID per emit, which is the "idempotency key per event" EZD-1301 needs (07 Delivery rules).
     - `at`: `now().toISOString()`, matching event\_log's `at` (03 event\_log).
     - `projectId` and `actorId`: `?? null`.
  3. It awaits each sink **in array order** (deterministic, so EZD-109's log sink can run before EZD-1301's enqueue). If a sink throws, the remaining sinks still run. After all have run, emit rejects with an `AggregateError` of the sink errors. Otherwise it resolves to the envelope. *Planner's choice*; the source is EZD-000 Errors and logging ("Nothing fails silently").
- `app/src/server/events/sinks.ts`: `export const defaultSinks: EventSink[] = []`, with a comment saying EZD-109 adds the event log sink and EZD-1301 the webhook sink.
- `app/src/server/events/index.ts`:
  - Exports `export const { emit } = createEmitter({ sinks: defaultSinks })`.
  - Re-exports `createEmitter`, `UnknownEventError` and the types.
  - Callers import `emit` from here and call it by that bare name. Aliasing it on import is not allowed, because the scan (Step 3) recognises the bare `emit(` call. This is written in docs (Step 4).
- No new dependency: `crypto.randomUUID` is a Node 22 global (EZD-000 Runtime). Nothing here imports `@supabase/*`, so this ticket touches no database.

### Step 3: Static scan (Done when; test-author writes it, guard-paths.mjs `test-utils/`)
`app/test-utils/events/find-unregistered-emits.ts` exports a pure helper, `findUnregisteredEmits(rootDir, roots, isRegistered) → Array<{ file, line, name }>`.
- **Files read.** It walks the given roots relative to `rootDir`. Missing roots are skipped (`worker/` does not exist yet). It reads `.ts .tsx .js .jsx .mjs .cjs` files.
- **Files skipped.**
  - `node_modules`, `.next`, `dist` and `coverage`.
  - Test files: `*.test.*` and `*.spec.*`.
  - Anything under `test-utils/`, `test-harness/`, `fixtures/` or `__fixtures__/` (the same exemptions as EZD-000 C4/C7).
- **What it matches.** Every bare call `emit(` with a string-literal first argument (`'…'`, `"…"` or a `` `…` `` template with no `${`). The call must not be preceded by `.` or by an identifier character. Method calls such as `stream.emit('error')` (Node EventEmitter) are therefore ignored.
- **What it reports.** Each literal that `isRegistered` rejects.
- **Repo scan.** The repo scan (T8) runs it over `app/src`, `packages/*/src`, `worker/src` against the real `isRegisteredEvent`.
- **What other layers catch.** Typed variables are caught at typecheck (T6), and anything else is caught at runtime by `UnknownEventError` (T5). EZD-000 Risks already accept that text scans can miss unusual forms.

## Risks
- **Scan blind spots.** The scan sees only bare `emit('literal'…)` calls. Aliased imports, wrappers that take a name variable, or `emit` re-exported under another name pass the scan. Typecheck and the runtime `UnknownEventError` cover these, but only when the path runs in a test. The docs rule (no aliasing) is enforced by review only.
- **Later tickets must add names.** Screen events outside section 07 (about 70 names across S01–S18, e.g. `project.created`, `render.requested`, `user.invited`) are not registered here. Each emitting ticket must add its name, with kind `log_only`, in the same commit or its gate goes red on T8 (and T1 (b) goes red if it uses another kind). That is the intended pressure, and the code-reviewer should expect it. Screen sections also use names that EZD-1314 later renames to the canonical ones (e.g. S17 `field.conflict…` vs 07 `field.conflict_flagged`, S17/X `task.completed` vs `field_task.completed`). Builders must use the 07 names.
- **EZD-1314's "later-phase mark".** EZD-1314 needs each registry name to have an emitter or a later-phase mark. This plan adds no such field, and EZD-1314 (or an earlier ticket) adds it to the entry shape `{ kind }`. Keeping `EVENTS` entries as objects keeps that change non-breaking.
- **Rows written per save.** `model.saved` fires on every autosave (07). If EZD-109's sink logged it, each save would write an extra row, against "rows written per save" (11 Performance; EZD-017). event\_log covers approvals, issues, locks, permission changes and deletes (03 event\_log; 11 Security and audit), so EZD-109's planner should filter by name.
- **Bundle size.** `registry.ts` is safe for the browser (about 1 KB of strings). `emit` lives under `src/server/` and must never be imported by client components. EZD-020's bundle report would show it if one is.
- **Depends on EZD-001 settings.** The plan assumes EZD-001's app Vitest include (`src/**/*.test.{ts,tsx}`) and that its tsconfig includes test files (needed for T6). If EZD-001 changes either at review, T6 or T7/T8 placement must follow.
