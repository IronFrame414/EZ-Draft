### Step 4: Service worker, `app/public/sw.js`
- A plain script served at `/sw.js`, with no build step (*planner's choice*; EZD-134 replaces it with a Workbox build). It contains:
  - a header comment: "EZD-013: no offline cache yet. EZD-134 adds the Workbox app-shell cache at this same URL";
  - `self.addEventListener('install', () => self.skipWaiting())`;
  - `self.addEventListener('activate', (e) => e.waitUntil(self.clients.claim()))`.
- There is no `fetch` handler, no `caches` use and no `importScripts` (ticket Scope "no offline cache yet").
- `skipWaiting` and `claim` make a new version take over at once. That is safe while nothing is cached. EZD-134 decides the update flow once a cache exists (03 rule 12: older versions drain their outbox and are then told to reload).
- **The URL `/sw.js` and scope `/` are a contract for EZD-134.** If the worker moves to another URL, devices that already installed the app keep the old worker registered. EZD-134 must keep the URL, or unregister the old worker. This is recorded in docs (Step 7).
- `app/next.config.ts` (extend EZD-001's file; append to `headers()` if one exists) gives `/sw.js` the header `Cache-Control: no-cache, no-store, must-revalidate`, so a new worker is fetched on the next visit (*planner's choice*, following Next.js's PWA guidance).
- ESLint: `app/public/sw.js` uses service-worker globals. If lint reports `no-undef`, the builder adds service-worker globals for that file in `eslint.config.mjs`. If that needs the `globals` package and EZD-010 did not already add it, the builder adds a Dependencies row with `Added by` = `EZD-013` (C1).

### Step 5: Registration
- **`app/src/lib/pwa/register-sw.ts`**: `registerServiceWorker(env = { navigator, window, document }): Promise<'registered' | 'unsupported' | 'failed'>`. It takes the browser objects as a parameter so it can be unit-tested in the `node` environment.
  1. If `!('serviceWorker' in env.navigator)` or `!env.window.isSecureContext`, it returns `'unsupported'`. Service workers need HTTPS; `http://127.0.0.1` used by the tests counts as secure.
  2. It waits for the window `load` event, or continues at once if `document.readyState === 'complete'`. The worker then never competes with the first paint (11 Budgets: "Projects page: first cards within 1 second").
  3. It calls `navigator.serviceWorker.register('/sw.js', { scope: '/', updateViaCache: 'none' })` once.
  4. If registration rejects, it calls `captureBrowserError(error, 'pwa.register')` once (EZD-024's `app/src/lib/errors/capture.ts`, vault/plans/EZD-024.md Step 6; the dotted location form follows EZD-024's `jobs.kick` and `email.send`, *planner's choice* for the name), then returns `'failed'` and throws nothing. Nobody sees a broken install, and no `console` call is allowed (C8).
- **`app/src/components/pwa/ServiceWorkerRegistration.tsx`** (`'use client'`): `useEffect(() => { void registerServiceWorker(); }, [])`. Returns `null`. It has no state, so it causes no re-render (11 rule 4).
- **Registration runs in every environment where the page is served.** That includes `next start` in the gate (EZD-007 Step 8: the Playwright web server runs `pnpm start`), previews and production. In `next dev` it is harmless while the worker has no fetch handler. EZD-134 decides whether dev mode registers once a cache exists.

## Risks
- **Origin-wide worker.** Scope `/` covers every page, including `/api/**` and the future client link. With no fetch handler that has no effect. From EZD-134 on, the cache rules decide what may be stored. Authenticated API responses, money fields (03 rule 2) and client-link pages (03 rule 11) must not be cached by mistake.
- **Contract with EZD-134.** EZD-134 must keep `/sw.js`, or unregister it, or installed devices keep an orphaned worker. Today's `skipWaiting` and `clients.claim` are only safe because nothing is cached. EZD-134 must decide the update flow together with its reload prompt (03 rule 12).
- **Client link and installation.** The manifest link is on every page under the root layout, so a homeowner on a share link (Phase 16) could add "EZ Draft" to their home screen, and it would open at `/sign-in`. The client-link ticket may want its own layout without the manifest link. That is its planner's call.
- **Leaving the app's scope.** In the installed app, links to EZ Binder (S01 "EZ Contractor Binder" link; the Back to EZ Binder control, 02) go to another origin outside scope. iPadOS opens them in an in-app Safari sheet; Chromium shows a browser bar. EZD-114 and the S01 back-link ticket should expect this.
- **Crew install.** R26 R15 assumes crews use the installed app on iPhone, but nothing tells them how to install it (iOS has no install prompt API). That is a product question for the Phase 14 crew-link planners (EZD-1421), not for this ticket.
- **Vercel preview protection.** If Vercel deployment protection is on for previews, browsers fetch the manifest without cookies and may get a 401 there, so installing from a preview may not work. Production, where the Field check runs, is not affected.
- **Pinned Next.js specifics:** the metadata route content type, the Apple meta tag names (B4 accepts both forms), whether `themeColor` belongs on `viewport` or on `metadata`, and the `link rel="manifest"` attributes. The builder and test-author read the pinned version, not memory.
- **Icon rendering.** Chromium screenshots may differ slightly between Playwright versions. The PNGs are committed outputs and tests check only signature, size and opacity, so a later re-render changes bytes, not test results.
- **Performance.** The registration component adds well under 1 KB of JavaScript to every entry point. The client link and field pack each have a 200 KB budget (11 Budgets), and EZD-017 measures them. Registration waits for `load`, so it does not delay first paint. Icons and the manifest are not JavaScript.
- **Field check timing.** Installing on the iPhone or the Surface needs HTTPS at the production address, so it waits on EZD-003, the Phase 0 merge (Q-0032 (a)) and Josh's cloud sign-in runbook steps (EZD-007 Step 10; Q-0024 (a), Q-0033 (a), Q-0035 (a), Q-0036).
- **iPad not field-checked.** The ticket row's Field check says "Josh installs it on the iPad home screen", but Josh has no iPad (Q-0053, Q-0088). This plan's Field check uses his iPhone and Surface instead; the orchestrator owns the row and may reword it to match. The iPad install path is covered only by U3/B4's Apple meta tags and manifest checks, not by a device run.
