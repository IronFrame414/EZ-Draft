### Step 1: Online status, `app/src/lib/network/online.ts` (shared browser code, EZD-000 Folder layout "src/lib/")
- `createOnlineSource(target?: Pick<EventTarget, 'addEventListener' | 'removeEventListener'>, nav?: { onLine: boolean })` returns `{ subscribe(cb): () => void; getSnapshot(): boolean }`.
  - The defaults are `globalThis.window` and `globalThis.navigator`. With no `window` (server), `getSnapshot` returns `true` and `subscribe` is a no-op.
  - It adds one `online` and one `offline` listener per subscriber and removes both on unsubscribe. It adds no timer and no request (11 rule 11; EZD-018 no-polling lint).
- `useOnline(): boolean` is `useSyncExternalStore(source.subscribe, source.getSnapshot, () => true)`. The server snapshot is `true`, so server markup never shows the banner, and the banner appears after hydration if the device is offline (*planner's choice*: no hydration mismatch).
- One module-level default source for the app. Later tickets (EZD-120b outbox, EZD-1401 icon) reuse `useOnline` rather than adding their own listeners (docs, Step 9). EZD-018's hub keeps its own `online` listener (vault/plans/EZD-018.md Step 5 item 5).

### Step 2: Skeleton, `app/src/components/states/Skeleton.tsx` + `Skeleton.module.css`
- `Skeleton({ width?, height?, radius? }: { width?: string; height?: string; radius?: 'sm' | 'md' | 'lg' })` renders `<span data-skeleton aria-hidden="true" className=… style={{ width, height }} />`.
  - `display: block`; `background: var(--ez-divider)`.
  - Radius: `sm` → `var(--ez-radius-5)`, `md` (default) → `var(--ez-radius-8)`, `lg` → `var(--ez-radius-12)` (04 radii).
  - Default `width: 100%` and `height: 14px` (*planner's choice*).
  - It does not animate (*planner's choice*: nothing moves on screen while idle and nothing costs frames on the iPad; 11 rule 4's intent).
- `SkeletonGroup({ count, children, className? })` renders `<div data-skeleton-group aria-busy="true" className=…>` with `children` repeated `count` times (keys by index).
  - `aria-busy` tells assistive tech the region is loading without adding wording (11 Accessibility; no new string).
  - EZD-117b passes `count={6}` (S01 "placeholder count 6") and a card-shaped child built from `Skeleton`s.
- Server-safe: no `'use client'`, no state.

### Step 3: Async loading, `async-state.ts` + `AsyncView.tsx` (`'use client'`)
- `async-state.ts` (no React) holds a reducer, `asyncReducer(state, action)`:
  - state `{ status: 'pending' | 'ready' | 'error'; run: number; data?: unknown; error?: unknown }`;
  - actions `{ type: 'start'; run } | { type: 'resolve'; run; data } | { type: 'reject'; run; error }`;
  - a `resolve`/`reject` whose `run` is not the current `run` is ignored, so a late answer from an earlier try never replaces a newer one;
  - `start` sets `pending`, clears `data` and `error`, and sets `run`.
- `useAsync<T>(load: (signal: AbortSignal) => Promise<T>)` returns `{ status, data, error, retry }`:
  - on mount and on each `retry()` it dispatches `start` with the next run number and calls `load` with a fresh `AbortController` signal;
  - it aborts the previous controller on retry and on unmount;
  - callers pass a stable `load` (`useCallback`), and docs say so.
- `AsyncView<T>({ load, skeleton, errorMessage, errorParams?, children }: { load; skeleton: ReactNode; errorMessage: MessageKey; errorParams?: MessageParams; children: (data: T) => ReactNode })` renders:
  - `pending` → `skeleton`;
  - `error` → `<InlineError message={errorMessage} params={errorParams} onRetry={retry} />`;
  - `ready` → `children(data)`.
  - Sources: S01 States (skeleton while loading; inline error with Retry); EZD-000 Errors and logging ("failed loads use the inline error with Retry (EZD-015)").
- No polling and no timers (11 rule 11).

### Step 5: Toast, `toast-store.ts`, `ToastProvider.tsx`, `ToastList.tsx`, `Toast.module.css`
- **`toast-store.ts` (no React)**: `createToastStore({ setTimeout, clearTimeout } = globalThis)` returns `{ show, dismiss, subscribe, getSnapshot }`.
  - `show(options)` returns `id` (an incrementing string). `options` is a union (*planner's choice* of shape, enforcing Q-0058 (a)):
    - plain toast: `{ message, params?, tone?: 'neutral', duration?: number | null }`;
    - toast that needs an answer: `{ message, params?, tone?: 'neutral', action: { label: MessageKey; onPress: () => void }, duration?: null }`. The type does not accept a number `duration` with an `action`.
    - A plain toast's `duration` defaults to `TOAST_DEFAULT_MS` = `5000` (Q-0058 (a): "toasts clear after 5 seconds"), exported from `toast-store.ts`.
    - A toast with an `action` always has duration `null`, whatever is passed at run time (Q-0058 (a): "toasts that need an answer stay until used or closed"; needed by EZD-126's "Start editing", S06).
    - `null` keeps the toast until it is closed or its action is pressed.
    - A number starts one `setTimeout` that calls `dismiss(id)`. This is a one-shot timer, not polling; EZD-018's lint allows `setTimeout`.
  - `dismiss(id)` removes the toast and clears its timer.
  - The snapshot is an immutable array, oldest first. Toasts stack, with no maximum (*planner's choice*).
  - `tone` is `'neutral'` only. EZD-126 extends the union with the green tone of S06 and adds its board tokens (Level-1 list).
- **`ToastProvider({ children })`** (`'use client'`) creates one store per provider (`useState`) and puts it in context.
  - `useToast()` returns `{ show, dismiss }`. It throws an `Error` whose message contains `ToastProvider` when used outside the provider (same pattern as EZD-026a `useT`).
  - The provider renders `children` and `<ToastViewport />`.
  - `ToastViewport` subscribes with `useSyncExternalStore`, so only the viewport re-renders when toasts change (11 rule 4).
- **`ToastList({ toasts, onDismiss })`** is the presentational part, so it can be unit-tested statically.
  - An always-mounted `<div data-toast-viewport role="status" aria-live="polite">`, so a toast is announced when it is added (*planner's choice*). It is `position: fixed; right: 16px; bottom: 16px; max-width: calc(100vw - 32px); display: flex; flex-direction: column; gap: 8px`, and it stacks above the dialog overlay (Step 6).
  - S06 places its toast at "Canvas, bottom right". Bottom right of the viewport is used for all screens, and EZD-126 may add a placement prop.
  - Each toast is `<div data-toast>`.
  - Card look from S06 `class="card"` with no green overrides: `background: var(--ez-surface); border: 1px solid var(--ez-border); box-shadow: var(--ez-shadow-card)`.
  - S06 layout: `display: flex; align-items: center; gap: 10px; padding: 9px 10px 9px 12px; border-radius: var(--ez-radius-10); font-size: 13px; color: var(--ez-ink)`.
  - Content, in order:
    1. the text `t(message, params)`;
    2. optional action `StateButton` (compact) `t(action.label)`, which calls `onPress` and then dismisses;
    3. a close button: `StateButton` variant `icon`, `<Icon name="close" size={18} />`, with `aria-label` and `title` both `t('common.close')`. The label is from the boards' `aria-label="Close"`, and the title satisfies 11 "labels and tooltips". It dismisses the toast.
  - The close button is on every toast, so a toast with `duration: null` can always be closed (11 Accessibility) (*planner's choice*).

### Step 6: Confirm dialog, `confirm-controller.ts`, `ConfirmProvider.tsx`, `ConfirmDialog.module.css`; buttons `StateButton.tsx` + `.module.css`
- **`confirm-controller.ts` (no React)**: `createConfirmController()` returns `{ open, choose, subscribe, getSnapshot }`.
  - `open(options): Promise<ConfirmChoice>` with `type ConfirmChoice = 'confirm' | 'cancel'`.

  - If `open` is called while a dialog is open, the open one resolves `'cancel'` and the new one replaces it (*planner's choice*: one dialog at a time).

### Data flow
- An entry-point layout resolves the language → `MessagesProvider` → `StateHost` → the screen.
- A screen's `AsyncView` calls its `load`, which goes through EZD-000's fetch helper to a route. It shows the skeleton, then the data or the inline error. Retry calls `load` again.
- `OfflineBanner` reads `useOnline()`, which is driven by browser events.
- `useToast().show` and `useConfirm()` go to per-provider stores, rendered by the viewport and the dialog.
- No server calls of its own, no Realtime, no polling (11 rule 11).

## Risks
- **Spanish quality (Q-0030 (a)).** The builder writes the Spanish of the four `common.` keys; it is checked only at the field checks and in Phase 15. These words (Retry, Offline, Cancel, Close) appear on every crew phone screen, so a poor choice is widely seen until then.
- **Toast time (Q-0058 (a)).** 5 seconds applies to every plain toast, including crew phones. A caller that needs the user to act must pass an `action`, which keeps the toast until used or closed; the store enforces this (Step 5, U5).
- **Earlier tests.** Only EZD-026a's lint test gets an EZD-015 describe (test-author; the builder may not edit it, CLAUDE.md rule 6). EZD-010 T1/T2 and T8 and EZD-026a A2 no longer assert fixed counts (phase 0 plan review, finding 8), so the new tokens, icons and keys need no edit to them.
- **Route error keys not added here.** No EZD-015 component shows a route error body; callers pass their own message key. `error.db_unavailable` is EZD-026a's (English per Q-0086 (a), "Can't reach the database. Try again in a minute."), and `error.not_authorized` / `error.job_not_found` are EZD-009's (Q-0086 (a)). A screen that shows a route `message_key` passes it to `InlineError` unchanged.
- **Offline detection.** `navigator.onLine === true` does not prove the server is reachable (captive portal, server down). Those cases show the inline error, not the offline banner. Phase 14's acceptance tests switch the network the same way, through EZD-016a's helper, so they agree with this definition.
- **Duplicate button look.** `StateButton` and EZD-011's `HeaderButton` both draw the board `.b`/`.bp`. Keeping `components/states/` free of `components/shell/` imports is deliberate (U15). A later shared button may merge them, and the code-reviewer may prefer that now.
- **Toast placement.** The viewport sits at the window's bottom right. S06 draws its toast inside the canvas column, above a floating toolbar (`right: 14px; bottom: 76px`). EZD-126 may add a placement option or a tone; both extend this API.
- **Bundle size.** Radix AlertDialog brings its dialog, focus-scope, portal and dismissable-layer modules into every entry point that mounts `StateHost`, including the field pack and client link (200 KB each, 11 Budgets). EZD-017/020 measure it. If needed, `ConfirmProvider` can load the Radix part lazily on the first `confirm()` call without changing the API.
- **Performance.** `useOnline`, the toast viewport and the confirm host use `useSyncExternalStore` and re-render only on their own changes. There is no pointer or scroll listener, no interval and no React commit during a pan (11 rule 4; EZD-017). Each toast has one one-shot timer.
- **No board for these states.** The look follows the nearest boards and the spec tokens. Josh first sees it at the Phase 0 preview review.
