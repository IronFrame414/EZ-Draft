### Step 1: Types (builder) `app/src/server/email/types.ts`
Server-only by location (EZD-000 Folder layout `src/server/`). Exact shapes, because the test-author's stub is written against them:

```ts
export type EmailMessage = {
  from: string;              // "Name <address>" or "address"
  to: string;                // exactly one recipient
  replyTo?: string;
  subject: string;
  text: string;
  html: string;
};
export type TransportResult =
  | { ok: true; messageId: string }
  | { ok: false; code: 'email_provider_error' | 'email_live_blocked_in_tests' };
export interface EmailTransport {
  readonly name: 'stub' | 'resend';
  send(message: EmailMessage, opts?: { idempotencyKey?: string }): Promise<TransportResult>;
}
export type SendEmailInput = {
  to: string;
  subject: string;
  paragraphs: string[];               // caller's text, already translated
  link: { url: string; label: string };
  replyTo?: string;
  fromName?: string;                  // replaces the display name of EMAIL_FROM for this message
  lang?: 'en' | 'es';                 // <html lang>, default 'en' (R26 R17)
  idempotencyKey?: string;
};
export type EmailErrorCode =
  | 'email_transport_not_set' | 'email_from_not_set' | 'email_key_not_set'
  | 'email_stub_not_allowed' | 'email_provider_error' | 'email_live_blocked_in_tests';
export type SendEmailResult = {
  link: string;                       // always input.link.url, also on failure
  status: 'sent' | 'failed';
  transport: 'stub' | 'resend' | null;
  messageId: string | null;
  errorCode: EmailErrorCode | null;
};
```
- One recipient per call (*planner's choice*): magic links and invite links differ per person (EZD-105; R26 R15), and one result per recipient gives the UI one Copy link per person. Callers loop for several recipients.
- `idempotencyKey`: job handlers must be safe to run twice (11 Operations), and EZD-024 sends from jobs. Passed to Resend's idempotency option.

### Step 2: Body builder (builder) `app/src/server/email/body.ts`
`buildEmailBody({ paragraphs, link, lang }) → { text, html }`, a pure function.
- `text` = the paragraphs joined by `\n\n`, then `\n\n`, then `link.url` on its own line, then `\n`. With no paragraphs, `text` = `link.url + '\n'`.
- `html` = `<!doctype html><html lang="<lang>"><body>`, one `<p>` per paragraph, then `<p><a href="<url>">label</a></p>`, then `<p><url as text></p>`, then `</body></html>`. Every paragraph, the label and the URL are HTML-escaped (`&` `<` `>` `"` `'`); the `href` uses the same escape. The URL is printed as text too, so it can be copied when the button does not work (R24 #15 reason: spam folders and link scanners). No styling, no images, no tracking pixel.
- The only link in either body is `link.url` (Done when).

### Step 3: Stub transport (test-author; harness) `app/src/server/email/test-harness/stub-transport.ts`
`createStubTransport({ dir }: { dir?: string }) → EmailTransport` with `name: 'stub'`, plus `readStubOutbox(): StubMessage[]` and `clearStubOutbox(): void`.
- `StubMessage` = `EmailMessage` + `{ id: string; idempotencyKey: string | null; sentAt: string }` (ISO time). `id` = `stub_` + `crypto.randomUUID()`; `send` returns `{ ok: true, messageId: id }`.
- The outbox is an array kept on `globalThis` (key `__ezdEmailStubOutbox`), so every module copy in one process shares it.
- Idempotency like the provider: a second `send` with an `idempotencyKey` already in the outbox records nothing and returns the first message's id.
- **File sink:** when `dir` is set (from `EMAIL_STUB_DIR`, Step 4), each recorded message is also written as `<dir>/<Date.now()>-<id>.json` (directory created if missing). This lets a browser test, which runs in a different process from the app server, read the email. EZD-110's Done when needs this ("the stub transport records its email" in a browser test).
- `app/test-harness/email-outbox.ts` (test-author): `readStubOutboxDir(dir): StubMessage[]` (sorted by file name), `clearStubOutboxDir(dir)`, and `linksIn(message): { text: string[]; html: string[] }`, which returns every `http(s)://…` URL in the text body and every unescaped `href` in the HTML body. Later tickets (EZD-024, EZD-105, EZD-110) use these.
- Location: the stub sits under `src/server/email/` because the helper picks it at run time from env (ticket Scope); it is a `test-harness/` path so the test-author owns it (guard-paths.mjs; PROCESS.md harness tickets).

### Step 4: Transport choice (builder) `app/src/server/email/transport.ts`
`getEmailTransport(env: Record<string, string | undefined>) → { ok: true; transport: EmailTransport; from: string } | { ok: false; code: EmailErrorCode }`. Reads env **per call, never at module load** (EZD-004 Step 5 rule; `next build` runs with no email env).

| Env | Result |
| --- | --- |
| `EMAIL_TRANSPORT` unset, empty, or not `stub` / `resend` | `email_transport_not_set` |
| `EMAIL_FROM` unset, or not `address` / `Name <address>` | `email_from_not_set` |
| `EMAIL_TRANSPORT=stub` and `VERCEL_ENV=production` | `email_stub_not_allowed` (*planner's choice*: production must never drop email silently) |
| `EMAIL_TRANSPORT=stub` otherwise | stub transport, with `dir` = `EMAIL_STUB_DIR` if set |
| `EMAIL_TRANSPORT=resend` and `RESEND_API_KEY` unset or empty | `email_key_not_set` (same pattern as EZD-021's "AI key not set") |
| `EMAIL_TRANSPORT=resend` with a key | Resend transport (Step 5) |

There is no default transport: an unset value fails loudly instead of choosing for the caller (*planner's choice*). Tests get `stub` from the Vitest config (Step 8).

### Step 5: Resend transport (builder) `app/src/server/email/resend-transport.ts`
`createResendTransport({ apiKey, client? }) → EmailTransport` with `name: 'resend'`.
- `client` defaults to `new Resend(apiKey)` from the `resend` package (02 Named tools; EZD-000 Dependencies row). Tests inject a fake `client` with an `emails.send` method, so no test reaches the network.
- `send` calls `client.emails.send({ from, to, replyTo, subject, text, html }, { idempotencyKey })`. The builder takes the exact field and option names from the pinned SDK's types (for example `replyTo` against older `reply_to`). If the pinned SDK has no idempotency option, the builder raises a question rather than dropping it.
- The SDK returns `{ data, error }`. `data.id` → `{ ok: true, messageId }`. An `error` object or a thrown error → `{ ok: false, code: 'email_provider_error' }`. `send` never throws.
- **Live block in unit tests:** if `process.env.VITEST` is set and no `client` was injected, `send` returns `{ ok: false, code: 'email_live_blocked_in_tests' }` without any request (CLAUDE.md rule 10). EZD-021 later adds the suite-wide guard.

### Step 6 (part A): Send helper (builder) `app/src/server/email/send.ts`, `index.ts`
`sendEmail(input: SendEmailInput, options?: { env?: Record<string, string | undefined> }): Promise<SendEmailResult>`; `env` defaults to `process.env`.
1. Validate `input` with Zod (02 Named tools). Invalid input throws `EmailInputError` (`code = 'email_invalid_input'`), because it is a programming error in the caller:
   - `to` and `replyTo` must be email addresses;
   - `subject` must be non-empty and contain no line break (header injection);
   - `link.url` must parse with `new URL()` and have protocol `https:` or `http:`; anything else (`javascript:`, `ftp:`, `mailto:`, a relative path) is refused;
   - `link.label` must be non-empty.
2. `getEmailTransport(env)`. On failure, return `{ link: input.link.url, status: 'failed', transport: null, messageId: null, errorCode: <code> }`.
3. Build the body (Step 2) and the `from` (`fromName`, when given, replaces the display name of `EMAIL_FROM`; quotes and line breaks removed from it).
4. `transport.send(message, { idempotencyKey })`. Return `status: 'sent'` with `messageId`, or `status: 'failed'` with the transport's code.
5. **The link is in every result, sent or failed** (R24 #15; 02 Users and role presets; 11 Security "Copy link fallback"), so the caller can always show Copy link.
- No log line: `logger.ts` does not exist yet and C8 forbids `console.` (EZD-000 C8). Recipients and links (which hold tokens) must never be logged (EZD-000 Errors and logging). EZD-024 routes failures to Sentry later.
- `index.ts` exports `sendEmail`, `EmailInputError` and the types. Nothing outside `src/server/` imports it (EZD-000 Server-only data access; EZD-133 adds the lint rule).

## Risks
- **Shared Resend quota and plan (Q-0003).** EZ Binder and EZ Draft share one account's sending limits and sender reputation. 11 Running cost assumes Email $0. If the account is on Resend's free plan, its daily limit (100 a day as of the planner's knowledge, not a vault source) is shared; invites, notifications and owner error emails could hit it on a busy day. Q-0035 asks Josh to state the plan.
- **Spam placement.** R24 #15 expects some mail in spam; the returned link is the fallback. A new subdomain starts with no sending reputation; the apex's DMARC is `p=quarantine` with no `sp=`, so a DKIM failure on the subdomain sends mail to spam. The field check shows it.
- **SDK specifics.** Field names (`replyTo`), the idempotency option and any peer package depend on the pinned `resend` version; the test-author and builder read the pinned SDK's types, not memory. A peer package needs a Dependencies row (C1).
- **Supabase Auth emails** (EZD-007) do not go through this helper. Until runbook step 6 is done on the cloud projects (after Q-0024), cloud magic links use Supabase's built-in sender, which is rate-limited and meant for testing. Locally, EZD-007 reads them from the mail catcher, which is unaffected.
- **The stub ships in server code.** It is selected only by env and refused when `VERCEL_ENV=production` (T3e). A preview with `EMAIL_TRANSPORT=stub` sends nothing; EZD-023 chooses preview values.
- **Download size.** The helper and SDK are under `src/server/` and must never be imported from browser code (EZD-000 Server-only data access; EZD-133 lint later); otherwise they count against the 200 KB budgets (11 Budgets), which EZD-017 measures.
- **DNS name clash.** Resend's records go under `send.ezdraft` and `resend._domainkey.ezdraft`. A record at `ezdraft` itself would clash with EZD-003's CNAME; the runbook says so.
