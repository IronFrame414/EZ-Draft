### Step 2: Inputs (builder)
- **Rooms manifest** (`src/manifest.ts`), JSON:
  ```json
  { "rooms": [ { "id": "room-1", "label": "Smith kitchen", "image": "room-1.png", "finishes": "…" } ] }
  ```
  - `id` matches `^[a-z0-9][a-z0-9-]{0,39}$` (it becomes a folder name); ids are unique.
  - `image` is a path relative to the manifest file, ending `.png`, `.jpg` or `.jpeg`. These are the types EZD-021's `AiImage` accepts that cameras and design tools export. `.webp` is also accepted. Anything else (including `.heic`) → `input_unsupported_type`.
  - `finishes` is non-empty: Josh's one or two sentences on the room's finishes (Q-0083 (a)).
  - **Instruction** (Q-0083 (a): "fixed opening sentence plus one or two sentences from Josh per room on finishes"): `INSTRUCTION_OPENING + ' ' + finishes`, where `INSTRUCTION_OPENING` (in `src/manifest.ts`) is exactly the opening approved with Q-0083 (a): "Turn this 3D view into a photograph of the finished room. Keep the room's shape and every cabinet, fixture, door and window exactly where they are and at the same size." The same instruction goes to all three providers.
  - A broken manifest → `manifest_invalid` before any request.
- **Input size.** The long side must be at most **2048 px**, read from the file header (`src/image-info.ts`), else `input_too_large`.
  - *Planner's choice:* it keeps every provider's request small and gives all three the same input. 2048 px is the size EZD-1106 already uses for site-photo display copies.
  - The spike does no resizing, so it needs no image library. The README tells Josh how to export at that size.
- **Models, chosen at run time** (Q-0084, deferred by Josh: "the script lets him pick at run time"). `--models <path>` names a JSON list of `{ provider: 'gemini' | 'openai' | 'bfl', model: string, label?: string, settings?: object }`; without it the run uses the spike's `models.json`, a starting list Josh may copy and edit.
  - Each `model` matches EZD-021's pattern `^[a-z0-9][a-z0-9.\-]{0,99}$`. `label` matches `^[a-z0-9][a-z0-9-]{0,39}$` and defaults to `model`; labels are unique within a provider, so one model can run twice with different settings.
  - `settings` are provider request fields the spike adds to the outgoing request inside its capture wrapper (Step 3), without changing app code (EZD-021 sends no size or quality fields): for `gemini`, top-level JSON body keys, and keys inside `generationConfig` merged one level; for `openai`, extra form fields (string values only); for `bfl`, top-level keys of the first POST body. A key the adapter already sets (for example `model`, `prompt`, `contents`, `input_image`, `generationConfig.responseModalities`) → `models_invalid` before any request (*planner's choice*: settings may add, never replace, what EZD-021 sends).
  - The starting `models.json` holds one model per provider with no settings: ids from each provider's docs on the build date *(builder confirms)*. It is not a decision; Josh picks at run time (Q-0084).
  - Run order is fixed: rooms in manifest order, and within a room `gemini`, `openai`, `bfl` (Q-0016's order), then the models file's order within a provider.
- **Prices** are looked up by `label`, then by `model`; `--prices <path>` replaces `prices.json` at run time. A model with no entry gets cost `null` with reason `price_not_set` (Step 4) and is listed on the confirmation screen.
- **Prices** (`prices.json`, builder), keyed by model id:
  ```json
  { "models": { "<model id>": { "provider": "gemini", "unit": "per_token", "inputPerMTok": 0, "outputPerMTok": 0, "sourceUrl": "https://…", "retrieved": "YYYY-MM-DD" },
                "<model id>": { "provider": "bfl", "unit": "per_image", "perImage": 0, "sourceUrl": "https://…", "retrieved": "YYYY-MM-DD" } } }
  ```
  - Rates are US dollars per million tokens, or per output image.
  - The builder fills them from the official price pages *(builder confirms)*. A rate it cannot confirm is `null`, never guessed; the cost for that model is then `null` with reason `price_not_set`.
  - The vault gives no prices: S15f's figures are examples (KNOWN-LIMITS 5).

### Step 3: Calling the providers (builder) `src/providers.ts`, `src/capture-fetch.ts`
- For each room × model, one call to EZD-021's adapter for that provider. Request:

  ```ts
  { purpose, provider, model, instruction: INSTRUCTION_OPENING + ' ' + room.finishes, image: { mediaType, data } }
  ```

  - `purpose` is `'test.image_edit'` in stub mode, so the built-in recordings match, and `'spike.render_trial'` in live mode.
  - If EZD-021 does not export an adapter by itself, the builder raises a question. This ticket changes no app file.
- The spike gives each adapter its own context:
  - `signal`: `AbortSignal.timeout(600000)`;
  - `timeLeft`: the time left to that deadline;
  - `sleep(ms)`: a timer that respects the signal (injectable in tests).

  600,000 ms (10 min) per render is a *planner's choice*, above S08's slowest tier estimate ("Photoreal … ~6 min").
- **Stub mode:**
  - key `stub-key`;
  - `fetch` = `createRecordedFetch(getStubRecording(provider, 'test.image_edit'))`, made fresh for every render, because a recording's exchanges are used up in order;
  - real keys are never read.
- **Live mode:**
  - key from `process.env[PROVIDER_KEY_ENV[provider]]`. Every needed key is checked **before the first call**; a missing or blank key → `AiError` `ai_key_not_set` (EZD-021 Step 1 wording `AI key not set`), and nothing is sent;
  - `fetch` = `globalThis.fetch`;
  - base URL for `gemini` and `bfl` from EZD-021's `getProviderBaseUrl(provider, process.env)` (Q-0076, deferred: Josh sets `GEMINI_BASE_URL` / `BFL_BASE_URL` in `.env.local` only if his chosen account needs it). Stub mode always uses the defaults, so the built-in recordings match.
- **Capture wrapper** (both modes) around the `fetch` given to the adapter. It adds the model entry's `settings` to the outgoing request (Step 2; Q-0084), then for every exchange it records:
  - method;
  - URL, with any `key` query parameter removed;
  - status;
  - the response's request-id header (`request-id` or `x-request-id`), if present;
  - the response JSON.

  Redaction rules for the recorded data:
  - every string longer than 256 characters is replaced by `"<redacted N chars>"` (*planner's choice*). That removes image data and long text;
  - non-JSON bodies (the BFL image download) are recorded as content type and byte length only;
  - **request headers and request bodies are never recorded** (they carry the key, the image and the instruction).

  The provider's usage block is read from the recorded JSON as `rawUsage`. Examples: Gemini `usageMetadata`, OpenAI `usage` with its token details, BFL status fields. The EZD-021 recordings and a later recording-refresh ticket can use these files.
- No retries: a failed render is recorded and the run goes on. Retrying is Josh's choice with `--resume` (Step 5), so a paid call is never repeated unasked (Q-0059 notes that retries cost money).
- Calls run one at a time.

### Step 4: Cost (builder) `src/cost.ts`
- `costFor(usage, price) → { costMicroUsd: number | null, reason: null | 'price_not_set' | 'usage_missing' | 'render_failed' }`:
  - `per_token`: `inputTokens × inputPerMTok + outputTokens × outputPerMTok`. Tokens × $/M-tokens is micro-dollars directly.
  - `per_image`: `images × perImage × 1,000,000`.
  - The sum is rounded once with `Math.round` to whole micro-dollars. `costUsd = costMicroUsd / 1,000,000`.
  - A `per_token` price with a null token count → `usage_missing`. A null rate → `price_not_set`. A failed render → `render_failed`, with cost `null`: S08 says failed renders are "not counted against the allowance". What the provider actually bills for a failure shows up in the billed check.
  - Integer micro-dollars avoid floating-point drift in totals (*planner's choice*).
- **Known limit, recorded in the README:**
  - EZD-021's usage has one input count, while some providers price image-input and text-input tokens differently.
  - The estimate uses one input rate. `rawUsage` keeps the breakdown, and the billed check is the measured figure.
- **Spend cap** (live: required; stub: optional, so tests can check it). `--max-usd <n>`:
  - before each render, if the run's estimated total is already ≥ n, the run stops with status `stopped_at_cap`, so it overshoots by at most one render;
  - the cap value is Josh's to type, so no default exists (CLAUDE.md rule 4: spending is Josh's);
  - a model whose price is `null` counts as 0 toward the cap. The confirmation screen (Step 6) says which models have no price.

### Step 5: Outputs (builder) `src/trial.ts`, `src/report.ts`
- `runTrial(options) → Promise<TrialSummary>` does the loop; `src/cli.ts` parses arguments (`node:util` `parseArgs`, ignoring a leading `--` that pnpm passes through) and calls it. The run folder is either `--run-dir <dir>`, emptied first, or `runs/<runId>` with `runId` = UTC `YYYYMMDD-HHMMSS-<mode>`.
- Per room: `<room>/input.<ext>`, a copy of the input, so the contact sheet stands alone; `<room>/<provider>--<label>.<ext>`, the output image (extension from its media type); `<room>/<provider>--<label>.exchanges.json`, the redacted exchanges from Step 3 (`label` defaults to the model id, Step 2).
- `costs.json`, the **cost record**: `{ runId, mode, startedAt, finishedAt, status, capUsd, totalMicroUsd, records: CostRecord[] }`. Each `CostRecord` holds:
  - which render: `roomId`, `provider`, `model`, `label`, `settings` (as given, or null);
  - the outcome: `status` (`ok` or `failed`), `errorCode` (the `AiError` code or null);
  - the image: `output` (relative path or null), `mediaType`, `bytes`, `width`, `height`;
  - usage: `usage` (EZD-021 shape), `rawUsage`;
  - price: `price` (`{ unit, rates, sourceUrl, retrieved }` or null), `costMicroUsd`, `costUsd`, `costReason`;
  - `requestId`, `ms` (wall clock of the call), `startedAt`.
- `costs.csv` (opens in Excel), with the header exactly `room,provider,model,status,error_code,cost_usd,ms,width,height,output` and one line per record.
- `summary` inside `costs.json`. Per model: `ok`, `failed`, `totalMicroUsd`, `meanMicroUsd` over ok renders, `meanMs`.
- `index.html`, a contact sheet for Josh's comparison. For each room it shows one row: the input, then the output of each model in run order. Each image has a caption with the provider, model id, estimated cost and seconds. Images use relative paths, and the page needs no server or script. Labels are ids and numbers only, with no product wording.
- `--resume <runDir>` reuses that run folder and its `runId`. It re-runs only the room × model pairs without an `ok` record and rewrites `costs.json`, `costs.csv` and `index.html`.
- `--providers gemini,openai` limits a run to some providers, for example while one key is still missing. Josh can complete it later with `--resume`.
- Run status: `complete`, `complete_with_failures`, `stopped_at_cap` or `cancelled`. CLI exit code (*planner's choice*):
  - **0** when the run ends with a status;
  - **2** when it is refused before any call (Step 6, or an invalid manifest, input or price file);
  - **1** on an unexpected crash.

## Risks
- **EZD-021's adapters must be importable by themselves.**
