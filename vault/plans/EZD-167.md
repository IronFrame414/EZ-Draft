# EZD-167 · Fix: path alias cannot bypass the import-boundaries lint

- **ACs:** AC-EZD-167-1 (`vault/spec/acceptance-criteria.md` row 324, generated from Done-when)
- **Complexity:** low (section 8)
- **User-visible result:** nothing on screen; the lint that keeps heavy code out of the fast pages can no longer be dodged by writing `@/…` instead of a relative path, so those pages stay fast.
- Phase: 1 · Planned by: planner · Date: 2026-10-24 · Status: planned

## 1. What to build

Chosen path (the ticket row allows either): **teach the rule to resolve the alias**, and keep the alias. Reasons: the Done-when's main clause is "is reported" (AC-EZD-167-1); the rule then stays correct while `app/tsconfig.json` keeps the create-next-app alias Next.js resolves (STATUS EZD-001 deviation (6); app/tsconfig.json:13-15); and a guard test makes any future `paths` or `baseUrl` entry fail until the rule knows it, which closes the gap for good (Q-0268). Removing the alias would leave no lint test case to add, against the ticket Scope ("Add a lint test case either way").

The rule runs on non-test files only (`eslint.config.mjs` EZD-020 block `ignores`), so "a test file importing `@/lazy/dev-sample`" in the Done-when means a lint test case that lints that import as a non-test file path, as EZD-020's L5 does.

No data, no migration, no UI.

| Remove the alias or teach the rule | Teach the rule; `app/tsconfig.json` is not edited | ticket Scope; AC-EZD-167-1; section 1 reasons |

| Path normalizing | `path.posix.join`, same as the relative branch (collapses `..` and duplicate `/`) | `import-boundaries.mjs` relative branch |
| Order of alias vs relative | Relative first (a spec starting `.` is never an alias), then aliases in list order, first match wins | `HEAVY_PACKAGES` "first match wins" convention, boundaries.mjs |
| `import()` and type-only imports through the alias | Never reported, as for relative paths | `import-boundaries.mjs` header; architecture `### Entry points…` |
