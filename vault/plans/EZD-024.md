### How the Done when is read (Level 1)
- "the stub transport" = the Sentry stub transport this ticket adds (ticket Scope: "with a stub transport in tests").
- "queues one owner email" = the EZD-008 stub email outbox records exactly one message to the alert recipient (EZD-008 Step 3: the stub "records messages").
- "a second identical error queues none" = a second error with the same fingerprint (Step 3) adds no message to that outbox.
- "the owner" = the recipients set by **Q-0067 (b)**: a new-error email goes to the single `ALERT_EMAIL_TO` address (errors belong to no company); a failed-job or failed-webhook email goes to `ALERT_EMAIL_TO` **and** to the Owner(s) of that job's company, meaning its active members who hold Manage users and settings (Step 5). In the Done when, "one owner email" is the one `ALERT_EMAIL_TO` message of a new error.
- Owner emails are English: they go to the office, and R26 R17 keeps office text English in v1.

### Design in one paragraph
Every error, wherever it starts, ends in one server module, `app/src/server/errors/`. Server errors arrive through Next.js's `onRequestError` hook and through explicit `reportError()` calls (job runner, `after()` kick, email failures). Browser errors (and later the render worker's) are sent by the Sentry SDK to the app's own tunnel route `/api/monitoring`, never straight to Sentry. That module (1) scrubs the event, (2) hands it to Sentry through the server client, whose transport is real Sentry, the stub, or off, chosen by env, and (3) records the error's fingerprint in the `error_alert` table through one database function. That function tells the caller whether this is the first time the fingerprint can be emailed. Only then does the module send the alert with EZD-008's `sendEmail`: one message to `ALERT_EMAIL_TO` for a new error. Failed jobs (EZD-009 `onJobFailed`) and failed webhooks (`reportWebhookFailure`, called by EZD-1301 later) use the same table and the same email path with their own fingerprints, and their alert also goes to the Owner(s) of that company, one message each (Q-0067 (b)).

### Step 1: Sentry options from env (builder) `app/src/server/errors/sentry-options.ts`
`getSentryOptions(env)` reads env per call, never at module load (EZD-004 Step 5 rule). It returns `{ enabled: true, dsn, transport, environment, release } | { enabled: false, code }`:

| Env | Result |
| --- | --- |
| `SENTRY_TRANSPORT` unset or empty | `{ enabled: false, code: 'sentry_off' }` |
| `SENTRY_TRANSPORT` not `stub` / `sentry` | `{ enabled: false, code: 'sentry_transport_invalid' }` |
| `stub` and `VERCEL_ENV=production` | `{ enabled: false, code: 'sentry_stub_not_allowed' }` (same rule as EZD-008 T3e) |
| `stub` otherwise | enabled; `dsn` = `PLACEHOLDER_DSN`; transport = the stub (Step 2) with `dir` = `SENTRY_STUB_DIR` if set |
| `sentry` and `SENTRY_DSN` unset or not a valid DSN | `{ enabled: false, code: 'sentry_dsn_not_set' }` |
| `sentry` and `process.env.VITEST` set | `{ enabled: false, code: 'sentry_live_blocked_in_tests' }` (CLAUDE.md rule 10) |
| `sentry` with a DSN | enabled; `dsn` = `SENTRY_DSN`; the SDK's default transport |

- *Planner's choice:* an unset value turns Sentry **off** instead of failing (EZD-008 fails loudly). Error reporting must never break the app it reports on. The owner email path (Steps 4–5) does not depend on Sentry being on, so new errors still email the owner before Josh has a Sentry account.
- `PLACEHOLDER_DSN = 'https://public@ezdraft.invalid/1'` (`.invalid` is a reserved name, RFC 2606). The browser always uses it (Step 6), and the stub uses it on the server.
- Common options: `environment` = `VERCEL_ENV` or `'local'`; `release` = `VERCEL_GIT_COMMIT_SHA` when set; `sendDefaultPii: false`; no tracing, profiling or replay (11 Budgets; nothing in the spec asks for them); `beforeSend` = `scrubEvent` (Step 3).
- `initErrorReporting(env, runtimeTag)` calls `Sentry.init` with these options when enabled, sets the tag `ezd.source`, and returns the code. It is safe to call twice.

### Step 3: Scrubbing and fingerprints (builder)
**`app/src/lib/errors/scrub.ts`** (shared by browser and server; pure; no imports). It enforces EZD-000's "never logged" list (tokens, keys, secrets, request bodies, email addresses; vault/plans/EZD-000.md Errors and logging) on everything sent to Sentry or put in an owner email.
- `scrubText(s)` applies, in this order:
  1. In `http(s)://` URLs, drop everything from the first `?` or `#`.
  2. Email addresses `[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}` → `<email>`.
  3. UUIDs → `<uuid>`.
  4. Tokens: runs of 24 or more `[A-Za-z0-9_-]` that contain at least one letter and one digit → `<token>` (share-link tokens, keys).
  5. Six-digit numbers `\b\d{6}\b` → `<code>` (the sign-in code, R26 R15).
- `scrubEvent(event)` returns a copy in which:
  - every exception `value`, the `message` and `request.url` go through `scrubText`;
  - `request.cookies`, `request.data` and `request.query_string` are removed, and `request.headers` keeps only `User-Agent`;
  - `user` keeps only `id`;
  - `extra` and `breadcrumbs` are removed.
  - *Planner's choice:* breadcrumbs carry URLs and console text, and nothing in the spec needs them.

**`app/src/server/errors/fingerprint.ts`** (server; Web Crypto only, so it runs in the Node and edge runtimes):
- `normalizeMessage(s)` = `scrubText(s)`, then hex runs `\b[0-9a-f]{8,}\b` → `<hex>`, then digit runs → `<n>`, then whitespace collapsed to one space, trimmed, and cut to 300 characters.
- `normalizeLocation(source, where)`:
  - browser: the URL path only (no origin, query or hash). A path segment that is a UUID, all digits, or 16 or more characters containing a digit becomes `<id>`.
  - function: Next.js's route pattern (`context.routePath`, for example `/api/jobs/[id]`), or the `location` the caller passes.
  - job: the job kind.
  - worker: `worker`.
- `errorFingerprint({ source, type, message, location })` = SHA-256 hex of `` `${source}\n${type}\n${normalizeMessage(message)}\n${location}` ``.
- *Planner's choice:* no stack frames in the fingerprint. Bundled file names and minified function names change at every deploy, which would make every old error "new" again after each release.
- `type` is `error.name` for an `Error`, else `'NonError'`. The stored title is `` `${type}: ${scrubText(message)}` `` cut to 300 characters.

So `error` rows (null tenant) are visible to no member, and a tenant's failure rows are visible to its members in scope. EZD-135 shows them later.
- Grants, explicit per EZD-006's **Table grants convention** (vault/plans/EZD-006.md Step 5): the table's migration ends with `grant select on public.error_alert to authenticated;` and `grant select, insert, update, delete on public.error_alert to service_role;`, nothing for `anon`. - *Planner's choice, security-reviewer confirms:* `tenant_id` is nullable instead of adding a `TENANTLESS_TABLES` exemption. The column exists, so EZD-006's audit codes still apply, and rows with no tenant are unreachable through RLS.

Functions (migration `<ts>_create_error_alert_functions.sql`): `security definer`, `set search_path = ''`, `revoke all … from public`.

**`public.record_error_alert(p_kind, p_source, p_fingerprint, p_title, p_ref, p_tenant_id, p_project_id) returns table (alert_id uuid, is_new boolean, email_claim uuid, capped boolean)`.** Execute is granted to `anon`, `authenticated` and `service_role`.
1. **Caller role** comes from the JWT `role` claim *(builder confirms the accessor for the pinned Supabase)*.
   - Any caller other than `service_role` may only record `p_kind = 'error'` with `p_source` in (`browser`, `function`, `worker`); otherwise it raises `42501`. Its tenant and project are forced to null.
   - `service_role` (the job runner) may record any kind with the tenant and project it passes.
2. **Row cap** (*planner's choice*, an abuse limit, because the tunnel route is open to the internet): a non-`service_role` call whose fingerprint does not exist yet, made when 100 or more `error` rows already have `first_seen_at` within the last hour, inserts nothing. It returns `(null, false, null, true)`.
3. `insert … on conflict (fingerprint) do update set occurrences = occurrences + 1, last_seen_at = now()`. `is_new` is true only for the call that inserted the row. When eight identical first errors arrive at once, exactly one is new.
4. **Email claim.** If the row's `emailed_at` is null and `email_claim` is null, the function checks the email cap:
   - under the cap: it sets `email_claim = gen_random_uuid()`, `emailed_at = now()` and returns the claim;
   - at the cap: it returns `capped = true` and no claim, and the row stays unemailed.

   The **email cap** is **20 alerts per rolling hour** (Q-0068 (a)): the number of rows with `emailed_at` in the last hour. One alert's messages (to `ALERT_EMAIL_TO` and each Owner, Step 5) count once, so no recipient gets more than 20 alert emails in an hour. A row whose fingerprint was never emailed can be claimed by a later occurrence. This covers both a capped alert and a failed send (Step 5).
5. Returns at most one row, and never the row's other columns.

**`public.release_error_alert_email(p_alert_id uuid, p_claim uuid) returns boolean`.** Execute for `anon`, `authenticated`, `service_role`. When the row's `email_claim = p_claim`, it sets `email_claim` and `emailed_at` back to null and returns true; otherwise it returns false. Only the caller that holds the claim knows the uuid.

- *Planner's choice, security-reviewer confirms:* both functions are callable with the publishable key. The request path (the tunnel route and `onRequestError`) never uses the secret key; EZD-000 allows it only in job handlers, migrations, seeds and admin scripts. EZD-009 T20 keeps `SUPABASE_SECRET_KEY` only in `app/src/server/jobs/db.ts`.
- `pnpm db:types`; commit `database.types.ts` (EZD-004 T9).

### Step 5: Report and alert (builder) `app/src/server/errors/`
- `sentry.ts`: `captureToSentry(errorOrEvent, { source, location, tags })` returns the Sentry event id, or `null` when no client is initialised. It imports nothing from `email/`, so `email/send.ts` can import it without a cycle.
- `report.ts`:
  - `reportError(error: unknown, ctx: { source: 'function' | 'job'; location: string; tags?: Record<string, string>; alert?: boolean }, deps?)` → `Promise<ReportResult>`.
  - `ReportResult = { sentryEventId: string | null; alert: 'emailed' | 'already_emailed' | 'capped' | 'not_alerted' | 'email_failed' | 'store_unavailable'; alertId: string | null }`.
  - Steps:
    1. `captureToSentry` with tags `ezd.source` and `ezd.location`.
    2. If `alert === false`, stop with `not_alerted`.

## Risks
- **Download size (11 Budgets).** The Sentry browser SDK goes into every entry point, including the 200 KB client link and field pack. Default integrations are off (Step 6), but the SDK core still costs size. EZD-017 (position 21) and EZD-020 (position 25) build **before** this ticket (plan review finding 28 corrects the earlier text, which said after). So this ticket's own gate run must keep the `perf` step green with the Sentry SDK added: EZD-017's `js-size:*` rows (200,000 / 500,000 gzip bytes, Q-0071 (a), Q-0072 (a)) and EZD-020's `entry-contents:*` rows and bundle report, where `@sentry/` is a watched package (vault/plans/EZD-020.md Step 2 `WATCH_PACKAGES`, E7) (tickets README rule 2). If an entry goes over budget, the builder uses the fallback within this ticket: a small hand-written reporter that posts the same envelope format to the same tunnel; the server side does not change. If that is still over budget, the ticket goes `blocked` with the bundle report's numbers.
- **No source maps.** Stack traces from the browser and the bundled server will be minified in Sentry. Source-map upload needs a build-time Sentry secret, and no source asks for it, so it is left out. A later ticket can add it once Josh has a Sentry account.
- **Abuse of the tunnel.** Anyone can post envelopes. The DSN check stops relaying to other Sentry projects. The 100-new-errors-per-hour row cap and the Q-0068 email cap bound the table and the inbox. A flood still uses up those caps, which hides real new errors for up to an hour.
- **Store down means no email.** When the database is unreachable, errors reach Sentry but send no owner email (T13), because without the store every repeat would email. A database outage is then visible only in Sentry's issue list: Sentry's own new-issue emails are off (Q-0070 (a)), so Josh sees it only when he looks or when the database is back and later alerts arrive.
- **Release blocked until Sentry exists.** EZD-023b's env check requires every non-comment `.env.example` name for Production. The first real release (before launch, Q-0113; earlier merges end `not_configured` and check nothing) therefore stops at `env_mismatch`, with the live site unchanged, until Josh enters the Sentry DSN and alert address in Vercel (Q-0070 (a), `needs-from-josh.md`); he then presses Re-run jobs on that run. This follows 11 Operations, which says production errors go to Sentry.
- **Preview emails.** Alerts use `EMAIL_TRANSPORT`, and previews default to the stub transport (Q-0041), so preview alerts are recorded, not emailed, unless Josh switches a preview to live sending. Preview and production share one Sentry project, separated by `environment`.
- **Owner lookup before permissions exist.** Until EZD-101 adds `user_permission`, Owners are found by `role_preset = 'owner'` (the only preset with Manage users and settings, 10 preset table). A user given that permission on a custom role, or an Owner whose permission is turned off, is handled only once EZD-101 switches the query (Depends on).
- **The 20-per-hour cap is shared by all companies** (Q-0068 (a): "at most 20 alert emails per rolling hour"). A flood of failures in one company can hold back another company's alerts for up to an hour. Today only tenant 1 exists.
- **SDK specifics** *(builder confirms)*: the `instrumentation-client.ts` file name, the `onRequestError` signature, the `tunnel` option, envelope parse and serialize helpers, how the server client forwards a raw envelope, and integration names. They depend on the pinned Next.js and `@sentry/*`. React's Dedupe integration may drop a repeated identical browser error before it is sent; T18 reloads between clicks for that reason.
- **Sequential DB tests.** The caps are global, so the DB tests clear the table and run in order inside two files. A later ticket whose tests cause many alerts in the same run could hit a cap. Its tests should use `alert: false` or clear the table in the same way.
- **Ticket size.** About a dozen small modules, two migrations, one route, a dev page, a script and 22 tests, which is comparable to EZD-009. It should fit one session. If it overruns, the natural split is EZD-024a (Steps 1–5, 8–9 server path, store, jobs and webhooks; T1–T8, T10–T16, T22) and EZD-024b (Steps 6–7, 10–11 browser, tunnel, worker contract, live check; T9, T17–T20).
