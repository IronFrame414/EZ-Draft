# EZD-141 · Fix: SET LOCAL warning during sign-in

- **ACs:** AC-EZD-141-1, AC-EZD-141-2
- **Complexity:** medium (section 8)
- **User-visible result:** none on screen. Once fixed, signing in no longer leaves "SET LOCAL can only be used in transaction blocks" warnings in the database log.
- Phase: 1 · Planned by: planner · Date: 2026-10-24 · Status: questions

## 1. What to build

**Cause, found at planning time (AC-EZD-141-2; evidence in section 2, E1–E6).** Supabase Auth (GoTrue v2.197.0, the image CLI 2.121.0 pins) sends `set local statement_timeout TO '2000'` and `set local statement_timeout TO default` around every Postgres-function hook (R-018: `internal/hooks/hookspgfunc/hookspgfunc.go` lines 90 and 101). For the before-user-created hook it runs them on a connection that is not in a transaction (R-018: `internal/api/hooks.go` lines 35–50 and 116–122; `hookspgfunc.go` lines 107–115). Postgres answers each one with WARNING 25P01. The hook runs only when a code request names an address that has no Auth account yet, whether the hook allows it or refuses it (E2–E4). Our hook functions and migrations contain no `SET LOCAL` (E5). The faulty statements are Supabase's code, and they run only because our configuration enables `[auth.hook.before_user_created]` (EZD-007a; Q-0165 (a)). Supabase issue supabase/auth#2852 (opened 2026-10-06) is open, and no Auth release fixes it yet (R-018). Auth config cannot turn the statement off (R-018 (4)). The ticket row says that in this case we stop and ask Josh (Q-0274).

The test (Steps 1–2) is the same whichever answer Josh gives. Step 3 depends on Q-0274.

Data: none (no migration, no table, no money field).

## 10. Open questions
- Q-0274: The two warnings come from Supabase Auth's own code (GoTrue v2.197.0 runs `set local statement_timeout` outside a transaction whenever our before-user-created hook runs; open issue supabase/auth#2852, no fixed release; the statement has no effect beyond the log line) and are triggered only by our account-gate hook (Q-0165 (a)). What should we do? (a) Keep the hook and wait for Supabase's fix: EZD-141 stays blocked until a fixed Auth and CLI release exist, then it bumps the CLI pin (the warning keeps appearing on each first sign-in until then, and on dev/prod until Supabase deploys the fix). (b) Move the account gate to an HTTP hook served by the app: no SQL statement, so no warning, but every new sign-in then depends on the app answering Auth, and it adds a public route and a signing secret. (c) Turn Auth sign-ups off (`enable_signup = false`) and drop the hook: Auth itself refuses unknown addresses, but the invite flow (EZD-105) must then create each person's Auth account with the secret key, which docs/architecture.md now limits to jobs and scripts. (d) Hide it by raising the log level for Supabase's Auth role: this hides every Auth warning, likely cannot be set on cloud projects, and is not a fix.
