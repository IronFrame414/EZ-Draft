## Approach

### Level-1 answers recorded here (not questions)
- **Where the page lives.** "Page under /spikes" means the repo folder `/spikes`, not an app route: spikes are "kept under /spikes and never imported by the app" (tickets README; vault/spikes/README.md). The page is a static HTML page with plain ES modules in `spikes/EZD-027-canvas/`, served by a small Node server in the same folder. *Planner's choice (CLAUDE.md rule 4):* no bundler and no TypeScript, so no new package (as EZD-028 chose `.mjs`). Three.js is loaded as the pinned `three` package's own ES module build.
- **Plain Three.js, not React Three Fiber.** The ticket says "one persistent Three.js orthographic canvas". The question the spike answers is whether the tablet can draw this much geometry in budget (R26 R9: "the plan canvas with a 150,000-entity drawing on the iPad"; under Q-0088 the tablet measured is Josh's Surface). 11 rule 4 already forbids a React render per pointer move, so React adds nothing per frame in the production design. EZD-207 adds React Three Fiber and is measured on the benchmark project (*planner's choice*; Risks).
- **Budget values come from 11 Budgets only:** pan and zoom frames every 16 ms on desktop (60 fps) and every 33 ms on the iPad (30 fps); no frame over 100 ms. The plan uses the fps forms as exact thresholds, 1000/60 = 16.67 ms and 1000/30 = 33.33 ms, because the spec states both and frames on a 60 Hz screen arrive in steps of 16.67 ms. **Which statistic** must meet them: **Q-0061 answered (a)** (answered-agent, code-reviewer): the 95th-percentile frame interval is at most the budget + 1 ms (1000/30 + 1 = 34.33 ms on the iPad, 1000/60 + 1 = 17.67 ms on desktop), and no frame is over 100 ms; EZD-017, EZD-207 and EZD-1701 reuse the rule. **Memory: Q-0062 answered (a)**: no number; memory passes if the page does not reload, go blank or error on Josh's field runs (on the Surface, Q-0088), and the byte counts are recorded.
- **Which budget the Surface run is held to: Q-0097 answered (a)** (answered-josh, 2026-10-12): the Surface is judged as a tablet, 30 fps: the 95th-percentile frame interval is at most 1000/30 + 1 = **34.33 ms**, and no frame is over 100 ms (11 Budgets iPad row; Q-0061 (a); Q-0088). This sets the threshold in Step 10 item 2 and F1.
- **The first frames are not pan frames.** Building buffers, uploading them and compiling shaders happen before the first frame. The budget row is "Pan, zoom, drag, draw". So a warm-up pass of the script runs first and is recorded separately, not counted against the budget (11 Budgets row wording).
- **What the build PC can and cannot measure (Q-0018, Q-0019).** The automated runs happen on the build PC: Intel UHD Graphics only, 16 GB RAM. Headless Chromium on Windows may draw WebGL in software (SwiftShader) rather than on the Intel GPU, and Playwright's WebKit on Windows is not Safari on an iPad. So:
  - Automated frame times are neither iPad numbers nor typical desktop numbers. They are recorded, with the WebGL renderer string so the note says what drew them, and never compared with 16.67 / 33.33 / 100 ms in a test. 11 Performance: "In CI the gate is on countable things that do not depend on a GPU … Frame times are recorded as a trend, and the real frame-time test is … Josh runs on the iPad"; R26 R10; KNOWN-LIMITS 7.
  - The automated test asserts countable things only: one canvas and one WebGL context, draw calls per frame, lines and triangles per frame, no buffer rebuilt during pan and zoom, no frame drawn while idle, and the results file (11 rule 4; 11 CI paragraph list).
  - The verdict therefore comes only from Josh's Surface run (Field check, Step 9; Q-0088). The automated `ipad-landscape` run stays a countable check only (B1), never a frame-time check.
  - The only desktop available is the build PC itself. **Q-0063 answered (a)**: its run is recorded only. The verdict is decided on the field device, which under Q-0088 is the Surface, and a build-PC result outside the 17.67 ms rule is flagged in the note for EZD-207 and EZD-1701.
  - Timing runs use 1 Playwright worker (within Q-0019's limit of 2) so two browsers never compete for the Intel GPU and CPU while timing, and the orchestrator never runs the spike while a gate is running (Q-0019). Memory is not a constraint: the scene's GPU buffers are about 4 MB (Step 3).
- **Q-0053 and Q-0088's effect.** The page measures whatever window it is opened in, so the Surface run needs no Surface viewport in code; the results file records the real viewport, pixel ratio and WebGL renderer. Q-0053 sets the viewport and pixel ratio of the automated `ipad-landscape` run (1180 × 820, scale 2, from EZD-016a). No automated `surface` project is added to the spike: the `desktop` project already runs the same engine (Chromium) for the countable checks, and automation cannot measure the Surface's frame times (11 CI paragraph). The note names the Surface model, Windows version and Edge version the verdict was measured on.

### Step 5: Scripted pan and zoom and the measurements (builder; `public/camera-script.mjs` and `public/stats.mjs` are pure)
- `cameraAt(t)` for t in ms, 0 ≤ t ≤ 3,000 (3 seconds: EZD-207 row "a scripted 3-second pan and zoom"; the path is the spike input). Zoom 1 = the whole extent fits the canvas:
  - 0–1,500 ms: pan, centre x = 240 + 480 · t / 1,500, centre y = 360, zoom 1;
  - 1,500–2,250 ms: zoom in on (720, 360), zoom = 8^((t − 1,500) / 750);
  - 2,250–3,000 ms: zoom out, zoom = 8^((3,000 − t) / 750).
- One **pass** = frames driven by `requestAnimationFrame`; each frame sets the camera from `cameraAt(elapsed)` (so dropped frames do not change the path), renders once, and records the rAF timestamp, the CPU time of `renderer.render` (`performance.now()` around it), and `renderer.info.render.calls`, `.lines`, `.triangles`. The pass ends on the first frame with elapsed ≥ 3,000 ms.
- A **run** = 1 warm-up pass (recorded as `warmup`, not counted), then `runs` measured passes (`?runs=`, default **3**, 1–5). Frame intervals are taken within a pass only, so the measured interval count is frames − passes.
- Also recorded: `buildMs` (scene data + buffers), `firstFrameMs` (navigation start to first drawn frame), the sum of every buffer attribute's and index's `version` before and after the measured passes (difference = buffers rebuilt), renders during a 2,000 ms idle wait after the run, long tasks during the measured passes (`PerformanceObserver` `longtask`; `null` where the browser has none), and canvas CSS size and drawing-buffer size.
- `frameStats(intervals)` → `{ count, mean, p50, p95, p99, max, over16_7, over33_3, over100 }`. Percentiles are nearest-rank (sorted ascending, element ⌈p/100 · n⌉ − 1) (*planner's choice*). "over X" counts intervals strictly greater than 1000/60, 1000/30 and 100 ms (thresholds from 11 Budgets).
- Memory: `jsHeapUsedBytes` from `performance.memory.usedJSHeapSize` where the browser has it (Chromium), else `null` (Safari has no such figure); `gpuBufferBytes` = sum of `byteLength` of every attribute and index array in the scene, instance matrices included; `textureBytes` = atlas width × height × bytes per texel. Also the WebGL renderer string (`WEBGL_debug_renderer_info` where allowed, else the plain `RENDERER`) and `MAX_TEXTURE_SIZE`.

## Risks
- **The verdict rests on one field run, on the Surface.** Nothing automated can measure the field device (11 Performance; R26 R10). If Josh cannot run it, the ticket stays `blocked` and the checkpoint keeps Phase 2 closed (Q-0064 (b)).
- **No real iPad is measured** (Q-0053: Josh has none). The iPad stays a supported target (Q-0088), but its frame times and Safari's memory limits (11 Also) are not checked on hardware; the automated `ipad-landscape` run checks counts only. A Surface `go` says nothing about an iPad; the note says so for EZD-207, EZD-237 and EZD-1701.
- **The Surface and the iPad differ.** Edge on Windows draws WebGL through a different graphics stack from Safari on iPadOS, and the Surface's graphics and screen differ from an iPad's. Results transfer to the iPad only roughly. The Surface is held to the 30 fps tablet row (Q-0097 (a)), like the iPad.
- **Surface model to be confirmed (Q-0053).** The run is valid whatever the model; the note records the model, viewport and pixel ratio the page measured.
- **Build PC frame times are not meaningful as budgets.** Headless Chromium may use software WebGL on this PC, and WebKit on Windows is not iPad Safari (Q-0018; KNOWN-LIMITS 7). The renderer string in every results file shows which.
- **WebKit on Windows and WebGL 2.** If Playwright's WebKit build on Windows gives no WebGL 2 context, B1's `ipad-landscape` run fails. The test-author reports that as a question; it is not skipped. The `desktop` run alone still proves the Done when's "runs its script … writes a results file".
- **1-pixel lines.** WebGL draws `LineSegments` 1 px wide. Plan line weights (09 orders line weights by role) would need thicker lines drawn as quads, which cost more. Not measured here; carried to EZD-207 and EZD-238 in the note.
- **Text volume is a spike input.** No source says how much text a 150,000-entity drawing holds. The `labels=15000` run (120,000 glyphs) gives EZD-901b a second point. Neither run hides text below a zoom threshold (11 rule 5 allows that in production), so both are worst cases.
- **Memory figures.** Edge on the Surface reports `jsHeapUsedBytes` (Chromium), Safari would not; either way the real crash limit is not observable except as a reload, which is why Q-0062 (a) uses "no reload, blank page or error" as the memory rule, applied to the Surface run.
- **Surface conditions.** Battery saver, running on battery, a background tab playing video, rotation or a hot Surface change results. The README and Step 9 list the conditions.
- **Office network access.** The Surface must reach the build PC on port 4027 over the office network. A guest network, client isolation on the Wi-Fi or a firewall refusal blocks it; **Download results** is the fallback for the file, but the page itself must load from the PC.
- **Float32 coordinates** are exact enough for a 960 × 720 in extent. Real DXF files in survey coordinates need a local origin first (EZD-901a's job).
- **React Three Fiber not measured.** EZD-207 adds it. With drawing on demand and camera-only pan (11 rule 4), its per-frame cost should be small, but EZD-207's own Done when is the proof.
- **First install of `three`.** EZD-027 is likely the first ticket to install the pinned `three` (EZD-030 is after it in `build_order`). A version bump, if needed, is visible in the commit (EZD-000 Risks).
- **Not decided here** (later planners must not read the spike as deciding them): line weights on screen, text-hiding zoom thresholds, the plan canvas pixel ratio, antialiasing, and the shell's canvas size on the tablets (EZD-014; Q-0054 (a), Q-0088), and which frame budget a Surface is held to in later tickets (Q-0097 (a) answers it for this spike: 30 fps tablet; EZD-207 and EZD-1701 reuse it only if their planners cite Q-0097).
