## 1. What to build
Section 2 ("Diagnosis") gives the reasons. N5's two wall-clock timings are not comparable under load, and `applyCpuThrottle` matches D-Throttle. The fix changes how N5 measures. N5 alternates plain and throttled runs under one Chrome trace and compares the main thread's CPU time of each run, still at rate 4 and still `b >= 2 * a`. **These code-bound blocks are written for Q-0743 option (b), the planner's recommendation. Q-0743 is still open.** If it is answered (a) or (c), this plan goes back to step code-bound before any build (section 9). The builder adds one pure helper, `markTaskCpu`, to `scripts/perf/trace-tasks.mjs`, so the CPU lookup has unit tests against a fixture and N5 is red until the builder's step lands (rule 5).

- Throttle mechanics, R-061 (vault/research/INDEX.md line 65, written for EZD-388; read through a retriever, body not read). Chrome's throttle runs from a separate thread. That thread signals the main thread and then sleeps 200 µs by wall clock. On each signal the main thread spins, by wall clock, for run × (rate − 1). Here "run" is the wall time since the last spin ended, capped at 1000 µs, so the spin is at most 3 ms per signal. The spin is on-CPU work on the main thread. R-061 does not cover behaviour under load, and its quotes come from a model-summarised view (R-061's own caveat). Chrome's throttle spin also shows as main-thread CPU time: docs/architecture.md, Performance check (EZD-017), Long tasks (G5) bullet; measured on ipad-1x as a pure 100 ms wait giving CPU 76-78 ms (Q-0623).
- **Diagnosis (planner, from the evidence above):**
  - D1. N5 passes in 13 past gate logs (`.claude/worktrees/<T>/gate.log` for EZD-212a, 221b, 224, 224b, 364, 365, 369, 372, 376, 377, 378, 387, 5601) in 338-744 ms each. That time includes the browser launch, 4 plain runs and 4 throttled runs, which is 20 plain loop times at a full 4x. A full 4x run of 338 ms therefore means a plain loop of at most about 17 ms (338 / 20, with the launch time still counted in the 338).
  - D2. The failing run's plain median was 23 ms. That is at least 1.35 times the unloaded loop time from D1 (23 / 17), so the plain timing was itself slowed by the other lane's load.
  - D3. The throttled median was 44 ms, about 4 × 11 ms: a near-unloaded loop time under a full 4x. So the failing run fits "the two timings saw different load" (comparable-timings cause). The second cause also fits: when the main thread waits for the CPU for more than about 1 ms, the 1000 µs run cap holds the spin to 3 ms while the run keeps growing, so the slowdown falls below 4 (R-061 run cap; a planner inference that R-061 does not state). One failure cannot tell the two apart. This ticket can fix neither of them in `applyCpuThrottle`: it is a three-line CDP call that matches D-Throttle, and the shortfall is in Chrome's throttler, not in our call. So the fix is in N5 (this ticket's test-author, Stage 3 step 4).

## 10. Open questions
Q-0743 (answered-agent, option (b)): Diagnosis D1-D5 (section 2) shows that N5 fails when the two wall-clock timings see different load, and that Chrome's throttler can also give under 4x when the main thread waits more than about 1 ms (R-061 run cap). A retry, a looser bound and a lower rate are ruled out, so what should N5 measure? (a) Keep wall time, but alternate plain and throttled timings on the two pages (five A/B pairs after the warm-ups, median of each side, same `b >= 2 * a`): cheap, and it fixes the load-shift cause, but not heavy steady load. (b) Planner's recommendation: alternate as in (a), but measure each run by the main thread's CPU time from a Chrome trace (`tdur` of the evaluate tasks, via `TRACE_CATEGORIES`, `stopTrace` and `readTraceEvents`), keeping rate 4 and `b >= 2 * a`. The plain loop's CPU time is its own work whatever the load (Q-0737 (a)), and the spin counts as CPU time (Q-0623), so preemption that inflates a run also inflates the next spin. Cost: the test gains trace plumbing, and the R-061 run cap can still lower the ratio when the main thread gets under about a fifth of a core. (c) Replace the timing with a stub CDP session check that `Emulation.setCPUThrottlingRate` was sent with `{ rate: 4 }`, plus a real-Chrome no-throw call: load-proof, but it no longer shows that Chrome slows the page, which narrows N5 (CLAUDE.md rule 16).
