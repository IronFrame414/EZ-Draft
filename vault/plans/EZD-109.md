# EZD-109 · Event log

- **ACs:** AC-EZD-109-1, AC-EZD-109-2, AC-EZD-109-3, AC-EZD-109-4 (`vault/spec/acceptance-criteria.md:1120-1123`, stage-0)
- **Complexity:** high (section 8)
- **Areas:** data-model, migrations, security, api, contracts, testing
- **User-visible result:** Nothing changes on screen. Every audited change now leaves a row that says which company, who did it (by name), what was done, to what, when and from which address. Nobody can edit or delete these rows, and the app has no screen that shows them in v1. The changes covered are joining by invite, saving a customer, the company or your profile, creating a project, and the permission, role and invite changes to come.
- Phase: 7 · Planned by: planner · Date: 2026-11-11 · Status: planned · Q-0734 (a) and Q-0735 (a) applied 2026-11-11

## 1. What to build

Ticket row (`vault/tickets/phases/phase-01.md:17`): Scope "event_log (actor, action, object, at, ip) and a write helper used by permissions, invites, locks, approvals, issues and deletes." / Done when "A permission change writes a row with actor and IP." / Depends on EZD-005, EZD-106 (dropped: Q-0734 (a); `depends_on` is EZD-005a, EZD-005b, EZD-022, EZD-101, EZD-006) / Spec ref "Data model · event_log; Non-functional · Security". The columns, the write rules and the "same transaction" split are Q-0695 (`vault/spec/decisions/03-data-model.md:33`), which overrides the 03c row's five columns.

Design in one line: one append-only table, two `private` SQL writers that other definer functions call inside their own transaction, one gated `public` RPC for the default sink, and one server sink that writes every emitted event the per-event rule map marks `sink`. Built in this order because the phase 7 tickets that change permissions, roles, members and invites call the writers from their first commit (Q-0720 (c), confirmed by Q-0734 (a): built before EZD-105a, EZD-105b, EZD-106a, EZD-107a and EZD-129).

Three paths write a row:
- **Same transaction (AC-3).** A definer function that changes permissions, roles, members, project scope or invites calls `private.write_event_log(...)`. That function takes the tenant and actor from the token claims. A flow with no tenant claim yet calls `private.write_event_log_as(...)` with explicit ids: invite acceptance, a job, a system action. A failed write raises, so the change rolls back (Q-0695: "write their row in the same transaction as the change").
- **Default sink (AC-3).** `emit()` hands every event to `defaultSinks`. `eventLogSink` looks up `EVENT_LOG[name]`. On `sink` it calls `rpc('log_event', ...)` with the signed-in user's session. A failure is reported with `reportError` and never thrown, so the action that already committed stands (Q-0695: "reports a failed write and never undoes the action").
- **System (AC-4).** `private.write_event_log_as(action, tenant, null, ...)` stores actor null, actor name null and ip null (Q-0695 "null for system"; Q-0697 "An auto release has actor system and IP null").
