# EZD-105 · Invite user (split proposal)

- **ACs:** AC-EZD-105-1 … AC-EZD-105-9 (`vault/spec/acceptance-criteria.md:1092-1100`, stage-0), shared out to the parts below. AC-1, -2, -3, -4, -5, -6, -7 and -8 are split by clause (AC map).
- **Complexity:** high (parts a and c), medium (part d); reasons per part
- **Areas:** auth, security, data-model, migrations, api, ui, testing
- **User-visible result:** On Settings → Users + permissions, Josh presses Invite user and enters an email, name, role, language and project access. The person gets an email with a 7-day link, and Josh sees the link with Copy link. A pending row appears with Resend and Copy link, and the invite can be cancelled. The invitee opens the link, presses Accept and is signed in, and their row turns active.
- Phase: 7 · Planned by: planner · Date: 2026-11-11 · Status: split proposal

## Split proposal

**Why.** Planned whole, the ticket would touch about 50 files and need about 50 tests. That is over the size rule (PROCESS.md section 6 "Ticket size": about 20 files or 25 tests; Josh 2026-10-22). The count:
- **Database (Q-0695, 10-permissions-and-settings rows 61, 63):**
  - the new `invite` table: tenant, membership (unique), per-invite random value, `expires_at`, code tries, `accepted_at`, `cancelled_at`, `created_by`, `sent_by`;
  - a partial unique index on `membership(user_id)` for active rows;
  - security-definer functions for create, resend, cancel and accept, each with the `settings_users` check (Q-0695 row 59), the three refusals and the default project access by role;
  - grants and the RLS audit lists (`app/test-harness/rls/table-grants.ts`, `private-execute.ts`, `gate.ts` `GATED_RPC_CALLS`).
- **Token code:** the link token and the 6-digit code worked out from the random value by HKDF with label `ezd-invite-v1` (the `app/src/server/auth/throttle.ts:23` pattern; architecture "Password sign-in (EZD-033)" (vii)). The invite is looked up by the token's sha-256.
- **Email:** the invite email through `sendEmail` with the company sender, and the link returned for Copy link (architecture "Email (EZD-008)": Sender, Copy link).
- **Three write routes** under `/api/settings/users/invites`, each joining `MONEY_ROUTE_CASES` (`app/test-harness/money/route-cases.ts`) and the same-origin walk (`proxy.test.ts`).
- **Accepting:**
  - a public page `/invite/<token>` that shows Accept on GET and accepts only on POST (Q-0695 row 61), with a `PUBLIC_PATHS` entry (`app/src/server/auth/public-paths.ts`);
  - a one-step database accept;
  - a session made through Supabase admin `generateLink(magiclink)` and `verifyOtp` in a new secret-key file. That file is a T34 list edit (`app/src/server/auth/session.test.ts`; architecture "Auth and session (EZD-007)", "Allowed Supabase client files") and needs a retriever-web report on the pinned supabase-js (Q-0706, 03-data-model row 50);
  - the page inventories (`page-cases.ts` `PAGE_FILES`, `money-routes.test.ts` C4, `money-pages.spec.ts` `EXPECTED_PATHS`; planner lesson EZD-209).
- **Screen:**
  - the Invite user button in `UsersPanel`'s `actions` slot (EZD-104 plan section 3: `SettingsMain` `actions`);
  - the dialog, which has no board (Q-0696, escalated to Josh);
  - the link with Copy link after Send;
  - wiring the pending row's Resend and Copy link that EZD-104 renders (`user-resend`, `user-copy-link`; EZD-104 plan section 3);
  - Cancel invite;
  - en catalog keys, the browser test of Josh's slice 7 script steps 1 and 2 (`vault/tickets/PHASES.md` slice 7), and the touch-target list.
- **Events:** user.invited, user.invite_resent, user.invite_cancelled and user.joined (`via: 'invite_link'`) in `app/src/lib/events/registry.ts` (architecture "Events"), each with its event_log row (AC-EZD-105-8; QP-1).

**Why cut here.**
- **Part a** is the server side Josh's team cannot see yet: table, functions, token code, email and the three routes. It needs no board, and the escalated Q-0696 does not hold it. Every invite write and refusal can be tested at the database and route level. EZD-138 (link and code for the sender) and part d build on its contract.
- **Part c** is the invitee's side: the public page, the one-step accept and the session made with the secret key. It is the part with the auth and secret-key risk. It gets its own security review and its own retriever report (Q-0706), and it can be reviewed apart from the screen work.
- **Part d** is the screen. It is the only part held by Q-0696 (no board for the Invite dialog). It goes last so its browser test can run the whole flow: Josh's slice 7 steps 1 and 2, and the ticket row's Done-when "Invite arrives by email; Copy link works; accepting turns the row active" (`vault/tickets/phases/phase-01.md:12`).
- **The letter b is skipped.** EZD-105b already exists: Owner-set password (Q-0695 row 65; STATUS.md). It is not a part of this split.

Built a → c → d. Each part is planned as its own unit from its section here, on template v2. Each part plan applies the planner lessons for its areas, notably:
- an explicit `revoke all … from public` on every new function, with its `PRIVATE_EXECUTE` entry and test callers that match the grants (L-016, L-023);
- SQL contract text run on the pinned stack (L-009);
- every harness list the part joins named as a test-author edit row (L-049; EZD-120a line);
- a migration timestamp after develop's newest (L-060);
- empty, maximum and malformed cases for every input, with a bound for each (L-052, L-061);
- for part c, the T34 edit for the new secret-key file (EZD-018 plan-gap round 2 line).

### Part EZD-105a · Invites: table, database functions, token, email and routes
- **Scope:**
  - **Migration 1:**
    - table `public.invite` with the Q-0695 row 61 columns: `id`, `tenant_id`, `membership_id` unique with `on delete cascade` (Q-0695 row 62: Remove and Cancel cascade the invite), `secret` (per-invite random value), `expires_at` (`invited_at` + 7 days, Q-0216, Q-0050), `token_sha256` unique, `code_tries` (bounded), `accepted_at`, `cancelled_at`, `created_by`, `sent_by`, `created_at`, `updated_at`;
    - RLS on, no table grants; reached only through definer functions (the `user_ai_key` precedent, 10-permissions-and-settings Q-0637);
    - partial unique index `membership(user_id) where status = 'active'` (Q-0695 row 63; Q-0043).
  - **Migration 2:** security-definer functions:
    - `create_invite`:
      - `settings_users` checked inside; tenant from the claims;
      - refuses an invalid email, an email active or invited in this tenant, and an email active in another tenant, with one code for the last that never names the other company (Q-0695 row 63);
      - a deactivated member here answers with a code the screen turns into the offer to Reactivate (Q-0695 row 63);
      - makes or reuses the `app_user` row (lower-cased email, `app_user.email` check in `20261019165202_create_app_user.sql`), the `invited` membership with `invited_at = now()`, scope from the request or the role's default (Owner and Designer `all`; Foreman, Crew and custom `listed`; Q-0695 row 63, S15 Decision 13), `user_permission` rows from the role's `default_permissions` (migration `20261024100006`; AC-EZD-105-1), language default `en` (Q-0029), and the invite row.
    - `resend_invite`: new random value and token hash, `invited_at = now()`, `expires_at` moved, `sent_by` = the caller, `code_tries` back to 0 (Q-0695 rows 61, 63).
    - `cancel_invite`: deletes the invited membership; the invite cascades (Q-0695 row 62).
    - The `list_users` redefinition that adds the last-sender half of `canCopyLink`, if Q-0718 is answered (a) as the EZD-104 plan is written (EZD-104 plan section 3 `UserRow.canCopyLink`; Q-0706).
  - **Server:**
    - `app/src/server/users/invite-token.ts`: HKDF-SHA256 from `SUPABASE_API_GATE_SECRET` via `serverGateSecret()` (`app/src/server/db/env.ts`), label `ezd-invite-v1`; link token, 6-digit code and token sha-256; no plain hash of the code is stored (Q-0695 row 61; AC-EZD-138-5 reads the same module).
    - `app/src/server/users/invites.ts`: parse, rpc, then `sendEmail` with `company` from the tenant (architecture "Email (EZD-008)" Sender), returning `SendEmailResult.link` to the sender whether the send succeeded or failed (Copy link rule, R24 #15).
  - **Routes:**
    - `POST /api/settings/users/invites`
    - `POST /api/settings/users/invites/[id]/resend`
    - `DELETE /api/settings/users/invites/[id]`
    - each `requireApiPermission('settings_users')` (`app/src/server/permissions/can.ts:52`), 403 otherwise (AC-EZD-105-9), with the error body of architecture "Errors and logging".
  - **Events:** user.invited, user.invite_resent, user.invite_cancelled as `log_only` (architecture "Events"; 03-data-model Q-0695 row 33), and their event_log rows in the same transaction (QP-1).
  - **Session triggers:** the fix so deleting an invited row never ends another company's sessions (QP-2).
  - **Inventories:** `GATED_RPC_CALLS`, `TABLE_GRANTS`, `PRIVATE_EXECUTE`, `MONEY_ROUTE_CASES`, `CAP_LOCK_READ_ONLY` if a function counts (EZD-117a lesson); `docs/architecture.md` section "Invites (EZD-105)".
- **Tests (about 24) and files (about 20):**
  - database tests: create, each refusal writes nothing, default scope per preset and a custom role, resend moves the clock and changes the token hash, cancel deletes both rows, the unique active index, 403 inside each function without `settings_users`;
  - unit tests for the token module: the same value gives the same token and code, two invites differ, the code is 6 digits, the sha-256 lookup;
  - route tests: 400, 401, 403 and 409 per route, and the stub outbox holding one email.
  - Files: 2 migrations, `database.types.ts`, `invite-token.ts`, `invites.ts`, the invite email builder, 3 route files, `registry.ts`, `en.ts`, 5 harness lists, `docs/architecture.md`, about 4 test files.
- **Done when:**
  - an invite with a valid new email, name, role, language and project access makes an invited membership with the role's switches, and the stub transport records one invite email whose link the route also returns;
  - an invalid email, an email active or invited in this company, and an email active in another company are refused with nothing written, and no refusal names the other company;
  - Resend moves the 7-day clock and changes the link token;
  - Cancel deletes the membership and its invite without signing the person out of any other company;
  - Foreman, Crew and custom roles default to Listed projects, Owner and Designer to All;
  - every invite write without `settings_users` answers 403.
- **ACs:** AC-EZD-105-9; AC-1 (membership, switches, language default, scope, one email); AC-3 (refusals, nothing written, wording-free codes); AC-4 (Resend moves the clock and issues a new token; the old hash no longer matches); AC-5 (deletes membership and invite; no sign-out elsewhere, QP-2); AC-6 (server default); AC-7 (the unique index); AC-8 (user.invited, user.invite_resent, user.invite_cancelled and their rows, QP-1).
- **Depends on:**
  - From the row: EZD-104 (`list_users`, `UserRow`; status `questions` with Q-0718 and Q-0719 open), EZD-008a, EZD-008b (`sendEmail`).
  - Done, missing from the row: EZD-101 (`role`, `user_permission`, `catalog.ts` `settings_users`), EZD-102 (`requireApiPermission`), EZD-005a (`membership`, `app_user`), EZD-007b (`private.invite_is_valid`, `link_app_user`), EZD-022 (event registry), EZD-033 (the HKDF pattern in `throttle.ts`).
  - Per QP-1 (a): none extra. Per QP-1 (c): EZD-109.
- **The part plan settles:**

### Part EZD-105c · Accept an invite: page, one-step accept and session
- **Scope:**
  - **Migration:**
    - `accept_invite(p_token_hash)`, definer, in one step: find the invite by hash, refuse when expired, accepted or cancelled, check the email has no other active company (Q-0043), make the membership active, set `accepted_at` (Q-0695 row 61; AC-EZD-105-7);
    - the `link_app_user` redefinition so a sign-in-page acceptance (Q-0050) also sets `accepted_at`, keeping link and code single use (Q-0695 row 61 "Both are single use");

  - **Server:** a new server-only secret-key file holding only the admin `generateLink({ type: 'magiclink' })` and `verifyOtp` calls. It never logs the action link (architecture "Errors and logging": tokens never logged). It needs the T34 list and the service-key bullet (Q-0695 row 61), and its stub is built from a retriever-web report on the pinned supabase-js. That report also says whether `generateLink` creates the auth user for a new email (Q-0706, 03-data-model row 50). Then `completeSignIn`'s refresh step (`app/src/server/auth/complete-sign-in.ts`) and `user.joined` with `via: 'invite_link'` (architecture "Events").

  - Files: migration, types, the secret-key file, the accept server code, page and form component, `public-paths.ts`, `next.config.ts`, `session.test.ts` T34, `registry.ts`, `en.ts` and `es.ts`, 3 page inventories, `docs/architecture.md`, about 3 test files.

  - accept checks the token and that the email has no other active company, makes the membership active and marks the invite accepted in one database step before any session is made;
  - user.joined is emitted with `via: 'invite_link'`.
- **ACs:** AC-4 (scanner GET, Accept on POST, expiry, old link refuses); AC-5 (the link refuses after Cancel); AC-7 (the one-step accept, session after); AC-8 (user.joined via invite_link).
