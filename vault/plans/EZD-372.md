# EZD-372 · Fix: the long-tasks-during-pan perf check still fails at random on a lane gate (desktop, 1 long task)

- **ACs:** AC-EZD-372-1
- **Complexity:** medium (section 8)
- **Areas:** tooling, scripts, testing
- **User-visible result:** none in the app; the gate's pan long-task check stops failing at random when the Mac is busy, and any task it still cannot explain carries its trace evidence in the results file.
- Phase: 4 · Planned by: planner · Date: 2026-11-10 · Status: planned

## Evidence (planning session, 2026-11-10)
- **E-1** The red run: `.claude/worktrees/EZD-367/perf-results/latest.json`, `runAt` 2026-11-10T18:22:45.902Z (EZD-367 lane 1 gate, gate.log:11477). Row `long-tasks-during-pan` (desktop, rate 1): value 1, `details.tasks` = `[{at:16763, ms:50, cpu:null, gc:null, top:null}]`, 149 waits (every one `cpu` 1-2, `ms` 50-249, mostly `FireAnimationFrame`), `load1` 9.84; the last wait is at 17,711 ms, against the 3,008 ms gesture (docs/architecture.md, Performance check, Benchmark pan). `:ipad` passed (1 wait).
- **E-2** Every pan row with `details.waits` in `perf-results/history.jsonl` of the main checkout and 12 worktrees (46 desktop records) was read this session. The task in E-1 is the only `cpu: null` task. Every other task matched a trace slice, including two other `ms` 50 tasks in the same run (at 1032 and 16297).
- **E-3** Code: `attributeTasks` (scripts/perf/trace-tasks.mjs; EZD-359 D-Attr (4)) takes only top-level slices with `dur > 50000` µs that start within 3 ms of `at`. The Long Task API lists tasks over 50 ms by Chrome's own task clock, and `ms` is `Math.round(duration)` (scripts/perf/pan-script.mjs), so an `ms` 50 task lasted 50.0-50.5 ms by that clock. A `cpu` null task counts (fail closed, Q-0621, Q-0622).
- **E-4** The trace of E-1 is gone. The gate copies back only `latest.json`, `history.jsonl` and `bundle-report.md` (scripts/gate-user.mjs `copyBack`, `PERF_FILES`; EZD-354 D12), and none of them holds trace events.
- **Cause (inferred from E-1 to E-3; the trace cannot confirm it, E-4):** the task sat on the 50 ms line. The API measured it just over 50 ms; the trace measured its slice at 50,000 µs or less, so the `dur > 50000` filter dropped the only slice that was the task. This is the one cause that fits all of E-1 to E-3: the miss is at the smallest `ms` the API can list, the start window worked for 148 tasks in the same run, and the trace still holds events after the miss. The record cannot rule out two other causes: the slice starting more than 3 ms after `at`, or no slice at all (a hole in the trace). D-Match closes the 50 ms line and stays fail closed for both of the others. D-Miss makes any later miss show which one it was, from the trace, in `latest.json` (ticket Scope: "find the cause from the trace").
