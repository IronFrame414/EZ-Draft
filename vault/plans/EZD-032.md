### Level-1 answers recorded here (not questions)
- **What "the empty editor shell" is:** `EmptyEditor` (vault/plans/EZD-012.md Step 4) with the header slot filled (ticket Scope "EmptyEditor with the header"; EZD-011 Step 2), as `/dev/shell` renders it (EZD-012 Step 6; Q-0039 (c)). It contains:
  - the six regions;
  - an empty rail (0 tools; EZD-012 Level-1, from EZD-230's row);
  - the full shell, not the phone tree, at desktop, iPad landscape and Surface (02 Platform; Q-0088; EZD-014 Step 2; all three widths are at least 1024 px, Q-0054 (a)).
- **Box values come from the formulas, with W × H read from the running project.**
  - At desktop the formulas give EZD-012 B1's numbers; at the iPad and Surface sizes they give EZD-014 B1's and B8's numbers.
  - The spec reads W × H from `page.viewportSize()` and checks it against the project: 1600 × 1000 for `desktop` (04), 1180 × 820 for `ipad-landscape` (Q-0053) and 1440 × 960 for `surface` (Q-0053, Q-0088), as EZD-016a T5 sets them.
- **"Through the REST API" means the server path.**
  - Q-0087 answered (ii): PostgREST refuses every anon or authenticated request that lacks the server-only gate header. A query without the header therefore returns zero rows for every user and proves nothing about RLS.
  - So the zero-rows check sends the request the way the app's session client does (EZD-007 `createSessionClient()`): the publishable key, the user's own access token (from the browser session the app created) and the gate header `x-ezd-api-gate` (EZD-006 Step 1b). EZD-016a's `serverDb` is built exactly that way (EZD-016a Step 3a; EZD-006 Step 7 `signIn()`).
  - The request runs against the same PostgREST, and only RLS and the token's claims decide which rows come back (03 rule 1, "row-level security stays on every table as the backstop"; 11 Operations).
  - The secret key is never used for these reads, because the secret key bypasses RLS (EZD-000 service-key rule, as cited in vault/plans/EZD-006.md).
- **Zero must be shown to mean "RLS filtered it".** Several things other than RLS also return zero rows:
  - a missing tenant claim (EZD-006 T8);
  - a refused request;
  - a mistyped filter.
  So B3 adds positive controls through the same client:
  - the second-tenant user reads their own tenant and membership;
  - Josh reads tenant 1 rows.
  These are *planner's choice*; the source pattern is EZD-006 T1, which checks own rows alongside the zero rows.
- **The browser path is refused.** B4 sends the same request without the gate header (EZD-016a's `browserDb`) and expects the refusal EZD-006 Step 1b defines (Q-0087, "fails closed"). It is the browser-path half of 03 rule 1.
- **Performance needs no new code.** EZD-017's `perf` step runs on every gate after `test:e2e`, and is never filtered by scope (EZD-001 Step 6.2). Its `editor` entry is `/dev/shell`, the page this spec opens, so it covers "passes on the empty shell" (vault/plans/EZD-017.md, Depends on and T1). "Runs in CI" is EZD-017 T16 on the Phase 0 PR (Q-0021, Q-0022). This ticket records both as its evidence (rows P and C in Tests).
- **Smoke.** "Each phase's Build gate browser test … tagged when it is written" is in the smoke set (vault/plans/EZD-001.md Step 6.1). The spec is tagged `@smoke`, so every later ticket's gate runs it in all three projects. Tags: `@desktop @ipad @surface @smoke` (the row's `@desktop @ipad @smoke`, plus `@surface` per Q-0088).

### Data flow
1. Gate `test:e2e` → `db:up` (reset and seed).
2. Playwright starts the web server, which is ready when `/api/health` returns 200 (EZD-016a).
3. The `desktop`, `ipad-landscape` and `surface` projects run the EZD-032 describe, with workers 2.
4. B1: `signInAsOwner`, through the app's real `/auth/confirm` path, then `/dev/shell`, then the DOM and box checks.
5. B3: `sessions.open([Josh, tenant 2 owner])` gives two app sessions. Each session's `serverDb` sends its own token with the gate header through PostgREST, the pre-request gate, the RLS policies and the token-hook claims. The test asserts on the rows returned.
6. B4: the same token through `browserDb` (no header), which the pre-request gate refuses.
7. After `test:e2e`, the gate's `perf` step runs on `/dev/shell` (EZD-017).

## Risks
- **EZD-006 and EZD-016a names.** Step 3 uses the names EZD-006's revised plan (Steps 1b, 7) and EZD-016a's plan (Steps 3a, 4, 6) give: header `x-ezd-api-gate`, env `SUPABASE_API_GATE_SECRET`, `serverDb` / `browserDb`, `sessionAccessToken`, `sessionDbs`. If the merged code names them differently, the test-author uses the merged names; if the session client stops using a header (for example a separate database role), B4 must be re-planned before Stage 3.
- **`/dev/shell` is a dev page.** Under Q-0039 (c) the build gate proves the shell on a page that 404s in production (EZD-010 Step 5). The shell component is the one EZD-120b's editor route renders later; when that route exists, its ticket may move B1 to it (its test-author, not its builder, CLAUDE.md rule 6). The docs subsection records this.
- **Local stack only.** The spec proves isolation on the local Supabase. It does not prove the cloud preview or production. Those depend on:
  - Josh's cloud steps: the token hook (EZD-006 runbook), the gate secret (needs-from-josh.md, Q-0087), and tenant 1 in the cloud (Q-0033 (a));
  - the Phase 0 Field check.
  The Build gate's "deploys to a preview URL" is EZD-003's and the phase gate's, not this spec's.
- **Gate time.** Every later ticket's gate runs these tests, because they are smoke. Three projects × (B1 one sign-in + B3 two + B4 one) comes to 12 sign-ins, one project of them in WebKit on this PC. That adds roughly 45–90 s per gate (*planner's estimate*, about half again over the earlier two-project estimate).
  - Workers stay 2 (Q-0019).
  - EZD-016a's per-email lock serialises the parallel sign-ins of the same seeded email across the projects.
- **Robust zero and control values.** B3 uses fixed seeded ids and filtered counts, not tenant totals. A later test that adds projects to a seeded tenant therefore cannot break it, and a zero can never come from a broken path because of the controls.
- **Not every table.** B3 covers `project`, `tenant`, `membership` (the Done when), `membership_project` and `app_user`. Tables added later are each covered by EZD-006's audit `no_isolation_test` and their own `describeTenantIsolation` call (tickets README). This spec is not extended per table.
- **Emulation is not the devices.** WebKit on Windows is not iPad Safari, and Chromium with touch emulation is not Edge on a Surface (EZD-016a Risks). Josh has no iPad (Q-0053), so the iPad part of B1 is emulation only; the Surface is checked by Josh at the field checks (Q-0088; tickets README rule 7; P5).

A confirmed width below 1024 px (Q-0054 (a)) would show the phone tree and fail B1, which is the intended signal.
