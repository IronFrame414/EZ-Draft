### Level-1 answers recorded here (not questions)
- **What "the empty editor shell" is:** `EmptyEditor` (vault/plans/EZD-012.md Step 4) with the header slot filled (ticket Scope "EmptyEditor with the header"; EZD-011 Step 2). It contains:
  - the six regions;
  - an empty rail (0 tools; EZD-012 Level-1, from EZD-230's row);
  - the full shell, not the phone tree, at desktop and iPad landscape (02 Platform; EZD-014 Step 2).
- **Box values come from the formulas, with W × H read from the running project.**
  - At desktop the formulas give EZD-012 B1's numbers.
  - At iPad they give EZD-014 B1's numbers for the Q-0053 size.
  - The spec reads W × H from `page.viewportSize()` and checks it against the project: 1600 × 1000 for `desktop` (04; EZD-016a T5), and the Q-0053 size for `ipad-landscape` (EZD-016a T5).
  - So this plan needs no iPad number of its own. Q-0053 blocks EZD-016a, not this plan.
- **"Through the REST API" means the server path.**
  - Q-0087 answered (ii): PostgREST refuses every anon or authenticated request that lacks the server-only gate header. A query without the header therefore returns zero rows for every user and proves nothing about RLS.
  - So the zero-rows check sends the request the way the app's session client does (EZD-007 `createSessionClient()`): the publishable key, the user's own access token (from the browser session the app created) and the gate header.
  - The request runs against the same PostgREST, and only RLS and the token's claims decide which rows come back (03 rule 1, "row-level security stays on every table as the backstop"; 11 Operations).
  - The secret key is never used for these reads, because the secret key bypasses RLS (EZD-000 service-key rule, as cited in vault/plans/EZD-006.md).
- **Zero must be shown to mean "RLS filtered it".** Several things other than RLS also return zero rows:
  - a missing tenant claim (EZD-006 T8);
  - a refused request;
  - a mistyped filter.
  So B3 adds positive controls through the same client:
  - the second-tenant user reads their own tenant and membership;
  - Josh reads tenant 1 rows.
  These are *planner's choice*; the source pattern is EZD-006 T1, which checks own rows alongside the zero rows.
- **The browser path is refused.** B4 sends the same request without the gate header and expects a refusal (Q-0087, "fails closed"). The orchestrator asked for this check ("may additionally assert"). It is the browser-path half of 03 rule 1.
- **Performance needs no new code.** EZD-017's `perf` step runs on every gate after `test:e2e`, and is never filtered by scope (EZD-001 Step 6.2). It measures `/dev/shell`, which renders the same `EmptyEditor`, so it covers "passes on the empty shell" under every Q-0039 answer (vault/plans/EZD-017.md, Depends on and T1). "Runs in CI" is EZD-017 T16 on the Phase 0 PR (Q-0021, Q-0022). This ticket records both as its evidence (rows P and C in Tests).
- **Smoke.** "Each phase's Build gate browser test … tagged when it is written" is in the smoke set (vault/plans/EZD-001.md Step 6.1). The spec is tagged `@smoke`, so every later ticket's gate runs it in both projects. The orchestrator gave the tags `@desktop @ipad @smoke`.

### Data flow
1. Gate `test:e2e` → `db:up` (reset and seed).
2. Playwright starts the web server, which is ready when `/api/health` returns 200 (EZD-016a).
3. The `desktop` and `ipad-landscape` projects run the EZD-032 describe, with workers 2.
4. B1: `signInAsOwner`, through the app's real `/auth/confirm` path, then `SHELL_PATH`, then the DOM and box checks.

6. B4: the same token without the header, which the pre-request gate refuses.
7. After `test:e2e`, the gate's `perf` step runs on `/dev/shell` (EZD-017).

## Risks
- **EZD-006's plan has not been revised for Q-0087 yet.** The header name, the env name, the local secret wiring, the harness client and the refusal shape are all named here as interfaces (Step 3), not assumed.
  - The plan reviewer must check this plan against EZD-006's revision.
  - If the revision changes how the session client authenticates (for example a separate database role instead of a header), Step 3 and B4 must be updated before Stage 3.
- **`/` changes owner in Phase 1 (variants (a) and (b)).** S01 Projects is "App home after sign-in" (vault/plans/EZD-007.md Sources). When a Phase 1 ticket gives `/` to Projects, B1 and B2 fail.
  - Because the spec is `@smoke`, that ticket's own gate will catch it.
  - Its test-author (not its builder, CLAUDE.md rule 6) must move B1 to the editor route (EZD-120b) or to `/dev/shell`, in the same commit. The docs subsection records this.
  - Under (c), `/dev/shell` stays stable.
- **Sign out on `/`.** Under (a)/(b), B1 requires `[data-testid=sign-out]` visible on `/`. The composing ticket must keep it until EZD-108 (EZD-007 Risks; EZD-016a T1 relies on it too).
- **Local stack only.** The spec proves isolation on the local Supabase. It does not prove the cloud preview or production. Those depend on:
  - Josh's cloud steps: the token hook (EZD-006 runbook), the gate secret (needs-from-josh.md, Q-0087), and tenant 1 in the cloud (Q-0033);
  - the Phase 0 Field check.
  The Build gate's "deploys to a preview URL" is EZD-003's and the phase gate's, not this spec's.
- **Gate time.** Every later ticket's gate runs these tests, because they are smoke. Two projects × (B1 one sign-in + B3 two + B4 one, plus B2 under (a)/(b)) comes to about 8 sign-ins, with WebKit on this PC. That adds roughly 30–60 s per gate (*planner's estimate*).
  - Workers stay 2 (Q-0019).
  - EZD-016a's per-email lock serialises the parallel sign-ins of the same seeded email across the two projects.
- **Robust zero and control values.** B3 uses fixed seeded ids and filtered counts, not tenant totals. A later test that adds projects to a seeded tenant therefore cannot break it, and a zero can never come from a broken path because of the controls.
- **Not every table.** B3 covers `project`, `tenant`, `membership` (the Done when), `membership_project` and `app_user`. Tables added later are each covered by EZD-006's audit `no_isolation_test` and their own `describeTenantIsolation` call (tickets README). This spec is not extended per table.
- **WebKit on Windows is not iPad Safari** (EZD-016a Risks). The iPad half of B1 is emulation; Josh's Field check on the iPad is the real test (tickets README rule 7; P5).
- **Q-0054.** If the Q-0053 iPad width falls below `FULL_SHELL_MIN_WIDTH`, the iPad project shows the phone tree and B1 fails (0 `[data-phone-region]`). That is the intended signal; EZD-014 B1 fails first.
- **Performance stand-in.** Under (a)/(b), the perf check measures `/dev/shell`, not the signed-in `/`. Both render `EmptyEditor`, but anything the route adds around it (for example session reads in the page) is not measured until EZD-120b moves the `editor` entry (EZD-017 Level-1).
