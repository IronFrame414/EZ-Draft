### Step 3: Sign-in helper (`app/test-harness/e2e/sign-in-as.ts`, `email-lock.ts`, `session-claims.ts`; test-author)
`signInAs(page, email): Promise<SignedIn>` signs a browser context in through the app's real link path without email (EZD-006's harness signs users in with the Auth admin API, vault/plans/EZD-006.md Step 7; EZD-007 T1/T2 already prove the email path):
1. Take the per-email lock (`withEmailLock`, below).
2. Admin client (secret key; allowed in tests, EZD-000 service-key rule): `auth.admin.createUser({ email, email_confirm: true })`; the "already registered" error is ignored, any other error is thrown. EZD-007's `before_user_created` rule refuses emails with no active membership, so an unknown email throws `no active membership for <email>` here, before the browser is touched.
3. `auth.admin.generateLink({ type: 'magiclink', email })`; an HTTP 429 is retried up to 5 times, 1,000 ms apart (*planner's choice*).
4. `page.goto('/auth/confirm?token_hash=<properties.hashed_token>&type=email')`, click `[data-testid=confirm-submit]`, wait for the URL path `/` (EZD-007 Step 5). If `[data-testid=confirm-error]` appears, throw with its text.
5. Release the lock. Return `SignedIn` = the fields of `sessionClaims(page.context())` (so `result.tenant_id` etc. read as before; EZD-032 B1 uses them) plus `accessToken`, `serverDb` and `browserDb` from `sessionDbs(page.context())` (Step 3a).
- `signInAsOwner(page)` = `signInAs(page, JOSH_EMAIL)`.
- **Why a lock:** a new `generateLink` for the same user replaces that user's previous one-time token, so two workers signing in the same email at once (the Done-when test runs Josh in four projects with 2 workers) would break each other. `withEmailLock(email, fn)`: lock file `<os.tmpdir()>/ezdraft-e2e-locks/<first 16 hex of sha256(email)>.lock`, created with flag `wx`; wait by polling every 100 ms up to 30,000 ms; a lock file older than 60,000 ms is treated as left by a dead process and taken over; released in `finally` (*planner's choices*; same temp-folder pattern as the gate lock in EZD-001 Step 6.4).
- `sessionClaims(context)`: reads the `sb-…-auth-token` cookie (joining numbered chunks in order; Playwright can read httpOnly cookies), decodes the session JSON per the pinned `@supabase/ssr` cookie format, and base64url-decodes the access token's payload (no verification, like EZD-006's `claimsOf`). Returns `{ sub, email, session_id, app_user_id?, tenant_id?, membership_id?, project_scope? }`.
- EZD-007's `signInWithCode` (email path) stays available for tests that need it; `sessionDbs(context)` works after it too.

### Step 3a: Server-path and browser-path clients (`app/test-harness/e2e/session-claims.ts`, `session-dbs.ts`; test-author; Q-0087)
Under Q-0087 the app's own data path is the server path: `createSessionClient()` sends the user's token and the gate header (EZD-007 Step 3). A spec that checks what a signed-in user can read must use the same path, or EZD-006's gate refuses it and the check proves nothing (EZD-032 plan, Q-0087 note).
- `sessionAccessToken(context)`: the raw access token from the same `sb-…-auth-token` cookie `sessionClaims` decodes, with the same chunk joining and decoding.
- `sessionDbs(context): { accessToken, serverDb, browserDb }`, built with EZD-006's revised harness the way its `signIn()` builds `serverDb` and `browserDb` (publishable key; `Authorization: Bearer <accessToken>`; `persistSession: false`; `serverDb` adds header `x-ezd-api-gate` = `process.env.SUPABASE_API_GATE_SECRET`, `browserDb` does not). If EZD-006's revised fixtures expose no constructor for a given token, the test-author adds `dbForToken(accessToken, { gated: boolean })` beside `signIn()` in `app/test-harness/rls/fixtures.ts`, built exactly as `signIn()` builds its two clients, and `signIn()` uses it.
- Both clients live only in the Node test process. Neither, nor the secret, is ever handed to the page (Step 2 "never reaches a browser").
- EZD-032's plan adds `sessionAccessToken` and a gated `dbForToken` itself if the harness lacks them; with this step they exist, so EZD-032 reuses them (for the orchestrator to note in EZD-032's plan).
