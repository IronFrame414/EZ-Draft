# EZD-150 · Fix: health check gives up on a slow database

- **ACs:** AC-EZD-150-1 (vault/spec/acceptance-criteria.md line 297)
- **Complexity:** low (section 8)
- **User-visible result:** when the database hangs, the site's health address answers "database unavailable" after a few seconds instead of hanging until the platform kills it, so the release check sees a clear failure.
- Phase: 1 · Planned by: planner · Date: 2026-10-24 · Status: questions

## 1. What to build

No data changes: no table, migration, policy or `schema_version` change. The route `app/src/app/api/health/route.ts` already turns any `readHealth()` throw into the 500 `db_unavailable` body (EZD-004b section 3), so only `readHealth()` changes: it gives up after `HEALTH_DB_TIMEOUT_MS` and throws.

1. `const client = createPublicDbClient();` (outside the timer, so a missing env throws before any timer exists).

## 10. Open questions
- Q-0285 (was QP-1): No source gives the health check's database time limit; options: (a) 3,000 ms (recommended: below the release check's 4,000 ms per-request abort, EZD-023e, so the release sees the route's own 500, with about 1 s left for the function to start and answer), (b) 2,000 ms (fails faster, but a cold dev database on a preview may need longer), (c) another value below 4,000 ms.
- Q-0286 (was QP-2): The health route answers 500 on a database failure (now also on a timeout) without calling `reportError`, so a hung database sends no Sentry event or owner email, while docs/architecture.md says a catch that turns an unexpected error into a 500 calls `reportError`; options: (a) keep it silent, since the release check and the live check watch `/api/health` and a reporting call would itself go through the slow database (recommended), or (b) call `reportError` with location `api.health` (deduplicated by fingerprint, one owner email per new fingerprint) as a separate fix ticket in phase 1.
