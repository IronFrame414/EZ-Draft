### Level-1 answers (with sources)
- **No Copy link on self-service sign-in, and the page never shows the link or code.** Copy link for crew is "on the sender's side" (S17), meaning the office user who sends a crew or invite link (EZD-105 app invite token; EZD-1421 crew link). When users ask for their own sign-in email there is no sender. Supabase also sends this email itself, so the app never sees the link (EZD-008 plan). Q-0035 (a) confirms the exception: "sign-in emails cannot show their link on screen, since anyone who typed an email would get in; the sign-in page tells the user to check spam and accepts the 6-digit code" (Step 6 `check_spam`; T23). R24 #15 and 11 Security are therefore met by EZD-105, not here.
- **Who may sign in** (R24 #14; Q-0050 (a); Q-0043 (a)). Users are invited in EZ Draft (R24 #14), so an email with no `app_user` row never gets an account (Step 2). Access after sign-in needs either an `active` membership, or a **valid pending invite**, which the sign-in then accepts (Q-0050 (a): "a person with a valid (unexpired, not cancelled) pending invite may sign in from the sign-in page; that accepts the invite"):
  - *valid* = membership `status = 'invited'`, `invited_at` not null, and `invited_at > now() − 7 days`. The 7 days are EZD-105's row ("an app invite token valid for 7 days until accepted"); `invited_at` is the invite's "sent date", which Resend updates (S15; EZD-005 Data). An invite with no sent date cannot be shown to be unexpired, so it is not valid (fail closed).
  - *not cancelled*: a cancelled invite is deleted or leaves `invited` (EZD-105 interface, Depends on).
  - **Already active in another company:** sign-in uses the active membership and leaves any pending invite `invited`. Q-0043 (a): "one active company per person in v1; inviting someone already active elsewhere is refused", so accepting a second one is not allowed.
  - **Two or more valid pending invites and no active membership:** the most recently sent valid invite (latest `invited_at`, the "sent date" that Resend updates) is accepted; the others stay `invited` until they expire or are cancelled (Q-0099 (b), Josh 2026-10-12). An exact tie on `invited_at` is broken by the higher `membership.id` so the result is deterministic (*planner's choice*; practically only possible in tests).
  - A deactivated membership alone gives no access (EZD-006 row).
- **Accepting an invite at sign-in does not sign the person out.** EZD-006's trigger ends sessions on any status change (vault/plans/EZD-006.md Step 4), but Q-0044 (b) ends sessions only on narrowing changes; `invited` → `active` widens access. This ticket narrows the trigger condition to match (Step 2.4).

### Step 2: Database functions (migrations; one concern per file, EZD-000 Migrations and C5; builder)
The three API functions are `language plpgsql` or `sql`, `security definer`, `set search_path = ''`, owned by the migration role, with `revoke all … from public` and an explicit `revoke execute … from anon` (Supabase's default privileges grant it by name *(confirm on pinned version)*; Data: "executable by `authenticated` only"). Function 1 also revokes from `authenticated` and `service_role` (below).
0. `<ts>_create_invite_is_valid.sql`. `private.invite_is_valid(p_status text, p_invited_at timestamptz) returns boolean`, `stable`, `set search_path = ''`: `p_status = 'invited' and p_invited_at is not null and p_invited_at > now() - interval '7 days'` (Q-0050 (a) "valid (unexpired, not cancelled)"; 7 days from the EZD-105 row; Level-1 answers). In `private` (not exposed to the API, EZD-006 Step 1); no grant to any API role. Functions 1 and 2 both use it, so the rule has one source. EZD-105 may redefine it (Depends on).
1. `<ts>_create_auth_before_user_created.sql`. `public.auth_before_user_created(event jsonb) returns jsonb`:
   - Allowed when `lower(event->'user'->>'email')` matches an `app_user.email` that has a membership with `status = 'active'` or with `private.invite_is_valid(status, invited_at)` (Q-0050 (a)). Returns `'{}'::jsonb`.
   - Otherwise returns `{"error": {"http_code": 403, "message": "sign_in_not_allowed"}}`.
   - `grant execute … to supabase_auth_admin`. Not granted to `anon` or `authenticated`: besides `revoke all … from public`, the migration also runs `revoke execute … from anon, authenticated, service_role`, because Supabase's default privileges grant execute on new `public` functions to those roles by name *(confirm on pinned version)*; EZD-006 T22 (j) would otherwise list it as a gated RPC.
   - If the pinned CLI has no before-user-created hook, the builder uses a `before insert` trigger on `auth.users` with the same rule and raises instead. Tests T6 and T7 then pass unchanged. The builder records which one was used in docs.
   - **Admin-API user creation (review finding 16).** A `before insert` row trigger on `auth.users` fires for every insert, so under the trigger fallback the Auth admin `createUser` **does not pass** for an email without an `app_user` that has an active membership. For the hook, no vault source says whether Supabase Auth runs the before-user-created hook on admin `createUser` *(confirm on pinned version)*; EZD-016a's plan (Step 5 item 2) already assumes it does. The test-author checks this first, with one admin `createUser` call for an unknown email on the pinned stack, and records the result in `### Auth and session (EZD-007)`. If admin creation does not pass (trigger fallback, or the hook covers admin calls), the test-author makes the edits listed under "Test edits allowed" below; if it passes, those edits are not needed and are not made.
2. `<ts>_create_link_app_user.sql`. `public.link_app_user() returns table (app_user_id uuid, has_access boolean, accepted_membership_id uuid, accepted_tenant_id uuid)`:
   - Reads `auth.users` for `auth.uid()`. If `email_confirmed_at` is null, it returns no row.
   - Otherwise `update public.app_user set auth_user_id = auth.uid() where email = lower(<that email>) and (auth_user_id is null or auth_user_id = auth.uid())`. If no row is linked to `auth.uid()` after that, it returns no row.
   - **Access and invite acceptance** (Q-0050 (a); Q-0043 (a)), on that user's memberships, locked with `for update`:
     - an `active` membership exists → `has_access = true`, nothing accepted (pending invites elsewhere stay `invited`, Q-0043 (a));
     - else one or more memberships with `private.invite_is_valid(status, invited_at)` → take the one with the latest `invited_at` (tie: higher `id`; Q-0099 (b)) and `update public.membership set status = 'active' where id = <it> and status = 'invited'`; return `has_access = true` with that membership's id and tenant id. `invited_at` and `last_active_at` are not changed; every other valid invite stays `invited` (Q-0099 (b); Q-0043 (a));
     - else `has_access = false`.
   - Idempotent: a second call finds the membership already `active` and accepts nothing. It never re-points a row already linked to a different auth user (EZD-005 Risks: "link only a verified email"), and it only accepts invites addressed to the verified email's own `app_user`.
   - `grant execute … to authenticated`.
3. `<ts>_create_current_app_user_id.sql`. `public.current_app_user_id() returns uuid`, `stable`. Returns null when `private.session_is_live()` is false (EZD-006 Step 3: the token's `session_id` no longer exists in `auth.sessions`, for example after deactivation); otherwise `app_user.id where auth_user_id = auth.uid()`, or null. It does not raise, so `getSession()` returns null and `requireApiSession()` answers 401 for a deactivated user still holding a valid JWT (Q-0052 (c): "`current_app_user_id()` returns null for an ended session so routes fail closed at 401"). `grant execute … to authenticated`. EZD-006 may reuse it in policies.

### Step 3: Session client and helpers (`app/src/server/auth/`; builder)
Server-only by location (EZD-000 Folder layout).
- **`supabase-server.ts`**: `createSessionClient()`. It wraps `createServerClient` from `@supabase/ssr` with Next's `cookies()`, the URL and publishable key from EZD-004's `env.ts` (read per call), and `auth.flowType` at the package default.
  - **API gate header (Q-0087 (ii)):** it sends `x-ezd-api-gate: <SUPABASE_API_GATE_SECRET>` on every request (`global.headers`), so PostgREST lets the server's calls through EZD-006's gate (EZD-006 Step 1b). `SUPABASE_API_GATE_SECRET` is a new **server-only** env name (never `NEXT_PUBLIC_`), read per call by a new `serverGateSecret()` in `app/src/server/db/env.ts` (Zod: string of at least 43 characters, matching EZD-006's `newGateSecret()`). Missing or invalid → `createSessionClient()` throws a config error, which `getSession()` and the middleware treat as "no session" (Step 4: "Missing Supabase env … counts as no session"). The value is never logged, never returned in a response, never passed to a client component.
  - `.env.example` gains `SUPABASE_API_GATE_SECRET=` (empty; CLAUDE.md rule 12). `scripts/db/local.mjs env` (EZD-004's, extended) prints it from the gitignored file EZD-006's `local.mjs up` writes (`supabase/.temp/ezd-api-gate-secret`), so the Playwright web server and `pnpm dev` get the local value. Cloud values: EZD-006's runbook step (Josh stores the hash in each project and the secret in Vercel).
  - Cookie options (*planner's choice*, except `maxAge`): `httpOnly: true`, `sameSite: 'lax'`, `path: '/'`, `secure` when the request is `https`, `maxAge` = `34560000` seconds (400 days, Q-0048 (a)). The server rewrites the auth cookies on every token refresh (at most once per `jwt_expiry` of use, Step 1), so the 400 days count from the last use, which is "400 days unused".
  - Reason for `httpOnly`, and for only the server setting cookies: Safari caps cookies written by script at 7 days. A cookie set by a server response is not capped. This is what lets field devices keep a long-lived session (ticket Scope). Browser code never holds the refresh token. EZD-018 gets a Realtime token from a server route (Risks).
- **`session.ts`**:
  - `type Session = { authUserId: string; appUserId: string; email: string }`.
  - `getSession(): Promise<Session | null>`, wrapped in React `cache()` so it runs at most once per request:
    1. `auth.getClaims()` if the pinned SDK has it (local JWT check), otherwise `auth.getUser()`;
    2. `rpc('current_app_user_id')`.
    It returns null when there is no user, no linked `app_user`, or an ended session (`current_app_user_id()` returns null, Step 2.3; Q-0052 (c)).
  - `requireSession(): Promise<Session>` for pages. With no session, `redirect('/sign-in')`.
  - `requireApiSession(): Promise<Session | Response>` for Route Handlers. With no session, returns `401` with `{ "error": { "code": "not_signed_in", "message_key": "error.not_signed_in" } }` (EZD-000 Errors and logging: 401 "not signed in").
  - The secret key is never used (EZD-000 service-key rule).
- **`complete-sign-in.ts`**: `completeSignIn(client): Promise<'ok' | 'no_access'>`, run after any successful verification:
  1. `rpc('link_app_user')`.
  2. No row, or `has_access = false`: `auth.signOut({ scope: 'local' })`, return `'no_access'`.
  3. If `accepted_membership_id` is set (an invite was accepted, Q-0050 (a)): `await emit('user.joined', { membershipId, appUserId, via: 'sign_in' }, { tenantId: accepted_tenant_id, actorId: appUserId })` through EZD-022's app-wide `emit` from `app/src/server/events/index.ts` (bare name, vault/plans/EZD-022.md Step 2). `user.joined` is added to EZD-022's registry as `log_only` in this commit, with that payload type (EZD-022 "Not in this ticket"; S15 Events). `via` lets EZD-105's invite-link path emit the same event with `'invite_link'` (*planner's choice*). Ids only, no email (EZD-000 redaction rule). An emit error is caught and does not fail the sign-in (the acceptance is already committed; *planner's choice*).
  4. `auth.refreshSession()` once, so the token is reissued after the link (and any acceptance) exists and EZD-006's token hook can add the active-tenant claim (Step 9). Return `'ok'`.
- **`actions.ts`** (`'use server'`):
  - `requestSignIn(formData)`:
    - Validates the email with Zod (lower-cased, trimmed).
    - Calls `auth.signInWithOtp({ email, options: { shouldCreateUser: true } })`.
    - Sets a short-lived `httpOnly` cookie `ezd_sign_in_email` with `Max-Age` `900` (15 minutes, the code's lifetime, Q-0049). This brings back the code step if iOS reloads the installed app while the user reads Mail (*planner's choice*).
    - **Always returns `{ step: 'code' }`** whether the email is known, unknown or refused, so the page does not reveal who has an account. Only a malformed email returns `{ error: 'invalid_email' }`. A Supabase rate-limit error returns `{ error: 'too_many_requests' }`.
  - `verifySignInCode(formData)`:
    - Takes the email from the cookie or the form, and the code, which must match `^\d{6}$`.
    - Calls `auth.verifyOtp({ email, token, type: 'email' })`, then `completeSignIn`.
    - `'ok'` → clear the cookie and `redirect('/')`. A wrong or expired code → `{ error: 'code_invalid' }`. `'no_access'` → `{ error: 'no_access' }`.
  - `confirmSignInLink(formData)`:
    - Takes `token_hash` and `type`. Only `type === 'email'` is accepted; anything else returns `{ error: 'link_invalid' }`.
    - Calls `auth.verifyOtp({ token_hash, type: 'email' })`, then `completeSignIn`. Redirects or errors as above, with `link_invalid` for a used or expired link.
  - `signOut()`: `auth.signOut({ scope: 'local' })`, which ends this device's session only (*planner's choice*: other devices, such as the crew phone, stay signed in; ticket Scope "long-lived"). Then `redirect('/sign-in')`.
  - `setSignInLanguage(formData)` (Q-0047 (a)): takes `lang`; `'es'` → `es`, anything else → `en`. Sets the cookie `ezd_sign_in_lang` (`httpOnly`, `sameSite: 'lax'`, `path: '/'`, `secure` on `https`, `maxAge` `34560000`, the same 400-day browser limit as Q-0048 (a); *planner's choice* of name and lifetime for "remembered on the device"). It does not redirect: setting a cookie in a Server Action makes Next re-render the current page, so the URL (including the confirm page's `token_hash`) is unchanged *(confirm on the pinned Next.js)*. It touches no database row.
- **`sign-in-language.ts`**: `getSignInLanguage(): Promise<Language>` reads `ezd_sign_in_lang` from `cookies()`: `'es'` → `'es'`, anything else or missing → `'en'` (Level-1 answers: English default, Q-0029 (a)). Used only by the signed-out pages (Step 5). It is never used for a signed-in surface, which keeps EZD-026a's rule that a signed-in user's language comes from the user record (EZD-026a Step 1; EZD-026b).
  - Server Actions carry Next's built-in same-origin check, so no extra CSRF token is needed.
  - None of these logs anything. Codes, token hashes and emails are never logged (EZD-000 Errors and logging; C8).

### Data flow
- **Link:** `/sign-in` → `requestSignIn` → Supabase Auth (the hook allows or refuses a new auth user) → email to the mail catcher (local) or SMTP (cloud) → the user opens the link → `/auth/confirm` button → `confirmSignInLink` → `verifyOtp(token_hash)` → `completeSignIn` (`link_app_user`, which accepts a valid pending invite; `emit('user.joined')` if it did; refresh) → httpOnly cookies → `/`.
- **Language:** the switch posts `setSignInLanguage` → `ezd_sign_in_lang` cookie → `getSignInLanguage()` on the next render of either signed-out page.
- **Code:** same until the email, then the user types the code → `verifySignInCode` → `verifyOtp(email, token)` → same.
- **Every later request:** middleware refresh → `requireSession` / `requireApiSession`.

## Data
- **No tables, no columns, no RLS policies, no `schema_version` change.**
- Three `security definer` functions (Step 2):
  - `auth_before_user_created`: executable by `supabase_auth_admin` only;
  - `link_app_user` and `current_app_user_id`: executable by `authenticated` only.
- One `private` helper, `private.invite_is_valid`, with no API grant; one redefined `private` trigger function, `private.membership_end_sessions` (EZD-006's; Step 2.4); one trigger on `auth.users`, `auth_users_password_guard` (Step 2.5, Q-0094), which blanks the password of any unconfirmed auth user.
- **Writes:** `app_user.auth_user_id`, only for the signed-in user's own verified email, and only when it is null or already theirs. `membership.status` `invited` → `active`, only for that user's own single valid pending invite when they have no active membership (Q-0050 (a); Q-0043 (a)). Auth's own tables are written by Supabase Auth.
- **Cookies:** auth cookies (400 days, Q-0048 (a)), `ezd_sign_in_email` (900 s, Q-0049), `ezd_sign_in_lang` (400 days, Q-0047 (a)); all httpOnly.
- `membership.last_active_at` is **not** written here. EZD-005 Risks asks that whoever writes it throttles it; no ticket row assigns it.
- No money fields.
- Secrets: one new **server-only** env name, `SUPABASE_API_GATE_SECRET` (Q-0087); its values live only in Vercel, the gitignored local file and the test process, never in the repo. On request paths: the publishable key and this secret, which is sent only server-to-Supabase.
