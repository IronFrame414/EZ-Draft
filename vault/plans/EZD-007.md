### Level-1 answers (with sources)
- **No Copy link on self-service sign-in.** Copy link for crew is "on the sender's side" (S17), meaning the office user who sends a crew or invite link (EZD-105 app invite token; EZD-1421 crew link). When users ask for their own sign-in email there is no sender. Supabase also sends this email itself, so the app never sees the link (EZD-008 plan). R24 #15 and 11 Security are therefore met by EZD-105, not here.
- **Who may receive a sign-in email.** Users are invited in EZ Draft (R24 #14), so an email with no `app_user` row never gets an account (Step 2). Access after sign-in needs at least one `active` membership: EZD-006's row refuses deactivated users, and EZD-105's row says "accepting turns the row active". Whether an `invited` member may sign in from the sign-in page is Q-0050.
- **Code length 6** (R26 R15; 02 Users and role presets).
- **No passwords** (ticket Scope; 02). The app has no password field and no password route. See Risks for the Auth API's own password endpoints.
- **The sign-in page title contains `EZ Draft`.** EZD-003's T8 follows `/` to the sign-in page and checks `<title>` (vault/plans/EZD-003.md Step 2).

### Step 2: Database functions (migrations; one concern per file, EZD-000 Migrations and C5; builder)
All three are `language plpgsql` or `sql`, `security definer`, `set search_path = ''`, owned by the migration role, with `revoke all … from public` and an explicit `revoke execute … from anon` (Supabase's default privileges grant it by name *(confirm on pinned version)*; Data: "executable by `authenticated` only"). Function 1 also revokes from `authenticated` and `service_role` (below).
1. `<ts>_create_auth_before_user_created.sql`. `public.auth_before_user_created(event jsonb) returns jsonb`:
   - Allowed when `lower(event->'user'->>'email')` matches an `app_user.email` that has a membership whose status is in the Q-0050 set (default reading: `active` only). Returns `'{}'::jsonb`.
   - Otherwise returns `{"error": {"http_code": 403, "message": "sign_in_not_allowed"}}`.
   - `grant execute … to supabase_auth_admin`. Not granted to `anon` or `authenticated`: besides `revoke all … from public`, the migration also runs `revoke execute … from anon, authenticated, service_role`, because Supabase's default privileges grant execute on new `public` functions to those roles by name *(confirm on pinned version)*; EZD-006 T22 (j) would otherwise list it as a gated RPC.
   - If the pinned CLI has no before-user-created hook, the builder uses a `before insert` trigger on `auth.users` with the same rule and raises instead. Tests T6 and T7 then pass unchanged. The builder records which one was used in docs.
   - **Admin-API user creation (review finding 16).** A `before insert` row trigger on `auth.users` fires for every insert, so under the trigger fallback the Auth admin `createUser` **does not pass** for an email without an `app_user` that has an active membership. For the hook, no vault source says whether Supabase Auth runs the before-user-created hook on admin `createUser` *(confirm on pinned version)*; EZD-016a's plan (Step 5 item 2) already assumes it does. The test-author checks this first, with one admin `createUser` call for an unknown email on the pinned stack, and records the result in `### Auth and session (EZD-007)`. If admin creation does not pass (trigger fallback, or the hook covers admin calls), the test-author makes the edits listed under "Test edits allowed" below; if it passes, those edits are not needed and are not made.
2. `<ts>_create_link_app_user.sql`. `public.link_app_user() returns table (app_user_id uuid, has_access boolean)`:
   - Reads `auth.users` for `auth.uid()`. If `email_confirmed_at` is null, it returns no row.
   - Otherwise `update public.app_user set auth_user_id = auth.uid() where email = lower(<that email>) and (auth_user_id is null or auth_user_id = auth.uid())`. It returns `id` and whether a membership in the Q-0050 set exists.
   - Idempotent. It never re-points a row already linked to a different auth user (EZD-005 Risks: "link only a verified email").
   - `grant execute … to authenticated`.
3. `<ts>_create_current_app_user_id.sql`. `public.current_app_user_id() returns uuid`, `stable`. Returns null when `private.session_is_live()` is false (EZD-006 Step 3: the token's `session_id` no longer exists in `auth.sessions`, for example after deactivation); otherwise `app_user.id where auth_user_id = auth.uid()`, or null. It does not raise, so `getSession()` returns null and `requireApiSession()` answers 401 for a deactivated user still holding a valid JWT (Q-0052 (c): "`current_app_user_id()` returns null for an ended session so routes fail closed at 401"). `grant execute … to authenticated`. EZD-006 may reuse it in policies.

No table, so no RLS policy and no `tenant_id`. EZD-006's policy and index CI test covers tables only (EZD-004 Machine checks note).

### Step 3: Session client and helpers (`app/src/server/auth/`; builder)
Server-only by location (EZD-000 Folder layout).
- **`supabase-server.ts`**: `createSessionClient()`. It wraps `createServerClient` from `@supabase/ssr` with Next's `cookies()`, the URL and publishable key from EZD-004's `env.ts` (read per call), and `auth.flowType` at the package default.
  - **API gate header (Q-0087 (ii)):** it sends `x-ezd-api-gate: <SUPABASE_API_GATE_SECRET>` on every request (`global.headers`), so PostgREST lets the server's calls through EZD-006's gate (EZD-006 Step 1b). `SUPABASE_API_GATE_SECRET` is a new **server-only** env name (never `NEXT_PUBLIC_`), read per call by a new `serverGateSecret()` in `app/src/server/db/env.ts` (Zod: string of at least 43 characters, matching EZD-006's `newGateSecret()`). Missing or invalid → `createSessionClient()` throws a config error, which `getSession()` and the middleware treat as "no session" (Step 4: "Missing Supabase env … counts as no session"). The value is never logged, never returned in a response, never passed to a client component.
  - `.env.example` gains `SUPABASE_API_GATE_SECRET=` (empty; CLAUDE.md rule 12). `scripts/db/local.mjs env` (EZD-004's, extended) prints it from the gitignored file EZD-006's `local.mjs up` writes (`supabase/.temp/ezd-api-gate-secret`), so the Playwright web server and `pnpm dev` get the local value. Cloud values: EZD-006's runbook step (Josh stores the hash in each project and the secret in Vercel).
  - Cookie options (*planner's choice*): `httpOnly: true`, `sameSite: 'lax'`, `path: '/'`, `secure` when the request is `https`, `maxAge` = the Q-0048 value.
  - Reason for `httpOnly`, and for only the server setting cookies: Safari caps cookies written by script at 7 days. A cookie set by a server response is not capped. This is what lets field devices keep a long-lived session (ticket Scope). Browser code never holds the refresh token. EZD-018 gets a Realtime token from a server route (Risks).
- **`session.ts`**:
  - `type Session = { authUserId: string; appUserId: string; email: string }`.
  - `getSession(): Promise<Session | null>`, wrapped in React `cache()` so it runs at most once per request:
    1. `auth.getClaims()` if the pinned SDK has it (local JWT check), otherwise `auth.getUser()`;
    2. `rpc('current_app_user_id')`.
    It returns null when there is no user, no linked `app_user`, or an ended session (`current_app_user_id()` returns null, Step 2.3; Q-0052 (c)).
  - `requireSession(): Promise<Session>` for pages. With no session, `redirect('/sign-in')`.
  - `requireApiSession(): Promise<Session | Response>` for Route Handlers. With no session, returns `401` with `{ "error": { "code": "not_signed_in", "message_key": "error.not_signed_in" } }` (EZD-000 Errors and logging: 401 "not signed in").
  - The secret key is never used (EZD-000 service-key rule).
- **`complete-sign-in.ts`**: `completeSignIn(client): Promise<'ok' | 'no_access'>`, run after any successful verification:
  1. `rpc('link_app_user')`.
  2. No row, or `has_access = false`: `auth.signOut({ scope: 'local' })`, return `'no_access'`.
  3. Otherwise `auth.refreshSession()` once, so the token is reissued after the link exists and EZD-006's token hook can add the active-tenant claim (Step 9). Return `'ok'`.
- **`actions.ts`** (`'use server'`):
  - `requestSignIn(formData)`:
    - Validates the email with Zod (lower-cased, trimmed).
    - Calls `auth.signInWithOtp({ email, options: { shouldCreateUser: true } })`.
    - Sets a short-lived `httpOnly` cookie `ezd_sign_in_email`, valid for the Q-0049 lifetime. This brings back the code step if iOS reloads the installed app while the user reads Mail (*planner's choice*).
    - **Always returns `{ step: 'code' }`** whether the email is known, unknown or refused, so the page does not reveal who has an account. Only a malformed email returns `{ error: 'invalid_email' }`. A Supabase rate-limit error returns `{ error: 'too_many_requests' }`.
  - `verifySignInCode(formData)`:
    - Takes the email from the cookie or the form, and the code, which must match `^\d{6}$`.
    - Calls `auth.verifyOtp({ email, token, type: 'email' })`, then `completeSignIn`.
    - `'ok'` → clear the cookie and `redirect('/')`. A wrong or expired code → `{ error: 'code_invalid' }`. `'no_access'` → `{ error: 'no_access' }`.
  - `confirmSignInLink(formData)`:
    - Takes `token_hash` and `type`. Only `type === 'email'` is accepted; anything else returns `{ error: 'link_invalid' }`.
    - Calls `auth.verifyOtp({ token_hash, type: 'email' })`, then `completeSignIn`. Redirects or errors as above, with `link_invalid` for a used or expired link.
  - `signOut()`: `auth.signOut({ scope: 'local' })`, which ends this device's session only (*planner's choice*: other devices, such as the crew phone, stay signed in; ticket Scope "long-lived"). Then `redirect('/sign-in')`.
  - Server Actions carry Next's built-in same-origin check, so no extra CSRF token is needed.
  - None of these logs anything. Codes, token hashes and emails are never logged (EZD-000 Errors and logging; C8).

### Step 4: Request gate (`app/src/middleware.ts`, or `app/src/proxy.ts` if the pinned Next.js uses that name; builder)
- On every request except static assets (`_next/static`, `_next/image`, files with an extension):
  - Builds a session client on the request and response cookies, which refreshes an expired access token and writes the rotated cookies.
  - Uses `getClaims()` / `getUser()` as in Step 3.
- **Pages are deny-by-default.** A page path not in `PUBLIC_PATHS` with no auth user gets a `307` to `/sign-in`. No `next=` parameter, so there is no open redirect (*planner's choice*). After sign-in the user lands on `/`.
- `app/src/server/auth/public-paths.ts` exports `isPublicPath(pathname)`:
  - true for `/sign-in`, `/auth/confirm`, `/api/**` (Route Handlers answer `401` themselves through `requireApiSession`; a redirect is wrong for an API), and `/dev/**`;
  - `/dev/**` is public because those pages need no sign-in in EZD-011 and EZD-012's browser tests, and they 404 in production (EZD-010 Step 5);
  - later public pages (client link, `/terms` from EZD-1707, inbound API) add themselves here in their own commit (recorded in docs).
- **Missing Supabase env or an Auth error counts as no session.** Pages redirect to `/sign-in`; the middleware never answers 500. The sign-in page itself renders with no env. EZD-003's T8 (`status 200`, title) therefore passes on a deploy whose Supabase values are not set yet.

### Data flow
- **Link:** `/sign-in` → `requestSignIn` → Supabase Auth (the hook allows or refuses a new auth user) → email to the mail catcher (local) or SMTP (cloud) → the user opens the link → `/auth/confirm` button → `confirmSignInLink` → `verifyOtp(token_hash)` → `completeSignIn` (`link_app_user`, refresh) → httpOnly cookies → `/`.
- **Code:** same until the email, then the user types the code → `verifySignInCode` → `verifyOtp(email, token)` → same.
- **Every later request:** middleware refresh → `requireSession` / `requireApiSession`.

## Risks
- **Build order.** `tickets.json` now lists EZD-026a, EZD-010 and EZD-006 as dependencies; its `build_order` runs EZD-006, EZD-010 and EZD-026a before EZD-007, and EZD-016a right after it; no further reordering is needed.
- **Gate secret (Q-0087).** If `SUPABASE_API_GATE_SECRET` is missing or wrong on a deploy, every signed-in page behaves as signed out (fails closed, Step 3), and cloud sign-in looks broken until Josh does EZD-006's runbook step. If the secret ever reached a browser, a member could bypass `can()` through PostgREST; T20 and T21 guard it, and the code-reviewer checks that no client component receives env values.
- **Admin user creation (finding 16).** Until the test-author's probe on the pinned stack, it is unknown whether the before-user-created hook covers admin `createUser`; the "Test edits allowed" list covers the case where it does.
- **Harness overlap with EZD-016a (Q-0045).** EZD-016a must extend `app/playwright.config.ts`, keep the `desktop` project, workers 2 and the web server on port 3000 (= `site_url`), and reuse `signInWithCode` and `mail-catcher.ts`. EZD-016a's planner should read this plan.
- **EZD-006's token hook (Step 9).** If it errors for an unlinked user, every first sign-in fails. If it runs only on sign-in and not on refresh, the first session has no tenant claim until the next refresh.
- **Supabase specifics depend on the pinned CLI and SDK:**
  - whether the before-user-created hook exists (otherwise the trigger fallback; Supabase limits changes in the `auth` schema, so the builder checks that the trigger is allowed);
  - "confirmation" vs "magic link" template use for new users;
  - `verifyOtp` `type` values;
  - `getClaims`;
  - the Inbucket or Mailpit API;
  - the `middleware` / `proxy` file name.
  The test-author and builder read the pinned versions, not memory.
- **Cloud.** None of the cloud Auth settings come from `config.toml`. Until Josh does the runbook (after Q-0024, Q-0033 and EZD-008 step 6, which hangs on Q-0035 and Q-0036), cloud sign-in uses Supabase's default template and sender: no code, link format wrong for the confirm page, low rate limit. The Phase 0 Field check waits on that.
- **Account enumeration** through the public Auth API stays possible: an unknown email gets a 403 from the hook. The app's own page hides it (T6). Supabase rate limits apply; the security-reviewer judges whether that is enough.
- **Passwords.** The app has no password UI. A known member could still set a password on their own account through the Auth API once signed in, which affects only themselves. A stranger cannot use the password sign-up: unknown emails are refused (T7), and with confirmations on, a known email needs the mailbox. If the security-reviewer wants password sign-in fully off, that needs a Supabase setting or hook the pinned version may not have.
- **The 6-digit code can be guessed** only within Supabase's verification rate limit and the Q-0049 lifetime. A longer lifetime widens the window.
- **Signed-in home vs Q-0039.** This ticket makes `/` require sign-in and show only Sign out. If Q-0039 makes `/` the empty editor (EZD-012) or a new ticket, that ticket must keep a Sign out control on the page until EZD-108's avatar menu ships, and must keep `requireSession()`.
- **Realtime (EZD-018).** Auth cookies are httpOnly, so browser code cannot read the access token; EZD-018 must get a short-lived token from a server route. That token in browser memory is refused by PostgREST without the gate header (EZD-006 Step 1b) and lives at most `jwt_expiry` = 3600 s (Q-0052 (c)).
- **Shared sign-on (EZD-114, EZD-1305)** must create a Supabase session server-side without the secret key on the request path (EZD-000). That is their design problem, and they should reuse `completeSignIn` and the cookie options.
- **Device data after sign-out.** IndexedDB working copies and the outbox (03 rules 9–10; EZD-134) stay on the device after sign-out. EZD-134 decides what sign-out clears.
- **Performance.** The middleware runs on every page and API request. With `getClaims()` and asymmetric signing keys the check is local. With `getUser()` it is one Auth round trip per request, which counts against "Projects page first cards within 1 second" (11 Budgets). `getSession()` adds one RPC per request (with one `auth.sessions` primary-key lookup for the liveness check, Step 2.3) until EZD-102 folds it into its per-request query; the `app_user_id` claim alone cannot replace it, because it cannot tell an ended session (Q-0052 (c)).
- **Local test environment.** Chromium must be installed once on this PC. The local `email_sent` limit is raised for tests only. `db:up` runs again in `test:e2e`, so the gate takes longer.
