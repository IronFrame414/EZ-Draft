# EZD-331 · Fix: the dead-lock take-over tests pass while other lanes run their gates

- **ACs:** AC-EZD-331-1, AC-EZD-331-2
- **Complexity:** low
- **Areas:** tooling, scripts
- **User-visible result:** the gate no longer fails at random on the EZD-256 lock tests when several lanes run gates at once, and a gate step that dies without output now says why.
- Phase: 1 · Planned by: planner · Date: 2026-11-04 · Status: planned

## 1. What to build

Cause (evidence in section 2, E1-E6). "Not a git repository" is not the failure: it is the first stdout line of every fixture gate (`printTouched` on a temp folder that is no git repository, `scripts/gate.mjs` lines 89-90), quoted at the head of K12's assertion message. The failure was K12 round 0 line 353: the lane 2 fixture gate's `test` step (`npm run test`) failed with zero output, not even npm's `> ezd256-fixture@0.0.0 test` banner, inside a 1.34 s round (E1). So the machine's `npm` process ended before it wrote anything, and `run()` in `scripts/gate.mjs` (lines 289-310) drops `r.error` and `r.signal`, so the reason was lost (E2). Shared lock paths, shared temp paths, process kills, a kernel process limit and the file's own concurrency are ruled out (E3-E6); the failure did not reproduce. Fix for the cause the evidence points to: (a) the fixture gates in `gate-lock.test.mjs` run their checks through a fixture-local `npm` that starts no machine npm, takes no PATH lookup of `node` and reads no `~/.npm`; (b) the gate names a spawn error or a signal of any step, so a recurrence carries its cause. No lock code and no existing assertion changes (AC-EZD-331-2).
