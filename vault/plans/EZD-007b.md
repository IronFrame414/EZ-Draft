### Steps

Rules for all three migrations (builder): created with `pnpm supabase migration new <name>` (docs/architecture.md Migrations; C5), timestamps after EZD-007a's three migrations, in this order: link, current, trigger. One concern per file. No table, so no RLS policy, `tenant_id` or isolation test (docs/architecture.md Migrations). No `drop`, `rename`, `set schema` or `cascade` text anywhere, including comments and function bodies (EZD-023a M4 scans dollar-quoted bodies). `language`, volatility and `security definer` as below; every function `set search_path = ''`, owned by `postgres` (the migration role).

**Function grants (finding B3).** Probed by the planner on the local stack (PostgreSQL 17.11, CLI 2.121.0; L-009; one transaction, rolled back): `pg_default_acl` for role `postgres` in schema `public` grants execute on new functions to `anon`, `authenticated` and `service_role`, and a new `public` function is executable by all three until revoked. EZD-006 revoked default privileges for tables only (STATUS EZD-006 security follow-up: "the first ticket adding a … `public` function revokes/grants explicitly"). So each API function migration has exactly these two statements (probed: afterwards `anon` false, `authenticated` true, `service_role` false):
- `revoke all on function public.<fn>() from public, anon, service_role;`
- `grant execute on function public.<fn>() to authenticated;`
Source for "authenticated only": parent Data ("`link_app_user` and `current_app_user_id`: executable by `authenticated` only"); parent V3.

**Step 1 · `<ts>_create_link_app_user.sql`** (builder; P-Step 2.2). `public.link_app_user() returns table (app_user_id uuid, has_access boolean, accepted_membership_id uuid, accepted_tenant_id uuid)`, `language plpgsql`, `volatile`, `security definer`, `set search_path = ''`. In order:
1. No row when `auth.uid()` is null.
2. No row when the token's session has ended: `private.session_is_live()` is false (*planner's choice*, finding B4: the function writes, and sessions fail closed once ended, Q-0052 (c); `completeSignIn` (EZD-007d) calls it right after `verifyOtp`, when the session is live, so sign-in is unchanged).
3. Reads `auth.users` for `auth.uid()`; no row when `email_confirmed_at` is null (P-Step 2.2 "link only a verified email"; EZD-005 Risks).
4. `update public.app_user set auth_user_id = auth.uid() where email = lower(<that email>) and (auth_user_id is null or auth_user_id = auth.uid())` (P-Step 2.2; `app_user.email` is stored lower-case, `20261019165202_create_app_user.sql` line 8). Then no row when no `app_user` has `auth_user_id = auth.uid()`. A row already linked to a different auth user is never re-pointed (EZD-005 Risks: "A wrong link would give one person another person's memberships").
5. Access and invite acceptance on that `app_user`'s memberships, locked with `select … for update` (P-Step 2.2; Q-0050 (a); Q-0043 (a); Q-0099 (b)):
   - an `active` membership exists → `(app_user_id, true, null, null)`; nothing accepted; pending invites elsewhere stay `invited` (Q-0043 (a): one active company per person);
   - else memberships with `private.invite_is_valid(status, invited_at)` (EZD-007a Step 2.0: `invited`, `invited_at` not null and within 7 days) → the one with the latest `invited_at`, tie broken by the higher `id` (parent Level-1 answers, *planner's choice* for the tie; Q-0099 (b)); `update public.membership set status = 'active' where id = <it> and status = 'invited'`; return `(app_user_id, true, <its id>, <its tenant_id>)`. `invited_at` and `last_active_at` are not written; every other valid invite stays `invited` (Q-0099 (b));
   - else `(app_user_id, false, null, null)`.
6. Idempotent: a second call finds the membership `active` and accepts nothing (P-Step 2.2).
7. Grants as "Function grants" above.

**Step 2 · `<ts>_create_current_app_user_id.sql`** (builder; P-Step 2.3). `public.current_app_user_id() returns uuid`, `language sql`, `stable`, `security definer`, `set search_path = ''`. Returns null when `private.session_is_live()` is false (EZD-006 helper: the token's `session_id` is not in `auth.sessions`); otherwise `public.app_user.id` where `auth_user_id = auth.uid()`, or null. It never calls `private.app_user_id()`, which raises `42501` on an ended session (parent V3); it never raises, so a deactivated user's still-valid JWT gets null and routes answer 401 (Q-0052 (c): "`current_app_user_id()` returns null for an ended session so routes fail closed at 401"). Grants as above. One `auth.sessions` primary-key lookup and one `app_user` unique-index lookup per call (11 Rules 10; parent Risks "Performance").

**Step 3 · `<ts>_membership_end_sessions_skip_invite_accept.sql`** (builder; P-Step 2.4; parent V3 (5)). `create or replace function private.membership_end_sessions()` with the merged body of `supabase/migrations/20261019170005_create_end_sessions_triggers.sql` lines 21–36 kept exactly (`returns trigger`, `language plpgsql`, `security definer`, `set search_path = ''`, `tg_op = 'DELETE'`, the scope clause, `perform private.end_user_sessions(old.user_id)`, `return null`), changing only line 29 `or new.status is distinct from old.status` to `or (new.status is distinct from old.status and not (old.status = 'invited' and new.status = 'active'))`. Source: Q-0044 (b) ("only narrowing changes end sessions"); without it, Step 1's acceptance would end the session being created (P-Level-1 answers). No `create trigger`, no `drop trigger`, no grant: `create or replace` keeps the existing trigger `membership_end_sessions` and the `revoke all … from public` (EZD-006's `rls.hook.test.ts` lines 126–135 still expect no execute for `anon` and `authenticated`). Every other status change, every scope change and every delete still ends sessions.
