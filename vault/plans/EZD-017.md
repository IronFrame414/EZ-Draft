### Step 4: Browser hooks (`scripts/perf/page-hooks.browser.js`; builder; plain browser script loaded with `context.addInitScript({ path })`)
It is installed before any page script runs. It defines `window.__EZD_PERF__ = { commits, renderers, longTasks, rafTimes, mark }`:
- **React commits** *(builder confirms against the pinned React)*:
  - The script installs `window.__REACT_DEVTOOLS_GLOBAL_HOOK__` as `{ supportsFiber: true, isDisabled: false, renderers: new Map(), inject(r) { … return id }, onCommitFiberRoot() { commits++ }, onCommitFiberUnmount() {}, onPostCommitFiberRoot() {}, checkDCE() {} }`.
  - React DOM production builds call `inject` at start-up and `onCommitFiberRoot` on every commit. This is how React DevTools reads production sites.
  - `renderers` counts `inject` calls. If it is 0 on a page that should run React, the measurement is an **error**, not 0, so a React upgrade that stops calling the hook cannot pass silently (T3c).
  - If the pinned React needs more hook methods, the builder adds empty ones.
- **Long tasks:** a `PerformanceObserver` for `longtask` with `buffered: true`. It stores `{ startTime, duration }` for each entry. A long task is a main-thread task over 50 ms, per the browser's Long Tasks API.
- **Frame times:** while `mark('pan-start')` is active, a `requestAnimationFrame` loop records rAF timestamps until `mark('pan-end')`. The loop exists only during the pan window, so the page draws nothing idle because of the check (11 rule 4).

### Step 5: Scripted pan (`scripts/perf/pan-script.mjs`; builder)
Input is real Playwright mouse and keyboard events, because app pan handlers later use pointer capture, which synthetic events do not get.
1. Load the pan URL (Phase 0: `/dev/shell`) in a fresh context with the `desktop` profile. Wait for `load`, then for no new network request for 1,000 ms (at most 15,000 ms). Read the bounding box of `[data-shell-region="canvas"]`; its centre is `(cx, cy)`. At 1600 × 1000 that is (792, 515), from EZD-012's box 352 + 880/2, 92 + 846/2.
2. Snapshot `commits`, the long-task count and the time. Call `mark('pan-start')`.
3. **Right-button drag:** `mouse.move(cx, cy)`, `mouse.down({ button: 'right' })`. Then 45 moves to `cx + 300 · i/45`, and 45 moves back to `cx`, each move followed by a 16 ms wait. Then `mouse.up({ button: 'right' })`.
4. **Space + left drag:** `keyboard.down('Space')`, `mouse.down()`, the same 90 moves, `mouse.up()`, `keyboard.up('Space')`.
5. Wait two animation frames, then call `mark('pan-end')`. Take the second snapshot.
6. Results:
   - commits = the difference between the two commit counts;
   - long tasks = entries whose `startTime` lies inside the window (`long-tasks-during-pan`); entries before the first snapshot, from navigation to `pan-start`, are `long-tasks-during-load` (Q-0073 (a));
   - frame intervals = the differences between consecutive rAF timestamps;
   - `pointerMoves` = **180**.
- The two gestures are the mouse forms of pan in EZD-207's row ("space-drag, right-drag"). The 300 px, 45 + 45 steps, 16 ms wait and 1,000 ms idle are *planner's choices*. The whole pan takes about 3 to 4 s, close to EZD-207's "3-second pan". The two-finger touch form arrives with EZD-207's iPad profile.
- Frame stats come from `scripts/perf/stats.mjs` `frameStats(intervals)`. Its definitions are the same as EZD-027 Step 5:
  - result fields: `count`, `mean`, `p50`, `p95`, `p99`, `max`, `over16_7`, `over33_3`, `over100`;
  - percentiles are nearest-rank;
  - the "over" counts are strictly greater than 1000/60, 1000/30 and 100.
  - The code is written fresh here, because spikes are never imported (tickets README; EZD-000 C4).

### Step 6: Download size per entry (`scripts/perf/js-size.mjs`; builder)
For each `js-size:*` entry:
1. Open a fresh context with the cache disabled (`desktop` profile), so every byte is downloaded. Before navigation, attach a listener for every response on the context.
2. Go to the entry URL. If the document status is not 200, the measurement is an `error` with the status (T6).
3. Wait for `load`, then for no new request for 1,000 ms (at most 15,000 ms). Do no clicks, keys or scrolls: lazy parts load only on use (11 rule 7).
4. Count each distinct URL once. A response counts when it is JavaScript:
   - request `resourceType()` is `script`; or
   - it is a dedicated worker's script (Web Workers started at load are downloaded code; 11 rule 3); or
   - its `content-type` is JavaScript.
5. **Not counted:**
   - the service-worker script and any request the service worker makes, i.e. `request.serviceWorker()` is non-null *(builder confirms in Chromium)*. The service worker installs in the background after `load` (vault/plans/EZD-013.md Step 3) and later precaches files for offline (11 Offline); that is not code the page needs to run.
   - inline `<script>` text in the HTML. It is page data (Next.js flight data), not a JavaScript file.
   - These two exclusions are *planner's choices*, recorded in docs.
6. `value` = the sum of `compressedSize(body)` over the counted files. It is computed from the response body, not taken from the server's `Content-Encoding`, so the number is the same locally, in CI and on Vercel (Q-0071 (a): gzip level 6, measured from the response body). `details` = the list of `{ url, rawBytes, compressedBytes }`, plus the service-worker bytes as `excludedServiceWorkerBytes`.

### Step 7: Probe page for the Done-when test (`app/src/app/dev/perf-probe/page.tsx`, `PanCommitProbe.tsx`; builder)
- The page follows the dev-page pattern: `notFound()` when `VERCEL_ENV === 'production'` (EZD-010 Step 5). It renders the same tree as `/dev/shell`: `MessagesProvider` with `catalogFor('office','en')` around `EmptyEditor` (EZD-012 Step 6). When the query has `inject=pan-commit`, it also renders `<PanCommitProbe />`.
- `PanCommitProbe` (`'use client'`):

## Risks
- **The Phase 0 check may fail on real sizes.**
  - Next.js and React alone take a large share of a 200 KB budget.
  - `/sign-in` and `/auth/confirm` also carry whatever the root layout mounts: possibly EZD-015's Radix `StateHost` (built before this ticket) if it sits in the root layout and not in entry layouts (EZD-015 Risks).
  - If `js-size:sign-in`, `js-size:auth-confirm` or `js-size:editor` is over budget when EZD-017 is built, the builder may not shrink other tickets' code under this ticket. The ticket then goes `blocked` with the numbers, and the fix becomes a question or an EZD-020 item.
  - EZD-018 (Realtime hub), EZD-020, EZD-024 (Sentry SDK) and EZD-013 (service-worker registration) build after this ticket (finding 28). Each must pass this check with its own code added; one that pushes a page over budget goes `blocked` with the numbers, not this ticket.
- **React hook dependence.** Commit counting relies on React DOM calling the DevTools hook in production builds. A React upgrade that changes this makes `react-commits-during-pan` an `error`, which is loud, not a silent 0 (T3c). The builder confirms the hook methods with the pinned React.
- **Long tasks depend on the CPU.** On this 16 GB PC under load (two Playwright workers, the Next server), the browser can see a long task that a quiet machine would not. Under Q-0073 (a) long tasks during the pan gate at 0, so T1 (run inside `test:e2e`, possibly beside the other Playwright worker) asserts 0 too. The gate's `perf` step runs alone and is the main proof. If T1 flakes on long tasks, the test-author raises a question; nobody loosens the budget or adds a retry.
- **`/dev/shell` is a stand-in.** It is a dev page, not what users load. Until the editor route exists, the editor number measures `EmptyEditor` plus the root layout. The editor-route ticket and EZD-020 must repoint the entries; until they do, those entries say so in `owner`.
- **Pending measurements can be forgotten.** A `pending` measurement never fails the check. Each owning ticket's code-reviewer and EZD-1701 must switch them to active. The summary prints the pending list on every run.
