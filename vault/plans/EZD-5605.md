| D-Save (how Accept saves) | Accept never calls `applyEdit`. A refusal or failure changes no model, undo stack, outbox entry or preview. | Q-0638 gap 10 ("preview stays until the server says saved; a save refused leaves everything as it was"); AC-5; `outbox-sync.ts` loop moves refusals to the conflict list, which would half-save |
| D-SendNow | Chained on `writes` like `keepMine`. (1) `changes.length` 0 or > `MAX_CHANGES_PER_SAVE` (100, `A/lib/outbox/outbox.ts:115`) → `{ kind: 'unsaved' }`, no storage call, no fetch. (2) `clearTimer()`; await `running`; disposed, `blocked()` or offline → `unsaved`. (3) `lock.tryRun(lockName, …)`: run `loop()` then `recordPending()` exactly as `drain` does; then `blocked()`, offline, or any `storage.list()` entry of `projectId` left → `unsaved`. (4) `storage.put(projectId, lockEpoch, changes, Date.now())`; `mine` = `storage.list()` entries with that project and an id in `changes`. (5) `stillValid()` false → `storage.drop(mine)`, `cancelled`, no fetch. (6) `send({ projectId, lockEpoch, send: mine, drop: [] }, [], true)`; body adds `assistant: true`. (7) `saved` → `o.onSaved?.(projectId, objects)`, `storage.commit(projectId, mine, objects)`, `set({ failures: 0, status: 'saved', lastSavedAt: Date.now() })`, return it. (8) `refused` or `failed` → `storage.drop(mine)`, `set({ status: restingStatus() })`, return the outcome; `problem` and `failures` untouched, nothing moved to conflicts. (9) Lock not taken → `unsaved`. (10) Any storage throw → `storageFailed(error)` (as the loop does), `unsaved`; a commit throw after `saved` pushes `{ projectId, sent: mine, saved }` on `unstored` first, as `loop` does, and still returns the `saved` outcome. | architecture "Patch store and outbox (EZD-120b)"; `outbox-sync.ts:405-520`; L-059 |
