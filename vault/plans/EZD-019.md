### Level-1 answers (with sources)
1. **Who issues the sign-on code.**
   - **Into EZ Draft:** EZ Binder asks EZ Draft for the code, and EZ Draft swaps it on its own server (ticket Scope; R26 R15; EZD-1305 row "EZ Binder requests a single-use 60-second code"). 07's "Verify a shared sign-on token" was written before R15 and is superseded for this direction (decisions override the spec, spec INDEX authority order).
   - **Into EZ Binder** (Back to EZ Binder; the "EZ Contractor Binder" link that "Opens EZ Binder in the same tab, signed in", S01): EZ Draft asks EZ Binder for a code and a return-to-job URL. Sources: ticket Scope "shared sign-on token and return-to-job URL"; 07 "Verify a shared sign-on token | … Back to EZ Binder". This is the same exchange as R15 with the roles reversed, so it uses the same 60 seconds and single use.
2. **The three Connect values come from EZ Binder.**
   - R32 says the webhook address, signing secret and inbound key are "entered at Connect in Settings". EZD-1303 says "the inbound key is issued per tenant at Connect".
   - Read together: EZ Binder generates all three on its side, and the owner enters them in EZ Draft's Connect (EZD-114).
   - EZ Draft stores only a hash of the inbound key (03 rule 11 pattern for tokens; R26 R14). It keeps the signing secret in a form it can sign with (EZD-114 decides how).
3. **Unknown or deactivated user at sign-on.** The answer is `404 user_not_found`, and no account is created (R24 #14: users are invited in EZ Draft). EZ Binder then sends the person to EZ Draft's `/sign-in` page (S17 States "SSO fails → magic-link sign-in prompt").
4. **Job visibility.** EZ Draft names the acting user by email (`as_user`), and EZ Binder returns only the jobs that user can see. Sources: S01 "Only jobs the user can see in EZ Binder"; S15a, users "matched … by email".
5. **Customer sync fields** are name, email, phone and address, plus both ids and `updated_at` for "latest edit wins" (S15a Sync customers and Validation; 03 customer). Archiving is not synced, because S15a lists only those four fields.
6. **User sync fields** are id, name, email and status (active / deactivated), plus `updated_at` (S15a "matched … by email; deactivation in either app is mirrored").
7. **No job-feed call.** R27 removed the job-feed ticket, so EZ Binder learns everything through the existing webhooks. Where 07 says "Add to job feed", that is EZ Binder's own handling of `field.conflict_flagged` and `client.commented`.
8. **Takeoff lines carry no money.** 02 Scope says Takeoff is "Quantities by room and trade, waste factors"; "Pricing engine" is out of scope; the push to an estimate is v2.
9. **Paging.** Every list call returns pages of at most 50 rows: `limit` 1–50, default 50 (11 Performance rule 9).
10. **Ids are opaque strings** on the EZ Binder side (EZD-005: `ezbinder_job_id` is `text`, "format set by the EZD-019 contract"). EZ Draft ids are UUIDs.
11. **`ezbinder_co_id` comes back in the webhook response.** S14 Send "stores ezbinder\_co\_id". The only call on Send is `change_order.sent` (W12; R24 "COs reach EZ Binder only when Send is pressed"). So EZ Binder's reply to that delivery carries the id.
12. **Money in payloads.** `change_order.sent` carries cost deltas (07 payload "lines (qty, unit, cost delta)"). Under R26 R2 those are company costs; they go only server to server, to the tenant's own EZ Binder. The `render_allowance.refilled` dollars are discussed in Step 5. Both are flagged for the security-reviewer.

### Step 1: The contract file `contracts/ezbinder-openapi.yaml` (builder)
- OpenAPI `3.1.0`, `info.title` `EZ Draft ⇄ EZ Binder contract`, `info.version` `1.0.0`.
  - *Planner's choice:* a breaking change bumps the major version and the path prefix `/v1`.
  - Placed at the repo root in `contracts/`, outside `app/`, because EZ Binder's repo uses it too (P6).
- **One document for both directions.**
  - `paths` holds the 12 calls in Step 3. Each operation carries `x-implemented-by: ezbinder | ezdraft`, a tag `EZ Binder implements` or `EZ Draft implements`, and its own `servers`:
    - EZ Binder API: `{ezbinderApiUrl}`, a server variable with default `http://127.0.0.1:3100` (the stub, Step 7) and the description "deployment value in EZBINDER\_API\_URL". The real EZ Binder address is not in any source; Josh sets it when EZ Binder's side exists.
    - EZ Binder web pages: `{ezbinderWebUrl}`, same default.
    - EZ Draft: `https://ezdraft.ezcontractorbinder.com` (R24 #1).
  - The top-level `webhooks` map holds the 13 deliveries in Step 5. The receiver is EZ Binder's, at the tenant's webhook address (R32; EZD-1301 "per-tenant endpoint").
- **Schema rules** (*planner's choice*, so that both repos see exact shapes and T3 can check them):
  - every object schema has `type: object`, `additionalProperties: false`, and `required` listing **every** property;
  - a value that can be absent is `type: [<type>, "null"]`, never left out;
  - JSON names are snake\_case;
  - dates are `format: date-time` (UTC, ISO 8601);
  - URLs are `format: uri`, emails `format: email`, EZ Draft ids `format: uuid`, EZ Binder ids `type: string, minLength 1, maxLength 100`;
  - schemas use only JSON Schema 2020-12 keywords. No `example`, `nullable`, `discriminator` or `xml`; use `examples` if needed. This keeps them valid for the Ajv 2020 validator (Step 6).
  - Shared schemas sit under `components.schemas` with the names used in Step 4.
- **`components.securitySchemes`:**
  - `ezdraftSignature`: `apiKey`, header `EZDraft-Signature`;
  - `ezdraftTenant`: `apiKey`, header `EZDraft-Tenant`;
  - `inboundKey`: `http`, `bearer`.
  - Each operation sets `security` per the Step 3 table. Browser pages use `security: []`.
- **`components.schemas.Error`:** `{ error: { code: string, … } }`.
  - `required: ["error"]`; inside, `required: ["code"]` with `additionalProperties: true`.
  - This is compatible with EZD-000's `{ error: { code, message_key } }` for EZ Draft routes, and lets EZ Binder add a `message`.
  - Every 4xx response references it.
- **`info.description`** is the prose contract for EZ Binder's developers. Required paragraphs (checked by T5):
  1. **Purpose.** "Neither app writes to the other's database" (07; 02).
  2. **Connect** (R32):
     - EZ Binder shows the tenant's webhook address, signing secret and inbound key, and the owner enters them in EZ Draft Settings → Company → Connect.
     - EZ Draft then sends `connection.check` to the webhook address. A `200` makes the connection active. EZ Binder binds the `ezdraft_tenant_id` from that delivery **only after its signature verifies** (paragraph 3) **and only if the `EZDraft-Tenant` header equals the body's `ezdraft_tenant_id`**; otherwise it answers `401 invalid_signature` and binds nothing (Q-0079 (a), change 1).
     - Disconnect deletes the values in EZ Draft (the inbound key's hash included); EZ Binder revokes them on its side (R32).
     - The signing secret and the inbound key are each **32 bytes from a cryptographically secure random generator, encoded base64url without padding: 43 characters**. EZ Draft's Connect (EZD-114) refuses a shorter value (Q-0079 (a), change 2; 11 Security; R32).
  3. **Requests EZ Draft sends** (every API call and webhook):
     - headers `EZDraft-Tenant: <ezdraft tenant uuid>` and `EZDraft-Signature: t=<unix seconds>,v1=<lowercase hex HMAC-SHA256>`;
     - the HMAC is computed with the tenant's signing secret over the string `<t>.<tenant>.<METHOD>.<path and query as sent>.<raw body>`, where `<tenant>` is the `EZDraft-Tenant` uuid exactly as in the header, `<METHOD>` is upper case, the path and query are those of the request URL exactly as sent, and the body is the raw bytes (empty for GET) (Q-0079 (a), change 1; 07 Delivery rules "HMAC-signed body");
     - EZ Binder finds the secret from `EZDraft-Tenant`, or from the webhook address for `connection.check`, and compares signatures in constant time;
     - EZ Binder refuses a bad signature or a timestamp more than **300 seconds** from its clock (Q-0079 (a)) with `401 invalid_signature`, and an unknown tenant with `401 unknown_tenant`.
     - One signing rule for webhooks and API calls, so R32's three values are enough and no fourth value is entered at Connect (Q-0079 (a)).
  4. **Requests EZ Binder sends:** `Authorization: Bearer <inbound key>` (EZD-1303 "sent as a bearer header"). EZ Draft finds the tenant by the key's hash and refuses anything else with `401 unauthorized`.
  5. **Webhooks** (07 Delivery rules):
     - header `EZDraft-Event` equals the body's `event`;
     - `Idempotency-Key` equals the body's `id`, and is the same on every retry;
     - any 2xx is delivered; anything else, or no answer, is retried with backoff (count and backoff are company Defaults, EZD-1301 and EZD-116);
     - a repeated `Idempotency-Key` gets the first answer again and is not processed twice;
     - deliveries may arrive out of order, so the receiver orders by `occurred_at`;
     - file URLs are short-lived signed links (03 rule 11), so the receiver downloads them on receipt.
  6. **Sign-on into EZ Draft** (R15): call `createEzDraftSignOnCode`, then send the browser to the returned `url` within 60 seconds. The code works once. EZ Draft swaps it on its server for a session and redirects to the target. A used, expired or unknown code goes to EZ Draft's `/sign-in`.
  7. **Sign-on into EZ Binder** (Back to EZ Binder; Level-1 answer 1): the mirror of paragraph 6, through `createEzBinderSignOnCode` and `openEzBinderSignOn`.
  8. **Paging:** `limit` 1–50 (default 50), opaque `cursor`, `next_cursor` null on the last page (11 rule 9).
  9. **Errors:** the `Error` body; the codes listed per operation.
  10. **Local testing:** the stub in `app/test-harness/ezbinder/` and the env value `EZBINDER_API_URL`.
  11. **Several EZ Draft projects per job** (Q-0078 (a); Josh's answers item 13): the paragraph says "one job can have several EZ Draft projects", that EZ Binder stores each `project_id` it receives and opens a project by it, and that a request with only a job id opens the Projects page showing that job's projects.

### Step 6: Test-harness contract helpers (`app/test-harness/ezbinder/`; test-author)
- **`contract.ts`:**
  - `CONTRACT_PATH`, the absolute path of `contracts/ezbinder-openapi.yaml`, resolved from `import.meta.url`.
  - `loadContract()`: `SwaggerParser.validate` (OpenAPI 3.1 check plus `$ref` dereference), cached per process.
  - `operation(id)` and `webhook(name)` return method, path, servers, security and schemas.
  - `validator(target, part, status?)` compiles the schema with Ajv 2020 (`ajv/dist/2020`, `allErrors: true`, strict mode) and `ajv-formats`, and returns `(value) => { ok, errors }`. `target` is an operationId or webhook name; `part` is `'request' | 'response' | 'query'`.
  - `class ContractViolationError` carries the operationId and the Ajv errors.
- **`signing.ts`:**
  - `signingString({ t, tenantId, method, pathWithQuery, body })` returns `` `${t}.${tenantId}.${METHOD}.${pathWithQuery}.${body}` `` (Q-0079 (a), change 1);
  - `sign(secret, parts)` returns `t=<t>,v1=<hex>`;
  - `verify(secret, header, parts, nowSeconds, toleranceSeconds)` returns `{ ok, code }`;
  - `signedFetch(url, { method, body, tenantId, secret, now })` sends a request signed the way EZ Draft will (tests and later tickets use it to call the stub as EZ Draft would).
  - Node `crypto` only. The compare is constant-time (`timingSafeEqual`).
- **`seed.ts`** exports the Step 7 data and the test constants:
  - `STUB_COMPANY_ID` = `ezb-co-001`;
  - `STUB_SIGNING_SECRET` = `ezd019-test-signing-secret-0000000000000000`;

  - Both are 43 characters from the base64url alphabet, the length of the real values (Q-0079 (a), change 2). They are test-only strings, not random and not secrets, so CLAUDE.md rule 12 does not apply.
- **`examples.ts`:** one valid example per webhook (13 `data` objects and envelopes) and per EZ Draft operation (#8, #9, #11, #12 requests and responses). EZD-1302 uses them as its "fixture payload" (phase-13 row). Values are invented test data on reserved domains (`example.com`, `example.test`).

- **Size.** One builder file of roughly 1,000 lines of YAML, and a test-author stub plus about 21 tests. If the test-author's half does not fit one session, the natural split is EZD-019a (contract file, env reader, docs; T1–T5, T18, T20) and EZD-019b (stub and contract tests; T6–T17, T19).
- **Two agents, one table.** The builder writes the YAML and the test-author writes the stub, independently from Steps 3–5. T3 and T6 catch any drift, but a gap in this plan's tables would show up as a review loop. The plan is the single source until the file exists; after merge the file is.
- **Payload shapes are planner's choices** wherever 07 is loose: the nested shapes of `selection.approved`, `revision.created` and `change_order.sent`, and the Round 24 additions, whose payloads 07 does not give. EZD-1302 must emit exactly these. Any change is a contract change: bump `info.version` and re-copy to the vault (Q-0012).
- **Phase order of sign-on.** EZD-114 (Phase 1) has the Done when "a user opens EZ Draft already signed in". That needs the inbound sign-on call and bearer auth, which the phase-13 rows EZD-1303 and EZD-1305 implement. For the orchestrator at Level 2: either EZD-114 builds a minimal #9 and #10 and Phase 13 extends them, or EZD-114's test waits. The contract does not change either way.
- **EZ Binder's real side** is separate work (P6; needs-from-josh). Until it exists, every field check against EZ Binder waits, and production `EZBINDER_API_URL` stays unset, so `getEzBinderApiUrl()` returns `ezbinder_not_configured` and EZD-114 shows EZ Binder as not connectable.
- **Package specifics** to confirm against the installed versions, not from memory:
  - OpenAPI 3.1 support in `@apidevtools/swagger-parser`'s `validate`;
  - Ajv strict mode with OpenAPI-only keywords, which Step 1 bans for this reason;
  - `ajv-formats` `email` accepting `example.com` addresses.
- **Port 3100** must be free on the build PC during `test:e2e`. Global setup fails loudly if another process holds it.
- **Notes for later tickets (security-reviewer, with the Q-0079 answer; sources 11 Security and audit, 07 Delivery rules, R32, R15, 03 rule 11, R26 R14).** The contract does not change for these; the owning tickets' planners and reviewers apply them:
  - **EZD-114 (Connect):** the inbound key is a tenant-wide impersonation credential: whoever holds it can ask #9 for a sign-on code for any user of the tenant. EZ Draft stores only its hash, refuses values shorter than 43 characters (Step 1 paragraph 2), and Disconnect deletes the hash (R32).
  - **EZD-119 (job picker) and every caller of #1, #2, #6:** `as_user` / `user_email` comes from the server session's own email, never from a browser parameter, so a user cannot read another user's EZ Binder jobs through EZ Draft.
  - **EZD-1305 (inbound sign-on):** every sign-on call (#9 issue and #10 swap, success or refusal) writes an `event_log` row (11 Security and audit). EZ Draft's codes are 256-bit (43 characters), stored hashed, single use, 60 seconds (R15; Step 4). `/auth/ezbinder` answers with `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, and its `303` goes to a URL without the code.
- **Clock skew.** The signature tolerance (300 s, Q-0079 (a)) must cover real clock differences between Vercel and EZ Binder's host. If it is too tight, deliveries fail and retry.
- **A job with several projects** (Q-0078 (a), answered). Notes for later tickets; the contract does not build them:
  - EZD-1304 creates a new project on every #8 call, so a retry by EZ Binder would create a second project; whether to dedupe retries is a *how* question for EZD-1304's planner;
  - EZD-1305 needs the Projects page to show one job's projects when only `ezbinder_job_id` is passed (S01 owns how it looks);
  - EZD-1306 implements Q-0080's version and render rule (Josh's answers item 14).
