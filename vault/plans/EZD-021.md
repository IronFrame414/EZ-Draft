### Step 2: Live-network guard (test-author; harness)
One core module and four entry points. Allowed hosts: `localhost`, `127.0.0.1`, `::1` / `[::1]` (the local Supabase, the Next server, the mail catcher, EZD-019's stub server). Everything else is blocked.
- `app/test-harness/net-guard/net-guard.mjs` (plain ESM, Node built-ins only, so Node can preload it): `installNetGuard({ onBlocked })` wraps `globalThis.fetch` and `http.request`, `http.get`, `https.request`, `https.get`. A blocked call records `{ via: 'fetch' | 'http' | 'https', method, host, at }` (never the path's query, headers or body), calls `onBlocked`, and fails at once (`fetch` rejects, `request` throws) with `NetGuardError` (`code = 'live_network_blocked_in_tests'`). Idempotent (a second install is a no-op); the wrapped `fetch` carries a marker symbol so tests can check it. `isLoopback(url)` exported.
- **Vitest** `app/test-harness/net-guard/vitest.setup.ts`, added to `app/vitest.config.ts` `setupFiles`: installs the guard; `afterEach` throws `Live network blocked in tests: <hosts>` when any attempt was recorded during that test, so a test that swallows the error still fails (ticket "fails the suite").
- **Node preload** `app/test-harness/net-guard/preload.mjs`: installs the guard; appends one JSON line per attempt to `EZD_NET_GUARD_LOG` when set; on process `exit` with any attempt, writes the hosts to stderr (`process.stderr.write`, not `console`) and sets `process.exitCode = 1`. Used by:
  - the root `node:test` run: root `test` script becomes `node --import ./app/test-harness/net-guard/preload.mjs --test --test-concurrency=2 "scripts/**/*.test.mjs"` then EZD-000's fan-out (builder; the strings EZD-001 T10 checks stay). T13 proves the test runner's child processes get the guard; if they do not, the test-author raises a question.
  - the app server under Playwright (next bullet).
- **Playwright** (extend EZD-016a's files):
  - `app/playwright.config.ts` `webServer.env` adds `AI_MODE=stub`, `AI_STUB_DIR=<app>/.e2e/ai-stub`, `EZD_NET_GUARD_LOG=<app>/.e2e/net-guard.log`, `NODE_OPTIONS=--import <file URL of preload.mjs>` (a file URL, because Windows absolute paths need one for `--import`), `NEXT_TELEMETRY_DISABLED=1` and `npm_config_update_notifier=false` (*planner's choice*: Next.js telemetry and pnpm's update check would otherwise trip the guard in the server process). ### Step 3: Stub providers and recorded responses (test-author; harness) `app/src/server/ai/test-harness/`
The stub works at the HTTP layer: in stub mode the **real** adapter runs with an injected recorded `fetch`, so the adapters' request building and response parsing are what the tests exercise (*planner's choice*).
- `recorded-fetch.ts`: `createRecordedFetch(recording, { sleep? })` returns a `fetch`-compatible function plus `requests()`. A recording:
```ts
type RecordedExchange = {
  match: { method: 'GET' | 'POST'; url: string };     // exact URL, or a prefix ending in '*'
  response: { status: number; headers?: Record<string, string>; json?: unknown; base64?: string; delayMs?: number };
};
type Recording = { provider: AiProvider; purpose: string; source: 'synthetic' | `live ${string}`; exchanges: RecordedExchange[] };
```
  Exchanges are served in order; a request that does not match the next exchange, or one past the last, throws `StubMismatchError` (mapped to `ai_stub_mismatch`). `delayMs` waits and honours the request's `AbortSignal` (for the timeout test). `requests()` returns `{ method, url, headers (lower-case names), bodyText | formData }` for assertions. It never touches the network.

## Risks
- **Recordings are synthetic.** No key exists (Q-0003), so every recording is written from the providers' API references, not captured. An adapter can pass every test and still misread a real answer. The first live calls are EZD-031's live render trial after Phase 10 (image providers; Q-0082) and EZD-606's field check (Claude). EZD-031's planner may add a way to save live exchanges as recordings (with keys and personal data removed) and replace the synthetic ones.
- **Provider facts are the planner's knowledge** (endpoints, headers, field names, BFL statuses and delivery host, Gemini `responseModalities`, the OpenAI form field names for the GPT Image family, the Anthropic SDK's `fetch`/`maxRetries`/request-id options). The builder confirms each on the build date; differences that change a test's expected value become questions.
- **Model ids.** `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5` come from the orchestrator's dispatch, not a vault source; which alias each purpose uses (and so its cost; 11 Running cost "AI text ~$10") is each purpose ticket's choice. Image model ids are passed by the caller; EZD-031 and EZD-1103 pick them (R24 #49; S15f examples are not decisions).
- **Cost of reruns and retries.** A rerun of an AI handler pays again in live mode; retries follow Q-0059 (a)'s default for `ai_read` (up to 5 tries). Only retryable codes are retried (Step 1; Step 5).
- **EZD-031 needs a cost record** ("saves the image and its cost"; Q-0016 "records the cost per render"). This ticket returns provider usage only; how EZD-031 turns it into dollars (published prices on the run date, or the providers' billing pages) is for EZD-031's planner.
- **EZD-031 runs outside the job queue** (a spike script run by hand). The provider adapters take plain `{ apiKey, fetch, signal, sleep, timeLeft }` and import nothing from Next.js, so the spike can call them with its own context; the "AI only inside jobs" check covers `app/src` only.
- **EZD-1103 overlap.** EZD-1103's row says it ships "the stub adapter and one real adapter for Google's Gemini". After this ticket it builds the render adapter interface, registry and model ids on top of these calls; its planner must read this plan.
- **Guard side effects.** Blocking every non-loopback host can catch harmless calls (Next.js telemetry, pnpm update check: both turned off in Step 2). WebSockets are not wrapped; providers are reached over HTTPS only. Specs that import `@playwright/test` directly skip the per-test fixture; the global teardown is the backstop. If `node --test` does not pass `--import` to its child processes on Node 22, T13 (c) fails and the test-author raises a question.
- **EZD-009 T19 wording.** If EZD-009's test hard-codes the handler keys as exactly `['test']`, adding `ai_read` breaks it; the test-author updates that expectation to `['ai_read', 'test']` in the same test commit (a test-author change, not a builder change), as EZD-009's plan describes the check as "each key appears in a call".
- **Result size.** `ai_read` results must fit EZD-009's 16,384-byte check; long outputs (translations of many phrases) must go to Storage (EZD-132) in their own tickets.
- **Ticket size.** About 15 modules, 4 adapters, a harness with four entry points and 20 tests: comparable to EZD-009. If it overruns, the split line is (a) guard, stub framework, Claude adapter, `ai_read` job (T1–T6, T10–T19) and (b) the three image adapters (T7–T9), which only EZD-031 needs in Phase 0. This plan does not propose that split.
- **Provider accounts are deferred (Q-0076).** A configurable base URL covers an account that serves the same API at another address. If Josh's tests pick an account with a different request format or sign-in (Google Cloud Vertex AI for Gemini, or a reseller such as fal.ai or Replicate for Flux), the adapter needs a follow-up change in the ticket that adopts it (EZD-1103 owns the render adapters in Phase 11); the provider pick is needed before Phase 11 (Q-0082). Until then the defaults are Q-0076's recommended endpoints.
- **The next release waits on the `AI_MODE` values (Q-0106).** Once this ticket adds `AI_MODE=` to `.env.example`, the release workflow's env check requires a Production `AI_MODE` (`missing`) and a Preview `AI_MODE` of `stub` or `live` (`preview_ai_mode`). Until Josh sets both in Vercel (runbook, Step 6), every merge into `main` stops at `env_mismatch` with the live site unchanged (vault/plans/EZD-023c.md Step 4). The orchestrator puts the runbook step in `needs-from-josh.md` before the phase PR.
- **A live preview spends money (Q-0077).** Previews default to `stub`; switching Preview `AI_MODE` to `live` with Preview keys makes every AI action tried on a preview a paid call. The runbook says so (Step 6).
