Ticket row (phase-01.md):
- Scope: Josh 2026-10-29 (chat): "phase 2 should be ready for the next step. it can start phase 2 while phase 1 finishes". Today the build pool takes product tickets only from the first phase with an open product ticket (`vault/tools/next_ticket.mjs` blockingPhase and buildPool, EZD-253 D6, D9), so on 2026-10-30 the launcher sat idle for over 5 hours with five phase 2 tickets `ready` while phase 1's only open product ticket (EZD-252) waited on a blocked dependency. Change: when the current phase has no product ticket that is `ready` with its dependencies done, the build pool takes the next signed-off phase's ready product tickets, in phase order. The planner raises how the phase gates and phase PRs (develop to main) carry each phase's work when phases overlap.
- Done when: With no buildable product ticket in phase N and a ready product ticket in signed-off phase N+1, the next unit builds the phase N+1 ticket (test). A buildable product ticket in phase N still comes before any in phase N+1 (test). An unsigned phase is never built early (test).

## 10. Open questions
- Q-0460 (was QP-1): When phase N+1 tickets build while phase N is open, how do phase N's gate and its develop→main PR carry that work? (a) recommended: phase N's PR carries everything on develop, lists the early phase N+1 tickets under "Later-phase tickets in this PR" (D7), its phase-auditor skips them and phase N+1's gate audits them with their plan and commit (D8), and Josh tests them at phase N+1's gate; they reach main, and production at that promotion (11 Operations), before phase N+1 is finished; this plan's steps 4-5 build it. (c) phase N's PR is cut from a release branch at the last commit before the first phase N+1 merge, later phase N fixes cherry-picked onto it: fragile when fixes and tooling commits interleave.
