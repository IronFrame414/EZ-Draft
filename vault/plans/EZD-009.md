### Design in one paragraph
A `job` row is the unit of work. A server route enqueues it through one database function, under the user's session (03 rule 1). Enqueue then starts a run in the same Vercel Function after the response is sent (`after()`), and a Vercel Cron request starts a run once a minute (the sweep). A run is a loop: claim one due job with `FOR UPDATE SKIP LOCKED` plus a lease (`run_id`, `lease_expires_at`), validate its payload, call the handler for its `kind`, and record the outcome. The outcome is done, continue (the handler stopped early to fit the time limit and saved a small cursor; the job goes back to `queued`), retry with backoff, or failed. Every write after the claim is conditional on the run's `run_id`, so a run whose lease expired cannot overwrite the run that took over. A trigger on `job` pushes `job.progress` on the project channel (EZD-018). Browsers never poll: they listen, and fetch the job once when it finishes and once after each Realtime resync.

- Why `public` and not `private`: the runner calls these through supabase-js `rpc()`, which reaches only the API schemas (EZD-006 Step 1 keeps `private` unexposed). Execute is revoked from `anon` and `authenticated` and granted to `service_role` only, so only the secret-key client can call the six queue functions.
- **Row lock and lease** (ticket Scope; 11 Operations): `for update skip locked` means two claims at the same moment never get the same row. The lease means a run that dies leaves a row another run can claim once `lease_expires_at` passes. All times come from the database clock (`now()`), never from function clocks.
- **Fencing:** every write after the claim carries `run_id`. A run that outlives its lease gets `false` and stops touching the job (Step 6). This is the queue's half of "handlers are safe to run twice".

### Step 4: Runner semantics (rules the code and docs follow)
- **Attempts.** `attempts` goes up at claim, not at failure, so a run that dies (out of memory, killed at the time limit) still counts and cannot loop for ever. A slice that ends with continue resets `attempts` to 0, so `max_attempts` limits failed runs of one slice, not the number of slices.
- **Retry with backoff** (ticket Scope): a handler error is retried while `attempts < max_attempts`. The wait is `min(baseMs × 2^(attempts − 1), capMs)`. Defaults from **Q-0059 (a)** ("up to 5 tries per job step, waiting 1, 2, 4 and 8 minutes"):
  - `maxAttemptsDefault` = `5`;
  - `baseMs` = `60000` (1 minute), so the waits after tries 1, 2, 3 and 4 are 60,000, 120,000, 240,000 and 480,000 ms (1, 2, 4, 8 minutes); a fifth failure is final (`failed`), with no wait;
  - `capMs` = `480000` (8 minutes, the longest wait Q-0059 (a) names). The `max_attempts` check (1–5, Step 1) means no job gets more than 5 tries, so the cap is never reached in practice; it guards `jobBackoffMs` against a bad input only.
  - A handler may set its own lower `maxAttempts` (for example a paid render call, decided by its own ticket; Q-0059 (a)). Nothing kicks a run at `run_after`; the next sweep or enqueue picks it up, so the real wait rounds up to the next minute (Risks).
- **Errors that never retry:** `invalid_payload` (Zod failure, or a Storage path outside the job's tenant), `invalid_result`, `no_handler` (no handler for the kind in this build), and a handler's `JobError` with `retry: false` (for example EZD-021's missing key). A generic throw is `handler_failed`, retried. A dead run is `lease_expired`.
- **Split to fit the time limit** (ticket Scope; 02 "each job is split so one run fits the function time limit"): the handler gets `ctx.timeLeft()`. When the next unit of work will not fit, it returns `{ continue: <state> }` and the job goes back to `queued` with its cursor; the next run (in the same loop if budget remains, or the next sweep) carries on from `state`. A handler always does at least one unit per slice, so a job cannot loop with no progress. Units must be smaller than the safety margin below.
- **Time values** (`app/src/server/jobs/config.ts`):
  - `JOB_FUNCTION_MAX_SECONDS` = `300`, the function time limit from **Q-0027 (a)** ("Vercel Pro default function limits (300 s, 2 GB)"). The sweep route exports the same number as a literal `maxDuration` (Next.js wants a literal; T9 checks they match). So `JOB_LEASE_SECONDS` = 360 and `JOB_RUN_BUDGET_MS` = 270,000 (formulas below).
  - `JOB_LEASE_SECONDS` = `JOB_FUNCTION_MAX_SECONDS + 60` (*planner's choice*). A run cannot outlive its function, so a live run's lease never expires under it, and a dead run is picked up at most one function lifetime plus 60 s after it started.
  - `JOB_RUN_BUDGET_MS` = `(JOB_FUNCTION_MAX_SECONDS − 30) × 1000` and `JOB_MIN_CLAIM_MS` = `10000` (*planner's choice*): a run stops claiming when less than 10 s of budget is left, and leaves 30 s of the function limit for its last unit and its final write.
  - Memory (2 GB, the other half of Q-0027 (a)) sizes handlers, not the runner; each handler ticket keeps its own unit of work inside it.
- **Handler contract** (recorded in docs): handlers are safe to run twice (ticket Scope; 11 Operations). Output paths are fixed by job id (`<tenant_id>/<project_id or tenant>/<job_id>/out/…` in the `jobs` bucket, EZD-000 Storage layout), so a second run overwrites with the same bytes. Any outside call that costs money or sends something carries an idempotency key made from the job id and the cursor. A handler runs with the secret key, which bypasses RLS, so it filters every query by `ctx.job.tenant_id` (and `project_id`) itself.

### Step 5: Server modules (`app/src/server/jobs/` and `app/src/lib/jobs/`; builder)
- `app/src/lib/jobs/kinds.ts`: `JOB_KINDS` (the eight values of Step 1, in that order) and `JOB_STATUSES`; types `JobKind`, `JobStatus`. Imported by browser and server.
- `app/src/server/jobs/config.ts`: Step 4 constants; `jobBackoffMs(attempts, { baseMs, capMs })`; `defaultRunnerConfig()`.
- `errors.ts`: `JobError(code, { retry })`; the code must match the `error` column check.
- `storage-path.ts`: `storagePathSchema` = Zod `{ bucket: 'sources' | 'renders' | 'exports' | 'media' | 'jobs', path: string }` (buckets from EZD-000 Storage buckets and paths). `path` has no leading `/`, no `..` segment and no `\`. `assertPathsInJob(value, job)` walks any JSON value. Every object shaped like a Storage path must have a `path` starting with `<job.tenant_id>/`, and for a project job, with `<job.tenant_id>/<job.project_id>/` or `<job.tenant_id>/tenant/` (EZD-000 layout). This runs on payloads at enqueue, on payloads before the handler, and on results. It keeps a crafted payload from making a secret-key handler read another tenant's files.
- `registry.ts`: `JobHandler<P, S, R> = { kind, payload: ZodType<P>, state?: ZodType<S>, result: ZodType<R>, maxAttempts?: number, run(ctx): Promise<{ done: R } | { continue: S }> }`. `ctx = { job (row without payload), payload, state, progress(pct), timeLeft(), sleep(ms), signal }`. `handlers.ts` holds one static map `kind → handler`. It includes `testJobHandler` only when `process.env.VERCEL_ENV !== 'production'`, read per call. No other kind has a handler yet; later tickets add theirs.
- `handlers/test-job.ts`: payload `{ steps: int 1–20, stepMs: int 0–10000, failFirst: int 0–10 = 0 }`, state `{ next: int }`, result `{ steps: int }`. Behaviour: if `ctx.job.attempts <= failFirst`, throw `Error('test failure')`. Then for `i` from `state?.next ?? 0` to `steps − 1`: when `i` is past the first unit of this slice and `ctx.timeLeft() < stepMs`, return `{ continue: { next: i } }`; else `await ctx.sleep(stepMs)` and `ctx.progress(Math.round(100 × (i + 1) / steps))`. At the end, return `{ done: { steps } }`. It has no side effects, so it is safe to run twice.
- `db.ts`: `createJobsDbClient()`, a supabase-js client with the **secret key**, the URL from `env.ts`, read per call (EZD-004 Step 5), `persistSession: false`. It is the only file in `app/src` that reads `SUPABASE_SECRET_KEY` (EZD-000 service-key rule: job handlers only; T20).
- `queue.ts`: typed wrappers over the six `rpc()` calls (Step 2), behind an interface `JobQueue`.
- `runner.ts`: `runJobs({ queue, handlers, config, clock, onlyTenantId?, onJobFailed? }): Promise<RunSummary>`. Steps:
  1. `job_fail_expired`, then `onJobFailed(job)` for each row returned.
  2. Loop while `deadline − clock.now() >= config.minClaimMs`: claim with a fresh `run_id` (`crypto.randomUUID()`); stop when nothing is claimed.
  3. Look up the handler (`no_handler`), parse the payload and state (`invalid_payload`), check paths (`invalid_payload`), run.
  4. `ctx.progress` writes only when the whole percent changes. A `false` from any write stops this job (`leaseLost`).
  5. Parse and path-check the result (`invalid_result`), then complete / continue / fail per Step 4.
  6. `onJobFailed(job)` once for each job that reaches `failed`.
  It never throws; each job's error is caught. `RunSummary = { claimed, done, continued, retried, failed, leaseLost }`. `clock` = `{ now(), sleep(ms) }`, real by default and fake in tests.
- `enqueue.ts`: `enqueueJob(db, { kind, projectId, payload, runAfter? }, { kick = kickJobRunner } = {}): Promise<{ id: string }>`. `db` is the caller's **session** client (03 rule 1: RLS stays the backstop). It parses the payload with the kind's schema, checks the 16,384-byte size and the Storage paths' shape (tenant prefix is rechecked by the runner, because the helper does not know the tenant id), calls `rpc('enqueue_job')` with `handler.maxAttempts ?? config.maxAttemptsDefault`, then calls `kick()` once. Permission checks with `can()` belong to the calling route (EZD-102 / EZD-133, Phase 1), not to this helper.
- `kick.ts`: `kickJobRunner()` registers `after(() => runJobs(defaults))` from `next/server`, so the run starts when the response has been sent and never delays it ("started on enqueue"; 11 Also "never block the editor"). Errors are swallowed: no logger exists yet (EZD-000 C8; EZD-004 and EZD-008 precedent), and the sweep retries. EZD-024 adds Sentry here.
- `index.ts`: exports `enqueueJob`, `JobError`, types. Handlers and `db.ts` are not exported to routes other than the two below.

## Risks
- **Plan and limits (Q-0027 (a), Q-0031 (a)).** The project lives in EZ Binder's Vercel team, which is on Pro (Q-0031 (a)), so the `* * * * *` cron is allowed; if that team ever moved to Hobby, crons would be limited to once a day and the deploy could fail. `JOB_FUNCTION_MAX_SECONDS` and `maxDuration` are 300 (Q-0027 (a)); the builder confirms the Pro default on Vercel's limits page on the build date (as Q-0027's question text asked) and raises a question if it differs, without changing T9.
- **Crons run on production only.** Preview deployments (dev database, 11 Operations) get no sweep. There, retries and dead runs are picked up only when another enqueue starts a run. Accepted for a dev environment; recorded in docs.
- **`after()` budget.** The kicked run lives inside the enqueuing request's function. A route that spends more than the 30 s margin before enqueuing, or lowers its own `maxDuration`, shortens the run. The lease then expires and the job is retried, which costs one attempt. Docs rule: enqueuing routes keep the default `maxDuration`.
- **Retry granularity.** Nothing starts a run at `run_after`, so every backoff rounds up to the next sweep (up to 1 minute). With Q-0059 (a)'s waits (1 + 2 + 4 + 8 = 15 minutes) a job that always fails reaches `failed`, and EZD-024's owner email, about 15 to 20 minutes after its first try.
- **Direct REST calls to `enqueue_job`: closed by EZD-006's gate (Q-0087 answered (ii), security-reviewer).** EZD-006 adds a PostgREST pre-request gate, `private.api_request_gate()` registered as `pgrst.db_pre_request`: every `anon` / `authenticated` PostgREST request without the server-only secret header is refused, fail-closed (allow-list: anon `rpc/health`). A member's browser token therefore cannot call `enqueue_job` or read `job` rows over REST; only server routes can, through EZD-007's `createSessionClient()`, which sends the header, after the route's own `can()` check (EZD-102 / EZD-133). `enqueue_job` keeps its tenant and project-scope checks (Step 2) and RLS keeps the select policy (Step 1) as the independent backstop (03 rules 1–2; EZD-000 "session client, RLS backstop"). The secret-key runner (`service_role`) is not affected by the gate. T10–T12 test that backstop through EZD-006's `signIn()` clients; if EZD-006's revised fixtures do not carry the gate header, the test-author raises a question rather than changing the expected codes. Per-kind permission checks and limits still belong to the tickets that add each kind.
- **Job rows readable by project members.** Any member who can see the project can select its jobs, including `payload` and `result` over REST. Hence the "no money, no secrets in job rows" rule. Handlers with money (catalog extraction with costs, EZD-16xx; render cost, EZD-11xx) must store it elsewhere. Security-reviewer checks those tickets.
- **Rows accumulate.** No source sets how long finished jobs are kept. The `cleanup` kind exists; a later ticket (EZD-123 or the System status page) should decide. Not needed for this ticket.
- **System-wide jobs.** `tenant_id` is required, so EZD-025's cross-tenant backup copy cannot be a `job` row. Its planner either runs it from its own cron route or adds a design. Noted for EZD-025.
- **Local GPU worker (Q-0020).** The claim functions are `service_role` only. A worker with its own revocable key (03 `render_worker`) needs its own claim path, which Phase 11 adds: Q-0020 ("Build it": R18 stands) keeps the local worker protocol.
- **Realtime ordering.** T1 and T13 expect events in commit order. Broadcasts sent from the database are expected to arrive in order, but this is not stated by any vault source. If the pinned Realtime reorders, the test-author raises a question rather than loosening the test.
- **Test interference.** Parallel test files share one local queue. `onlyTenantId` and keeping the unfiltered sweep tests in one file prevent cross-claims. Later job tickets (EZD-021) must use `onlyTenantId` in their tests (docs and harness README).
- **`longtask` in T1.** A tiny page receiving 6 WebSocket messages should produce none, but a slow CI machine could. If it flakes, the test-author raises a question, not a retry.
- **Ticket size.** Three migrations, about 12 small server modules, three routes, a dev page and about 20 tests. This is comparable to EZD-018 and fits one session. If it overruns, the natural split is database plus runner (T2–T15, T19–T21) versus routes, browser helper and dev page (T1, T16–T18). This plan does not propose that split.
