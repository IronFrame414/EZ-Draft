# EZD-129 · User project scope (split proposal)

- **ACs:** AC-EZD-129-1 … AC-EZD-129-4 (`vault/spec/acceptance-criteria.md:1124-1127`, stage-0), shared out to the parts below. Each AC is split by clause (AC map).
- **Complexity:** high (part a), medium (part b); reasons per part
- **Areas:** security, migrations, data-model, api, ui, testing
- **User-visible result:** In Settings → Users + permissions, Josh sets each person's Project access to All projects or Listed projects and picks the projects. He can do the same in the Invite user dialog. In the New project wizard he picks a Foreman, who is then listed on the new project. A person limited to listed projects sees only those projects on Projects, and the app returns nothing for any other project.
- Phase: 7 · Planned by: planner · Date: 2026-11-11 · Status: split proposal

**Why cut here.**
- **Part a** is every write, read and check on the server, testable at the database and route level with no screen. It carries the security risk: definer writes that grant project access, session ending on narrowing, a redefinition of the one project write path that main still calls. It gets its own security review.
- **Part b** is the screens over part a's finished routes. It decides nothing on the server.
- **Held by different things.** Part b is held by Q-0696 (escalated to Josh: no board for "the Project access control with its project picker" or "the Foreman picker in the New project wizard") and by EZD-105d and EZD-106b, which build the dialog and the inspector it extends. Part a is held by neither.

### Part EZD-129a · Project scope on the server: writes, reads, Foreman listing and routes
- **Scope:**
  - **Migration 1 (scope functions), each `security definer`, `set search_path = ''`, `private.require_api_gate()` first, tenant from the claims, `settings_users` checked inside for the claim membership (Q-0695 row 59: "every write on Settings → Users (… scope …) needs `settings_users`"):**
    - `save_member_scope(p_membership_id uuid, p_scope text, p_add uuid[], p_remove uuid[])`:
      - works on an `invited`, `active` or `deactivated` membership of the caller's company, since the Invite dialog writes the list of a new invite (S15 Decision 13; AC-EZD-129-2);
      - takes the target membership row `for update` first, so two saves of one member run one after the other;
      - `listed` inserts `p_add` (each a project of the claim tenant, not archived, not the benchmark project; else 22023 `project_unavailable`) and deletes `p_remove`;
      - `all` deletes every listed row and refuses a non-empty `p_add`, because `membership_project` holds "the listed projects of a scoped membership" (`20261019165205_create_membership_project.sql:1`; 03c membership row);
      - a listed list of zero projects is allowed (Q-0695 row 63; 09n Project scope row 2);
      - removals are deletes and the scope change is an update, so the existing triggers end sessions (Q-0695 row 64; 20261026112732). Inserts end none (09n Project scope row 4);
      - writes one event_log row `user.scope_changed` with the old and new scope and the added and removed ids, only when something changed, in the same transaction (03-data-model Q-0695 row 33: "Permission, role, membership, scope and invite changes write their row in the same transaction as the change"), through whichever ticket's write function Q-0720 names.
    - `member_scope(p_membership_id uuid) returns jsonb`: the member's scope and listed projects (`id`, `name`), sorted by name.
    - `list_scope_projects(p_search text)`: the company's projects that are not archived and not the benchmark (the `list_projects` filter, `20261106140001_*`), matched on name or address, sorted by name, first 50 and a `more` flag.
      - It lists every project of the company, not only the caller's own. Q-0695 row 59 lets a `settings_users` holder change any member's scope, their own included, so a holder can always make themselves All; hiding projects from a Listed holder protects nothing. The security-reviewer confirms this at part a.
  - **Migration 2 (Foreman):**
    - `create_project` and `create_project_with_objects` are recreated with a trailing `p_foreman_membership_id uuid default null`. When it is set, the member must be `active` in the claim tenant (else 22023 `foreman_unavailable`). When that member's scope is `listed`, one `membership_project` row is added in the same transaction, `on conflict do nothing` when the Foreman is the creator (Q-0202: "picking someone as a project's Foreman lists them on it automatically"; Q-0397; AC-EZD-129-3). That listing writes its `user.scope_changed` event_log row (03-data-model Q-0695 row 33).
    - The Foreman is not stored on the project: 03c has no such column. R31 (`13-decisions-and-remaining-items.md:161`) uses the wizard's Foreman only for the field-measure link, which is EZD-1422's.
    - The old argument lists still resolve through the default, so main's calls keep working (Q-0264 live site), and D1 in `app/src/server/projects/create-project.db.test.ts` passes unchanged.
    - `list_foreman_candidates()`: the active members of the claim tenant (membership id, name, email), sorted by name then email. It is checked with `create_projects` inside, since the wizard is gated by Create projects (S01 Permissions). Other members' names and emails are already readable by any member (`app_user_select`, `20261019170006_*:16-21`), so nothing is widened.
  - **Server:**
    - `app/src/lib/users/scope.ts`: types and bounds.
    - `app/src/server/users/scope.ts`: parse, rpc, error mapping with the body of architecture "Errors and logging".
    - `app/src/server/projects/projects.ts`: `parseNewProject` takes `foremanId: string | null` (optional, so today's bodies still parse), and `createProject` maps `foreman_unavailable`.
  - **Routes** (the cut line part b is planned against):
    - `GET /api/settings/users/[id]/scope` → 200 `{ scope: 'all' | 'listed', projects: { id: string; name: string }[] }`;
    - `PUT /api/settings/users/[id]/scope`, body `{ scope, add: string[], remove: string[] }` → 200 the same shape as GET; 400 `invalid_input` / `project_unavailable`; 404 `member_not_found`;
    - `GET /api/settings/users/projects?q=` → 200 `{ items: { id: string; name: string; address: string }[], more: boolean }`;
    - each of the three `requireApiPermission('settings_users')` (`app/src/server/permissions/can.ts:52`; Q-0695 row 59);
    - `GET /api/projects/foremen` → 200 `{ members: { membershipId: string; name: string | null; email: string }[] }`, `requireApiPermission('create_projects')`;
    - `POST /api/projects` accepts `foremanId` → 400 `foreman_unavailable`;
    - every route: 401 `not_signed_in`, 403 `permission_denied`, 500 `db_unavailable`, `Cache-Control: no-store`.
    - `[id]` is the membership id carried by EZD-104's `UserRow.membershipId` (EZD-104 plan section 3), as in EZD-106a's routes.
  - **Events:** `user.scope_changed` as `log_only` in `app/src/lib/events/registry.ts`, emitted after the commit (architecture "Events": "screen events not named in 07 are added as `log_only`"; the EZD-106a pattern).
  - **Inventories:**
    - `GATED_RPC_CALLS`: the four new functions; the two recreated ones keep their entries;
    - `MONEY_ROUTE_CASES` and the same-origin walk for the new routes;
    - `database.types.ts`;
    - `docs/architecture.md` section "Project scope (EZD-129)", and the "New project wizard (EZD-118)" Function bullet updated for the Foreman parameter.
