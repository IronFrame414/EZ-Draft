# EZD-5604 · Assistant change format and preview (split proposal)

- **ACs:** AC-EZD-5604-1 … AC-EZD-5604-10 (`vault/spec/acceptance-criteria.md:1853-1862`, stage-0), shared out to the parts below (AC-1, AC-8 and AC-9 split by clause; AC map)
- **Complexity:** high (both parts; reasons per part)
- **Areas:** ui, testing, security, data-model
- **User-visible result:** After Josh asks the Assistant for a change, the plan shows it as a preview: blue for what is added, red dashed for what is removed, with the legend and the new object's number. Nothing is saved until he accepts (EZD-5605). A reply that does not fit the drawing changes nothing and says so plainly. If the drawing changes under the preview, the preview goes stale and gives his prompt back.
- Phase: 56 · Planned by: planner · Date: 2026-11-09 · Status: split proposal

## Split proposal

**Why.** Planned whole, the ticket would touch about 22 files and need about 35 tests. That is over the size rule (PROCESS.md section 6 "Ticket size": about 20 files or 25 tests; Josh 2026-10-22). Where the count comes from:
- **10 stage-0 ACs, four of them compound.** AC-8 has four clauses and AC-9 has four.
- **A change format with three operations on three object kinds.** These are add, update and remove of walls, doors and windows (Q-0637 change format row). It has:
  - sent refs and temporary refs (Q-0638 gap 15; Q-0638 gap 9 "refs are good for one request only");
  - the floor rule (Q-0641 row 56-5);
  - status that cannot be written (Q-0638 gap 15);
  - the typed-or-auto rough opening rules (Q-0641 row 56-6; Q-0642 row 4; Q-0640 row 56-3);
  - the 100 limit on the full save set, room changes and host updates included (Q-0640 row 56-1);
  - every hand-drawing check (AC-2; 09k).
- **A new canvas layer and panel state.** The preview needs:
  - blue additions and red dashed removals, with an update's old shape red dashed and its new shape blue (Q-0474; Q-0638 gap 15);
  - the legend pill and the provisional number chip (board S03c; Q-0640 row 56-6);
  - Accept, Adjust and Reject shown only with a preview (Q-0638 gap 13);
  - × acting as Reject;
  - the prompt box disabled while a preview is open (Q-0637 "one open preview at a time");
  - stale handling for changes by this user or another (Q-0637; Q-0640 row 56-9).
- **Unbuilt dependencies.** None of the dependencies is built. EZD-204, EZD-208, EZD-211, EZD-213 and EZD-5603 are split proposals, and EZD-5603's panel parts have no interface contract yet (`vault/tickets/STATUS.md`, read 2026-11-09; `vault/plans/EZD-5603.md` has no section 3). The preview's panel controls cannot match a contract that does not exist yet. The change format and its checks can: they need only P5602 section 3, P204 section 3, P211 section 3, P217 section 3 and merged code.

**Why cut here.**
- Part a is pure TypeScript plus EZD-5602's reply parser and recordings, with unit tests only. Part b is the screen. This is the same cut as EZD-213 (a: edits and view rules; b: the screen) and EZD-212.
- **Seam.** Part a returns one result type, `AssistantPreview` (glossary 00f "AI preview": "EZD-5604 plan names it"). It is either a full save set with its drawing roles, or a refusal reason. Part b only draws and holds it. So the checks Accept relies on live in one place, and EZD-5605 reuses them at Accept (Q-0640 row 56-1: "when the reply is checked and again at Accept"; CLAUDE.md rule 18: no second copy).
- Built a → b. EZD-5605 depends on the base number, so it waits for both parts (`vault/tickets/README.md`, "How tickets are written").

Each part is planned as its own unit from its section here. Each part plan applies the planner lessons for its areas, notably:
- L-043: every function it calls, with its file path found by grep;
- L-048: staleness as one invariant over every mutation;
- L-050: a Tests row for every check;
- L-052: the empty, over-limit and malformed cases;
- L-054: checklist rows measured from the board HTML;
- L-060: Accept, Adjust and Reject in `expectTouchTargets`;
- L-021: grep the tests that pin the edited lists, and name each edit.

### Part EZD-5604a · Assistant change format, apply and check
- **Scope:**
  - **change schema.** `app/src/lib/assistant/changes.ts` is new. That folder is shared by browser and server (P5602 D-Docs, Folder layout line). It exports `assistantChangeSchema` and the type `AssistantChange`. The schema is a strict zod union keyed by `op` (`add`, `update`, `remove`) and `type` (`wall`, `door`, `window`):
    - **Fields.** They are taken from the sent shapes (P5602 D-Projection `SentWall`, `SentOpening`). They exclude `status`, `number`, `floor` on an update, ids, and the typed-or-auto flag (Q-0638 gap 15; Q-0640 row 56-3; P5602 D-Reply already refuses `roughOpeningMode` at any depth).
    - **Temporary refs.** An add carries a temporary `ref` that later changes in the same reply may name (Q-0638 gap 15).
    - **Updates.** An update names only the fields it changes (Q-0642 row 4).
    - **Remove.** A remove carries only `ref` and `type`.
    - **Limits.** Every length is a finite number of inches. The part plan gives each field's bound, from `MAX_WALL_LENGTH_IN` (`packages/geometry/src/length.ts:10`), `wallDataSchema` (`G/schema/wall.ts`) and `openingDataSchema` (P204 section 3).
  - **server parse.** In `app/src/server/assistant/assistant.ts` (P5602 step 11):
    - `AssistantReply.changes` and `AssistantSuccess.changes` become `AssistantChange[]` (P5602 section 3: "EZD-5604 … replaces the `changes: unknown[]` element type").
    - `parseAssistantReply` checks each change with `assistantChangeSchema`, so a wrong shape gives `null` and the billed 502 `assistant_invalid_reply` (P5602 D-Map).
    - `ASSISTANT_SYSTEM_PROMPT` gains the change fields (P5602 D-System: "EZD-5604 adds the change fields to it").
    - The reply goes to the provider with no tools (AC-6; P5602 D-Request). Part a adds a test that the stub request body has no `tools` key.
  - **recordings.** Rewrite the `add_door`, `move_wall` and `delete_window` change arrays in `ASSISTANT_RECORDINGS` (`app/src/server/ai/test-harness/recordings/anthropic.ts`). Each must become a valid reply on P5602 T3's `v4.json` projection (P5602 D-Stubs: "EZD-5604 owns the change format and rewrites those three arrays in this file"). Name every P5602 test that pins those arrays as a test-author edit (L-021).
  - **apply and check.** `app/src/editor/assistant/apply-reply.ts` is new and runs in the browser. It exports `applyAssistantReply(input: { objects: Objects; floorId: string; changes: readonly AssistantChange[]; refs: Readonly<Record<string, string>>; highs: NumberHighs; newId: () => string }): AssistantPreview`. It applies the changes, in order, to a scratch copy of the drained model (Q-0637 change format row; Q-0638 gap 9). Any one failure refuses the whole reply, with no partial result (Q-0637 "one bad change rejects the whole reply"):
    - a ref that is not in `refs` and not a temporary ref added earlier in the same reply;
    - a change or host wall off the sent floor (Q-0641 row 56-5);
    - a wall that fails `createWallData` / `wallLengthProblem` (`G/walls/wall.ts:30,38`);
    - an opening that fails `placeAtOffset` (`invalid_input`, `past_corner`, `overlap`; P204 section 3) or `withOpeningSize` (P211 section 3);
    - any result that fails the stored schema (`wallDataSchema`, `openingDataSchema`);
    - a full save set over `MAX_CHANGES_PER_SAVE` (100; `app/src/lib/outbox/outbox.ts:115`; AC-10).
  - **change rules.** The checks above use the same functions as hand drawing (AC-2). Where a hand-drawing check sits only inside a reducer, the part plan moves it into an exported function that both callers use, with no second copy (rule 18). The rules for each kind of change:
    - **Wall changes.** They go through `wallEditChanges(objects, level, walls, newId, highs)` (`app/src/editor/tools/model-changes.ts:72`), so rooms reconcile and P204 appends the host updates.
    - **Update thickness.** An update of `thickness` uses EZD-213a's thickness edit (P213 part a: the stud layer absorbs the difference; 09k Thickness), not its own copy.
    - **Opening changes.** They use `openingChange` (P217 E2) and `withOpeningSize` (AC-EZD-211-13; P211 section 3).
    - **remove.** It uses `deleteChanges` (P217 E1), so it acts as the Delete key (Q-0638 gap 15).
    - **New objects.** They are Existing (AC-EZD-204-14; Q-0638 gap 15).
    - **Rough opening.** A rough opening the reply sets counts as typed. If an add omits it, it is auto. A named value equal to the sent value counts as not named, so an auto rough opening keeps following the size (Q-0641 row 56-6; Q-0642 row 4).
  - **result.** `type AssistantPreview = { ok: true; changes: Change[]; added: string[]; removed: string[]; updated: string[]; touched: string[]; provisional: Record<string, number> } | { ok: false; reason: AssistantRefusal }`. The fields:
    - `changes` is the full save set, which EZD-5605 commits as one `applyEdit`.
    - `touched` is every id the save set writes, plus the host walls of its openings. Part b's staleness reads it (Q-0637 "stale when any touched object changes").
    - `provisional` gives each new object highest + 1 by type, from `numberNewObjects` (EZD-294, as `wallEditChanges` does; Q-0640 row 56-6). The real number is given at Accept (AC-EZD-294-3).
    - `AssistantRefusal` is a closed string union that part b maps to one plain message.
- **Tests (about 20) and files (about 11):**
  - Schema unit tests:
    - each op × type accepted;
    - an unknown key, `status`, `number`, `roughOpeningMode` and a non-finite length refused;
    - 0 and 100 changes accepted, and 101 refused.
  - `parseAssistantReply` (P5602 T9) edits for the new element type.
  - The rewritten recordings parse, and their apply succeeds on `v4.json`.
  - A no-tools request test.
  - Apply tests on `v4.json` and the geometry fixtures (`packages/geometry/src/walls/test-utils/fixtures.ts`):
    - each 09k row that hand drawing refuses is refused here too (offset maximum, exact fit, door resize, thickness 1", wall 2400 1/16");
    - an unknown ref, another floor's ref, and a temporary ref used before its add;
    - a temporary ref used after its add;
    - remove of a hosting wall matching `deleteChanges`;
    - the rough opening cases (typed, omitted means auto, equal means not named);
    - a save set of exactly 100 accepted and 101 refused, counted with room changes and host updates;
    - provisional numbers;
    - the input objects left unchanged (a frozen-input check).
  - Files: `lib/assistant/changes.ts`, `editor/assistant/apply-reply.ts`, `server/assistant/assistant.ts`, `server/ai/test-harness/recordings/anthropic.ts`, any check moved out of a reducer, `docs/architecture.md`, and their tests.
- **Done when:**
  - The three rewritten recordings parse and apply on `v4.json` as one door added, one wall moved and one window removed.
  - A reply with `status`, an unknown key, an unknown ref, another floor's ref or 101 changes is refused whole.
  - Every 09k row hand drawing refuses is refused for a reply.
  - A full save set of 101, with room changes and host updates, is refused, and 100 is accepted.
  - A rough opening the reply sets stays typed; one omitted on an add is auto; one equal to the sent value keeps auto.
  - The model objects passed in are unchanged.
- **ACs:** AC-EZD-5604-2, -6, -10; AC-1 (format, the 100 cap and whole-reply refusal); AC-8 (temporary refs, status not writable, remove as Delete, the update's old and new shapes in the result); AC-9 (provisional number value, the rough opening rules).
- **Depends on:**
  - from the row: EZD-5602 (parser, refs, recordings, system prompt), EZD-211 (`withOpeningSize`), EZD-213 (part a: the thickness edit);
  - **missing from the row:** EZD-204, both parts (`placeAtOffset`, `openingHostUpdates`, `autoRoughOpening`, `openingDataSchema`), and EZD-217 (`deleteChanges`, `openingChange`; for "remove acts as the Delete key"). The row's EZD-5603 is not needed by this part;
  - done: EZD-294 (`numberNewObjects`, `NumberHighs`), EZD-210a (`wallEditChanges`), EZD-120b (`Objects`, `Change`).
- **The part plan settles:**
  - each field of each op × type and its bound, from `wallDataSchema`, `openingDataSchema` and the sent shapes;
  - whether an added opening is placed by `center` or by an offset, through `placeAtOffset`;

### Part EZD-5604b · Assistant preview on the canvas and in the panel
- **Scope:**
  - **preview store.** In `app/src/editor/assistant/`, one open preview at a time (Q-0637). It holds:
    - the part a result;
    - the prompt text that produced it;
    - a stale flag.

    **Staleness** is one invariant over every model mutation (L-048). It goes stale on any `applyEdit`, `undo`, `redo` or `applyRemote` of `ModelStore` (`app/src/editor/model/model-store.ts:27-33`) whose changed ids meet `touched`, by this user or another (AC-4).
  - **canvas.** The preview layer draws:
    - added objects and the new shape of an update in blue;
    - removed objects and the old shape of an update in red dashed (Q-0474; Q-0638 gap 15).

    It uses the canvas scene (ARCH Plan canvas; `app/src/editor/plan/batches.ts`). The legend pill "Preview · blue is added · red dashed is removed" sits at the canvas bottom centre (board S03c; S03c wording). The provisional number chip is placed as on the board (Q-0640 row 56-6). Nothing is saved or put on the undo stack (AC-3). The part plan checks whether the scene can draw dashed lines and plans the change if it cannot.
  - **panel.** Accept, Adjust and Reject show under the reply only with a preview. A text-only reply has none (Q-0638 gap 13). This part wires them as follows:
    - **Reject and ×.** Both call the store's `reject()`, which clears the preview and nothing else. AC-7 makes × act as Reject here, and the stale action needs the same clear (AC-4).
    - **Accept and Adjust.** They take handlers from EZD-5605 and render natively `disabled` until those exist. EZD-5605 makes them act (phase-56 row EZD-5605 scope).
    - **Prompt box and send.** Both are disabled while a preview is open (AC-5).
    - **Refused reply.** A refused reply shows one plain line (AC-1) and no buttons.
    - **Stale preview.** It shows a plain line and an action. The preview cannot be accepted. The action clears the preview and returns the prompt text to the box with no automatic send; the photo is attached again by hand (Q-0640 row 56-9).
    - The "Adjust:" hint and "Accepted changes can be undone." belong to EZD-5605 (AC-EZD-5605-1, -3).
  - **touch.** Accept, Adjust and Reject have tap targets of at least 44 px under `expectTouchTargets` (AC-EZD-5603-10, if Q-0651 is answered (a); L-060).
  - **wording.** en and es keys for the board strings. Proposed wording under 3a for the stale line, the stale action and each refusal line (Q-0637 wording row: "stale preview, invalid reply … follow PROCESS.md 3a").
- **Tests (about 16) and files (about 12):**
  - Store unit tests: a matrix of each mutation (`applyEdit`, `undo`, `redo`, `applyRemote`) against touched and untouched ids (L-048); one open preview; reject.
  - Component tests:
    - the buttons only with a preview;
    - none for text-only;
    - × as Reject;
    - the prompt disabled while a preview is open;
    - the refusal line;
    - the stale line, and its action returning the prompt text with no request sent.
  - The legend text.
  - Touch targets.
  - Browser specs on the stub recordings. Each copies the recording to `<AI_STUB_DIR>/anthropic/assistant.plan.json` (P5602 section 3; P5603 part a):
    - `add_door` draws a blue preview and the server's model is unchanged;
    - a change by another session stales it;
    - `delete_window` draws red dashed.
  - Files: the store, the preview layer and its scene hook, the legend, the chip, the panel actions, `ProjectEditor.tsx` wiring, the en and es catalogs, and the tests.
- **Done when:**
  - A valid reply draws its preview, blue for added and red dashed for removed, with the legend and the provisional chip, and the saved model and undo stack are unchanged.
  - A refused reply shows its plain line and no buttons.
  - A change to a touched object, by this user or another, stales the preview. Its action returns the prompt text with no send.
  - The prompt is disabled while a preview is open, and × clears the preview.
  - Accept, Adjust and Reject pass the 44 px check.
- **ACs:** AC-EZD-5604-3, -4, -5, -7; AC-1 (the plain message); AC-8 (old shape red dashed, new shape blue); AC-9 (the chip shown as on board S03c).
- **Depends on:**
  - EZD-5604a;
  - from the row: EZD-5603 (both parts; the panel, prompt box and conversation, and part a's contract), EZD-211 (overlay and chip pattern, P211 D:Overlay), EZD-213 (the panel replaces the inspector);
  - **missing from the row:** EZD-208 (scene highlight and selection, P208 A8 and A9), EZD-016a (done; browser harness, because the part has a visual checklist).
  - Q-0651 decides whether the touch check is this part's.
- **The part plan settles:**
  - the store's exported names and the panel props, matched to EZD-5603a's contract;
  - the colour tokens for blue and red (`app/src/styles/tokens.css`; L-013);
  - how the chip text is built from the board;
  - the scene change for dashed lines, if one is needed.
- **Complexity:** high. It is a new canvas layer, a store with an invariant over local and remote mutations, and panel states across three tickets' contracts (PROCESS.md section 4). Test-author Sonnet 5.5; builder Opus 5.5.
- **security-review: no.** Nothing is saved, and no route, table or policy changes; part a carries the untrusted-input checks. **Reviewers:** code-reviewer · calc-auditor no · ui-verifier yes · security-reviewer no.
