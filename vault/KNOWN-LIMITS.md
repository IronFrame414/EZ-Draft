# Known limits of the vault documents

Every agent that plans, builds or reviews reads this once. None of these blocks the start. (From the planning session's setup brief, Oct 11, 2026.)

1. **`spec_files` in `tickets/tickets.json` is best-effort.** It was derived from each ticket's Spec ref text. The Spec ref text governs. Some sub-heading references (for example "Geometry rules", "Objects inside model_json") sit inside files the ticket already lists or inside Data model (`03`) and Calculations (`09`).
2. **Electrical rules are not checked against the code book.** Of the 480 NEC rules, 307 come from published summaries and 173 are unverified; the NEC text could not be opened. Of the 768 Florida rules, 756 were read from the code text in the official online viewer, 5 come from published summaries and 7 are unverified. Every rule ships with the "not yet verified" tag until a licensed person marks it in Settings 15g (EZD-1710).
3. **Rule tickets take their numbers from the catalog's check text** in `spec/code-rules.json`. They must not look up, quote or copy code text.
4. **Code editions.** In force now: Florida Building Code 8th Edition (2023) with the 2020 NEC. For permits applied for after December 31, 2026: 9th Edition with the 2023 NEC. The catalog's `section_now` and `section_next` hold both. Some mockups show "NEC 2023 · FBC 9th ed."; that is sample data for a 9th Edition project.
5. **Mockup sample data is not a decision.** Names, prices and numbers on the boards are illustration, except the Electrical board's load calculation (35,868 VA, 149.5 A), which matches the worked example in Calculations.
6. **The Oct 11 audit's counts are historical** (346, then 381 tickets; 401 at export). The repo ledger holds 405 after splits.
7. **Not verified yet:** whether Playwright's WebKit supports the Phase 14 service-worker tests (found out in Phase 14), and whether CI machines hold the frame budgets without a GPU (Round 26 moved the CI gate to countable measures).
8. **The last 31 ticket-table edits** (the code-rule tickets, Phase 6) were exported from the doc but not diffed cell by cell against the intended text. Planners read those rows with extra care and raise anything that looks inconsistent as a question.
9. **36 tickets depend on a later-numbered ticket in the same phase**, so "next number" is not the rule. Use `node vault/tools/next_ticket.mjs`, which follows `depends_on` in `tickets/tickets.json` (base IDs such as EZD-120 already expanded to every lettered part).

- **Direct Supabase Auth calls bypass the app sign-in throttle (Q-0105, Oct 12, 2026).** Anyone with the public key can call Supabase Auth's password and code endpoints directly; those calls are limited only by Supabase's per-IP limits, the 8-character minimum (Q-0094 override, Oct 18, 2026), leaked-password protection and the unconfirmed-password guard. Accepted for tenant 1; revisit before other companies join and at EZD-1705.

- **Acceptance criteria for Phase 0 are generated from Done-when text** (`vault/tools/gen_acs.mjs`, Oct 18, 2026), split at sentence ends and semicolons. A clause that is a note rather than a check (for example "applying to the cloud dev project waits for Josh's keys") still carries an AC ID; the test-author maps such an AC to the ticket's note in the plan rather than a test. From Phase 1 on, Stage 0 writes real ACs.

- **The shell guard is an accident guard, not a sandbox (Q-0135 (a); Q-0361 (b), Oct 27, 2026).** `.claude/hooks/guard-bash.mjs` refuses a Keychain lookup or a `.claude/` path that holds `$`, a backtick or a wildcard, but it cannot see a whole command, or a whole path, held in one variable, a lookup whose command and subcommand are both hidden, or a search that never names the sign-in file (`find ~/.claude -name …`). Since EZD-280 (Nov 5, 2026) every word of a command is judged by the read guard's secret-file rules, and a path built after a `cd` into the folder (`cd ~/.claude; cat .c*`) or a wildcard `cd` target is refused; still open: a quoted wildcard (`find . -name '.env*'`) and a folder held in a variable (`cd "$HOME/.claude"`). Some harmless commands are refused too (`-s "$NAME"` lookups, any `cd` with a wildcard, a word equal to a secret path in a search pattern or message).

- **Units run unsandboxed for now (Josh, Nov 3, 2026, applied `vault/handoff/sandbox-off.patch`):** `scripts/run.mjs` no longer passes `--settings scripts/unit-sandbox.json`, so the holes below do not apply until the sandbox is back; it returns after every unit type (build, plan, questions, review-plans, gate-phase, wrap, repair) has had a sandboxed dry run. The path and read guards still apply. Before it returns: `vault/handoff/SANDBOX-AUDIT-2026-11-03.md` section 5, including the GitHub-login gap (D-021).
- **The unit sandbox has known holes (Josh, Nov 2, 2026: sandbox option 3 now, option 1 with the lanes work).** Every launcher unit runs its shell commands in the OS sandbox (`scripts/unit-sandbox.json`), except: (1) the gate command (`node scripts/gate.mjs *`) runs outside it, because Playwright's Chromium cannot start in the macOS sandbox, so everything the gate runs, including agent-written app code and tests, has full access; (2) sandboxed commands may use the Docker socket, which reaches the whole Mac through a container; (3) the worktree and merge steps (`node scripts/unit-steps.mjs worktree *`, `node scripts/unit-steps.mjs merge *`) run outside it, because they write a worktree's `.claude/agents`, `.claude/skills` and similar files, which the sandbox always protects and no setting unlocks (D-008, Nov 2, 2026); (4) sandboxed commands can write the main checkout's `scripts/`, so a unit could change `scripts/gate.mjs` or `scripts/unit-steps.mjs` and then run it outside the sandbox through (1) or (3); the next unit's preflight refuses a checkout with changed tracked files outside `vault/`, but only after that unit ends. (5) Outside the repository, sandboxed commands may also write `~/Library/Logs/ezdraft/inflight` (each unit's records queue, which the launcher validates and applies, and the in-flight records) and `~/.supabase` (the Supabase CLI's telemetry and version cache; no sign-in token is kept there on this Mac). (6) `node scripts/ui-run.mjs *` runs outside the sandbox (the ui-verifier's screenshots; Chromium cannot start inside it): it runs only a `.spec.ts` under the ticket worktree's `app/e2e/`, but that spec is agent-written and has full access, as the gate's tests do (D-013). (1) and (2) close when each lane's gate and database run outside the unit (option 1, EZD-172 and EZD-174). Read, Edit and Write are outside any sandbox; the path and read guards cover them. Details: `vault/spikes/sandbox/NOTES.md`.
