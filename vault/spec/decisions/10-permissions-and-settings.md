| Q-0695 | 2026-11-11 | Invites (EZD-105, EZD-138). The new table `invite` holds tenant, membership (unique), a per-invite random value, expires_at = 7 days after the last send, the code tries count, accepted_at, cancelled_at, created_by and sent_by. The link token and the 6-digit code are worked out from the random value with a server-held key (HKDF, label ezd-invite-v1, as throttle.ts and architecture "Password sign-in" (vii)), so they can be shown again on the pending row. Lookup is by the token's sha-256; no plain hash of the code is stored. /invite/<token> shows Accept and accepts only on POST, so an email scanner cannot accept it. Accept runs in one database step: check the token, check the email has no other active company (Q-0043), make the membership active and mark the invite accepted; only then make the session. The session comes from Supabase admin generateLink(magiclink) and verifyOtp, in one narrow server-only secret-key file: update the T34 list and the service-key bullet, never log the action link, and check whether generateLink creates the auth user for a new email on the pinned version. The code path is "Have an invite code?" on /sign-in (email and code). Five wrong codes lock the code, not the link, until Resend; the sign-in per-IP limit also applies; unknown email, no invite and wrong code all get one answer. Both are single use. The link and code are shown to the person who last sent the invite and to active Owner-preset members (Q-0216).
